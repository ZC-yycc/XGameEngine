**刚体表增量修补**接入后，增删实体 / 换代 / 改构建参数不再整表重建：`crates/xgc-sim/src/rapier_world.rs` 的 `ensure_built` 第一次建表仍走整份 `rebuild`（按 ID 排序插入，保证岛屿构建顺序确定），之后按 `BodySignature` 的 ID 序列做差量——只对"新增、换代、构建参数变了"的条目 `insert_body`、对"删掉或被替换"的条目 `bodies.remove(..., true)`，没变化的刚体保留原来的 handle。整表重建会把所有刚体的 handle 重排、在飞的速度与接触缓存全丢，而 rapier 的岛屿构建顺序与插入顺序有关（旧端同样按 ID 排序建体），这也是"改判据容易、改顺序要重新验证确定性"的那半句。同步后只有真的动过表时才 `query.update(&colliders)`（碰撞体增删后射线 / 形状查询必须重建 BVH），计数口径分成两个：`RapierWorld::rebuild_count()` 是整表重建次数（稳态恒 1），`RapierWorld::body_patch_count()` 是增量修补次数（每次修补各算一次、同一帧多处增删合并为一次，稳态恒 0；诊断不区分一次修补里动了多少条目）。为守住单文件 600 行软上限，整块刚体表（签名、整表重建、增量修补）从 `rapier_world.rs` 拆到 `crates/xgc-sim/src/rapier_world/bodies.rs`（与 `characters.rs` / `slopes.rs` 同一分工，`rapier_world.rs` 只留 `step` 编排与写回，两个文件分别 326 / 351 行）。新增 3 条回归（`crates/xgc-sim/tests/rapier_schedule.rs`，文件现 10 条）：`adding_a_body_patches_the_table_without_a_full_rebuild`（中途放一个远处立方体，`rebuild_count` 不变、`body_patch_count` 恰好 1，已有刚体继续下落、新增刚体也被推进）、`removing_a_body_patches_the_table_without_a_full_rebuild`（`despawn` 之后同样只修补一次，留下的刚体继续下落、静态地面不被误删）、`patching_does_not_disturb_existing_bodies`（同一份世界跑两遍，一遍中途加远处立方体一遍不加，未受影响那个刚体的位置 / 朝向 / 线速度都逐位相同）。红的证据：把增量分支退回整份 `rebuild` 之后，`rebuild` 的空表断言会先拦下（临时连这条断言一起去掉再跑，仍是 5 条红）—— 「新增实体不该整表重建（否则所有刚体重排、在飞速度清零）」「中途新增远处刚体不该改变已有刚体的轨迹（增量修补不许整表重排）」「改参数只该增量修补，不该整表重建」，外加 `removing_a_body_...` 与表驱动用例的计数断言。第 150 帧逐字节不变（`hash=bb3fdc99df20aa31`、14 个场景 draw / 7 次 draw call / 8 个 UI draw、PPM SHA-256 `4A47275DD54A4AA2780353B6B37E6BD2999F9D16BEDA20197973BA6DB48A0927`，证据世界的 10 个刚体从头到尾没有增删，等价于"一次建表 + 稳态不修补"；`body-patch-150.ppm` 与上一版 `body-signature-150.ppm` 字节相同），`run 60` 的哈希仍 `f4bc029f5f995b91`。**未闭环**：增量修补仍是"整表按 ID 序列做差量"，修补计数只按「修补了几次」累计，不区分一次修补里动了多少条目；新增刚体的 handle 复用 `RigidBodySet` 的空闲槽，因此同一场景"一开始就全量建表"与"中途逐个补入"的 handle 编号不同 —— 岛屿顺序与遍历顺序因此可能不同，浮点结果已用逐位断言钉住只要不接触就一致，接触链上还缺一条大规模场景的实测；`Transform` 的平移 / 旋转 / 缩放仍不进签名（与旧端同取舍，见上一节）；改 `PhysicsBody` 字段必然重建那一个刚体，在飞速度对它仍然清零。
