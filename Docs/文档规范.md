# 文档规范

> **体裁：规范 / 政策。** 本文只回答“文档放哪、叫什么、写什么、什么时候归档、
> 怎么检查”，不记录项目状态，也不重复子系统约束。
>
> 状态看 [`../ROADMAP.md`](../ROADMAP.md)；开放差距看 [`差距分析.md`](差距分析.md)；
> 不可推翻的约束看 [`决策记录.md`](决策记录.md)；迁移规则看
> [`架构收敛约定.md`](架构收敛约定.md)。
>
> 效力：新增或大改文档必须遵守；违反 §4 / §8 / §10 的 PR 不合并。
> 历史档案不追溯修改，只在下次动它时顺手补齐。

---

## 1. 要解决的问题

文档混乱通常不是“写得少”，而是**体裁混用**：

- 状态台账里塞进设计推演，读者不知道哪句是现状；
- 优先级表里塞进关闭日志，旧排序和今天的待办混在一起；
- 一次性审计长期留在活跃目录，结论过期后仍在被引用；
- 同一件事在 README、ROADMAP、PLAN、决策记录各写一遍，然后一起漂移。

本规范用两条规则根治：

1. **一类问题只归一份文档**（§2 / §3）。
2. **历史必须 visibly 冻结**（§8）：移动、加横幅、改链接，而不是删掉或假装它还活着。

## 2. 六类文档

| 体裁 | 回答的问题 | 允许写 | 禁止写 | 当前载体 |
|---|---|---|---|---|
| **状态台账** | 做到哪了？ | 阶段、勾选、日期、未完成项、证据链接 | 大段设计论证、优先级排序 | `ROADMAP.md` |
| **开放差距 / 优先级** | 还差什么？先做哪个？ | 开放差距、排序原则、验收边界、关闭记录链接 | 教程、实现细节、第二张优先级表 | `Docs/差距分析.md` |
| **约束台账** | 改这块之前不能翻什么案？ | 结论、理由、实测数据、反例 | 进度、教程、一次性审计 | `Docs/决策记录.md` |
| **指南 / 参考** | 怎么用？字段是什么？ | 步骤、示例、参数、输出、易错点 | 决策争论、路线图 | `README.md`、`FLOW.md`、`Docs/脚本API.md`、`Docs/无头运行.md`、`Docs/MCP.md` |
| **规范 / 政策** | 遇到某类事该怎么做？ | 判据、标准动作、门禁、检查清单 | 当前状态、具体 bug 修复记录 | `Docs/架构收敛约定.md`、本文 |
| **历史档案** | 当时为什么？基于哪次提交？ | 旧结论、旧数据、旧设计、审计快照 | 现状描述、新待办 | `Docs/历史/` |

判断口诀：**“这句话明年还会真吗？”**
会真 → 约束 / 规范；只在某个版本真 → 状态 / 差距；只对当时真 → 历史。

## 3. 唯一真相源

### 3.1 一问一源

| 问题 | 唯一真相源 |
|---|---|
| 阶段完成了吗？ | `ROADMAP.md` |
| 现在先做什么？ | `Docs/差距分析.md` 顶部开放差距表 |
| 这条约束能不能改？ | `Docs/决策记录.md` |
| 迁移能不能留兼容层？ | `Docs/架构收敛约定.md` |
| 这个命令怎么用？ | `README.md` / 对应参考手册 |
| 这个 JSON 字段叫什么？ | `Docs/无头运行.md` / `Docs/MCP.md`（契约） |
| 当时为什么？ | `Docs/历史/` |

### 3.2 派生文档只链接

- 同一事实出现第二处时，**删掉旧的那处，留链接**。
- 允许“一句话摘要 + 链接”，不允许“完整复制 + 各自维护”。
- 发现两处不一致：先判断哪份是真相源，改另一份；不要两处都改一半。

### 3.3 代码与文档冲突

- **行为**以代码为准：先改文档，再决定是否改代码。
- **契约**（脚本 API 名、JSON 字段、退出码、GUID / 实体 ID 语义）以文档为准：
  改代码前先改对应契约文档与测试。
- **约束**以 `Docs/决策记录.md` 为准：想推翻必须新增一节，写清代价与替代方案。

## 4. 目录与命名

### 4.1 根目录白名单

仓库根目录只允许这四份 Markdown：

```
README.md     用户指南
ROADMAP.md    状态台账
FLOW.md       运行流程
AGENTS.md     Agent 入口
```

其他文档一律进 `Docs/`。根目录出现第五份 `.md` = 违规；`tools/check-docs.ps1`
会失败。

### 4.2 活跃目录

```
Docs/
├── README.md            索引（本目录唯一入口）
├── 文档规范.md           本文
├── 文档整改计划.md        一次性计划（完成后归档）
├── 差距分析.md           开放差距 + 优先级
├── 决策记录.md           约束台账
├── 架构收敛约定.md        反兼容层规范
├── 脚本API.md            参考
├── 无头运行.md           参考
├── MCP.md               参考
└── 历史/                 冻结档案（见 §8）
```

### 4.3 命名

- 活跃文档**不带日期**：日期只属于历史档案与一次性审计。
- 不用版本 / 新旧后缀：`最终版`、`新版`、`v2`、`old`、`备份`、`副本` 全部禁止。
  版本由 git 管。
- 历史文档保留原文件名；一次性审计可带 `-YYYY-MM-DD`。
- 文件名用中文或稳定的英文术语，不用缩写谜语；同一概念全仓同名。

## 5. 首屏横幅（强制）

每份活跃文档的前 15 行必须有一块引用横幅，至少回答四件事：

```markdown
> **体裁：** 状态台账 / 开放差距 / 约束台账 / 指南 / 参考 / 规范 / 索引。
> **回答：** 这份文档只回答什么问题。
> **不回答：** 哪些问题应去看别的文档（给链接）。
> **真相源：** 本文与其他文档冲突时，谁优先；或者本文就是唯一源。
```

历史档案改用归档横幅（§8），不写“真相源”。

**为什么强制**：读者打开一份 5000 行文档，第一眼必须知道它是“现状”还是“历史”，
否则会把旧结论当今天的设计。横幅是廉价的防误读装置。

## 6. 长度、拆分与追加式文档

### 6.1 阈值

| 行数 | 要求 |
|---|---|
| ≤ 800 | 正常 |
| 800–1500 | 必须有目录或清晰的二级标题导航 |
| > 1500 | 必须拆分，或声明为“追加式文档”并给出索引 |

行数按 `(Get-Content <file>).Count` 计，不按字数。

### 6.2 拆分规则

- **按问题拆，不按日期拆**：`Docs/决策记录.md` 可按子系统拆，`PLAN.md` 不拆
  （它本身就是按日期追加的历史）。
- 拆完必须更新所有引用与 `Docs/README.md`；旧文件删除，不留转发壳。
- 拆出的子文档共享一个索引；索引只放标题 + 链接 + 一句话，不复述正文。

### 6.3 追加式文档例外

以下文档允许超过 1500 行，因为“按时间追加”本身就是它们的价值：

- `Docs/决策记录.md`（约束台账，只增不改旧结论）；
- `ROADMAP.md` 的历史阶段段（按日期倒序）；
- `Docs/历史/*`（冻结档案，不再整理）。

追加式文档必须满足：顶部有索引 / 导航；新内容只追加到约定位置；旧内容不重写
（除非被推翻，且要留下“为什么推翻”的记录）。

## 7. 状态标记

统一使用这六个符号，别自创：

| 标记 | 含义 | 判据 |
|---|---|---|
| ✅ | 已完成 | 代码已合并 + 有回归测试或验收记录 |
| 🟨 | 部分完成 | 主路径可用，但明确列出的子项未做 |
| ⬜ | 未开始 | 没有实现，也没有排期 |
| ❌ | 缺失 / 不支持 | 明确没有这个能力 |
| 🚫 | 明确不做 | 有决策记录说明为什么不做 |
| 🧊 | 冻结 / 归档 | 只用于历史档案 |

**✅ 不等于“设计完成”**：只有文档、没有代码或测试的条目，最多写 🟨。

## 8. 归档流程

### 8.1 什么时候归档

满足任一条即归档，不要留在活跃目录：

- 一次性审计 / 对标报告，结论已被后续工作吸收；
- 设计稿已实现，或已被新设计取代；
- 历史实施记录（`PLAN.md` 这类按日期追加的日志）；
- 旧版本快照、导出的 HTML / PDF 报告；
- 已完成的一次性计划（如本文档整改计划）。

### 8.2 动作（五步，缺一不可）

1. `git mv <文件> Docs/历史/<文件>`（保留历史，不用删除 + 新建）。
2. 顶部加归档横幅：

   ```markdown
   > **已归档（YYYY-MM-DD），内容冻结。** 这是一次性 <审计 / 设计 / 记录>，
   > 基线是 <提交 / 日期>；文中“未实现 / 当前 / 下一步”都指写作当天。
   > 现状看 <活跃文档链接>。
   ```

3. 修正文内相对链接（多一层目录）。
4. 在 `Docs/历史/README.md` 的清单里加一行：文档、性质、归档日、现状应看。
5. 从 `Docs/README.md` 的活跃清单移除，并在索引里保留历史入口。

### 8.3 归档后规则

- **只修链接与错别字**，不再补新结论。
- 发现历史结论与代码冲突：不改历史，改活跃文档或决策记录。
- 同一主题已有活跃文档时，归档文档必须写明“现状应看哪一份”。

## 9. 变更同步矩阵

改代码时，按下表检查文档；**不是每项都改，但每项都要想一遍**：

| 代码变化 | 必须同步 |
|---|---|
| 新增 / 改名 / 删除脚本 API | `Docs/脚本API.md` + `xgame-core::script_api` 清单 + `--export-script-api` 测试 |
| 场景 / 预制体落盘字段变化 | `xgame-core::schema::scene_schema()` + `Docs/决策记录.md` + `ROADMAP.md` |
| 新增 / 推翻子系统约束 | `Docs/决策记录.md`（新小节）+ `AGENTS.md` 约束索引 |
| 完成一个阶段 / 关闭一个差距 | `ROADMAP.md` 勾选 + `Docs/差距分析.md` 开放表移除 + 关闭记录（归档） |
| 出现新差距 / 排序变化 | 只改 `Docs/差距分析.md` 顶部开放表 |
| 用户可见命令 / 行为变化 | `README.md` + 对应参考手册 |
| 主循环 / 调度顺序变化 | `FLOW.md` + `Docs/决策记录.md`（若形成约束） |
| CLI / MCP 的 JSON 字段或退出码变化 | `Docs/无头运行.md` / `Docs/MCP.md` + 契约测试 |
| 迁移 / 重构政策变化 | `Docs/架构收敛约定.md` + `AGENTS.md` 硬规则摘要 |
| 新增 / 移动 / 归档文档 | `Docs/README.md` + 所有入链文档 |

## 10. 禁止项

以下每一条都真实发生过，别再犯：

1. **同一事实两份完整正文**（README + ROADMAP + PLAN 各写一遍）。
2. **活跃文档里保留已过期的“设计稿，未实现”**；实现了就改为现状或归档。
3. **活跃文档用日期命名**（`差距分析-2026-10-26.md` 这种只许在历史区）。
4. **根目录堆历史日志**（`PLAN.md` 9000 行放根目录）。
5. **只写“见 PLAN”而不把约束写进决策记录**：PLAN 是历史，不能当今天的约束源。
6. **TODO 没有 owner / 日期 / 判据**；没有到期日的债务等于永续债。
7. **把一次性审计当现状引用**；审计有基线，代码一动就过期。
8. **归档文件继续更新**；要么活跃，要么冻结，不许半活半死。
9. **删除历史代替归档**；失去“当时为什么”的证据。
10. **新增文档不登记索引**；一个月后没人找得到。

## 11. 门禁与检查

提交前跑：

```sh
powershell -File tools/check-docs.ps1
```

检查项：

- 根目录 `.md` 是否在白名单内；
- 活跃文档文件名是否带日期；
- Markdown 相对链接是否可解析（跳过外链与纯锚点）；
- `Docs/历史/*.md` 是否有归档横幅；
- 活跃 `Docs/*.md` 是否有“体裁”横幅（警告，不阻塞）。

CI 可把 `-Enforce` 打开，把警告也变成失败；在存量清理完成前只阻塞硬规则。

## 12. 提交前清单

- [ ] 新事实写进了正确的体裁（§2），没有第二份正文
- [ ] 首屏横幅存在，且“回答 / 不回答”写清楚
- [ ] 活跃文档文件名不带日期，根目录没有新增 `.md`
- [ ] 移动 / 归档的文件已 `git mv`，链接已改，索引已登记
- [ ] 归档文件顶部有“已归档（日期）”横幅
- [ ] 历史结论没有被当成现状引用
- [ ] `tools/check-docs.ps1` 通过
- [ ] 同一件事没有在 README / ROADMAP / 决策记录里三份并存
