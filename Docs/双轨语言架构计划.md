## 〇、一页结论

引擎提供两条开发轨道，共享**同一编辑器、同一场景格式、同一套 API 名字**：

| | 方案 A：Rust（极致性能） | 方案 B：Lua（极致方便） |
|---|---|---|
| 对齐参照 | **UE**：C++ 游戏模块 + Live Coding | **Unity**：脚本即资产；外加热更（无 Domain Reload） |
| 用户写什么 | cdylib 插件 crate（`src/lib.rs`，**无 main**） | `Scripts/*.lua` |
| 挂载方式 | 场景引用类型名（Inspector 选） | Inspector 选脚本文件 |
| 迭代方式 | 改代码 → 编辑器侦测 → `cargo build`（增量）→ 重载 DLL | 保存即热重载，下一帧生效 |
| 发布形态 | 静态链接 + LTO（**零边界开销**） | 解释执行（沙箱内） |
| 沙箱 | 无（插件=引擎一部分，panic 边界兜底） | 有（指令计数 + 内存上限） |
| 需要安装 | Rust 工具链 | 无 |

- **Rhai**：暂保留，P2.5 基准闸门用真实负载实测 Rhai vs Lua，数据决定去留（预期 Lua 胜）。
- **C# / Verse / 四语言中立层**：已否决，理由见决策记录。

## 一、决策记录

### D1. 语言范围收敛为 Rust + Lua（2026-10-13）

原设想支持 C#、Lua、Rhai、Rust 四语言。否决其余的理由：

| 候选 | 结论 | 理由 |
|---|---|---|
| C# | ❌ 否决 | hostfxr 嵌入 .NET + Roslyn 运行时编译 + 编组层 = 2–4 月级工程；每台机器要 .NET 运行时；C# 无法沙箱化（unsafe + P/Invoke）；编辑器调试器是独立大工程 |
| Verse（UE 新脚本语言） | ❌ 出局 | **资格问题**：当前绑死 UE（跑在 Blueprint VM 上，Epic 官方明确"tied to Unreal"），独立运行时未发布；语义依赖 AutoRTFM（定制 LLVM + 事务内存），无法 drop-in 嵌入；零公开基准，且 BP VM 是 UE 公认最慢脚本路径 |
| 四语言中立层（`ScriptEngine` trait + `ScriptValue`） | ❌ 取消 | 只有一门脚本语言时不需要多语言分发抽象（YAGNI）；`ScriptValue` 中立值类型取消——Lua 值直接用 mlua 原生转换 |

### D2. Rust 走 UE 模式，Bevy 模式保留为逃生舱

- **UE 模式**：用户的 Rust 代码是 **cdylib 插件**，被引擎（编辑器/播放器）用 `libloading`
  加载；用户项目**永远不出现 `fn main()`**。开发循环对齐 UE Live Coding：改代码 →
  增量编译 → 重载 DLL → 重启 Play 会话。
- **Bevy 模式不消失**：门面 crate（`xgame`）本身可被普通 cargo 项目引用，
  纯逻辑迭代可以 `cargo run` 直接跑最小宿主，不经过编辑器、不付 DLL 重载成本。
  **产品形态是 UE 模式，工程后门是 Bevy 模式。**
- 选 UE 模式为主干的根据：游戏的代码量:资产量 ≈ 1:10~1:100，高频迭代是
  "改数据/手感"而非"写逻辑"；Unity/UE/Godot 全部收敛到编辑器中心不是巧合。
  Bevy 式纯代码模式在团队协作、内容规模、非程序人员参与上系统性吃亏。

### D3. Lua 走 Unity 模式 + 热更

脚本是项目里的数据资产（`Scripts/*.lua`），Inspector 挂载，编辑器 ▶ Play 内运行；
改脚本保存即热重载（比 Unity 的编译+Domain Reload 更快，且不重置状态）。

### D4. Rhai 由数据决定去留（P2.5 闸门）

不凭直觉删既有资产。Lua 宿主（P2）完成后、删除 Rhai（P3）之前做基准闸门，
**决策规则事先声明**：Lua 全胜 → 删 Rhai；Rhai 任一关键负载反超 >20% → 保留双宿主。

预期 Lua 胜的结构性依据：Rhai 是 AST 树遍历解释，Lua 5.4 是字节码 VM——
胶水负载快 2–5×，纯计算更快；且 Lua 生态（IDE 支持/教程/绑定）远大于 Rhai。

### D5. 性能结论（先算账后动工）

| 形态 | 相对"什么都不改"的代价 |
|---|---|
| 发布期（静态链接 + `lto = "fat"`） | **零开销**——与"直接写 main"同速 |
| 开发期（跨 DLL 调用） | 每帧微秒级（间接跳转 ~1–2ns × API 调用次数），对 16.7ms 帧预算可忽略 |
| Rust 组件 vs Rhai 钩子 | 快**一个数量级**（省掉 AST 解释 + Dynamic 装箱） |

跨 DLL 的两条边界纪律（正确性问题，写进插件边界设计）：

1. **分配器隔离**：边界只传只读借用/句柄；插件分配的对象由插件导出的销毁函数释放；
2. **panic 隔离**：每个跨边界调用点 `catch_unwind`，插件崩溃不带走引擎进程。

### D6. P0 落地注记（2026-10-14，PLAN.md 十五）

P0 六件事全部完成，落地时有三处对计划文档的修正（均已回写到对应章节）：

1. **`GameCtx` 落在 `xgame-script` 而非 `xgame-runtime`**（见 C1 注记）——
   api.rs 转发壳调用它，放 runtime 会形成反向依赖；
2. **`EngineApi` 只带 `version` + `log`**（见 C4 注记）——查询/变更类能力

3. **组件热路径零哈希**：钩子函数指针在装配期拷进实例（`BehaviorInstance`），
   `start` 标记下沉到组件。微基准（1000 no-op 实体）：组件分发 68.95 →
   **37.61 µs/帧**（验收线 50 µs），对照 Rhai 脚本轨 493.89 µs/帧 =
   **13.1×** —— D5"快一个数量级"由数字坐实。

### D7. P0.5 落地注记（2026-10-14，PLAN.md 十六）

编辑器 PIE 全部落地，四条决策是**不能推翻**的约束，写在这里免得日后被"优化"掉：

1. **`Plugins/` 是唯一的规范目录**。编辑器把 `target/` 里的产物复制进
   `<项目>/Plugins/`，玩家只读这里，打包器只复制这里。`target/` 是 cargo 的
   地盘（可能被并发构建清空、改名），三者共用它等于三方抢一把锁。编辑器是唯一
   写入方、玩家只读 —— 单向数据流，不需要锁。`.gitignore` 已加
   `projects/*/Plugins/`（构建产物不入库）。
2. **加载永远走临时副本，源文件永不被 dlopen**。Windows 上被 `dlopen` 的 DLL
   会锁到进程结束，下一次 `cargo build` 覆盖它必然 sharing violation。所以宿主
   先复制成 `%TEMP%/xgame-plugin-cache/xgame-plugin-<pid>-<counter>-<原名>` 再
   dlopen 副本。玩家进程是独立的、只读一次、不参与编译，**直接读 `Plugins/`**
   即可（没有覆盖需求）。历史残留由启动时的 `sweep_temp_copies` 尽力清理。
3. **旧代 DLL 句柄永不卸载，泄漏到进程结束**。`FreeLibrary` 之后 DLL 里的静态
   析构、TLS 析构仍可能跑，而只要还有一个 `Box<dyn Lifecycle>` 实例活着，它的
   vtable 就指进已卸载的代码区 —— 下一次调用是未定义行为。编辑器**无法证明**
   "没有实例活着"，所以采取 UE Hot Reload 同款策略：句柄只增不减。代价是每换
   一代多几 MB 镜像映射，换来"永不悬垂"的硬保证。连带的硬约束：宿主里持有
   句柄的字段必须声明在 `game_runtime` / `world` **之后**（struct 字段按声明
   顺序 drop，指向 DLL 的函数指针得先于句柄销毁）。
4. **演示项目本身是 workspace 成员**（`projects/BehaviorsDemo`）。它就是"用户
   项目形态"的插件，与 `examples/spinner-plugin`（引擎自带示例）互补。放进
   workspace 是为了共享 `target/` 与根 profile：从成员目录跑 `cargo build`
   只编本 crate 及其依赖，引擎那部分早已编好。**实测确认**子进程 `cargo run`
   在程序运行期间不持构建目录锁，编辑器与项目构建不会互锁。

另有一条容易踩的实现细节：新鲜度判定里"编辑器 exe 比 DLL 新 ⇒ 要重建"（引擎
变更的代理）与"cargo 源码没变就不重写产物"会打架，导致每次按 Play 都白跑一轮
cargo。解药是产物同步进 `Plugins/` 后统一盖一个"现在"时间戳。回归测试
`sync_makes_plugins_fresh_even_when_cargo_did_nothing` 守着它。

### D8. P1 落地注记（2026-10-14，PLAN.md 十七）

`#[derive(Inspect)]` 与编辑器调参全部落地。四条是**不能推翻**的约束：

1. **"可检视"是组件契约的一部分，不是可选项**。组件注册约束是
   `Behavior: Lifecycle + Inspect`（空 body + blanket impl），不是 `Lifecycle`。
   理由是硬的：编辑器不链接用户代码，要拿到 `&mut dyn Inspect` 只能靠实例**自带**
   的字段表；而存 `Box<dyn Lifecycle>` 时这个降级做不到（需要 downcast，
   跨 DLL 边界没有共享类型信息）。`impl_no_inspect!` 是"我不开放字段"的一行
   逃生舱，不要把它变成默认写法。
2. **表 + 下标，不要改回调**。`Inspect` 是"读第 i 个 / 写第 i 个"两个对象安全
   方法，表是 `'static`。改成闭包就得处理跨 DLL 的 panic 隔离与函数指针生命周期，
   而热路径（每帧每可见字段）连一次哈希都不该有。`FieldValue` 是**拥有**的
   （不是 `Cow` / 借用版）：字段里可能有 `String`，借用版会把 API 复杂度推给每个
   消费者。要优化加 `inspect_get_into(&self, i, &mut FieldValue)` 即可，表结构不动。
3. **寻址名与显示名分离**。`FieldDesc::label` 只改 Inspector 显示的文字，
   寻址名永远是 Rust 字段名 —— 重命名显示名不能破坏已有脚本与场景数据。
   同理 Rust 侧重命名字段会破坏场景（P1.5 落地存盘后），那属于"结构性变更"，
   与 UE 改 UPROPERTY 名同款后果。
4. **组件字段改动不进场景撤销栈**。`show_content` 的 `touched` 意味着"改了
   `working`，要写回场景 + 推一条撤销"。组件参数不在场景文件里（P1.5 才落地），
   动它会凭空多出一条场景撤销记录 —— 按 Ctrl+Z 会撤掉一个并不存在的改动。

另有两条不是决策、但下次会被踩的实现事实：

- **`PluginSession` 留了一份常驻注册表**（加载时装配的那份，原先读完名字就丢）。
  每帧要查字段表、要构造编辑态组件的路径**必须**走它，不能走 `build_registry()`
  —— 后者每次重跑插件入口且失败时 `log::error!`，一旦"名字在、重跑没注册上"，
  构造每帧失败 ⇒ **每帧一条错误日志**。
- **插件注册表是跨编译单元的内存布局**。P1 给 `BehaviorEntry` 加 `fields` 字段后，
  `plugin_loading` 集成测试里"过期的 `target/*.dll`"会让旧 DLL 三段写、新宿主四段
  解，读歪 `HashMap` 再经构造函数指针跳过去 = `STATUS_ACCESS_VIOLATION`。
  **`cargo test` 不产出 cdylib**，所以那些 DLL 极易过期；现在取 DLL 前先嵌套构建
  一次。给插件注册表加字段 = 改 ABI，务必想起这条。

### D9. P1.5 落地注记（2026-10-14，PLAN.md 十八）

组件参数落盘进场景文件。两条是**不能推翻**的约束：

1. **参数表的键是注册名，不是数组下标**。`Entity::behavior_params:
   BTreeMap<String, FieldValues>`（注册名 → 字段寻址名 → 值）。下标会错位（用户在
   `behaviors` 中间插一个组件，后续下标全变），而参数是**持久化数据** —— 错位写参的
   表现是"改 A 组件的参数写进了 B 组件"，两边字段都是 `f32` 时编译器和运行时都发现
   不了。注册名天然稳定。
2. **`FieldKind` / `FieldValue` 的 serde 变体标签即磁盘格式**。改标签名等于作废所有
   旧场景文件。`field_value_ron_variant_labels_are_stable` 钉死它。

**推翻 D8 第 4 条**（组件字段改动不进场景撤销栈）：参数进场景文件后，它已成为
场景数据，不进撤销栈会凭空丢一条场景编辑。现改为组件字段编辑接上场景撤销栈
（拖拽挂 `undo_pending`、松手入栈、离散编辑当场 push），与 Name/Transform 同一通道。
D8 第 4 条的前提（"参数不在场景文件里"）已被 P1.5 移除，故其结论一并作废。

两条实现事实（下次会被踩）：

- **apply 静默吸收陈旧/错型条目**：组件字段表改了之后，旧场景里的陈旧参数不该让
  加载崩溃。这与世界层 `apply_field_values` 既有取舍一致（检视是旁路，一个下标算错
  不该拖垮宿主）。
- **`PluginSession` 的 `register_for_test` 是 `#[cfg(test)]` 后门**：编辑器测试要构造
  带字段表的组件实例，但生产路径只有 `build_registry()`（重跑插件入口）。后门只在
  测试编译期存在，保住"注册表只构建一次"的每帧性能取舍 —— 不要把它变成生产 API。

### D10. P2 落地注记（2026-10-14，PLAN.md 十九）

Lua 宿主（mlua 0.10）上线，双轨按扩展名分流；顺带修掉两宿主每帧 3 处路径
`String` 克隆（路径驻留表 `xgame-script/src/intern.rs`）。四条是**不能推翻**
的约束：

1. **每脚本环境表的 `__index` 必须挂真元表**（`meta.__index = globals` 之后
   `env.set_metatable(...)`）—— 往 env 塞同名**普通字段**对读取完全无效，
   表现是"脚本里宿主 API 全变 nil"。踩过一次（首跑 9 条测试红），
   别为了少一张表改回字段写法。
2. **两轨分流必须恰好全覆盖**：`.lua` → LuaHost，其余 → Rhai
   （`is_rhai = !is_lua`）。漏了 = 两边都不管、脚本静默不执行；重了 =
   两边都编译、每帧假报编译错。`rhai_host_skips_lua_scripts` 钉死 Rhai 侧。
3. **路径驻留表的 id 永不回收、表永不清空**：状态表键是 `(EntityId, 路径 id)`，
   `invalidate` / `invalidate_all` 只清编译缓存。清表 = 热重载后每实体状态
   **静默错位**（A 脚本读到 B 的计时器，两边都是 `f32` 无从发现）。双宿主
   各有 `state_survives_hot_reload_even_when_intern_order_changes` 钉死它
   （红对照 = "热重载时顺手清空驻留表"这个看似合理的实现，实测两宿主皆红：
   b = 100 vs 期望 200，即状态从 0 重计）。
4. **沙箱预算两边同量级**：Rhai `set_max_operations(200_000)` 与 Lua 指令钩子
   （每 1024 条指令查一次、预算 200_000、扣到 0 中断本次调用）语义等价 ——
   "死循环脚本只毁掉自己这一帧"。改预算时两轨一起改，否则同一份逻辑换个
   语言就换个行为。

两条实现事实（下次会被踩）：

- **借 `self.intern` 的 `&str` 跨不过 `&mut self` 方法调用**（借用检查器看不出
  "它就是 self 身上的一块"）。所以 `ensure_loaded` 拆成"先 intern 再转"的
  path 外壳 + `ensure_loaded_id` 内核（解析在方法**体内**做，字段级拆借），
  `run_hook` 收 `path_id`。想"顺手把 &str 传进去"会撞借用检查。
- **mlua 0.10 的 API 细节**：`load(chunk)` 只收 1 个参数（chunk 名用
  `.set_name(...)`）、`AsChunk` 只对 `&[u8]` 实现、`set_metatable` 返回 `()`、
  `Table::set` 无 turbofish、没有 `T: UserData` 的 `FromLua` blanket impl。
  查 API 优先看本地源码 `~/.cargo/registry/src/*/mlua-0.10.5`，别凭记忆写。

性能（先量后改，数据表在 PLAN.md 十九）：探针量出三处克隆上限 ≈110 µs/帧；
端到端 Rhai 轨分发 819.6 → **713 µs/帧**（-13%，同机 4 轮背靠背）——
微基准与端到端交叉验证吻合。Lua 轨每帧性能未测，留给 P2.5 闸门。

## 二、目标架构

```
        用户 Rust 插件(cdylib)          用户 Lua 脚本(数据资产)
                │ libloading 加载            │ 解释执行
                ▼                            ▼
        ┌─────────────── xgame 门面 crate ───────────────┐
        │  prelude / Lifecycle / Ctx / App / export_plugin │
        └──────────────────────┬─────────────────────────┘
                               ▼
              xgame-runtime::World（唯一编排者）
        ┌──────────────┬─────────┴─────────┬──────────────┐
        ▼              ▼                   ▼              ▼
   GameCtx 方法层   组件分发(+新)      脚本分发(现有)    物理/渲染/输入
   （API 真相源）   Lifecycle 钩子     Rhai(现状)/Lua(P2)
```

**一条关键原则**：脚本 API 与 Rust 组件 API 是**同一套 `GameCtx` 方法**的两个投影
——"脚本层是公共 API 的第一个用户"，保证两个轨道能力边界一致、行为一致。

用户视角的两种项目（同一骨架，逻辑层分道扬镳）：

```
MyGame/
├── project.ron / Scenes/ / Resources/ / input.ron   ← 两轨相同
├── Cargo.toml + src/lib.rs                          ← 方案 A（cdylib，无 main）
└── Scripts/*.lua                                    ← 方案 B
```

## 三、核心设计决策

### C1. 方法层挂在 `GameCtx`，不是 `World`（别推翻）

直觉是 `impl World { fn pos(&self) ... }`，但会撞上 `world.rs::run_dispatch` 的
**字段级拆借**架构（`let World { scene, physics, input, scripts, .. } = self;`——
四个互不重叠的字段同时借出，不需要 RefCell）。方法挂 `World` 上要求 `&mut self`
会把整个 World（含正在借用的 scripts 字段）借走，借用检查直接失败。

正解：新建捆绑结构 `GameCtx<'a>`——它恰好就是"一次派发所需的全部状态"：

```rust
// crates/xgame-runtime/src/ctx.rs（新）
pub struct GameCtx<'a> {
    pub scene: &'a mut Scene,
    pub physics: &'a mut PhysicsWorld,
    pub input: &'a Input,
    pub delta: f32,
    pub time: f32,
    pub entity: EntityId,   // 触发本次调用的实体（"self"）
}
impl GameCtx<'_> { /* 100+ 个方法，从 xgame-script/api.rs 平移 */ }
```

`run_dispatch` 构造它（借用拆分保持原样），三个消费者：
① Rust 组件的 `Ctx`（安全包装）；② Rhai 薄壳 `ScriptCtx`（改为持一个 GameCtx
地址束，外部行为零变化）；③ 未来的 Lua 绑定。

> **落地注记（D6）**：`GameCtx` 实际落在 `xgame-script/src/ctx.rs` 而非本节写的
> `xgame-runtime` —— api.rs 转发壳要调用 GameCtx，若放 runtime 会形成
> script → runtime 的反向依赖（既定方向是 runtime → script）。`Ctx` 是
> `GameCtx` 的类型别名（将来换成真包装零迁移成本）。

### C2. `Lifecycle` trait 与四钩子语义对齐

```rust
// crates/xgame-runtime/src/lifecycle.rs（新）
pub trait Lifecycle: Send + Sync + 'static {
    fn start(&mut self, ctx: &mut Ctx) {}
    fn update(&mut self, ctx: &mut Ctx, dt: f32) {}
    fn fixed_update(&mut self, ctx: &mut Ctx, dt: f32) {}
    fn on_destroy(&mut self, ctx: &mut Ctx) {}
}
```

与 Rhai `Hook` 枚举（`host.rs`：start/update/fixed_update/on_destroy）**同名同语义**
——脚本作者与 Rust 作者共享心智模型，也共享调度时机（start-before-update、
on_destroy 先于移除等既有语义）。

### C3. 注册表 + `Entity.behaviors` 字段

- 注册表：`name → (TypeId, 构造 + 分发函数指针)`，`register::<T>("Name")` 写入；
- `Entity` 新增序列化字段 `behaviors: Vec<String>`，用与 `scripts` 完全同款的
  兼容模式（`#[serde(default, skip_serializing_if = "Vec::is_empty")]`）——旧场景
  文件照常加载；
- `World` 装配时按名字查注册表实例化；未注册的名字记日志跳过（沿用"脚本崩溃不
  拖垮引擎"的容错哲学）。

### C4. 插件边界（UE 模式的核心基建）

- **入口**：`export_plugin!()` 宏生成 `#[no_mangle] extern "C" fn xgame_plugin_entry`，
  收引擎 API 函数表 + 注册表句柄，返回版本码；
- **`EngineApi` 函数表**（`#[repr(C)]` 指针表）：P0 只带最小闭环所需 ~10 个函数
  （log、self_id、pos/set_rot、action_pressed、delta/time），随需求扩表；
- **版本握手**：门面 crate 版本 == 引擎版本（同 rustc、同依赖、同 build flags
  编译——UE 对模块要求同款 MSVC，同理）；不匹配**拒载 + 明确报错**；
- **对象生命周期**：插件构造的组件对象由插件导出的销毁函数释放（分配器纪律）；
- Rust ABI 不稳定是已知风险：实践可行的前提是握手保证"同版本工具链"，写进文档。

> **落地注记（D6）**：`EngineApi` 最终只带 `version` + `log` 两个字段 ——
> 本节列的 pos/set_rot/action_pressed/delta/time 在 C1 落地后**全是 `Ctx` 的
> 方法**，而四个钩子本来就拿到 `&mut Ctx`；再造一张裸函数表等于给同一套能力
> 第二份真相源。扩表时机：出现"入口期 / 非钩子上下文"确实需要的能力再加。
> 入口符号生成为 `unsafe extern "C"`（dlsym 的固有语义），版本码用
> `0x58` 魔数 + 三段 8 位字段打包（永不为 0，与错误码不撞）。

### C5. 编辑器不链接用户代码（P0 范围声明）

编辑器二进制不含任何用户类型，P0 阶段编辑器**只编辑数据**（Behaviors 字段
Inspector 暂不显示，无害）；编辑器内 Play 跑 Rust 插件（PIE）推迟到 **P0.5**。
Bevy 式 `cargo run` 最小宿主是 P0 期间验证 Rust 组件全链路的方式。

> **落地注记（D7，P0.5 已完成）**：约束本身没有放松 —— 编辑器**至今不链接**任何
> 用户代码，它只是在运行期 `dlopen` 用户项目的 cdylib。Inspector 现在有
> Behaviors 区（组件**名**列表，与 Scripts 同构），编译由后台 `cargo build`
> 完成、产物同步进 `Plugins/`。`cargo run -p xgame-game` 逃生舱保留。

### P0 验收标准

1. `cargo test --workspace` 全绿——现有 Rhai 测试**不许改语义**（平移的回归网）；

7. **微基准**：1000 个 no-op 组件实体，组件分发一轮 < 50 µs；顺带对照
   1000 个 Rhai 脚本实体的分发耗时（把"快一个数量级"变成数字）。

## 六、P2.5 基准闸门（决策规则事先声明）

三负载，用**本引擎真实负载**（不是语言级 benchmark）：

| 负载 | 测什么 |
|---|---|
| 1. N 实体 × M 脚本的每帧 `dispatch` | 宿主调度 + 边界开销（两侧都在修掉 String 克隆后同一起跑线） |
| 2. 每帧若干次 `pos/set_pos/input` 吞吐 | API 边界穿越 |
| 3. 纯计算循环 | 解释器本体（拉开差距的项目） |

**规则**：Lua 三负载全占优 → P3 删 Rhai；任何一负载 Rhai 反超 >20% → 保留双宿主
并重新评估。预期：Lua 全胜（AST 解释 vs 字节码 VM 的代差）。

## 七、风险清单

| 风险 | 应对 |
|---|---|
| Rust ABI 不稳定，dylib 互操作无官方承诺 | 版本握手强制同工具链同版本；边界只走 C-ABI 函数表与 trait 对象（同版本门面 crate 下实践可行，UE 对 C++ 模块同理）；写进插件文档 |
| DLL 无法真正卸载（Rust 限制） | 热更 = 换文件名加载新副本，旧版泄漏至进程结束（开发期可接受）；带状态组件的迁移靠 P1 反射序列化快照回填 |
| 插件 panic / 死循环 | 每个跨边界调用 catch_unwind；死循环插件无解（与 UE C++ 模块同级风险），文档声明 |
| 维护面扩大（每 API 两绑：Rust 方法 + Lua 胶水） | Lua 绑定行级机械映射可审计；真到痛处再做绑定生成，不过早投资 |
| P0 平移 api.rs 出现行为漂移 | 现有 11 个 Rhai 测试不改语义；每平移一组跑一次 |
