## 一、结论与实际进展

### 1.1 当前阶段的准确定位

**XGameEngine 已越过“渲染器加演示场景”的阶段，形成具有编辑器、统一运行时、资产身份、Lua/Rust 扩展与机器可读工具接口的小型 3D 游戏引擎原型；尚未达到通用商业游戏生产工具的完整度与验证强度。**

它的优势在于架构边界清晰、三宿主复用运行时、文本数据易检查、无头工具齐备、基础编辑保护已经建立。主要差距同时存在于三个层面：

- **正确性闭环**：导入、多个角色并存、销毁、场景切换、发布包和主文件保存，还存在静态审查暴露的风险。新增效果之前要先保证已有能力在组合场景下正确。
- **生产工作流**：有材质数值不等于能忠实导入美术资产；有动画播放不等于动画师能制作角色；有 UI 按钮不等于能制作设置、背包和输入表单；有 GUID 不等于完整资产构建系统。
- **规模与交付**：跨平台、真实目标设备、资源预算、异步加载、GPU 分析、发布包测试、长期兼容和生态尚未形成体系。

不宜继续使用“内容层齐平”“编辑器产品化收口”“渲染只剩 SSAO”等总括结论。更准确的说法是：**多数基础能力已有最小实现，离可反复制作、调试、发布实际游戏仍有系统性差距。**

### 1.2 已取得的进展，不能被新差距清单抹掉

| 方面 | 当前有证据的成果 | 应保留的边界 |
|---|---|---|
| 分层与宿主 | core/math/功能模块/runtime/editor-game 分层；`World::update` 复用 | 宿主输入、渲染、音频监听、打包仍可能不同，不能推出全链路一致 |
| 场景与实体 | RON、父子层级、局部/世界变换、稳定身份、只读重复 ID 检查 | 损坏文件的历史父子意图无法凭空恢复；跨文件来源身份仍需审计 |
| 基础编辑器 | 层级、Inspector、Gizmo、撤销、复制粘贴、Prefab、项目枢纽 | 多选、吸附、字段级覆盖、批量资源操作和复杂 UI 制作不足 |
| 编辑保护 | 未保存提示、Save As、自动保存/恢复、布局持久化 | autosave 原子写不等于主文件保存全部原子化 |
| 渲染 | 标量金属度 PBR、albedo、HDR/ACES、Bloom、天空 IBL、CSM、实例化、视锥剔除、FXAA、基础 TAA | 法线/MR 贴图、局部照明、动态物体历史、规模渲染不足 |
| 动画 | glTF 骨骼、剪辑、交叉淡入、阈值状态机、分层混合/遮罩、CPU morph | 根运动、IK、重定向、制作工具、多 skin/多轨道保真不足 |
| 玩法基础 | 角色控制器、碰撞事件、时间缩放、场景切换、Prefab 生成 | 移动平台、存档、导航、网络等仍缺 |
| 内容表现 | 基础屏幕 UI、CPU billboard 粒子、静态音频与空间衰减 | UI 复杂交互、粒子材质、混音/流式音频尚不足 |
| 扩展 | Lua 沙箱/指令预算/编译缓存；Rust 行为插件与字段 Inspector | 内存预算、调试、插件 ABI、全生命周期一致性仍需完善 |
| Agent 工作流 | 12 个 MCP 工具、schema、脚本 API、check/headless/screenshot | 缺事务补丁、并发版本检查、输入驱动验证和取消/超时 |
| 验证 | Windows CI、回归测试、历史分档性能基准 | 不能据此宣称多平台、完整 GPU 画面或发布包已验证 |

近期修复应明确计入进展：普通实体 ID 分配与读盘预留、复制粘贴按位置分配 ID、删除子树避免同 ID 连坐、UI ID 表首占位、显式 Lua `on_destroy`、脏检查覆盖层与 morph、逐实体 morph 顶点缓冲隔离。**本报告不把这些旧问题重复列为未修。**

### 1.3 数量与成熟度的正确解读

- 当前脚本目录及注册核查对应 **160 个函数、6 个生命周期钩子**；UI 注册 26 个。见 K12。旧文档的 155/158/23 已过时。
- 决策记录最新历史全量结果为 **873 passed / 0 failed / 7 ignored**，不是本次重新执行的结果。见 K25。
- 200 个能力细项不是 200 个 bug，也不是 200 个同等工作量的任务；其中包括已有基础能力的生产深度、明确缺失、待验证边界和特定产品才需要的高级能力。
- 不给“追平 Unity 多少百分比”或“整体领先某开源引擎”的分数：功能边界、包组合、场景负载和团队目标不同，不存在可信的统一分母。
- 历史的微秒数据只说明相应机器、版本与负载下的局部改进；不能换算成完整游戏帧率，也不能与其他引擎官网数据直接比较。

## 二、比较口径与证据纪律

### 2.1 为什么不声称穷尽“所有优秀引擎”

市场不存在稳定且可穷尽的优秀引擎名录。许多工作室内部引擎没有足够公开实现资料，不能据宣传逆向填表。本报告选择 19 个代表对象，覆盖高端通用 3D、Rust 引擎、移动/Web、2D、叙事以及框架型开发。

Frostbite、RE ENGINE、Decima、RAGE、Snowdrop 等内部引擎不作为逐项可验证基线；其成品观感可以启发目标，但不能据此推断可授权工具、公开 SDK、多人实现或编辑器细节。中间件如 Wwise/FMOD、Havok/Jolt、Recast 也不冒充完整引擎。

### 2.2 比较单位

每项能力应至少拆成：**数据与 API → 运行正确性 → 编辑制作 → 诊断 → 构建与平台交付**。例如“有 LOD”至少还要问：如何生产低模、在哪里配置、过渡是否闪烁、阴影/碰撞是否一致、如何显示预算和覆盖率。

本文矩阵采用以下状态：

| 状态 | 含义 |
|---|---|
| 基础 | 有运行/编辑链路，但不代表生产深度完成 |
| 部分 | 明确存在只接了一部分的能力或消费路径 |
| 缺失 | 文档明确未做，且相关源码/数据结构未发现集成 |
| 待验 | 有具体代码风险或缺少目标环境验证，不能写成已复现 |
| 专项 | 取决于产品方向，不构成所有游戏共同阻塞 |

证据 K01—K25 对应仓库文件与关键位置，外部 S01—S50 对应官方资料。矩阵每节列出证据范围；行内“借鉴”是设计推荐，不表示该引擎具有该项能力的排他性优势。

### 2.3 版本、许可与平台

本次查阅当前官方页面，也使用明确版本的历史技术文档证明已实现能力。**不将历史包版本称为最新版，不把路线图当发布事实，不推测价格与授权条件。**

Unity 必须区分 URP/HDRP 和不同扩展包；Bevy/Babylon.js/MonoGame 的工具形态不能与完整编辑器直接等同；UNIGINE 的 Sim 能力不能自动归到所有 SDK 档位；O3DE 是开源引擎，CRYENGINE 的源码可访问不等于开源许可证。主机导出均需单独核实平台资格与 SDK，不能由“支持 C++/Rust 或 Vulkan”推出。

### 应学的原则，而不是照抄的表面形式

- 从 Unity/Godot/Fyrox 学“改一个资源，立即看到可信结果”，包括失败提示和撤销。
- 从 Unreal/O3DE/MonoGame 学“源资产不等于运行时资产”，需要依赖构建与目标平台处理。
- 从 Bevy 学反射、调度与显式资源寿命；不要只为架构名词重写已可工作的 World。
- 从 Defold/Panda3D 学可解释的性能：作者应能回答某个卡顿、某块显存、某次 draw 从哪里来。
- 从 PlayCanvas/GDevelop 学低摩擦创作，但先解决命令事务、并发保护和稳定 ID。
- 从 Ren'Py 学“产品完整性”：设置、读档、回退、本地化可以比一种高级阴影更影响作品能否发布。

## 四、优先复现的正确性与交付风险

本节与后续功能矩阵分开。下面是**静态审查发现**，不是已经跑过的回归失败；修复前应先建立旧实现失败的新测试。没有在本轮修改引擎代码。

| ID | 代码事实与触发条件 | 影响/建议验证 | 证据 |
|---|---|---|---|
| R01 | `content_dirs()` 未枚举 `scripts_dir`；默认 Scripts 不在 Resources 下 | 导出包可能缺 Lua；创建只依赖独立 Scripts 的样例，脱离源码目录启动产物 | K01:301 |
| R02 | 构建流程未另复制项目根 `input.ron`，播放器从项目根读取 | 自定义按键发布后退回默认；比较编辑器与产物同一输入动作 | K01:218；K21:219 |
| R03 | GPU 蒙皮按 `(skin_slot-1)*256` 寻址，CPU 上传只追加实际骨数，没有逐槽补齐 | 两个不足 256 骨的角色第二个读错矩阵；合成两副小骨架，验证上传布局及 GPU 姿态 | K02:960、2475 |
| R04 | `take_spline_values` 将 CUBICSPLINE 当“切线块/值块/切线块”截中间三分之一 | glTF 实际按每关键帧入切线/值/出切线排列；多关键帧取错。先测 2—3 关键帧已知数据，morph 单独按 stride 测 | K03:1029；S49 |
| R05 | GameRunner 的 window 声明早于 app，注释误称字段按反序析构；Surface 借用被延长 | Rust 字段按声明顺序析构，安全论证不成立；检查退出/异常路径，优先采用有所有权的窗口引用方案 | K21:137、574；S50 |
| R06 | `write_scene/write_prefab` 直接写目标文件，主保存不同于 autosave 的原子替换 | 中断/磁盘写失败可能损坏主文件；注入失败，确保旧文件仍可读 | K04:813、1023 |
| R07 | Prefab Apply 用实例子树重新生成模板，保留实例 ID 而非映回 source_id | 模板来源身份可能漂移；两个实例并存，一处 Apply 后验证所有来源映射与 Revert | K05:1831；K06:109 |
| R08 | 固定步最大步数限制单帧工作，但积压保留；time_scale=0 不清积压 | 高倍速后暂停仍可能补物理步；构造超预算积压，断言暂停策略。需先定义“丢步/保留/冻结”契约 | K07:70、83；K08:777 |
| R09 | 点光 range 存在于配置，但未进入对应 GPU 灯数据及范围截断计算 | 作者改范围可能无效果；不同 range 对照截图及数值衰减测试 | K09:51；K02:2094、1152 |

## 六、跨子系统的深层差距

### 6.1 “功能存在”与“生产能力”之间缺的是组合契约

材质系统单测正确，但导入器丢 normal/MR、node 变换或 alpha cutoff，美术资产仍无法忠实落地。动画采样单测正确，但两个角色同屏时骨骼缓冲布局错误，单角色 Demo 无法揭露。Prefab 可生成，但 Apply 改变来源身份，长期内容维护会失去基线。每个子系统都应按真实工作流组合验收，不能继续只按目录是否有实现划勾。

建议把功能完成定义固定为五项：有效输入、错误输入、多个实例、资源生命周期、发布包中运行。GPU 功能另加目标设备与图像验证。只有满足适用项，才从“基础实现”升为“生产可用”。

### 6.2 资产管线是当前最重要的横向基础

现有 GUID 解决“引用谁”，meta 参数解决一部分“怎么导入”；仍缺“依赖什么、哪个产物有效、何时释放、怎样打包”。应建立四层：

1. **源资产**：用户可编辑文件、GUID、导入参数、外部依赖。
2. **导入产物**：按源内容/工具版本/配置生成的平台中立数据。
3. **目标产物**：压缩纹理、优化网格、音频、shader等平台结果。
4. **运行句柄**：加载状态、generation、引用/预算、错误及取消。

GUID 保持稳定；哈希用于缓存，不替代身份。GPU对象按generation更换，避免裸指针地址复用误命中。改变一张贴图应能沿依赖图失效材质，而不是重建整个世界。构建器也应使用同一依赖图，这样“漏文件”和“无用文件全复制”才能一起解决。

### 6.3 动画需要内容模型、运动模型与诊断模型一起升级

动画 Phase B 不应只理解成增加状态机字段。完整角色需要：骨架/剪辑资产、时间与循环语义、过渡与事件、root motion、IK约束、morph与蒙皮混合、与控制器的冲突规则。最终位移由谁决定必须唯一，否则会出现动画走了而物理没走、网络校正后脚滑等问题。

从 CRYENGINE 借动作语义与标签，从 Unity/Fyrox 借混合和约束，从 UE 借选择过程可视化。先做一个走/跑/跳/攻击角色，显示当前剪辑、过渡、权重、事件、root delta、物理结果；再讨论复杂动画图或 Motion Matching。

### 6.4 实体生命周期必须跨宿主、跨脚本、跨资源一致

`World::update` 单入口是重要优势，但不能掩盖场景卸载、Stop、原生析构与Lua回调的差别。建议以显式状态机定义：未启动→活动→待销毁→销毁回调→解绑资源→移除。允许回调中做什么、能读到什么、是否允许再生成/删除对象，应写成可测试契约。

结构变更可采用明确阶段的命令消费，不要求立即重写成ECS。关键是Lua快照、Rust行为索引、物理体、UI捕获、音频follow、动画缓存必须对同一生命周期事件作一致响应。场景切换也需复用该协议，而非分别clear各张表。

### 6.5 UI 是交互基础设施，不是一批绘制控件

当前整屏批绘制是可取的性能选择，但增加裁剪、字体图集、九宫格和材质后，应接受有依据的批次拆分。为了“1 draw”牺牲正确裁剪和输入语义不值得。

应优先形成：布局测量/排列→可见/裁剪树→命中→捕获/焦点→事件传播/消费→状态改变→绘制。游戏输入应能知道UI是否消费事件；父控件禁用/隐藏、模态窗口、拖出释放、删除捕获对象都有明确处理。然后才是背包、设置、输入框等高级控件。

### 6.6 性能优化不能由架构时尚驱动

“Vec单线程”不自动构成必须迁Bevy ECS的证据；“Rust+wgpu”也不自动构成性能优势。旧微基准中的Rapier瓶颈、实例化收益有价值，但必须补真实混合负载。动画临时Vec、音频同步列表、重复导入失败、资源重载滞留可能先于实体存储结构成为问题。

优先顺序应为可观测→复现→剖析→局部修复→同负载A/B。后台解码、离线导入、异步IO可以逐步引入，不改变编辑器视口必须UI线程同步的既有约束。任何渲染图、任务系统、ECS提案都要附可测收益与迁移成本。

### 6.7 Agent-Native 的下一步是可审查事务，而非单纯增加工具数量

12个工具已经能读/写/查/跑，这是差异化地基。要升级到可靠自动制作，需要：读取带revision；patch带expected_revision；批量修改全成或全退；返回语义diff；运行有预算/取消；验证可注入输入；截图能定位实体。

编辑器UI、CLI、MCP应调用同一命令/验证服务，不建立第二份规则。人类改属性与AI改属性都能撤销和看差异，才能降低双端协作风险。机器能导出schema只证明契约可读，不证明整个项目已可由AI稳定制作。

### 6.8 安全边界是可靠性工程的一部分

项目会运行Lua与原生插件，二者信任模型不同。Lua指令预算不等于内存上限；原生插件不具备脚本沙箱隔离；插件版本一致也不保证Rust ABI一致。常驻ctx裸指针依赖执行窗口，必须针对顶层代码与热重载单独验证。

这里不把未复现的风险写成已证实漏洞。近期应先核验窗口/Surface析构、ctx有效性、文件路径与输出目录互相包含等确定边界，再根据产品分发范围决定可信项目提示、禁用插件模式、独立进程或权限隔离。内部单人开发与下载陌生项目有不同要求。

## 七、融合各家优势的目标架构

### 7.1 保留现有核心约束

保留现有crate依赖方向、World唯一编排、GUID转换只在磁盘边界、parent单真相源、局部transform、共享模型加载入口、新字段默认兼容、UI线程同步视口、只读check、默认关闭新增高成本效果。任何新方案先对照 [`决策记录.md`](决策记录.md)，避免为了模仿其他引擎重复踩坑。

### 7.2 建议形成的共用基础服务

| 追踪事件与Profiler | UE Insights、Statoscope、PStats | 低开销结构化事件，现有面板显示摘要，文件保留详细trace | 用证据决定后续优化 |
| 平台能力/质量配置 | Unity URP/HDRP、UNIGINE DRS | 可查询设备能力，配置决定效果和预算；显式降级 | 防止效果只能在开发机器可用 |
| 可验证作品模板 | Godot/GameMaker/Ren'Py制作闭环 | 一个真实小型游戏覆盖菜单到结束与存档，不只功能场景 | 检验子系统组合与交付 |

建议的数据流为：源资产与项目数据 → 统一校验/导入 → 可缓存产物 → World/渲染资源 → 编辑器、独立玩家、无头验证；编辑器和Agent的写操作统一经命令/事务入口。无需为了这个方向立即创建新crate或一次性替换现有实现。

### 7.3 不建议立即做的“大重写”

- 不为追随Bevy重写全部ECS；先解决可复现的热路径瓶颈。
- 不以Nanite/Lumen作为近期“追平”门槛；法线贴图、导入保真与发布包正确性收益更直接。
- 不先做完整材质/行为/动画节点编辑框架；先稳定资产与运行语义，再共享图编辑基础。
- 不先做云端多人编辑；本地文件事务、ID、覆盖合并和并发版本检查是前提。
- 不同时开2D、移动、Web、主机、网络五条产品线；选一个小型3D作品验证主线，其余按需求开分支。
- 不把完整SaveGame、背包、任务、在线服务全部塞进core；通用设施在引擎，品类规则放可选包/示例。

## 九、候选实施阶段与依赖

### G0：证明现有能力能正确组合与发布

目标是消除已有能力的基础正确性风险，而非增加功能数量。

1. 针对R01/R02/R03/R04/R05建立最小失败用例；核验并修复实际问题。
2. 主文件原子保存、构建staging替换、输出目录与源范围冲突保护。
3. Prefab来源ID、销毁/切关/Stop生命周期、固定步积压与暂停语义。
4. 对ctx窗口、插件ABI、质量/范围参数兑现进行定向审计，不把审查推断直接当完成修复。
5. CI加入“打包→独立目录运行→脚本执行→自定义输入→切关”的端到端门禁。

**退出标准**：风险有测试或明确反证；旧实现能证明失败；产物不依赖仓库目录；主写入失败不毁旧文件。继续遵守check/clippy/test与适用的GPU/UI验证纪律。

### G1：做出一款完整小型3D游戏

- 资产：normal/MR、alpha mask、mip、glTF节点/动画基本保真。
- 交互：手柄或FPS锁鼠按作品选定；UI输入消费、焦点、滚动/缩放、基础设置控件。
- 玩法：存档/玩家设置、镜头跟随、移动平台、动画事件；需要NPC时补静态导航。
- 音频：BGM/SFX/UI分组、监听一致性与基本资源释放。
- 工具：日志落盘、错误溯源、API注解、输入驱动headless验证。

**退出标准**：菜单→开始→暂停→设置→存档→退出→读档→下一关→结束完整流程；外部机器在没有源码和开发工具时能运行。

### G2：让内容生产可扩展

依赖G0/G1实际作品暴露的痛点：资产依赖/cook/异步句柄、内存分析、动画图/IK/重定向、Prefab字段覆盖/嵌套、多选/吸附/全局命令、LOD/局部探针/点光阴影、粒子贴图与音频流式、GPU时间、自动性能趋势。

**退出标准**：重复切关/重载资源能回落；复杂角色和外部资产有合规样例；作者大部分常见工作不需手改RON或引擎Rust；导入变更只重建受影响资源。

### G3：平台、团队或网络的选择性扩展

三条可独立立项：桌面第二平台/移动Web；团队内容协作与迁移；网络多人。每条需明确人力、目标设备和样板作品，不以“同一依赖理论支持”作为完成。

**退出标准**：支持矩阵有实际测试记录；目标环境可诊断/回滚；网络在线路故障下有量化结果；多人编辑不静默覆盖。

### G4：高端能力与新产品线

虚拟几何、动态GI、复杂水/云/布料、Motion Matching、行星尺度、2D完整工具、叙事/低代码、主机/XR等分别立项。必须证明目标作品需要，且基础内容管线和验证条件能够支撑。

### 关键依赖链

- 精准LOD/HLOD、流送、补丁 → 资产依赖与派生产物 → 句柄/预算/Profiler。
- 材质图 → 稳定shader接口/变体/诊断 → 完整材质输入与色彩空间。
- 根运动/预测 → 固定步与生命周期 → 角色控制器/输入回放。
- 嵌套Prefab/协作 → 稳定来源ID → 字段patch/事务 → 语义diff/版本前置检查。
- 移动/Web → 输入/UI缩放/字体 → 平台生命周期/资源压缩 → 独立构建与设备测试。
- AI自动制作 → 命令服务/schema → 精确事务 → 输入驱动运行 → 图像/状态联合断言。

## 十、验收场景与评测方法

### 10.1 建议建立的基准场景库

| 场景 | 构造 | 关键断言 |
|---|---|---|
| A 资产合规 | 标准glTF：节点实例、双面/裁切、normal/MR、UV、线性/样条动画 | 导入警告准确；无静默错位；参考截图和通道数值 |
| B 多角色 | 2个不同小骨架、同模型不同morph、带层混合 | 骨骼槽互不串、阴影一致、权重独立、动态bounds |

| J 网络（立项后） | 多客户端，延迟/抖动/丢包/掉线矩阵 | 校正误差、带宽、server tick、重连恢复可量化 |

### 10.2 公平对跑规则

1. 统一资产、相机、分辨率、视觉质量目标与功能开关，记录每家实际配置和包版本。
2. 统一硬件/驱动/系统/构建类型；区分编辑器与独立player，debug不与release混比。
3. 分开CPU提交、GPU、IO、脚本、物理与总帧时间；不要简单把重叠阶段相加。
4. 报告预热、采样时长、p50/p95/p99、1% low定义、峰值内存/显存以及画面差异。
5. 负载不能只用同材质方块；加入动画、透明、UI、音频、不同材质与切关尖峰。
6. 不拿873测试数量与别家的测试数量排名；关注具体契约、失败路径及覆盖的真实风险。
7. 同机逐字节截图与跨GPU近似正确分开；TAA需明确累积帧数，不能把模拟帧数当渲染历史帧数。

**决策落点**：优先让现有功能在真实作品、复杂资产、反复编辑与独立发布中保持正确；随后建设资产依赖、生命周期、事务与性能观测这些共享基础；再有选择地借鉴各引擎的专长。XGameEngine的可取方向是轻量、清晰、可自动化验证的3D制作工具，而不是在缺少生产闭环时同时追逐所有大型引擎的功能名单。
