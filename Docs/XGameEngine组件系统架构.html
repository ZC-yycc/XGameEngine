XGameEngine 组件系统
从磁盘身份到每帧调度的完整链路

这不是一张只列类型名的类图，而是回答五个真正决定系统行为的问题：组件值存在哪里、实例身份由谁保存、编辑如何进入 Undo 与磁盘、运行时如何装配 Rust / Lua、Prefab 与 Agent 如何在并发写入下保持同一组件。

源码基线：8bf296e · feat: split visual inspector components；分支 master。报告覆盖 xgame-core、xgame-editor、xgame-runtime、xgame-script、xgame-mcp 与项目决策记录。单文件 HTML，CSS / SVG / 筛选脚本均内嵌，可离线阅读；源码链接固定到该提交。

1份运行时可变组件值模型
11种内建组件（10 种可增删）
2类扩展挂载：Rust + Lua
(E, C)稳定地址：实体 ID + 局部组件 ID

01 · 核心判断

一句话：当前系统已经具备 Unity 式的可发现、可寻址、可增删、可保存组件实例，但没有把运行时改造成第二套 ECS。磁盘 v2 保存强类型组件与稳定身份；编辑器和运行时仍共同修改唯一的 Scene / Entity 值模型；RuntimeSceneIdentity 只是一张不含组件值的身份侧车。[S6]

值所有权

Entity 的原字段仍是渲染、物理、脚本和 Inspector 共同读写的真值。v2 装载后会投影到它，而不是让每帧系统同时维护 SceneV2。

唯一可变值

身份所有权

磁盘 v2 的 ComponentIdentity 与 next_component_id 负责跨保存稳定；运行时只提取本地 ID、来源 ID、高水位和种类。

稳定寻址

行为所有权

Rust 组件实例由 BehaviorRegistry 构造，Lua 状态由 LuaHost 按实体与脚本维护；两轨共享同一 GameCtx。

独立运行态
问题准确答案常见误读
是不是 ECS？主场景模型不是稀疏 ECS：Entity 是带强类型字段的对象，World 编排各系统。看到 ComponentMap 就推断所有可保存组件都在 TypeId Map 里。
v2 是否复制组件值？磁盘 / 编辑会话保留 v2 身份；运行时 RuntimeScene 只有一份 Scene 值和可选身份侧车。认为脚本需要同时写 Scene 与 SceneV2。
组件 ID 是否全局？ComponentId 只在实体内唯一；完整地址是 (EntityId, ComponentId)。只传组件 ID 就能跨实体定位。
Prefab 来源 ID 是本地 ID 吗？不是。id 属于实例，source_component_id 指向资产组件；初次实例化可恰好同值，但语义分离。把资产 ID 直接当实例身份并在本地分配时继续共用。
Parent 是组件吗？不是。父子关系唯一入口是 Hierarchy，数据是 Entity.parent 元数据。在 Inspector 再造一个 Parent 组件或第二套父选择器。

02 · 全景架构图

读图时不要把“映射”当“复制后双写”：编辑器 v2 会话确实同时持有 Scene 值视图和 SceneV2 身份快照，但 UI 只改前者；保存、Undo、Play 前才通过 reconcile_from_v1 把值合回身份候选。运行时则在装载边界直接拆成值 + 侧车。[S8]

03 · 代码里三种“组件”必须分开

同一个词在仓库里指向三套不同生命周期。如果不先拆开，最容易得出“组件已经在 ComponentMap 里统一”或“Rust Behavior 就是磁盘组件本体”的错误结论。

概念真实载体是否落盘身份 / 生命周期主要消费者
可保存挂载物v1：Entity 强类型字段、behaviors、behavior_params、scripts；v2：ComponentData。是v1 地址可能是列表槽位；v2 用 (EntityId, ComponentId)。Inspector、ProjectHandle、Prefab、MCP、World 装配。
Rust 行为实例BehaviorInstance { component: Box<dyn Behavior>, hooks, started }。实例不落盘 只保存注册名与字段值每次 World / Play 会话构造；启动标志按实例保存。dispatch_behaviors、运行态 Inspector。
临时类型状态Entity.components: ComponentMap<TypeId, Box<dyn Any>>。否 #[serde(skip)]每 Rust 类型每实体一份；克隆 Entity 时 Map 清空。角色状态、物理句柄等系统私有运行态。

第四类：系统私有运行态

PhysicsWorld 的刚体、AnimationDriver 的时钟、粒子桶、音频句柄、Lua state_* 都不是场景组件值。它们由 World 按实体 ID 同步、切场景时清理或保留。

为什么仍保留 ComponentMap

它适合“每帧读写但不应保存”的强类型状态：O(1) TypeId 查询、单类型单件、命中时可零分配。把它序列化会引入跨 DLL 类型名、版本和克隆语义问题。

命名上的陷阱：register_component<T> 注册的“纯数据 Rust 组件”并不进入 ComponentMap；它被 DataComponent<T> 包装成空钩子的 Behavior，继续复用 behaviors / behavior_params 持久化通道。[S7]

04 · 当前组件目录与数据归属

BuiltinComponent::ALL 是编辑器和工具统一发现内建组件的清单。Transform 固有；其余 10 种都可独立增加、删除和获得 v2 身份。Mesh / LOD / Material 已在当前基线拆成三份真实组件，不再共用旧 Render 身份。[S2]

组件唯一值所在“存在”判据可移除主要运行时消费者
TransformEntity.transform恒存在；v2 单列 transform_identity否层级、渲染、物理、相机、脚本。
Meshmodel + morph_weights模型路径或权重非空是模型装载、morph、渲染、拾取。
LODlod: LodGroupLOD 级非空是模型选择、绘制距离、拾取。
Materialmaterial_asset + material资产或逐实体覆盖存在是材质解析、批次键、渲染。
UI Elementui: Option<UiElement>Some是布局、命中、焦点、UI 绘制。
Animatoranimator: Option<Animator>Some是AnimationDriver、根运动、动画事件。
Physicsphysics: Option<PhysicsBody>Some是Rapier 刚体 / 碰撞体同步。
Charactercontroller: Option<CharacterController>Some是运动学胶囊、坡面、台阶、接触。
Audio Sourceaudio: Option<AudioSource>Some是autoplay、空间位置、音频总线。
Cameracamera: Option<Camera>Some是主相机解析、三宿主取景。
Particle Emitterparticle: Option<ParticleEmitter>Some是CPU 粒子模拟、billboard 绘制。
Rustbehaviors[] + behavior_params{name→fields}注册名挂在列表按具体行BehaviorRegistry → BehaviorInstance。

是实体元数据，不是组件

name、id、parent、prefab、layer。其中 Parent 只由 Hierarchy 管理；Prefab 引用描述来源；Layer 影响物理分组。

是场景数据，不挂实体

Scene.lights 与 ambient 仍在场景级。不要因为 Camera 已是实体组件，就推断 Light 也走同一组件目录。

05 · v2 稳定身份：地址、来源与高水位

StableComponentAddress = (EntityId, ComponentId)

本地 ID

ComponentId 非 0、非 u64::MAX，只在一个实体内部唯一。Transform 也有自己的本地 ID。

来源 ID

source_component_id 只在 Prefab 实例上出现，指向资产实体中的组件 ID；普通实体必须为 None。

持久高水位

next_component_id 随实体保存。删除最高项、Undo 回退、重排都不降低它；耗尽时拒绝，不回绕。

5.1 v2 文件形状

SceneV2
└─ EntityV2
   ├─ id / name / parent / prefab / layer
   ├─ transform: Transform
   ├─ transform_identity: { id, source_component_id? }
   └─ components: ComponentSet
      ├─ next_component_id
      └─ entries: [
           ComponentInstance {
             identity: { id, source_component_id? },
             data: ComponentData::Mesh | Lod | Material | Ui | Animator |
                   Physics | Character | Audio | Camera | Particle |
                   Rust { registered_name, fields } | Lua { path }
           }
         ]

5.2 身份如何在编辑后认回

旧身份快照按实体 ID 找到上一版 EntityV2
→
当前值视图从 Entity 枚举内建 / Rust / Lua
→
稳定键匹配内建种类、注册名或脚本路径
→
已有项保留本地与来源 ID
→
新增项从持久高水位分配
→
候选全验证成功后才替换会话身份

Lua 路径 / Rust 注册名在 v1 值视图里既是内容又是关联键。只有“旧同种类恰好一项、新同种类恰好一项、且旧项没有 Prefab 来源”时，改名才可视作同一实例；有歧义就分配新 ID，不猜。[S5]

5.3 旧视觉布局如何迁移

拆分前 v2 用 Render(model, lod, material_asset, morph)，另有 MaterialOverride。当前格式将其拆为 Mesh、LOD、Material。旧文件仍可读，但新建和 Agent 修改禁止生成旧变体；首次经编辑器保存时，一个旧 ID 最多交给一个实际存在的新组件，其余从高水位分配。这样不会伪造“一份身份同时属于三项”。

过渡门禁：实体只要还含旧 Render / MaterialOverride，MCP 的通用组件编辑连 Transform patch 都拒绝；先让编辑器保存完成布局迁移。[S5] [S12]

06 · 编辑器：UI 改值，保存阶段合身份

6.1 Inspector 的统一结构入口

菜单 / 右键
只产生 ComponentAction::{AddBuiltin, AddRust, AddLua, Remove}。
working 副本
克隆选中 Entity，调用 add_* / remove_attached_component 修改原字段。
动作门禁
Play / Pause 不仅按钮置灰，执行层的 editing 也会拒绝结构变化。
Undo
替换实体之前 push_undo()；v2 会同时把当前值合入一份身份历史快照。
写回
用 working 替换 scene.entities[index]；UI 不直接分配任何 ComponentId。

标题右键、具体 Rust / Lua 行右键、Inspector 空白右键与底部 Add Component 共用同一个动作枚举。Scripts / Behaviors 标题只是集合，不能“一键移除整个标题”；Transform 真实存在但锁定；Mesh / LOD / Material 的移除边界互不连带。[S9]

6.2 v2 编辑会话

V2EditorSession {
  identity: SceneV2,   // 组件 ID / 来源 / 高水位的会话快照
  disk_bytes: Vec<u8> // 打开或上次写入时的完整磁盘原文
}

EditorState.scene: Scene // Inspector、Hierarchy、Gizmo 实际编辑的唯一值视图

Undo / Redo

值快照与 v2 身份快照成对推进。Undo 恢复旧内容时，keep_allocated_ids 取前后历史的较大高水位，避免撤销后复用已经发放的 ID。

Save

加载所有引用 PrefabV2，克隆身份快照，reconcile_from_v1 构造完整候选；条件写入成功后才更新会话身份、磁盘字节和脏检查基准。

并发编辑的结果是“保草稿、拒覆盖”：若外部 Agent 已改过磁盘原文，write_scene_v2_if_unchanged 失败；内存草稿仍在，用户可重新打开或处理冲突。Play 中保存则硬拒绝，因为此时 Scene 是物理和脚本正在改的运行副本。[S8]

6.3 进入 Play

编辑器不会把裸 Scene 直接交给 v2 World。它先把未保存值合回身份副本，再调用 RuntimeScene::from_v2；编辑器 Play、独立游戏与无头运行因此共享同一份“值 + 身份”载荷和同一段 World::update。

07 · ProjectHandle：所有磁盘语义的边界

阶段ProjectHandle 的责任为什么不能旁路
读取 v2项目相对路径门禁、严格 RON 解码、GUID → 路径、加载来源 Prefab、核对来源组件 ID 与种类。单独解析 SceneV2 只能验证文件内部，无法证明来源 ID 仍指向同一种资产组件。
严格解码serde_ignored 检出嵌套未知字段；专用 MapAccess 拒绝 Rust 参数 / 动画参数重复键。普通 serde 可能吞未知字段或让 BTreeMap 后值覆盖前值，下一次保存会不可逆丢数据。
资产引用磁盘存 guid://…，内存存项目相对路径；v2 的 Mesh、LOD、Material、Lua、Audio、UI、Prefab 来源都走统一遍历。GUID 进入运行热路径会污染大量消费者；直接写路径又失去移动稳定性。
条件写入比较本次读取的完整原文字节，持有单文件 OS 锁，再编码 GUID、原子替换；内容相同不改 mtime。revision 只是快速令牌；只比 hash 或写前不持锁仍有 TOCTOU 窗口。
版本隔离v1 入口拒绝 v2；v2 写入口只写新文件或合法 v2；运行专用入口按版本返回完整载荷。to_v1() 会丢组件身份，绝不能再经旧入口覆盖 v2 文件。
最危险的错误路径：load_scene_v2 → to_v1 → write_scene。值看似完整，组件 ID、来源 ID 与高水位却全部消失；旧入口明确拒绝 v2 正是为了阻断这种静默降级。[S10]
v1 为什么仍然存在？

一是兼容旧项目与测试；二是 Scene / Entity 已被渲染、物理、脚本等大量消费者验证，是当前高效值模型。v2 的目标是补齐持久实例身份和严格结构，不是强迫所有每帧系统改读一套嵌套枚举。旧磁盘 v1 的 Rust / Lua 地址仍是槽位，MCP 会明确返回 address_stability: legacy；只有显式迁移后才可用稳定 ID 写。

08 · 运行时：一份值、可选侧车、两条代码轨

8.1 RuntimeScene 与身份侧车

RuntimeScene
├─ scene: Scene                         // 唯一可变组件值
└─ identities: Option<RuntimeSceneIdentity>
   └─ RuntimeEntityIdentity
      ├─ entity_id
      ├─ transform: RuntimeComponentIdentity
      ├─ next_component_id
      └─ components[] { identity, kind }

RuntimeComponentKind = Builtin(kind) | Rust(name) | Lua(path) | legacy visual

World::component_identity(entity, component) 不只查侧车，还确认该种类仍存在于当前 Scene；宿主若直接经 scene_mut() 删除值，不会得到“幽灵身份”。正式的运行时结构写入口仍必须同时维护侧车。[S6]

8.2 Rust 轨：声明、注册、实例

磁盘声明behaviors[] 保存注册名
→
插件注册register<T> 或 register_component<T>
→
装配按名构造 Box<dyn Behavior>
→
套参数behavior_params[name] 经 Inspect 写入
→
热路径调用预复制的函数指针，不再按字符串查表

Behavior = Lifecycle + Inspect。字段表既服务编辑器，也让装配期能恢复持久值；生命周期包含 start、update、fixed_update、碰撞 enter / exit、动画事件与 destroy。插件 DLL 的旧句柄不会卸载，避免存活 trait object 的 vtable 悬垂。[S7]

8.3 Lua 轨：路径资产、隔离环境、每实体状态

LuaHost 以项目相对路径缓存编译结果；每个脚本有独立环境表，元表的 __index 指向宿主全局 API。state_* 表按 (EntityId, path_intern_id) 保存，路径驻留 ID 永不清；热重载只清编译缓存，因此状态不会因驻留顺序变化而错位。每次钩子还有 20 万指令预算与 128 MiB VM 内存上限。[S11]

这也是“同路径多实例”尚不能开放的根因：Lua 状态键还没有 ComponentId；Rust 参数也仍按注册名存。仅放宽 Inspector 去重会让多个实例共享状态或字段，必须先改运行时寻址。

8.4 两轨为什么能力一致

Rust Lifecycle 的 Ctx 只是 GameCtx 别名；Lua API 也是对同一批 GameCtx 方法的一行转发。场景、物理、输入、音频、时钟、日志、结构命令和当前实体都在这一束里。固定顺序是同阶段 Rust 先、Lua 后：Rust 本阶段写入对 Lua 当帧可见，反向不保证。[S10] [S11]

08.1 · 每帧时序与结构改动语义

操作Scene 值何时变化命令何时结算组件系统后果
spawn_entity钩子内立即阶段后登记身份、补物理；新实体下轮 Start。同一钩子可立刻按返回 ID 改位置。
spawn_prefab整棵子树立即每个新实体一条 EntitySpawned，附可选身份。v2 资产把资产 ID 转成“本地 ID + 来源 ID”。
destroy整棵子树立即移除阶段后 on_destroy、刚体、状态、身份侧车清理。Destroy 钩子触发时实体已不在 Scene，但 Lua state 尚可读到回调结束。
load_scene不立即帧末只认最后一次请求。钩子剩余代码仍在旧场景；新场景 Start 下一帧运行。

这套“Scene 立即、系统通知稍后”的生成 / 销毁设计，解决了最自然的 spawn → set_pos 连写；派发使用实体 ID 快照且不跨钩子持有 Entity 索引，因此容器变化不会造成悬垂索引。场景切换无法同样立即，因为钩子正在借用 Scene，且固定物理步还可能把旧刚体回写。

切场景时清什么、留什么

清理

旧刚体 / 接触基线、Behavior 实例、Lua started 与每实体 state、动画实体时钟、粒子、UI 交互、音频 autoplay、实体存档变量、组件身份侧车。

保留

Lua 编译缓存、路径驻留表、脚本模块级全局、日志缓冲、全局存档变量、可复用资产缓存。模块全局跨场景与 Unity 不重载 domain 的语义一致。

09 · Prefab：本地身份与资产来源的双坐标

9.1 运行时实例化

RuntimePrefab::instantiate 先让旧 Prefab 值模型分配新的场景实体 ID、重映射内部 parent、贴 PrefabInstanceRef；随后按同一实体顺序把资产组件身份转为实例身份。v1 资产只能在无歧义时生成临时本地身份，重复旧挂载物会放弃该实体身份但不阻断原有运行行为。

9.2 Apply 分成两条路径

路径触发条件身份行为写盘行为
值 Apply资产实体、组件种类和关联键结构完全一致。资产 ID、来源 ID、高水位和顺序全部保留，只替换名称、父级、层、Transform 与组件值。Prefab 单文件条件写；当前场景原文也必须仍等于会话基准。
结构性 Apply实体 / 组件增删，或 Rust 注册名 / Lua 路径等关联结构变化。存活来源沿用资产 ID；新增资产实体 / 组件从资产侧独立分配；当前实例回填来源元数据。锁住资产与所有引用场景，使用可恢复多文件事务同步来源元数据。

其他实例不会被偷偷 Revert：存活来源保持，资产删除的实体转为本地实体，失效组件只解除来源关联；不注入资产新增项，也不覆盖本地字段。没有逐字段 override 记录时，全量覆盖会吃掉用户修改，因此“取资产值”只由显式 Revert 完成。

9.3 Revert

Revert 在内存副本重建子树，按 source_component_id 认回实例已有组件的本地 ID；资产新增组件从实例原高水位分配，资产删除项消失。实体 ID、根世界变换和父节点保留；空资产不动手。准备成功后才压 Undo，不写 Prefab 资产。[S5] [S8]

10 · MCP / Agent：从只读发现到条件局部写

工具适用格式输出 / 操作安全边界
component_catalog_read格式无关从 scene_schema() 筛出 11 种内建目录。不加载插件 DLL，不复制字段定义。
entity_components_readv1 值视图内建、Rust、Lua 的统一只读列表。明确 address_stability: legacy，槽位不可跨结构变化持有。
component_upgrade_previewv1 → v2 预览候选 ID、来源 ID、高水位。preview_only；不写盘，数字不可作为写目标。
entity_components_v2_readv2稳定 ID、来源 ID、强类型值、原文 revision。读取前后原文字节变化即拒绝。
component_v2_editv2patch / replace / add / remove / move。revision、严格字段、语义体检、完整字节条件写与文件锁。

Agent 写入协议

1 · Read
按实体 ID 读取组件，取得 revision 和目标 component_id。
2 · Intent
patch 只能指向已有 JSON Pointer；replace 不准改组件种类；Transform 只允许 patch。
3 · Decode
add / replace 的 data_ron 走与 v2 文件相同的严格解码；未知或重复字段拒绝。
4 · Validate
组件结构约束 + 投影后的整场景语义体检 + Prefab 来源验证。
5 · Commit
在 OS 锁内再次比较完整原文字节，然后原子替换；返回新 revision。
revision 不是事务本身：它让 Agent 快速发现陈旧请求；真正防覆盖的是 core 在锁内对完整原文字节的比较与条件替换。外部绕开 ProjectHandle 直接写文件的程序不受该锁协议约束。[S12]

11 · 架构红线与典型故障模式

红线如果破坏会怎样现有防线
运行时只有一份组件值脚本改 Scene、查询却读 SceneV2；两份值立刻漂移。RuntimeScene::from_v2 提取身份后投影到 Scene。
高水位永不回退删除 / Undo 后复用 ID，旧 Agent 引用或历史来源指向另一个组件。ComponentIdSequence::validate、Undo 取 max。
来源 ID 不冒充本地 ID实例本地新增项与资产分配冲突；Apply / Revert 对错组件。ComponentIdentity 两字段分存，来源校验按资产实际 ID。
不把 v1 槽位称作稳定 IDRust / Lua 重排后 Agent 改错实例。MCP 标注 legacy；迁移预览只读。
v2 未知字段必须拒绝旧程序读取后保存，悄悄删除新字段。serde_ignored + 严格 MapAccess。
GUID 转换只在项目边界热路径和数百消费点都要理解 guid://，值模型失去可直接打开的路径。visit_asset_references + ProjectHandle 统一编解码。
结构动作不绕过 Undo右键删除与 Add Component 行为不同，脏检查 / 身份历史断裂。全部 UI 入口收敛为 ComponentAction + working 副本。
同名多实例先改运行时状态键两个 Rust 同名项共享参数；两个同路径 Lua 共享 state。当前 v2 验证和 Inspector 都拒绝重复。
为什么身份侧车不是每帧从 Scene 重建？

Scene 没有 ComponentId；重建只能重新按种类 / 名称 / 路径猜身份，不但 O(n)，还会在删除、改名和 Prefab 来源上产生新 ID 或歧义。当前做法只在装载时构造一次，在 spawn / destroy 事件上增量维护。

为什么 Transform 不放进 entries？

Transform 是实体固有属性，所有现有系统都直接读取；v2 让它获得 transform_identity 即可满足稳定寻址，同时保持不可移除语义。MCP 把它作为组件返回，但结构操作不允许删除。

为什么 Parent 不作为组件？

父关系已经由 Entity.parent 和 Hierarchy 的保世界变换 / 防环逻辑维护。再在 Inspector 建一个 Parent 组件会形成第二个编辑入口和潜在真相源；当前决策明确由 Hierarchy 独占。

12 · 扩展组件系统时该改哪里

12.1 新增内建可保存组件

  1. 在 Entity 增加兼容字段：通常需要 #[serde(default, skip_serializing_if = ...)]，并明确 PartialEq / 脏检查语义。
  2. 扩展 BuiltinComponent 的 ALL、ADDABLE、code/name、存在判据、schema 映射和增删行为。
  3. 给 ComponentData 增加严格 v2 变体，补 from_v1 / apply_to_v1 / kind / legacy_key，资产路径还要进入统一遍历。
  4. 同步 scene_schema() 的类型目录与示例；这是 CLI / MCP 唯一内容源，穷举测试会钉住遗漏。
  5. 接 Inspector 展示 / 默认值 / Play 门禁，以及真正消费它的 runtime / render / physics 系统。
  6. 补 v1 往返、v2 严格编解码、ID 增删、编辑器 Undo / 保存、MCP 读写和 Prefab Apply / Revert 回归。

12.2 新增 Rust 组件

有生命周期

实现 Default + Lifecycle + Inspect，插件入口调用 registry.register::<T>("Name")。场景保存注册名与 Inspect 字段值。

只有数据

实现 Default + Inspect，调用 register_component::<T>；内部包装为空钩子 Behavior，不需要新增场景格式。

跨插件边界不要依赖 TypeId 匹配 trait object；完整契约已经把 Lifecycle 与 Inspect 合在 Behavior。注册名是持久关联键，改名会影响旧场景、Prefab 来源和 Agent 寻址。

12.3 新增 Lua 能力或挂载

挂载新的脚本资产只需经 Inspector / Entity 的脚本路径列表；新增宿主 API 则以 GameCtx 方法层为真相源，lua_api.rs 只写转发，并同步机器可读 script_api() 与 Docs/脚本API.md。不要在 Lua 绑定层复制业务逻辑。

12.4 真正开放同名多实例

这不是删一行去重：至少要把 Rust 参数从注册名键改成 ComponentId 键，把 BehaviorInstance 与 Lua state 按 ComponentId 隔离，让派发 / Inspector / Prefab / MCP / 存档都能区分实例，并定义同类型实例顺序与脚本 API。否则“多个实例”只有文件层，运行时仍串状态。

13 · 当前能力边界与下一层问题

边界现状意味着什么
同种多实例每内建种类一份、每 Rust 注册名一份、每 Lua 路径一份。v2 已有实例 ID，但运行时状态键尚未全面按 ID 隔离。
Prefab 高阶能力实体 / 组件结构 Apply 与 Revert 已完整；嵌套 Prefab、Variant、逐字段 override 可视化仍缺。其他实例只同步来源元数据，不自动传播值；显式 Revert 才取资产内容。
自定义 InspectorRust 标量 / 字符串 / 向量等走 Inspect 表；复杂内建面板手写。尚无 Unity Custom Editor / Property Drawer 级扩展；Quat / Color 等复杂 FieldKind 仍是遗留。
完整 ECS没有 archetype / sparse set 调度；Entity 仍是聚合对象。当前优化与 API 应围绕已测 World 热路径，不应假设数据导向批处理已存在。
运行时结构 API脚本生成 / 销毁 / Prefab 会维护侧车；直接 scene_mut() 的任意结构修改不自动补身份。宿主扩展应走正式入口或同步维护身份，查询会过滤幽灵身份但不会凭空生成新 ID。
Light仍是 Scene.lights，不在组件目录。“全部场景能力都已实体组件化”并不成立。

这些是能力边界，不等于当前架构失败。现有设计刻意优先保持旧值模型、运行热路径和文本资产稳定，同时把跨保存寻址、Prefab 结构事务和 Agent 写入补齐。仓库当前优先级真相仍是 Docs/差距分析.md；组件方向的主要后续差距是嵌套 Prefab、Variant 和逐字段 override。[S14]
