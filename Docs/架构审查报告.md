## 零、本次实际修复的缺陷（先给结论）

| # | 级别 | 位置 | 缺陷 | 后果 | 回归测试 |
|---|------|------|------|------|----------|
| 1 | **P1** | `xgame-core/src/scene.rs` `impl PartialEq for Entity` | 新增的 `layer`、`morph_weights` 两个落盘字段没进相等比较 | 只改层/形变权重时 `scene_dirty()` 仍为 `false` → 标题栏不显示未保存、关窗不提示、自动保存不触发**静默丢改动** | `persisted_layer_participates_in_equality`<br>`persisted_morph_weights_participate_in_equality` |
| 2 | **P1** | `xgame-script/src/ctx.rs` → `lua_host.rs` → `xgame-runtime/src/world.rs` | Lua `on_destroy` 没有任何调用点；`states` / `started` 永不清除 | 脚本的销毁回调**从不执行**（资源/音效/订阅泄漏）；每次 spawn-destroy 泄漏一条状态表 + 一个已启动标记，**无界增长** | `destroying_an_entity_runs_lua_on_destroy_and_releases_its_state` |
| 3 | **P1** | `xgame-render/src/scene_pipeline.rs` + `morph.rs` + `gltf_loader.rs` | morph 状态挂在**共享图元**上，所有同路径实体写同一份顶点缓冲 | 同一模型的两个实体设不同表情权重 → **最后写入者获胜**，两个实体显示同一个表情；合批还会把它们混成一批 | `independent_instances_keep_their_own_weights_and_vertices` |

三条都在旧实现上分别跑过并确认失败（前两条是断言失败，第三条是旧 API 下无法表达"两个实例各自的状态"），修复后转绿。

### 修复要点

**1) `Entity::eq`**
改成 **穷尽解构**（exhaustive destructuring）：字段列表必须完整写出，否则编译失败。这样以后再加落盘字段，编译器会强制作者决定"它参不参与脏检查"，而不是悄悄漏掉。`components` 显式 `: _` 排除（`#[serde(skip)]` 的运行时数据，且 `Box<dyn Any>` 无法比较）。

**2) Lua 销毁生命周期**
根因不是忘了调函数，而是**命令里没有足够信息**：`GameCtx::destroy` 在脚本里立即从场景移除子树，只往队列塞 `EntityId`；等运行时代理这条命令时，实体已经不在场景里，查不回它的脚本列表。

修法：
```rust
// xgame-script/src/context.rs
pub struct RemovedEntity { pub id: EntityId, pub scripts: Vec<String> }
ScriptCommand::EntitiesRemoved { entities: Vec<RemovedEntity> }
```
```rust
// xgame-runtime/src/world.rs —— destroy_command
for removed in report.removed {
    self.destroy_behaviors(removed.id, delta, time);      // Rust 行为轨（原有）
    scripts.dispatch_destroy(&mut frame, removed.id, &removed.scripts);  // Lua 轨（新增）
    if let Some(body) = self.body_of_entity.remove(&removed.id) { self.physics.remove_body(body); }
    self.character_contacts.remove(&removed.id);
}
```
`dispatch_destroy` 先跑 `on_destroy`，再 `forget_entity` 清 `started` 与 `states`。语义上刻意为"销毁前状态仍可读"（与 Unity `OnDestroy` 可读自身字段一致），测试用 `state_get_or(ctx,"token",...)` 断言了这一点。

**3) 逐实体形变隔离**
把"缓存状态"从 `MorphTargets`（共享，`Mutex<MorphState>`）下移到 per-instance 的 `MorphBuffer`；`ScenePipeline` 按 `(EntityId, *const GltfPrimitive)` 持有 `HashMap<key, MorphBuffer>`，每帧 `morph_buffers_used` 记录使用者，收集结束后 `retain` 回收。

同时解决合批正确性：批次键加 `prim.morph.is_some().then_some(entity.id)` —— 带形变的图元按实体拆批，**静态网格的实例化合批路径完全不变**（零性能回归）。主 pass、半透明 pass、阴影 pass 三处 `set_vertex_buffer` 统一走 `batch_vertex_buffer()`，静态返回共享缓冲，形变返回独占缓冲（wgpu 句柄克隆只加引用计数，不复制显存）。

## 一、架构与模块边界

**现状判断**：分层干净、依赖单向，无循环依赖（Rust 本身禁止 crate 循环）；`xgame-runtime` 作为唯一帧语义宿主，让编辑器 Play / 独立游戏 / 无头运行共享同一条更新路径，这是自研引擎最容易做错的地方，这里做对了。

**问题**

- **P2 — `scene_pipeline.rs` 是事实上的上帝模块**（约 2900 行）。收集、批次分配、阴影、主 pass、半透明、morph、蒙皮槽位全在一个 `impl` 里。它没有"泄漏抽象"，但**任何渲染改动都要动这个文件**，多人协作会持续冲突。
- **P2 — 渲染层与窗口层耦合**：`RenderContext` 持有 surface，`Surface<'static>` 靠 transmute 取得，平台对象生命周期与渲染对象缠在一起（详见维度七）。
- **P2 — `xgame-editor` 单 crate 承载了 gizmo / panels / plugin_build / autosave / hot_reload / state**，当前规模尚可，但 `state.rs` 与 `panels/*` 已互相依赖成网，建议后续按"编辑操作 / 视图 / 服务"三分。

**根因**：这不是设计失误，是增量演进的正常结果 —— 每个 pass 是分次加进来的，拆模块的收益一直没超过当时的改动成本。现在规模到了该拆的临界点。

**建议与验证**
- 按 pass 拆分 `scene_pipeline`：`collect.rs`（收集 + 剔除 + 批次分配）、`opaque.rs`、`blended.rs`、`shadow.rs`，共享 `ScenePipeline` 的字段。**收益**：单文件降到 ~600 行，编译器并行度提高；**风险**：字段私有性要重新设计，一次大改动。建议作为独立任务，不与功能改动混提。
- 验证方式：拆分前后对比 `cargo build -p xgame-render` 耗时与 `cargo test -p xgame-render`，行为一致性靠现有 181 条渲染测试 + headless 截图冒烟兜住。

## 二、内存管理

**现状判断**：无自定义分配器（合理 —— Rust 所有权已覆盖绝大部分场景），热路径复用缓冲做得到位；但**句柄系统缺世代位**，这是当前多条生命周期问题的共同根因。

**问题**

- **P1（已修复）** `Entity::eq` 漏字段 —— 见第零节。它表面是"比较函数写得糙"，实际暴露的是**"落盘字段清单"没有单一真相来源**：字段加在 `struct` 上、序列化也跟着走，唯独相等比较靠手写维护。
- **P2 — `EntityId` 无 generation** (`xgame-core/src/id.rs`)：原子递增、永不复用。好处是不会 ABA；代价是"已销毁 ID"与"从未存在 ID"不可区分，所有按 ID 的旁挂映射（`body_of_entity`、Lua `states`、`character_contacts`、`morph_buffers`）都只能靠**每处都记得删**来维持有界。这次的 Lua `states` 泄漏就是这条结构缺陷的第一次兑现。
- **P2 — `ComponentMap` 的手工 `unsafe impl Send/Sync` 是冗余的**（`xgame-core/src/component.rs`）。内部是 `HashMap<TypeId, Box<dyn Any + Send + Sync>>`，本来就自动满足 `Send + Sync`。
  > 说明：我最初把它判为 P0，读完字段定义后**主动收回** —— 它不是内存安全问题，只是多余的 unsafe，会误导后来者以为这里"有需要手工担保的东西"。
- **P2 — `Entity` 结构体偏大**（20 个字段，多个 `Option<Box<...>>`）。层级遍历/剔除是按 `Vec<Entity>` 线性扫，cache 压力随实体数上升。当前样例 24 实体，**不构成瓶颈，不建议现在动**。

**建议与验证**
- 删掉 `ComponentMap` 的两个 `unsafe impl`，让编译器推导。若编译失败，说明内部类型确实不满足 —— 那才是真问题，值得单独立项。**收益**：减少一处 unsafe 审计面；**风险**：几乎为零。
- 给 `EntityId` 加 8 位 generation（`u32 index | u32 gen`），`World` 维护 `alive: Vec<bool>`；跨 slot 访问先校验 generation，不匹配直接 `return`。**收益**：所有旁挂映射的"忘删"从"无界泄漏"降级为"惰性残留 + 可断言检测"；**风险**：ID 是序列化内容（`scene.ron` 里存的是裸 `u64`），要么保持 `u64` 序列化兼容、要么加迁移。**建议先做不改变序列化格式的内部版本**（gen 只存在于运行时表）。
- 验证：加一个 `spawn/destroy 十万次后 states.len() == 0` 的压力测试（现在的 Lua 测试是单次，能挡住"完全没删"，挡不住"漏删某条路径"）；内存侧用 `heaptrack`/Windows 的 `MTM` 观察稳态 RSS 是否随帧数线性增长。

## 三、渲染管线

**现状判断**：单线程录制、按图元实例化合批、半透明单独按距离排序；HDR + Bloom + IBL + TAA + FXAA + 阴影齐全。批次结构是对的，但**批次键的稳定性靠隐式不变量**。

**问题**

- **P1（已修复）** morph 共享缓冲 last-writer-wins —— 见第零节。
- **P2 — 批次键用裸指针**：`prim as *const GltfPrimitive as usize`（`scene_pipeline.rs` 内 `batch_index` / `shadow_batch_index` / `morph_buffers` 的键）。
  当前**是安全的**，因为：① 三个索引每帧开头 `clear()`；② `model_cache` 在收集与录制期间只 `.get()`，从不插入（我核对过全部 6 处引用），所以整帧内地址稳定。
  但这是一条**没有写下来的不变量**：谁把"模型加载"挪进收集循环，`HashMap` realloc 会让旧地址失效，最坏情况是新图元落到一个被回收的旧地址上 → **两个不同图元被合并进同一批次，用错材质**。
- **P2 — `MAX_RENDER_DRAWS` 超限静默丢弃**：调试期表现为"某些物体莫名不画"，很难归因。建议超限时打一次限流日志，并把"本帧丢弃数"接到 profiler 面板。
- **P2 — 无多帧飞行（frame-in-flight）**：每帧录制完 `submit` 一次，没有 GPU 资源环形缓冲。当前正确（wgpu 会保证队列顺序），但**要上异步上传、多线程录制或 GPU 侧回读，必须先建 per-frame 资源池**，否则就会出现"写到正在被 GPU 读的 buffer"。
- **说明 — CPU morph 是既定取舍**（`ROADMAP.md` 记录），不是新发现。按实体拆批后代价是 `O(形变实体数)` 份顶点缓冲 + 每帧 `O(顶点数 × 实体数)` 上传。

**建议与验证**
- 把批次键从裸指针换成稳定标识：`(模型路径驻留 id, prim_index)`。**收益**：消除地址依赖，允许未来在收集阶段懒加载模型；**风险**：需要给 `GltfMesh` 加一个路径 id（可在 `model_cache` 插入时分配）。
- morph 上传量埋点：在 `apply_source` 返回 `true` 时累加 `vertex_count * stride`，暴露到 profiler。**判断阈值**：若单帧上传 > 2 MB 或占帧时间 > 1 ms，再考虑把形变搬到 compute shader（每实例一个 storage buffer + dispatch）。
- 验证：`cargo test -p xgame-render`（181 条）+ 现有 `tests/instancing_cost.rs`、`tests/culling_cost.rs` 成本测试；GPU 侧用 RenderDoc 抓一帧，确认"同模型两个不同权重的实体"顶点位置确实不同、且落在两个不同 draw call。

## 四、多线程与并发

**现状判断**：主线程单线程更新；插件编译走后台线程 + `mpsc`；物理内部少量 `Mutex`。**没有任务系统/Job 依赖图** —— 这是 `Docs/差距分析.md` 已记录的延期项，不算本次新发现。

**问题**

- **P2 — `MorphTargets` 原来的 `Mutex<MorphState>` 是"用锁表达共享可变"**。单线程渲染里零竞争，锁本身不是性能问题，但它**掩盖了语义错误**：把"每个实体各有形变状态"错写成"每个图元一份状态"。已改为按实例持有，锁一并删掉。
  这条值得记下来：**锁的存在会让设计错误显得合理**。
- **P2 — `xgame-script/src/context.rs` 的 `ErasedMut<T>` + 常驻上下文槽**是全仓库最高风险的 unsafe 边界：把 `&mut T` 擦除类型存进一个跨调用存活的槽，靠"每次只借一个、且在同一帧内不重叠"来保证唯一性。我通读了 `ScriptCtx` 的构造与释放路径，**没有构造出可复现的 UB**，因此**不列为 P0**，但它没有任何编译期或运行期保护。
- **P2 — 无锁结构**：仓库里没有自研无锁队列，全部用 `mpsc`/`Mutex`。对于当前单线程模型这是正确选择，不建议为了"有并发"而引入。

**建议与验证**
- 给 `ErasedMut` 加一层 debug 期哨兵：在槽里存一个 `Cell<Option<TypeId>>`，借用时断言"当前为空 / 类型匹配"，释放时断言"确实是我"。**收益**：把 UB 变成 `debug_assert` 失败，能在开发期抓住重入；**风险**：`Cell` 在 `Sync` 约束上要小心（用 `AtomicU64` 存 type id hash 更稳）。
- 把 `Miri` 纳入 CI，只跑纯逻辑 crate：`cargo +nightly miri test -p xgame-core -p xgame-script -p xgame-math`。wgpu/winit 跑不了 Miri，但 `ErasedMut` 所在的 `xgame-script` 可以。
- 若要真正上多线程更新，第一步不是加线程池，而是**先把 `World::update` 拆成"只读阶段 / 写阶段"**，现在它边读场景边写物理体，天然不可并行。

## 五、资源管线

**现状判断**：按路径缓存、同步加载、无引用计数、无流式；热重载可用。规模小的时候这套能跑，但**卸载语义完全缺失**。

**问题**

- **P2 — 模型缓存只增不减**：`HashMap<String, GltfMesh>` 随场景切换持续增长。切换 20 个场景后老模型仍驻显存。
  建议照抄刚给 `morph_buffers` 做的模式：每帧记"使用者集合"，连续 N 帧未使用则 `remove`。**注意**：`GltfMesh` 可能被同一帧内多个实体共享，淘汰判定必须基于"本帧无人引用"，不能用引用计数外的启发式。
- **P2 — 音频同步解码**（`xgame-audio/src/lib.rs`）：长音频会阻塞加载线程。流式是已知延期项。
- **P2 — 无资源依赖图**：`xgame-core/src/check.rs` 已经能校验场景引用的资产是否存在（输出 `scenes=1 entities=24 ... material_refs=7 assets=15`），这其实就是依赖图的雏形，但没有被持久化/查询。建议把它升级为可查询结构，支撑"删除资产前的影响面提示"。
- **说明 — 形变图元现在按实体独占顶点缓冲**，这改变了显存占用的量级规律：静态网格 = O(模型数)，形变网格 = O(形变实体数 × 顶点数)。这是正确性换来的必要代价，但**需要在文档里写清**，否则以后有人看到显存涨了会误判成泄漏。

**建议与验证**
- 验证卸载：加一条测试"加载 A → 渲染 → 切到 B → 连续 N 帧后 `model_cache` 不含 A"。显存侧用 `wgpu` 的 `on_uncaptured_error` + 驱动工具（Windows 用任务管理器的专用 GPU 内存）观察。
- 依赖图：从 `check.rs` 的扫描结果直接产出 `asset -> Vec<引用者>` 的 JSON，接到 MCP 工具里（`xgame-mcp` 已有工具注册体系）。

## 六、脚本/反射绑定

**现状判断**：mlua + Lua 5.4，独立环境 + 指令预算 + 编译缓存 + 按 `(EntityId, path_id)` 存状态，工程质量高于多数自研绑定；但**生命周期接线只有 Rust 轨完整，Lua 轨此前是断的**。

**问题**

- **P1（已修复）** Lua `on_destroy` 从不派发 + 状态无界增长 —— 见第零节。
  值得强调：仓库里原本就有 `destroying_an_entity_runs_on_destroy` 测试，但它**只覆盖 Rust `Lifecycle` 组件轨**，所以一直绿着。**双轨架构的测试必须两轨都覆盖**，否则一条轨断了没人知道。
- **P2 — 脚本错误无熔断**：错误进日志不 panic（正确），但没有"每脚本错误计数"。一个每帧报错的脚本会以 60 条/秒刷爆控制台，把真正有用的日志挤掉。建议每脚本累计错误数，超阈值后禁用并记一条汇总。
- **P2 — 热重载后的状态语义未确认**：`states` 按 `(entity, path_id)` 保存，脚本重编译后 `path_id` 不变，因此**旧状态表会跨版本保留**。这对"改配置"是好事，对"改了状态结构"可能是隐患。**需查看 `lua_host.rs` 的热重载/`ensure_loaded_id` 路径确认是否会清表** —— 我尚未验证到确定结论，不臆断。
- **P2 — 跨 crate 命令协议易碎**：`ScriptCommand` 是 `xgame-script` → `xgame-runtime` 的契约，这次给 `EntitiesRemoved` 加字段就波及了 `world.rs`，且**旧代码会因为 `Vec<EntityId>` 变成 `Vec<RemovedEntity>` 直接编译失败**（这是好事，没有被静默忽略）。建议给这类命令加 `#[non_exhaustive]` 或统一用结构体变体，降低未来改动面。

**建议与验证**
- 熔断：`struct ScriptHealth { errors: u32, disabled: bool }`，`run_hook` 出错时 `errors += 1`，超过 100 置 `disabled` 并在日志里写一条"脚本 X 因连续错误被禁用（共 N 次）"。验证：写一个每帧 `error("boom")` 的脚本，跑 200 帧后断言日志条数远小于 200 且包含禁用提示。
- 热重载语义：先补一条测试锁死**当前实际行为**（重载后 `state_get` 是否还能读到旧值），再决定是否改。**先测量，再决策**。

## 七、平台抽象

**现状判断**：winit 0.30 + wgpu 23；输入层与 winit 彻底解耦（`xgame-input` 用自己的 key/action 枚举，上层不 import winit 类型）；项目路径统一按项目根解析，不依赖 cwd。抽象是干净的，**但有一处依赖 drop 顺序的 unsafe**。

**问题**

- **P2（潜在 P0，取决于平台）— `Surface<'static>` 的 transmute**（`xgame-render/src/lib.rs`、`xgame-game/src/main.rs`）：把带生命周期的 surface 声明成 `'static`，实际依赖"window 比 surface 活得久"。Windows 上目前正确，但这是**内存安全的未定义行为边界**：字段顺序、`Drop` 顺序、或未来把 `RenderContext` 移进 `Arc` 都可能破坏它。
  建议：把 `Arc<Window>` 与 `Surface<'static>` 包进同一个 struct，用 `Arc` 克隆让 surface 自己持有窗口的强引用（wgpu 23 支持 `Surface<'static>` 由 `Arc<Window>` 创建），这样**顺序不再重要，transmute 也可以删掉**。
- **P2 — CI 只跑 Windows**，没有任何非 Windows 的编译检查。代码里存在 `cfg(target_os)` 分支但没被验证过。跨平台不是"写了就能跑"。
  最低成本补法：加一个 `cargo check --target x86_64-unknown-linux-gnu --workspace`（只要编译，不跑测试、不需要 GPU）。**收益**：能挡住 `cfg` 漏写、`std::os::windows` 泄漏到通用代码；**风险**：需要装 Linux target，CI 时间 +2~3 分钟。
- **说明 — 当前只声明 Windows 实测**，这是文档里的明确边界，不算隐瞒。但"未验证"和"无法验证"是两件事，编译检查属于后者可以立刻消除的部分。

**建议与验证**
- 按上述改造 surface 生命周期后，用 `cargo miri` 无法覆盖（wgpu 不支持），改用**地址检查器**：Windows 上开 `Application Verifier`，Linux 上 `ASAN_OPTIONS=detect_leaks=1` 跑 headless 冒烟，确认关闭窗口时无 use-after-free。
- 验收标准：`--headless` 跑 30 帧 + 正常退出，进程退出码 0，无驱动层报错。

## 八、数学与容器库

**现状判断**：数学全用 `glam`（成熟、SIMD 友好），容器全用 `std`，无自研容器、无自研分配器。**这个维度没有需要立刻修的问题** —— 这是一件好事，说明没有为了"自研"而自研。

**问题**

- **P2 — 投影约定缺少锁定测试**：`xgame-math/src/projection.rs` 用 glam 的透视矩阵，必须与 wgpu 的 NDC（z ∈ [0,1]，非 OpenGL 的 [-1,1]）一致。画面目前正常，但没有测试锁死这个约定。换投影实现或升级 glam 大版本时，**错误会表现为"远处物体被裁掉"，很容易被误判成剔除 bug**。
  建议加：`project(near) → z ≈ 0`、`project(far) → z ≈ 1`、`project(中心) → x,y ≈ 0`。
- **P2 — 线性父子查找的复杂度**：`Scene` 用 `Vec<Entity>` + 按 `parent` 字段线性扫描解算层级，`O(n²)`。24 实体无感，1 万实体会明显。
  **明确不建议现在改**：加 children 索引会牵动场景序列化格式与 `Entity::eq`（刚修过的地方），属于"高耦合低成本收益"的典型。
- **说明 — 层级矩阵记忆化是对的**：按 (entity, 是否脏) 缓存世界矩阵，避免每帧重算整棵树。这是渲染侧正确的做法。

**建议与验证**
- 投影测试：三条断言即可，纯数学、无 GPU 依赖，Miri 也能跑。
- 若将来要扩到万级实体：先用 `tests/culling_cost.rs` 的现有基准量出当前曲线，确认确实是指数级劣化，再动结构。**不要凭直觉优化**。

## 九、构建与工具链

**现状判断**：workspace 分 crate 合理（改 core 不必重编 render）；CI = Windows stable + `check --locked` + `clippy -D warnings` + 全量测试 + 4 项二进制冒烟。这套纪律比多数自研引擎严。**缺口在"平台矩阵"和"性能闸门"两块**。

**问题**

- **P1 — 单一平台 CI**（`.github/workflows/ci.yml`）：无 Linux/macOS 编译检查、无 Miri/ASan/TSan、无专门的 unsafe 统计。仓库里存在 `unsafe`（`ErasedMut`、surface transmute、`ComponentMap` 的冗余 impl），但**没有任何自动化手段限制 unsafe 增长**。
- **P2 — 无性能回归闸门**：仓库已有 6 个成本测试（`culling_cost` / `instancing_cost` / `postfx_cost` / `ui_cost` / `update_throughput` / `behavior_dispatch_throughput`），全部带 `#[ignore = "不进 CI 门禁"]`。
  这个决定本身是**有理由的**（GPU 基准在共享 runner 上波动大，做成硬门禁会天天红），不算疏漏。但缺口是真实的：**没有任何环节在跟踪这些数字**，于是性能优化可以互相抵消而无人发现 —— 这正是"每个 PR 都快一点，合起来慢一倍"的成因。
- **P2 — 无 GPU 时间戳查询**：`wgpu` 的 `timestamp_query` 没接，profiler 面板只能看 CPU 侧耗时。要做真正的渲染 profiling，这是必需项。
- **P2 — `dev` profile 已开依赖优化**（`Cargo.toml`），这是正确的取舍（调试期不至于卡成幻灯片），但 `opt-level` 提高会让 debug 单步跳变，建议在文档里写清"调试断点可能不按行停"。

**建议与验证**
- CI 补三件事（按性价比排序）：
  ```yaml
  - name: Linux compile check
    run: cargo check --locked --workspace --target x86_64-unknown-linux-gnu
  - name: Miri (pure-logic crates)
    run: cargo +nightly miri test --locked -p xgame-core -p xgame-math -p xgame-script
  - name: Perf gate
    run: cargo test --release --locked -p xgame-render --test instancing_cost -- --ignored --nocapture
  ```
  性能闸门建议**先只记录不失败**（把数值写进 job summary），积累 20 次数据后再定阈值，否则会因为 CI 机器波动天天红。
- 验证改进本身：`cargo build --timings` 对比拆分前后的编译关键路径；`hyperfine` 对比 headless 30 帧的墙钟时间。

## 十、可测试性与可维护性

**现状判断**：**862 条测试、0 失败**，覆盖 scene / script / render / physics / ui；文档体系完整（`ROADMAP` / 差距分析 / 决策记录 / `PLAN` / 脚本 API / MCP）。`Docs/决策记录.md` 记录"不能推翻的结论"，这是自研引擎里极罕见的正确做法 —— 它防止了架构被反复推翻。

**问题**

- **P2 — 缺端到端场景测试**：现有测试以单元为主，二进制冒烟只验证"能启动、能跑 30 帧、能导出"。**本次 `Entity::eq` 缺陷就是一个端到端测试本该抓住的问题**：如果有"改 layer → 保存 → 重载 → 比对"的用例，第一次就会红。
  建议把 headless 冒烟升级为**快照式**：跑 N 帧 → dump 场景状态 → 与已提交的快照比对。它能同时守住序列化、脏检查、脚本改场景三条链。
- **P2 — 双轨测试覆盖不均**：Lua 轨的生命周期此前完全没有测试，只有 Rust 轨有。建议给"每个生命周期钩子"建一张对照表，两轨各一条测试，缺一条就红。
- **P2 — 大文件可维护性**：`scene_pipeline.rs` ~2900 行、`script_api.rs` 单次改动 +1270 行。注释质量高（每处决策都写了"为什么"），但**注释不能替代结构**。
- **P2 — 接口稳定性**：`xgame-script` 的 `ScriptCommand`、`xgame-core` 的 `Entity` 都是跨 crate 契约，字段变更会波及多个 crate。这次 `Entity` 加 `morph_weights` 就漏了相等比较 —— 说明**"加字段"这个动作缺少强制检查点**。已通过穷尽解构补上，同类结构（`RemovedEntity`、`DrawUniform`）建议同样处理。

**建议与验证**
- 端到端快照测试落地路径：`--headless --frames N --dump-scene > snapshot.ron`，CI 里 diff。**收益**：一个用例守住多条链；**风险**：快照易碎（无害改动也会红），所以只 dump 语义字段，不 dump 浮点全精度（用 1e-5 容差）。
- 双轨对照表：写成一个测试宏，`for hook in [start, update, fixed_update, collision, destroy]`，两轨各断言一次调用次数。
