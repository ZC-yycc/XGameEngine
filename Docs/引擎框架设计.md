## 0. 一页结论

**一句话：** 把引擎从"一堆会改世界的代码"变成**一个可查询、可计划、可回放的
世界状态机**；性能来自数据布局与确定性并行，AI 可操作性来自**唯一写路径**与
**自描述注册表**。

**五个结构性决定 H1–H5**（其余设计都是它们的推论）：

| # | 决定 | 解决什么 |
|---|---|---|
| H1 | **一切修改 = 命令**：编辑器、脚本、MCP、测试共用一条 `Command` 管线，事务化、可逆、有日志 | 当前三套写路径（直改 `Scene` / 整文件 RON / `GameCtx`）语义不一致 |
| H2 | **一切描述 = 注册表**：类型、字段、默认值、范围、单位、文档、序列化、Inspector、工具 schema 全部由注册表生成 | 加一个内建组件要改约 20 处；文档与代码漂移 |
| H3 | **一切查询 = 修订 + 快照**：世界有单调 revision，查询可过滤 / 分页 / 增量，结果列式可选 | AI 只能拿整份 RON 或"跑完 dump" |
| H4 | **一切并行 = 声明访问 + 确定性合并**：系统声明读写集，调度器证明无冲突才并行，合并顺序固定 | 单线程 `&mut Scene` 把所有系统锁在一条串行链上 |
| H5 | **一切验证 = 轨迹 + 结构化诊断**：每次仿真产出 state hash / 事件 / 输入轨迹，诊断有稳定 code 与 subject | AI 只能"重跑整个项目 + 读文本日志"猜结果 |

**四个数字目标**（初版预算，M0 校准，条件见 §13）：

| 指标 | 目标 | 现状基线 |
|---|---|---|
| 10k 实体 / 1k 动态体 / 60 Hz 的 CPU 帧 | ≤ 6 ms（仿真 ≤ 3 ms，提交 ≤ 1.5 ms） | 1000 密集接触体单物理就 13.75 ms |
| 100k 实例的渲染 CPU 提交 | ≤ 1.5 ms，draw calls ≤ 500 | 未合批 2000 实体提交 3.3 ms、2000 批 |
| 10k 个用 batch 写法的 Lua 实体 | ≤ 500 µs/帧 | 1000 个 no-op 实体 562 µs/帧（逐实体写法） |
| 10k 实体场景冷加载 | ≤ 100 ms | 8000 实体存档解析 17 ms（场景另计） |

**三个闭环**（验收单位，不是功能清单）：

1. **编辑闭环**：`query → plan → apply → check → capture → revert`，全链路机器可读。
2. **仿真闭环**：`run → trace → replay → 首分歧帧 → 对比`，同二进制逐位可复现。
3. **性能闭环**：`预算 → 基准 → 门禁 → 回归定位`，每个 PR 都跑得起。

**明确不做**（v1 范围外，理由见 §16.2）：C# / 多语言中立层、可视化脚本、2D / Tilemap、
地形 / 水体、网络同步、跨平台逐位确定性、引擎内代码编辑器、带状态迁移的原生插件热重载。

**需要拍板的 8 件事**见 §16.1。默认推荐已写在每条后面；没有拍板前不进入 M1。

## 1. 为什么需要新框架

### 1.1 现有引擎已经证明有效的纪律（必须继承）

这不是"推倒重来"。XGameEngine 有七条被实测和事故证明有效的纪律，目标框架一条都不能丢：

| 纪律 | 现状证据 | 目标框架的对应机制 |
|---|---|---|
| **同输入逐位确定性** | 同二进制两跑 `f32::to_bits` 相等，进 CI（决策记录 §五十六） | 固定步 + 确定性调度 + 确定性数学层 + 每帧 state hash |
| **稳态零分配是门禁** | 预热后 60 帧断言 0 次分配，并证明"真的跑了"（决策记录 §五十四） | 每帧 arena + 容量复用 + CI alloc gate（覆盖所有热路径） |
| **单一帧循环** | 编辑器 Play / 独立游戏 / 无头共用 `World::update`（决策记录 §六） | 一个 `Simulation::step`，宿主只是适配器 |
| **schema / API 单一内容源** | `scene_schema()` 与 `script_api()` 是唯一源，确定性导出（决策记录 §三十二、§三十三） | 注册表即 schema，工具 / 文档 / Inspector 全部生成 |
| **保守剔除 + A/B 像素等价** | 每条剔除都有"开/关逐位一致"测试（决策记录 §十一、§八十七） | 渲染每个优化都带 A/B 像素合同 |
| **路径 / 写盘 / 身份纪律** | 一条 `normalize_project_relative`、一份 `fsx`、GUID 只在读写边界转换（决策记录 §十四、§四十九、§六十五） | 同一套规则搬进 `xgc-base`，读写两个边界继续拒 |
| **无头 + MCP 的 Agent-Native 方向** | 15 个 MCP 工具、确定性无头、可复现截图（MCP.md） | 升级为会话式 Agent 协议，MCP 只是适配层 |

**判断：** 这些纪律是资产；真正到顶的是**数据布局、所有权模型、工具面**，不是纪律本身。

### 1.2 五个结构性上限（有证据）

| 上限 | 证据 | 后果 |
|---|---|---|
| **线性 `Vec<Entity>` + O(n) 查找** | `find_entity` / `index_of` 全仓 67 处调用；`world_matrix` 每层再 `index_of` ⇒ 单实体 O(n·depth)；8000 实体读档从 50 ms 降到 1.7 ms 只是"建了一次索引" | 2 万实体时 O(n·depth) 路径先崩；AI 最常写的"读别人位置"天然 O(n²) |
| **每帧全表扫描 ≈17 次** | 1 个固定步下按调用点计：UI 1–4、start 2、固定步 4、update 2、sync_bodies 1、动画 3、粒子 2、音频 1；文档只数了 5 个系统入口（决策记录 §六十七） | 加一个系统 = 再扫一遍；2000 实体纯视觉 49.9 µs 已接近编排上限 |
| **物理单线程** | 1000 个密集接触体 13,753 µs/帧；rapier `parallel` 会打乱体间顺序，与逐位确定性正面冲突（决策记录 §六十七） | 千体密集接触到顶；物理也无法搬出主循环 |
| **Lua 逐实体钩子** | 1000 个 no-op 实体 562 µs/帧；每个钩子构造 `GameCtx`、重置 20 万指令预算、查状态表 | 线性外推万实体约 5.6 ms/帧；脚本越重越难并行 |
| **三套写路径 + 无事务** | 编辑器直接改 `Scene`（100 份整场景快照做撤销）；MCP 写整份 RON；脚本经 `GameCtx` 改场景 | 校验 / 撤销 / 冲突 / 审计各一套；AI 无法"先预览再提交" |

补充三个放大器：

- **加一个内建组件 ≈ 20 处**：`BuiltinComponent` 7 个 match、`Entity` 3 处、
  `ComponentData` 7 个 match、`RuntimeComponentKind`、schema 目录、资产引用遍历……
  AI 改漏一处，编译器不一定报错（按当前 `BuiltinComponent` / `ComponentData` 的
  match 分支计数）。
- **单体文件**：`world.rs` 250 KB、`scene_pipeline.rs` 282 KB、`schema.rs` 144 KB、
  `screenshot.rs` 230 KB。AI 改一个行为要读巨大上下文，人也一样。
- **渲染没有 render graph**：pass 顺序硬编码在 1233 行的 `render()` 里，帧图在
  编辑器 / 游戏 / 截图三个宿主各抄一遍；加一个 pass 要改三处（当前 `render()` 的
  pass 顺序与三个宿主的帧图副本）。

### 1.3 为什么不能靠增量修补

三条硬理由：

1. **数据模型是地基**：`Entity` 是 21 个落盘字段的 god struct，组件值、磁盘投影、
   身份侧车、schema 目录、编辑器面板都依赖它。把它改成注册表驱动的列式存储，
   等于重写所有子系统；在旧结构上叠一层只会得到"两套真相"。
2. **所有权模型挡住并行**：每个钩子把 `Scene` / `Physics` / `Audio` / 日志 / 命令
   全部以 `&mut` 捆进 `GameCtx`，擦成地址交给 Lua。任何多线程方案都要先拆这把锁；
   拆完之后的 API 与现在不是同一套。
3. **反兼容层规则不允许双轨**：本仓库的硬规则是"迁移 = 替换 + 拆除"
   （[架构收敛约定](架构收敛约定.md)）。在同一个 workspace 里让新旧两套运行时
   并存，正是这条规则禁止的形态。

**结论：** 新框架是**新地基**，不是旧代码的第七次重构。旧引擎冻结为参照实现
（tag + 文档），割接时整体替换；不做兼容层，不并行两套。

## 2. 设计原则

每条原则都带**判据**：做不到这句判据，就是没落实。

| # | 原则 | 判据 | 典型反例 |
|---|---|---|---|
| 原则 1 | **单一真相源** | 同一事实在仓库里只有一处可改；其余是生成物或引用 | schema 手写 3503 行、文档抄一份字段表 |
| 原则 2 | **数据与行为分离** | 组件是纯数据；系统是 `(View, Commands) → ()` 的纯函数式步骤 | 组件里塞 `Arc<Mutex<...>>`、钩子里直接改全局 |
| 原则 3 | **唯一写路径** | 任何结构性修改都能在 `CommandLog` 里找到；热路径的数值写入是同一份数据的快速通道 | 编辑器直改、MCP 整文件写、脚本三套语义 |
| 原则 4 | **稳定身份** | 跨文件引用只用持久 ID；名字 / 路径只是索引，歧义即拒绝 | 用名字寻址、用 Vec 下标做键 |
| 原则 5 | **确定性优先于极限并行** | 并行只在"合并顺序可证明"的切分上；浮点归约顺序固定 | `par_iter().sum()`、HashMap 迭代进仿真 |
| 原则 6 | **零分配稳态 + 显式预算** | 每个系统有 CPU / 内存 / 实体数预算；超预算在 CI 红 | 每帧 `collect()`、`format!`、`Vec::new()` |
| 原则 7 | **GPU 驱动优先** | CPU 只提交"工作描述"；剔除 / LOD / 批次在 GPU 或一次性预处理完成 | CPU 逐实体收集 + 逐批 `set_bind_group` |
| 原则 8 | **资源即数据** | 资产身份用 GUID、烘焙产物 content-addressed、导入是纯函数、加载可缓存 | 运行时双读、隐式补 `.meta`、GUID 进热路径 |
| 原则 9 | **可观测即接口** | 每个子系统有计数器 / 时间线 / 诊断码；AI 与人读同一份 | `FrameReport` 只有 4 个计数、基准全 `#[ignore]` |
| 原则 10 | **扩展靠注册，不靠改核心** | 新增组件 / 系统 / pass / 工具 = 注册 + 声明，不改 N 处 | 加组件改 20 处、加 pass 改 3 个宿主 |
| 原则 11 | **破坏性演进** | 数据格式版本化、一次性迁移；旧实现同 PR 删除 | `V2` 类型、`serde(alias)`、"暂时保留" |
| 原则 12 | **AI 是一等用户** | 每个能力都有机器可读契约、可预览、可回滚、可验证 | 只有 GUI 能做的操作、只有文本错误 |

**原则之间的优先级**：原则 5（确定性）> 原则 7（性能）> 原则 12（AI 易用）> 其余。
冲突时按这个顺序裁决；例如"并行能快 2 倍但会打乱顺序"——不做。

## 3. 总体架构

### 3.1 两张平面

```text
┌─────────────────────────────────────────────────────────────────────┐
│ 意图平面（Intent Plane）                                             │
│  Agent 协议 · 编辑器 · CLI · 测试 · 构建                              │
│  query / plan / apply / revert / sim / diag / capture / describe     │
└───────────────────────────┬─────────────────────────────────────────┘
                            │  Command（事务、可逆、带 revision）
                            │  Query（只读、分页、确定性顺序）
┌───────────────────────────▼─────────────────────────────────────────┐
│ 仿真平面（Simulation Plane）—— 单写者、固定步、确定性                  │
│  World(ECS) · Schedule · Physics · Animation · UI · Script · Audio    │
│  Particle · Navigation                                               │
└──────────┬───────────────────────────────────────┬───────────────────┘
           │ FrameSnapshot（不可变）                │ Snapshot / Trace
┌──────────▼──────────────┐            ┌───────────▼───────────────────┐
│ 渲染（GPU）              │            │ 资产 / IO（异步）              │
│  RenderGraph · Passes    │            │  import · cook · stream       │
└─────────────────────────┘            └───────────────────────────────┘
```

**关键点：意图平面没有"特权通道"。** 编辑器按钮、Lua 脚本（结构性修改）、MCP、
测试驱动、CI 迁移全部走同一套 `Command`；`Query` 也只有一套。这样"人做得到的事
AI 一定做得到"，反之亦然。当前引擎的三套写路径（编辑器直改 / MCP 整文件 /
`GameCtx`）正是要在新框架里消失的东西。

### 3.2 crate 分层

```text
xgc-base       ID / 句柄 / 时间 / 诊断码 / arena / 确定性数学
xgc-reflect    注册表 / schema IR / 动态值 / diff / patch
xgc-world      ECS 存储 / 查询 / 命令 / 事件 / 层级 / 快照
xgc-frame      提取 DTO（RenderFrame / PhysicsFrame / AudioFrame / UiFrame）
xgc-asset      GUID / .meta / 导入 / 烘焙 / 依赖图 / 流式
xgc-render     wgpu / RenderGraph / pass / 材质 / 着色器
xgc-physics    后端 trait + 首个后端（rapier）
xgc-anim       剪辑 / 状态机 / 采样 / 根运动
xgc-audio      kira / 总线 / 空间化 / 流式
xgc-ui         布局 / 输入 / 焦点 / 绘制列表
xgc-script     Lua VM / 批处理行为 / 能力 / 热重载
xgc-sim        调度 / 固定步 / 服务编排 / 快照 / 回放 / 提取
xgc-agent      协议 / 查询 / 计划 / 诊断 / 会话 / MCP 适配
xgc-editor     egui 客户端
xgc-player     独立游戏宿主
xgc-cli        `xgc` 二进制（check / run / build / agent / bench）
xgc-xtask      代码生成 + 架构门禁（dev-only）
```

**依赖方向（只许向下，`xtask dep-check` 强制）**：

| crate | 允许依赖 | 禁止依赖 | 理由 |
|---|---|---|---|
| `base` | `glam` 等基础库 | 任何 `xgc-*` | 不做 `xgame-math` 那种 28 行 re-export 壳；数学直接用 `glam` |
| `reflect` | `base` | `world` | 注册表不知道世界 |
| `world` | `base`、`reflect` | `render`、`physics`、`script`、`sim` | 核心数据结构不认识任何子系统 |
| `frame` | `base` | 其余 | 只是不可变 DTO，渲染 / 物理 / 音频的共同语言 |
| `asset` | `base`、`reflect` | `world`、`render` | 资产库不反向依赖场景 |
| `render` | `base`、`frame`、`asset` | **`world`、`sim`** | 渲染只读提取帧；可离线单测、可换线程 |
| `physics` | `base`、`frame` | **`world`、`sim`** | 物理只读刚体描述 + 写回结果 |
| `anim` / `audio` / `ui` | `base`、`asset`、`frame` | `world` | 同上 |
| `script` | `base`、`world`、`reflect`、`asset` | `render`、`editor` | 脚本只通过命令 / 查询改世界 |
| `sim` | `world`、`frame`、`asset`、`physics`、`anim`、`audio`、`ui`、`script` | `editor`、`agent`、`render` | 编排只产出提取 DTO，不反向依赖渲染 / 宿主 |
| `agent` | `sim`、`world`、`reflect`、`asset` | `editor`、`render` | 协议不依赖 UI |
| `editor` / `player` / `cli` | `sim`、`render`、`agent` 等 | — | 宿主在最上层 |

**为什么 `render` 不能依赖 `world`：** 当前 `ScenePipeline::render` 直接读 `Scene`，
于是渲染和编辑 / 物理 / 脚本共享同一把 `&mut`，只能在同一线程同一帧内跑；也没法
单独给渲染喂合成数据做像素测试。新框架用 `xgc-frame` 的不可变 DTO 切开：
`sim` 在帧末提取，`render` 只读 DTO。代价是一次提取拷贝（100k 实例约 6 MB/帧），
用脏区间增量更新摊掉（见[运行时 §6.2](引擎框架设计-运行时.md)）。

### 3.3 一帧的完整路径

```text
[OS 事件 / 手柄 / 网络]                        主线程
        │
        ▼
InputState（边沿 + 电平，固定结构）             主线程
        │
        ▼
CommandQueue（外部编辑 / 脚本结构性修改 / AI）   任意线程入队，sim 线程按序结算
        │
        ▼
Simulation::step(dt)                           sim 线程（单写者）
  ├─ PreSim     输入快照 / 命令结算 / 流式完成 / 时间推进
  ├─ FixedSim   固定步循环 ×N
  │    ├─ fixed 系统（玩法 / 角色 / 物理前置）
  │    ├─ 命令结算（fixed 屏障）
  │    ├─ physics.step(fixed_dt)
  │    ├─ 物理回写 / 碰撞事件
  │    └─ fixed 后处理（动画事件 / 触发器）
  ├─ Sim        update 系统（脚本 / 动画 / UI / 音频 / 粒子）
  ├─ PostSim    命令结算 / 层级传播 / 可见性 / 提取
  └─ Publish    FrameSnapshot { revision, RenderFrame, AudioFrame, UiFrame, stats }
        │
        ├──────────────▶ 渲染线程 / 主线程：RenderGraph → GPU
        │
        └──────────────▶ Agent / 编辑器：安全点查询（读 revision 对应的世界）
```

**安全点（safe point）** 是本文反复出现的概念：世界只在帧边界、阶段屏障、系统
切换点对外可见。查询不是"随时抢锁读"，而是排到安全点执行；结果是某一 revision 的
一致切片。代价是查询最多等一帧，收益是没有数据竞争、没有半更新状态。

### 3.4 线程模型

| 线程 | 职责 | 数量 | 备注 |
|---|---|---|---|
| 主线程 | 窗口 / 输入 / egui / `queue.submit` | 1 | wgpu surface 与 winit 事件循环在这 |
| 仿真协调 | 跑调度器、结算命令、发布快照 | 1 | 逻辑上单写者；不是"只用一个核" |
| 仿真 worker | 并行系统 / 查询 / 提取 | N−1（默认 = 物理核数 − 2） | 工作窃取；确定性分区 |
| IO | 资产导入 / 烘焙 / 流式读 | 2–4 | `std::thread` + 有界通道；不阻塞仿真 |
| Agent server | JSON-RPC / 查询 / 计划 | 1 | 读快照 + 命令入队；不直接改世界 |
| GPU | 队列时间线 | — | 异步计算 / 图形两条队列（能力允许时） |

**上屏与延迟**：编辑器默认 `AutoNoVsync`（输入→像素同帧，继承当前取舍）；播放器默认
`Fifo`，可配 `Mailbox` / `Immediate`；在飞帧数默认 1，不引入第二帧延迟。帧调度
目标是"输入采样在帧首、仿真与提交同帧、上屏不排队等两个 vsync"。

**编辑器为什么可以"内联仿真"**：编辑态没有"后台世界"，`Simulation` 直接在主线程
跑固定步，输入→像素零管线延迟（继承当前引擎的取舍，FLOW §4b）。Play 态切到
worker 模式，渲染用插值快照；编辑器的暂停 / 单步仍走同一 `Simulation`。

### 3.5 五个关键取舍

| 取舍 | 选择 | 代价 | 不这样做的后果 |
|---|---|---|---|
| 渲染与世界的耦合 | 用 `FrameSnapshot` 切开 | 一次提取拷贝 | 渲染无法离线测试、无法换线程、无法并行 |
| 谁写世界 | 仿真线程单写者 | 查询最多等一帧 | 到处加锁 / 原子 / 半更新状态 |
| 外部编辑怎么进 | 全部 `Command` | 命令有序列化 / 校验开销 | 三套写路径、无事务、无审计 |
| 系统内数值怎么写 | 直接 `Mut<T>`（热路径） | 绕过 journal | 每帧每实体一条命令，开销不可接受 |
| 旧引擎怎么办 | 新仓库 + 一次性割接 | 迁移成本 | 双轨并行，违反反兼容层规则 |

## 13. 性能目标与验收

### 13.1 基准场景（XG-Bench）

固定六个场景，随仓库提供资产与脚本；每个场景有"低 / 中 / 高三档"，CI 跑中档：

| # | 场景 | 内容 | 主要压什么 |
|---|---|---|---|
| S1 | Static City | 200k 实例 / 8 材质 / 1 方向光 + 8 点光 / 4 级 CSM / 1080p | 渲染提交、GPU 剔除、批次 |
| S2 | Physics Yard | 5k 动态盒 + 20k 静态 / 60 Hz | 物理求解、同步、睡眠 |
| S3 | Crowd | 500 个 200 骨骼角色 + 2k 动画实例 | 蒙皮、动画采样、骨骼上传 |
| S4 | Script City | 10k 个 batch 写法 Lua 实体 | 脚本分发、命令、状态 |
| S5 | Streaming | 2 GB 资产 / 60 s 相机遍历 | 异步 IO、内存预算、卡顿 |
| S6 | Editor | 50k 实体 / 层级 + Inspector + 撤销 | UI 虚拟化、查询、命令 |

每个场景同时产出：CPU 帧分布（p50 / p95 / p99）、GPU 各 pass 时间、draw calls、
分配次数 / 字节、峰值内存、加载时间、state hash。

### 13.2 预算

| 场景 | CPU 帧 | GPU 帧 | 内存 | 加载 |
|---|---|---|---|---|
| S1 | ≤ 6.7 ms（150 fps 上限） | ≤ 11 ms（1080p 中端） | ≤ 3 GB 显存 | ≤ 300 ms |
| S2 | ≤ 6.7 ms（物理 ≤ 4 ms） | ≤ 4 ms | ≤ 1 GB | ≤ 200 ms |
| S3 | ≤ 6.7 ms（动画 ≤ 2 ms） | ≤ 10 ms | ≤ 2 GB | ≤ 300 ms |
| S4 | ≤ 6.7 ms（脚本 ≤ 0.5 ms） | ≤ 4 ms | ≤ 1 GB | ≤ 200 ms |
| S5 | 卡顿 ≤ 4 ms（p99） | ≤ 11 ms | ≤ 2 GB | 流式无 OOM |
| S6 | UI 帧 ≤ 8 ms | ≤ 4 ms | ≤ 1 GB | ≤ 500 ms |

**说明**：中端 GPU 以 RTX 3060 / RX 6600 为参照；CPU 以 i5-12400 / Ryzen 5 5600
为参照。数字是初版预算，M0 用真机校准；校准后写进 `bench/budgets.json`，PR 只能
在预算内波动（超 5% 需说明并复测）。

### 13.3 微基准

| 基准 | 目标 | 说明 |
|---|---|---|
| `query_1m_reads` | ≤ 1 ms | 1M 次组件字段读，单线程 |
| `transform_100k` | ≤ 2 ms | 10 万实体层级传播（单线程） |
| `command_10k` | ≤ 5 ms | 1 万条 `SetField` 计划 + 应用 |
| `snapshot_10k` | ≤ 20 ms | 1 万实体快照（二进制） |
| `hash_100k` | ≤ 1 ms | 10 万实体增量哈希（无脏 chunk） |
| `schema_export` | ≤ 50 ms | 全量 schema JSON 导出 |
| `script_dispatch_10k` | ≤ 500 µs | 1 万实体批处理分发 |
| `physics_5k` | ≤ 4 ms | 5k 动态盒一步 |
| `render_submit_100k` | ≤ 1.5 ms | 10 万实例提交（不含 GPU） |
| `import_1gb` | ≤ 60 s | 1 GB 资产导入（4 线程） |

**微基准是设计约束，不是营销数字**：任何一条连续两个版本不达标，就要在路线图里
开一条"性能债"并排期，不能装作没看见。

### 13.4 测量方法

继承当前引擎已验证的纪律，并补三条：

1. **同机背靠背**：改动前后交替跑，至少 5 轮取中位；报告区间，不报单次最好值。
2. **断言"真的跑了"**：实体数 / 访问计数 / 哈希变化至少一项非零；否则基准无效。
3. **固定环境**：release、关闭 debug assertion、固定驱动 / 分辨率 / 电源模式；
   CI 机器单独标注，不与开发机数字混比。
4. **分离 CPU / GPU**：CPU 用 `Instant` + 采样；GPU 用 timestamp query；不用
   "帧时间"笼统代替。
5. **噪声判定**：差异 < 5% 视为噪声；5–10% 需复测；> 10% 才判回归。
6. **基准也进代码审查**：新增热路径必须带基准；基准代码与产品代码同 PR。

### 13.5 门禁

| 层级 | 频率 | 内容 |
|---|---|---|
| PR | 每次 | 微基准（快档）+ 单元 / 集成 / schema / 确定性 |
| Nightly | 每天 | XG-Bench 中档 + 内存 / 加载 + golden 图 |
| Release | 每个里程碑 | 三档全跑 + 真机截图 + 迁移项目验收 |

- 超过预算 5%：PR 红，附前后对比与解释；超过 10%：必须修复或走例外审批。
- 基准结果存 `bench/results/<commit>.json`，可视化趋势；不用"感觉快了"验收。
- 性能回归定位：按系统 / pass 的 `SystemStats` 切片，先定位再改，不猜。

## 14. 实施路线

> 估算前提：3–4 名熟悉 Rust / wgpu 的工程师，AI 辅助开发；不含美术与内容。
> 每个里程碑都有**出口判据**，不达标不进入下一个；允许砍范围，不允许砍判据。

### M0 地基（3–4 周）

**范围**：新仓库 / workspace、CI、`base` / `reflect` / `world` 最小实现、
`xtask`（dep-check / size-check / schema 生成 / bench runner）、架构地图、ADR 模板。

**交付**：10k 实体创建 / 查询 / 销毁；组件注册 + schema 生成；微基准跑通；
`cargo xtask check` 一条命令。

**出口**：`query_1m_reads` / `transform_100k` / `schema_export` 达标；
零分配门禁覆盖基础世界循环；文档与架构图生成。

### M1 Agent MVP（4–6 周）

**范围**：命令 / 事务 / journal、快照 / 回放、查询 IR、诊断、Agent 协议、
CLI（`xgc check / run / agent`）、无头仿真（**先不做渲染**）。

**交付**：[AI 分册 §10.12](引擎框架设计-AI操作面.md) 的 10 个 Agent 任务全部可跑；
`plan → apply → revert` 闭环；
state hash / replay；`diag.list`。

**出口**：10 个任务 ≥ 8 个一次通过；查询 1k 行 ≤ 5 ms；事务 100 op ≤ 50 ms；
回放首分歧帧定位准确；无渲染也能跑 S2 / S4 场景。

### M2 渲染 v1 + 垂直切片（6–8 周）

**范围**：RenderGraph、Tier 0、PBR、CSM、后处理、glTF 导入、截图 / golden、
最小可玩 demo（角色 + 3 关 + UI + 音频）。

**交付**：S1 50k 实例 60 fps；截图逐字节确定；A/B 像素测试框架；
一个"能玩 10 分钟"的 demo。

**出口**：S1 的 50k 档预算达标；golden 图稳定；demo 无 P0 bug；渲染 crate 可脱离
世界单测。

### M3 编辑器（4–5 周）

**范围**：会话、Hierarchy、生成式 Inspector、Assets、Console、Profiler、
Gizmo、撤销 / Play / 暂停 / 单步、命令面板。

**交付**：不改文本文件完成"建场景 → 摆物体 → 挂脚本 → Play → 截图"。

**出口**：S6 预算达标；所有编辑器动作有 headless 等价；三档窗口截图无溢出。

### M4 玩法对等（8–10 周）

**范围**：物理（rapier 后端 + 角色 + 查询）、动画（状态机 / 层 / 根运动 / 事件）、
音频、UI、粒子、Lua 批处理、嵌套预制体 / 变体 / 字段级 override、输入映射。

**交付**：能力对等矩阵 P0 / P1 全部 ✅；三个当前示例项目迁移后可玩。

**出口**：P0 / P1 无缺口；脚本 API 名字与当前兼容；预制体 Apply / Revert 语义
通过回归；S2 / S3 / S4 达标。

### M5 性能（6–8 周）

**范围**：Tier 1 GPU 剔除 + bindless + 聚簇光照、作业系统调优、流式、内存预算、
GPU 粒子、性能面板。

**交付**：XG-Bench 六场景中档全部达标；p99 卡顿 ≤ 4 ms；内存不超预算。

**出口**：§13.2 全绿；性能回归门禁进 CI；三条"已证明走不通"的路没有被重新引入
（同帧全几何预通道 / 复制实例做剔除 / 编排层索引）。

### M6 迁移与割接（4–6 周）

**范围**：`xgc migrate`、契约适配（GUID / ID / JSON / 脚本名）、旧项目迁移、
文档、发布、回滚演练。

**交付**：当前仓库的 3 个示例项目 + 1 个真实项目迁移并验收；旧仓库冻结 tag；
新仓库默认分支可发布。

**出口**：迁移后 `check` 0 问题、golden 图通过、性能达标、回滚演练成功。

## 15. 迁移与割接

### 15.1 仓库策略

**推荐：新仓库 + 一次性割接。**

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| **A（推荐）** | 新建 `xgc` 仓库；旧仓库打 tag `xgame-freeze-2026-11`；M6 一次性迁移 | 无兼容层；CI / 依赖 / 构建独立；可并行验证 | 需要维护两份代码到割接 |
| B | 同仓库新 workspace 成员 | 复用 CI / 工具 | 容易误引用旧运行时；违反"不并行两套"的精神 |
| C | 就地大爆炸替换 | 不分叉 | 迁移期间旧引擎不可用；回滚靠 git |

**无论哪种，都不做"新旧运行时同时被产品路径引用"的兼容层。** 这是
[架构收敛约定](架构收敛约定.md) 的硬规则，不是偏好。

### 15.2 必须保留的外部契约

| 契约 | 为什么保留 | 新框架怎么实现 |
|---|---|---|
| `guid://` 资产身份 | 用户资产与场景引用它 | 继续用 GUID；磁盘 / 内存转换点只有一处 |
| 实体 ID 跨进程语义 | 存档 / 预制体 / 外部工具引用 | 项目级 `EntityId`，只增不复用；**迁移时一次性重映射**并输出 old→new 映射表，之后永不再变 |
| MCP / CLI 的 JSON 字段名与退出码 | CI 与外部 Agent 消费 | 旧字段名保留；新协议 additive；退出码 0/1/2 不变 |
| 脚本 API 名字 | 用户已写脚本 | 名字保留，内部重实现；新 API 另起 |
| 场景路径语义 | 项目清单 / 构建 / 发布 | 同一套相对路径规则 |

**不保留**：内部类型名、文件格式细节、插件 ABI、schema 生成方式、编辑器状态模型。
这些允许一次性破坏（同一份约定）。

### 15.3 内容迁移

```text
xgc migrate <xgame-project> --out <xgc-project> [--dry-run]
  ├─ project.ron        → project.xgc
  ├─ Scenes/*.ron       → scenes/*.scene.ron
  ├─ Prefabs/*.ron      → prefabs/*.prefab.ron
  ├─ assets + .meta     → assets + .meta（GUID 不变）
  ├─ Materials/*.mat    → materials/*.xgmat
  ├─ Scripts/*.lua      → scripts/*.lua（不改内容；API 名兼容）
  └─ input.ron          → project.xgc 的 input 节
```

- **dry-run 先出报告**：实体数 / 组件数 / 引用数 / 无法迁移项 / GUID 冲突。
- **保留备份**：迁移输出到新目录，不原地改；旧项目可继续用旧引擎打开。
- **失败可恢复**：迁移是事务；中途失败不留下半套项目。
- **脚本不改写**：API 名保留；182 个函数逐个映射到新命令 / 查询；语义变化的
  （如 `spawn` 的可见时机、物理命令的结算帧）用迁移报告逐条列出，人工确认；
  无法映射的给替代并标 breaking，不静默改行为。
- **实体 ID 重映射**：当前 ID 只在单文件内唯一，新框架是项目级唯一。迁移分配新 ID，
  输出 old→new 映射，改写文件内父子 / 预制体来源引用；旧存档按映射迁移。
- **组件映射**：当前 `Entity` 上的可选字段拆成组件，迁移按下表投影；组件级
  `source_component_id` 改为 `(组件类型, 字段路径)` 的 override 路径。

| 当前字段 | 目标组件 |
|---|---|
| `name` / `layer` | 实体元数据（名称列 / 层列） |
| `prefab` | `core.prefab_instance`（来源 / `source_id`） |
| `transform` / `parent` | `core.transform` / 层级列 |
| `model` / `lod` / `material_asset` / `material` / `morph_weights` | `core.mesh` / `core.lod` / `core.material` / `core.morph` |
| `physics` / `controller` | `core.rigidbody` / `core.character` |
| `animator` | `core.animator`（状态机 / 层 / 事件） |
| `audio` | `core.audio_source` |
| `ui` / `particle` / `camera` | `core.ui_node` / `core.particle` / `core.camera` |
| `scripts` / `behaviors` / `behavior_params` | `core.script` / 注册的 Rust 组件 |

- **预制体**：`source_id` 映射到新项目级 ID；嵌套 / 变体在迁移时展开或保留，
  以报告为准。

| 跨平台 | P2 | 🟨 | 🟨 | Windows 先，Linux 次之 |

### 15.5 割接门禁

1. P0 能力全 ✅、P1 差距有明确排期；
2. 3 个示例项目 + 1 个真实项目迁移后 `check` 0 问题、可玩、golden 通过；
3. XG-Bench 中档预算全绿，且不劣于旧引擎同场景；
4. 确定性 / 截图 / 零分配 / 回放四条门禁全绿；
5. 发布 / 回滚 / 迁移三条演练成功；
6. 文档（用户指南 / 参考 / 迁移指南）齐备。

### 15.6 回滚

- 旧仓库 tag 永久保留，可随时构建旧引擎；
- 迁移输出到新目录，旧项目不动；
- 新引擎发布包与旧包并存一个版本周期；
- 回滚演练写进 M6 出口，不靠"应该能回"。

### 15.7 作者视角：使用与开发上的变化

| 场景 | 旧引擎 | 新框架 |
|---|---|---|
| 操作入口 | 编辑器是主入口；MCP 是无状态工具 | 协议是主入口；编辑器 / CLI / AI 走同一套命令 |
| 读世界 | 整份 RON，或按 ID / 名字单点读 | 分页查询 + `diff` + `explain` + 状态哈希 |
| 改世界 | 直改 / 整文件写 / 单实体 upsert；无预览 | `plan` 预览 diff → `apply` 原子提交 → `revert` |
| 验证 | `--check` + 300 帧无头 + 读日志 | `check` + 定向 `sim` + state hash + 截图 diff |
| 撤销 | 编辑器内存里 100 份整场景快照 | 任意客户端的 `tx` 回滚，跨文件事务 |
| 脚本 | 每实体每钩子一次调用；182 个 API | API 名保留；新增 batch 写法；`script.check/profile/test` |
| 预制体 | 整树 Revert；无嵌套 / 变体 / 字段级覆盖 | 嵌套 + 变体 + 字段级 override / Revert |
| 材质 / Shader | 内联 WGSL；两个材质槽 | `.wgsl` 资产 + naga 反射 + 材质类型 / 变体 |
| 大场景 | 千体物理、万实体脚本接近上限 | 10k 实体 / 5k 刚体的预算；GPU 剔除 + 流式 |
| 调试 | 日志 + Profiler 少量计数 | `world.explain` / `trace` / `replay` / 帧图查看器 |
| 构建 | `--build` + 原子发布 | `xgc build` + cooked + manifest + 可复现 |
| 加组件 / API | 内建组件约 20 处；API 手写 | 1 个文件 + 1 行注册；生成 schema / 绑定 |

**不变的部分**（降低迁移焦虑）：

- 心智模型仍是"实体 + 组件 + 脚本"，场景 / 预制体 / 材质 / 动画 / UI 的概念不变；
- Lua 仍是主语言，已有 API 名字保留（语义变化逐条列出）；
- GUID 资产身份、项目相对路径、`--check` / 无头 / MCP 的 JSON 字段与退出码保留；
- 编辑器面板、Play 模式、确定性无头、逐字节截图继续保留；
- 路径 / 写盘 / 身份 / 确定性的纪律原样继承。

**要付的代价**：

- 项目 / 场景 / 预制体格式一次性迁移（工具 + 映射表 + 备份，不是双读）；
- 自定义 shader / 材质、Rust 插件需要按新 ABI 重写或重编译；
- 组件 ID、实体 ID 在迁移时重映射；旧存档按映射迁移；
- 编辑器在 M2 / M3 之前不完整；新框架初期功能对等之前，旧引擎仍是参照；
- 2D / 网络 / 地形 / 可视化脚本仍然不做（与旧引擎的边界一致）。

## 16. 风险与需要拍板的问题

### 16.1 需要拍板的 8 件事

| # | 问题 | 选项 | 推荐 | 影响 |
|---|---|---|---|---|
| 1 | 与现有引擎的关系 | 替换 / 独立产品 / 仅内核 | **独立新仓库，目标替换** | 仓库、迁移、团队 |
| 2 | 目标平台 | Windows / +Linux / +macOS / +Web | **Windows 首发，Linux 次之** | 渲染后端、打包、测试 |
| 3 | 目标规模 / 类型 | 小游戏 / 3D 动作 / 开放世界 / 多人 | **3D 动作 / Roguelike，10k 实体、5k 刚体** | 流式、物理、网络范围 |
| 4 | 脚本策略 | Lua / Lua+WASM / Rust 优先 | **Lua 必选，WASM v2** | 性能、沙箱、生态 |
| 5 | 物理后端 | rapier / Jolt / 自研 | **rapier 先，M1 spike 后定** | 性能上限、确定性 |
| 6 | 渲染野心 | Tier 0 / +Tier 1 / +Tier 2 | **M5 做 Tier 1，Tier 2 可选** | 工期、风险 |
| 7 | 确定性范围 | 同二进制 / 跨平台逐位 | **同二进制同平台**；跨平台靠快照 | 数学库、物理、性能 |
| 8 | 团队 / 工期 | 1–2 人 / 3–4 人 / 更多 | **3–4 人 9–12 个月** | 里程碑范围 |

**没有拍板前的默认动作**：只做 M0 的 `base` / `reflect` / `world` 与基准骨架，
不碰渲染与物理后端；这些工作在任何选项下都需要。

### 16.2 明确不做（v1）

| 不做 | 理由 |
|---|---|
| C# / 多语言中立层 | 决策记录 D1 已否决；两套语言边界成本远超收益 |
| 可视化脚本 | AI 写 Lua / Rust 更直接；图形化编辑器是另一个产品 |
| 2D / Tilemap | 3D 管线优先；2D 需要独立的渲染与物理路径 |
| 地形 / 水体 | 大世界 v2；先保证 10k 实体与流式 |
| 网络 / 多人 | 确定性 / 快照 / 回滚是前置；v2 再评估 |
| 跨平台逐位确定性 | 成本高；用快照迁移状态 |
| 引擎内代码编辑器 | 外部 IDE / Agent 更好；不做第二套编辑器 |
| 带状态迁移的原生插件热重载 | 复杂度高；脚本热重载已覆盖大部分场景 |
| DCC 插件（Blender / Maya） | 先做好 glTF 导入 / 导出 |
| 主机平台 | 认证 / SDK / 工具链成本；v2 以后 |

### 16.3 风险清单

| 风险 | 概率 | 影响 | 缓解 | Kill criteria |
|---|---|---|---|---|
| 渲染器范围失控 | 高 | 高 | 分 Tier；M2 只做 Tier 0；每层独立验收 | M2 超期 4 周 → 砍后处理 / 阴影范围 |
| 物理达不到预算 | 中 | 高 | M1 spike；rapier 调优；Jolt 备选 | 5k 动态 > 6 ms 且调优无效 → 换后端 |
| Lua 批处理不达标 | 中 | 中 | 批处理 + 数据导向 API；WASM 备选 | 10k 实体 > 1 ms → 评估 WASM |
| 确定性并行做不出来 | 中 | 高 | 先串行正确，再逐系统并行；每步跑哈希门禁 | 并行导致哈希不稳 → 回退串行 |
| 多线程复杂度 | 高 | 中 | 单写者 + 快照 + loom / 压力测试 | 数据竞争无法收敛 → 减并行范围 |
| Agent 协议过度设计 | 中 | 中 | L0–L4 先做；10 任务验收 | 任务通过率 < 7/10 → 简化协议 |
| 编辑器重写拖累 | 中 | 中 | 复用 egui；命令驱动；M3 只做核心面板 | 超期 → 先 CLI / Agent，后 GUI |
| 迁移丢数据 | 低 | 高 | dry-run + 备份 + 事务 + 回滚演练 | 任一项目迁移失败 → 停止割接 |
| 团队 / 时间不足 | 高 | 高 | 砍范围不砍判据；M1 先证明价值 | 6 个月无可用 MVP → 重新评估 |
| 生态 / 资产少 | 中 | 中 | glTF 优先；不做 DCC 插件 | — |

### 16.4 三条"止损线"

1. **M1 结束**：10 个 Agent 任务 < 7 个通过 → 先改协议 / 工具面，不进入渲染重写。
2. **M2 结束**：S1 50k 实例达不到 60 fps → 砍渲染范围或换实现路线，不硬撑。
3. **M4 结束**：P0 能力仍有缺口 → 推迟割接，旧引擎继续维护；不带着缺口发布。
