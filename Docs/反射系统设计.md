# 反射系统设计（Reflect）

> 状态：**设计稿，未实现**。本文只描述方案与取舍，不描述现状能力。
> 现状能力见 `Docs/差距分析.md`；已落地的约束见 `Docs/决策记录.md`。
> 撰写依据：`crates/xgame-core/src/inspect.rs`、`crates/xgame-core/src/schema.rs`、
> `crates/xgame-derive/src/lib.rs`、`crates/xgame-editor/src/panels/inspector.rs`、
> `crates/xgame-core/src/{scene,component_view,scene_v2}.rs`。

---

## 1. 结论摘要

目标是让**内置组件与插件组件共用同一套枚举 / 读 / 写接口**，从而让 Inspector、MCP、Lua
不再各写一套。这件事在 Rust 里不需要 UE 的 UHT —— proc macro 直接拿到 AST，
`#[derive(...)]` 就是 UHT 的等价物且更可靠。

需要补的只有三样：**递归的值模型、嵌套类型的元数据、统一的路径寻址**。
磁盘格式、运行时热路径、`Inspect` / `FieldValues` 都不动。

**明确不做**：不把 `Entity` 的具名字段换成统一容器（见 §10.2）。

---

## 2. 问题陈述

### 2.1 现状：两套编辑路径，一份存储

| 组件种类 | 存储 | 字段元数据 | 编辑器怎么画 |
|---|---|---|---|
| 内置（10 种） | `Entity` 具名字段 | **无** | `inspector.rs` 手写 12 个 `section_bar` |
| Rust 插件组件 | `behaviors` + `behavior_params` | `FieldDesc` 静态表 | 通用循环 |
| Lua 脚本 | `scripts` | 无（只有路径） | 路径行列表 |

`grep "impl Inspect for"` 全仓只有两个实现（`inspect.rs` 的 `Handwritten`、
`world.rs` 的 `Tunable`），**没有一个内置组件实现 `Inspect`**。所以"统一"目前只统一到
`component_view.rs` 的 `AttachedComponent`（存在性 + 名字 + 参数），没有统一到字段读写。

### 2.2 为什么 `Inspect` 扩不动

`FieldValue` 只有 10 个扁平标量变体（`inspect.rs:143-155`）：

```rust
pub enum FieldValue { F32, F64, I32, I64, U32, Bool, String, Vec2, Vec3, Vec4 }
```

而内置组件的字段形态远超它：

| 组件 | 超出表现力的字段 |
|---|---|
| `PhysicsBody` | `shape: CollisionShape`（带载荷枚举，5 个变体各带尺寸） |
| `Animator` | `machine: Option<AnimMachine>`（内含 `BTreeMap<String,f32>` + 两个 `Vec`） |
| `ParticleEmitter` | `lifetime/speed: [f32;2]`、`gravity: [f32;3]`、`start_color: [f32;4]`、`shape: EmissionShape`（带载荷枚举）、`seed: u64` |
| `UiElement` | `style: UiStyle`、`text: UiTextStyle`、`image: Option<UiImageStyle>` |
| `LodGroup` | `levels: Vec<LodLevel>` |

并且 `FieldKind` **没有 `U64`**（`seed: u64` 无法表达），`FieldValue` 也没有数组/Map/嵌套。

### 2.3 为什么不能直接给 `FieldValue` 加变体

`FieldValue` 是 `ComponentData::Rust { fields: Option<StrictFieldValues> }` 的**落盘格式**，
`inspect.rs:145` 明写"变体名是**磁盘格式的一部分**——重命名会破坏已有场景文件"。

如果为了反射去扩它（加 `U64` / `Struct` / `List`），等于让**编辑器的一个显示需求**
去改**场景文件契约**。这条耦合必须断开。

---

## 3. 为什么不需要 UHT

UHT 的存在理由只有一个：C++ 没有语言内反射，只能造一个外部工具去读**头文件文本**。
它的代价是可见的 —— `.generated.h` 必须是最后一个 include、`GENERATED_BODY()` 必须在类体
最前面、UHT 自带一套 lexer/parser 且解析失败就是构建失败。

Rust 的 proc macro 拿到的是**已解析的 AST**，且：
- 不需要"约定 include 顺序"（生成代码走 `::xgame::...` 完全限定路径）
- 不会出现"工具看不懂某个语法"
- 属性（`#[reflect(...)]`）由编译器解析后交给宏，不用自己解析字符串

所以工作量不在"造解析器"，而在**元数据模型的设计**和**每个类型的元数据覆盖**。

---

## 4. 非目标

1. **不改磁盘格式**。反射不参与落盘（§7.1）。
2. **不进热路径**。反射是字符串路径 + 动态分发，只能服务编辑器 / MCP / Lua 等慢路径。
3. **不替换 `Inspect`**。它继续服务插件组件的 `behavior_params` 落盘（§5.6）。
4. **不追求"反射出完美 UI"**。见 §9。
5. **不做函数反射**（`UFUNCTION` 等价物）。脚本侧已有 `GameCtx` + `script_api` 清单，
   把它收敛成宏生成是另一条线，且会动脚本沙箱约定，不在本期。

## 5. 设计

### 5.1 四层结构

```
元数据层（编译期常量）   TypeMeta / FieldMeta / TypeRef        ← derive 生成
        ↓
访问层（借用）           Reflect::get / get_mut → ValueRef<'a>  ← 不拷贝、不分配
        ↓
路径层（运行期）         get_path / set_path                    ← "machine.states[0].name"
        ↓
消费层                   Inspector · MCP · Lua · --check        ← 只走慢路径
```

磁盘层（`ComponentData` / `FieldValues`）**独立在右侧，不经过这四层**。

### 5.2 元数据模型

```rust
/// 一个类型的完整元数据。全部 `'static`，编译期常量。
pub struct TypeMeta {
    pub name: &'static str,
    pub doc: &'static str,
    pub kind: MetaKind,                    // Struct / Enum
    pub fields: &'static [FieldMeta],      // Struct 用
    pub variants: &'static [VariantMeta],  // Enum 用
}

pub struct FieldMeta {
    pub name: &'static str,                // 寻址名（字段名）
    pub label: Option<&'static str>,       // 显示名（改它不动寻址）
    pub ty: TypeRef,
    pub range: Option<(f32, f32)>,
    pub speed: Option<f32>,
    pub step: Option<f32>,
    pub unit: Option<&'static str>,
    pub doc: &'static str,
    pub flags: FieldFlags,                 // HIDDEN / READ_ONLY / MULTILINE
}

/// 类型引用。递归指向另一个 `TypeMeta`，或标量。
pub enum TypeRef {
    Scalar(ScalarKind),                    // F32..U64 / Bool / String / Vec2..Vec4
    Struct(&'static TypeMeta),
    Enum(&'static TypeMeta),
    List(&'static TypeRef),
    Array(&'static TypeRef, usize),        // 定长 [T; N]
    Map(&'static TypeRef, &'static TypeRef),
    Option(&'static TypeRef),
}

pub struct VariantMeta {
    pub name: &'static str,
    pub doc: &'static str,
    pub payload: Option<TypeRef>,          // 带载荷变体
}
```

`ScalarKind` 相对现有 `FieldKind` **新增 `U64`**（`ParticleEmitter.seed` 需要）。
这不动磁盘 —— 它是独立类型（§5.6）。

**静态性怎么保证**：derive 为每个类型生成

```rust
impl ReflectMeta for Camera {
    fn meta() -> &'static TypeMeta {
        static META: TypeMeta = TypeMeta { /* 全 const */ };
        &META
    }
}
```

字段的 `TypeRef::Struct(T::meta())` 要求 `T::meta()` 可在 const 上下文调用 ——
所以元数据表用 `&'static TypeMeta` 而不是 `fn() -> &'static TypeMeta`。
**前提是类型图不递归**；已核实 `Animator` / `AnimMachine` / `AnimLayer` 之间无回指
（`animation.rs:109-119`、`:243-255`），`AnimLayer` 不回指 `AnimMachine`。
若将来出现递归，需退回 `fn()` 间接（届时再定）。

### 5.3 访问模型：借用，不拷贝

```rust
pub trait Reflect: Any {
    fn meta(&self) -> &'static TypeMeta;
    fn get(&self, field: &str) -> Option<ValueRef<'_>>;
    fn get_mut(&mut self, field: &str) -> Option<ValueRefMut<'_>>;
}

pub enum ValueRef<'a> {
    F32(&'a f32), F64(&'a f64), I32(&'a i32), I64(&'a i64), U32(&'a u32), U64(&'a u64),
    Bool(&'a bool), Str(&'a str), Vec2(&'a Vec2), Vec3(&'a Vec3), Vec4(&'a Vec4),
    Struct(&'a dyn Reflect),
    List(&'a dyn ReflectList),
    Map(&'a dyn ReflectMap),
    Enum(&'a dyn ReflectEnum),
    None,                                   // Option::None
}

pub trait ReflectList {
    fn len(&self) -> usize;
    fn get(&self, index: usize) -> Option<ValueRef<'_>>;
    fn get_mut(&mut self, index: usize) -> Option<ValueRefMut<'_>>;
    /// 增删：返回是否成功（越界 / 不支持时为 false）
    fn insert_default(&mut self, index: usize) -> bool;
    fn remove(&mut self, index: usize) -> bool;
}

pub trait ReflectEnum {
    fn variant(&self) -> &'static str;
    fn variant_mut(&mut self, name: &str) -> bool;   // 切变体（载荷重置为默认）
    fn payload(&self) -> Option<ValueRef<'_>>;
    fn payload_mut(&mut self) -> Option<ValueRefMut<'_>>;
}
```

**为什么借用而不是返回 `Value` 树**：Inspector 每帧都要读一批字段。如果读一次就分配一棵
`Value` 树，一个 `Animator` 展开后可能几百次分配 —— 与 `alloc_steady_state` 的纪律冲突
（虽然编辑器不在那条测试里，但没有理由自找）。借用式读是零分配的。

代价：`ValueRefMut` 只能一个一个拿（不能同时持有两个 `&mut`），且它的生命周期绑在
`&mut dyn Reflect` 上。Inspector 的实际用法是"读全部 → 画 → 改一个 → 重新读全部"，
不违反这个约束。

### 5.4 路径层

语法取 JSON Pointer 的**子集**（不用 `~0`/`~1` 转义，字段名不含 `.` 与 `[`）：

```
"clip"                       顶层字段
"machine.entry"              嵌套字段
"machine.states[0].name"     列表元素
"machine.parameters"         Map（整体）
```

MCP 的 `component_edit` 已经在用 JSON Pointer 语义（`patch_existing_field` 要求指向已有字段），
所以这一层可以直接复用同一套语义，不必新发明。

```rust
pub fn get_path<'a>(root: &'a dyn Reflect, path: &str) -> Result<ValueRef<'a>, ReflectError>;
pub fn set_scalar(root: &mut dyn Reflect, path: &str, v: ScalarValue) -> Result<(), ReflectError>;
// set_scalar 只写标量；结构改动（切变体 / 增删元素）走 ReflectEnum / ReflectList 的专用方法
```

**只允许写标量**是有意的：`set_path` 能写任意结构就等于"用字符串重建类型"，会绕开
所有类型检查。结构改动必须通过 `ReflectEnum::variant_mut` / `ReflectList::insert_default`
这类有明确语义的方法。

### 5.5 derive 契约

`#[derive(Reflect)]` 支持：

| 字段形态 | 处理 |
|---|---|
| 标量（f32…u64 / bool / String / Vec2..4） | `TypeRef::Scalar` |
| `Option<T>`（T 可反射） | `TypeRef::Option` |
| `Vec<T>`（T 可反射） | `TypeRef::List` |
| `[T; N]`（N ≤ 4 且 T = f32） | 映射到 `Vec2/Vec3/Vec4`（与现有 UI 一致） |
| 嵌套 struct（同 crate 或字段 `pub`） | `TypeRef::Struct` |
| 无载荷 enum | `TypeRef::Enum`（只能切变体） |
| 带载荷 enum | **拒绝**，要求手写 impl |

属性：`#[reflect(skip)]`（不出现）、`#[reflect(label = "...")]`、
`#[reflect(range = 0.0..=1.0)]`、`#[reflect(speed = 0.01)]`、`#[reflect(read_only)]`。

**拒绝编译**（给出明确错误而不是静默跳过）：泛型类型、元组结构体、`&'a T` 借用字段、
`HashMap`（无序）、带载荷 enum。理由与 `#[derive(Inspect)]` 现有做法一致 ——
`xgame-derive` 已经会因为"不支持元组结构体"直接报错（`derive/src/lib.rs:317`）。

### 5.6 与 `Inspect` / `FieldValues` 的关系

**两个 trait 共存，职责分开**：

| | `Inspect`（现有） | `Reflect`（新增） |
|---|---|---|
| 目的 | 插件组件参数**落盘** | 任意组件**编辑与查询** |
| 值类型 | `FieldValue`（磁盘契约） | `ValueRef`（借用，不落盘） |
| 表达能力 | 扁平标量 | 递归 + 集合 + 枚举 |
| 覆盖 | 插件组件 | 插件组件 + 内置组件 |

`Reflect` **不复用 `FieldValue`**，理由就是 §2.3：`FieldValue` 的变体名进了场景文件，
扩它就是改契约。反射自己一套值类型，磁盘一个字节都不用动。

`Behavior` trait 的约束不变（仍要求 `Inspect`），因为 `behavior_params` 仍要落盘。
将来若要支持"插件组件带嵌套参数"，那是一次**独立的磁盘格式变更**，需单独决策。

## 6. 表达力边界（诚实清单）

| 边界 | 影响 | 处理 |
|---|---|---|
| 带载荷枚举（`CollisionShape`、`EmissionShape`） | derive 覆盖不到 | 手写 impl（每个约 60-100 行） |
| `BTreeMap<String, f32>`（`AnimMachine.parameters`） | derive 可支持 Map，但 UI 表达是键值表 | S3 再决定；S1/S2 可先 `#[reflect(skip)]` |
| `u64`（`ParticleEmitter.seed`） | 现有 `FieldKind` 无 U64 | `ScalarKind` 新增 U64（不动磁盘） |
| 泛型类型 | derive 无法生成 | 不支持；现有组件无泛型，暂不受影响 |
| 跨 crate 私有字段 | derive 在定义模块展开，可访问私有；跨 crate 字段需 `pub` | 内置组件都在 `xgame-core`，不受影响 |
| 递归类型图 | `&'static TypeMeta` 会无限展开 | 已核实当前无递归；出现时改 `fn()` 间接 |
| 同时两个 `&mut` | 借用式访问不支持 | 现有用法（读全部→改一个→重读）不受影响 |

## 7. 三个关键取舍

### 7.1 反射不参与落盘

**取舍**：`Reflect` 只服务编辑与查询，不参与 `SceneV2` 的编解码。

**理由**：磁盘格式已经被 `ComponentData`（内置）+ `FieldValues`（插件）定义清楚，且
`deny_unknown_fields` + `serde_ignored` 两道闸门在保护它。让反射去碰落盘，就要么改
`FieldValue`（改契约），要么引入"反射驱动的序列化"（需要类型注册表 + 跨版本兼容）。
两者风险都远大于收益。

**代价**：内置组件的磁盘形状与反射形状可能不一致（例如 `MaterialData { asset, overrides }`
在磁盘是一个组件，在 `Entity` 是两个字段）。这个不一致**已经存在**（§2.1），反射不解决它，
也不加剧它。

### 7.2 借用而非拷贝

见 §5.3。核心是"读字段不分配"。

### 7.3 慢路径隔离

**取舍**：反射 API 只允许出现在编辑器、MCP、`--check`、Lua 的字段访问里。

**理由**：字符串比较 + 动态分发。`Entity` 的 10 个槽位之所以是字段，就是为了热路径零成本
（`pull_dynamic_bodies` 每帧 O(n)）。如果运行时系统改用 `get_path("physics.mass")`，
每帧几千次字符串比较，性能会直接崩。

**约束**：`Reflect` 不进入 `xgame-runtime` 的任何每帧函数。这条要写进决策记录。

## 8. 分期与验收

### S1 — Camera + AudioSource（垂直切片）

范围：`TypeMeta` / `Reflect` / `ValueRef` / `get_path` / `set_scalar` 全部落地；
`#[derive(Reflect)]` 支持标量 + `Option<标量>`；`Camera`、`AudioSource` 接入；
Inspector 新增"反射通道"但**默认关闭**，靠一个开关与手写 section 并存。

验收：
- `crates/xgame-core` 新增测试：`Camera` 全字段 `get_path` 读 → `set_scalar` 写 → 值相等；
  越界路径返回 `ReflectError` 而不是 panic。
- `crates/xgame-derive` 新增测试：拒绝元组结构体 / 带载荷 enum 的编译失败消息。
- Inspector：`--ui-shot --ui-select` 在带 Camera 的实体上截图，反射通道与手写 section
  **逐像素一致**（用 `.workbuddy/tools/rowscan.py` 量分段）。
- `cargo clippy --workspace --all-targets` 0 警告；`alloc_steady_state` 仍通过。

**S1 的意义**：证明"derive → 元数据 → 借用访问 → 路径 → UI"整条链路成立，且不动磁盘。

### S2 — 带载荷枚举 + 列表

`PhysicsBody`（含 `CollisionShape`）、`CharacterController`、`LodGroup`（`Vec<LodLevel>`）。
需要 `ReflectEnum` 与 `ReflectList` 落地，以及 `CollisionShape` 的手写 impl。

验收：Inspector 的 Physics / Character / LOD 三个手写 section 被反射通道替换，
截图一致；`CollisionShape` 的 5 个变体都能切换且载荷正确重置。

### S3 — 嵌套结构与数组

`ParticleEmitter`（`[f32;2..4]` + `EmissionShape`）、`UiElement`（三个嵌套样式结构）。

### S4 — Animator（建议不做通用反射）

`AnimMachine` 是"状态 + 转移 + 参数"的图，反射画出来是一堆表格，不如现有专用编辑器。
**建议保留专用 section，只把标量字段（`clip` / `speed` / `fade_time`）接入反射。**

### 不在分期里

- 函数反射 / `#[xgame_fn]`
- 插件组件的嵌套参数落盘
- 统一存储容器

## 9. 风险与反例

1. **"反射就等于统一 UI"是错觉。** UE 的 Details 面板背后是 `meta=(ClampMin, EditCondition,
   DisplayName)` 加大量 `IDetailCustomization` 手写定制。反射给的是**能用**的通用 UI，
   不是**好用**的。`Animator`、`UiElement` 大概永远需要专用编辑器。
2. **derived UI 的回归风险高。** 手写 section 有大量对齐/宽度细节（`theme::axis_field_width`
   必须在放控件前取一次、`add_sized` 只保证最小尺寸）。反射通道如果自己排版，很可能
   在 1280 窗口下溢出。S1 的"逐像素一致"验收就是防这个。
3. **元数据会漂移。** 手写元数据表与真实字段不同步，是这个模式最大的长期病。缓解手段
   与 `schema.rs` 一致：derive 生成而不是手写，且 `FieldMeta.name` 用 `stringify!(字段名)`，
   字段改名后不同步会编译失败。
4. **`Reflect` 与 `Inspect` 双轨并行，可能长期共存。** 如果最终只做到 S2 就停，
   会留下"内置组件走 Reflect、插件组件走 Inspect"的新不一致 —— 比现在还多一套。
   **这条是本期最大的战略风险**：要么做完 S3，要么别开始。

## 10. 备选方案

### 10.1 扩 `FieldValue`（否）

给 `FieldValue` 加 `U64` / `Struct` / `List`。看起来最省事，但它会改磁盘契约（§2.3），
且让"编辑器显示"与"场景文件格式"永久耦合。

### 10.2 把 `Entity` 的槽位换成统一容器（否）

`Entity { components: Vec<ComponentInstance> }`，内置与插件走同一容器。这就是 UE / Unity
的形态，也是**唯一能让反射变成唯一入口**的方案。

不选的理由（每条都有代码依据）：

| 代价 | 依据 |
|---|---|
| 约 1100 处直接字段访问要改写 | `transform` 369 / `animator` 166 / `ui` 140 / `physics` 136 / … |
| `serde` 失去编译期类型集 | `ComponentMap` 键是 `TypeId`，不可序列化，故 `#[serde(skip)]`（`scene.rs:201`） |
| `Clone` 需 `dyn_clone` | `ComponentMap::clone` 返回空表（`component.rs:147`），而 undo / Play 快照靠 `Scene::clone` |
| `Transform` 丢掉"必存在" | 它是唯一非 `Option` 组件字段，369 处访问无一处 `unwrap` |
| 脏检查失去编译期强制 | `impl PartialEq for Entity` 穷尽解构（`scene.rs:421`） |

> **判断**：等到内置组件数量从 10 涨到 30+，或者需要"内置组件运行时插拔"，这套交换

### 12.2 实现中发现的三处与设计稿不符（已按实现修正）

**① `TypeRef::Struct` + `TypeRef::Enum` 合并成 `TypeRef::Named`。**
derive 只看得到字段的**类型名**，看不到目标类型的定义，所以它在生成元数据时
无法判断 `AudioBus` 是结构体还是枚举 —— 初版一律猜 `Struct`，测试
`nested_type_reference_points_at_target_meta` 当场抓到了。现在只记"指向哪个类型"，
结构体 / 枚举由目标 `TypeMeta.kind` 回答。**不猜比猜错好。**

**② 元数据从 `const` 改成 `OnceLock` 惰性构建。**
原设计想用 `static META: TypeMeta = …` 全静态。但嵌套引用要拿到 `&'static TypeRef`，
而 `Box::leak` 是运行期调用，不能出现在 `const` / `static` 初始化里；若改成
`<T as ReflectMeta>::META` 关联常量，递归类型图会让编译器无限展开。
现状：每种类型第一次访问时构建一次，`Box::leak` 一次（进程内总量与类型数同阶）。
代价可接受，换来 `TypeRef` 不必是常量表达式。

**③ `Reflect::meta(&self)` 改名 `type_meta(&self)`。**
`ReflectMeta::meta()` 是关联函数，两者同名会让 `Camera::meta()` 这种最常用写法
报 E0034（多个候选）。改名后 `Camera::meta()` 唯一指向静态元数据。

## 14. S2 记录（带载荷枚举 + 列表）

### 14.1 最关键的一步：`#[derive(Reflect)]` 支持枚举

S1 时枚举只能手写（`reflect/audio_bus.rs` 一百行）。S2 要覆盖 `CollisionShape`
（5 个变体，其中 4 个有载荷）与 `BodyKind`，逐个手写就是三份样板 —— 所以先把
derive 补上。

支持两种形状：

| 形状 | 生成 |
|---|---|
| 单元变体 `Auto` | `variant()` / `set_variant()` / `payload_meta() → None` |
| 具名载荷 `Cuboid { half_extents }` | 再加一张**按变体**的载荷字段表 + 按名读写 |

载荷字段的 `#[reflect(...)]` 与结构体字段**同一套**，所以 `half_extents` 也能
声明范围、步长、单位。

拒绝元组变体（`Variant(T)`）：载荷没有名字可寻址，编辑器画不出一行 ——
错误消息直接说"请改成 `Variant { name: T }`"。

副产品：`AudioBus` 的手写反射（`reflect/audio_bus.rs`，100 行）**删掉了**，
改成 `#[derive(Reflect)]` + 三个 `#[reflect(label = "sfx")]`。

### 14.2 载荷接口从"一个 `ValueRef`"改成"按字段名"

原设计里 `ReflectEnum::payload()` 返回 `Option<ValueRef>`，隐含假设"载荷是一块
可以借出去的连续内存"。这个假设**不成立** —— 载荷散在枚举变体里，没有独立地址。
所以换成与 `Reflect` 同形的三个方法：

```rust
fn payload_meta(&self) -> Option<&'static TypeMeta>;
fn payload_get(&self, field: &str) -> Option<ValueRef<'_>>;
fn payload_get_mut(&mut self, field: &str) -> Option<ValueRefMut<'_>>;
```

配套的两处修正：

- **路径层删掉 `value` 伪字段。** 原来写 `machine.value` 取载荷，现在载荷字段
  直接按名字寻址：`shape.radius`。枚举体内没有额外层级，多一层只是噪声。
- **`Reflect: Any` 去掉了。** `Any` 要求 `'static`，而编辑器要把载荷包装成一个
  持有 `&mut dyn ReflectEnum` 的适配器（`EnumPayload`）交给同一套字段渲染器 ——
  它不可能是 `'static`。反射本来也不做向下转型（类型由 `TypeMeta` 描述），
  `Any` 是多余的约束。

`EnumPayload` 这个适配器是 S2 的结构性收益：**载荷与真结构体走同一个
`show_fields`**，所以 `CollisionShape::Cuboid.half_extents` 与 `PhysicsBody.mass`
是同一段代码画出来的，没有第二套控件分派。

### 14.3 元数据又补了 3 项、spec 又补了 2 个钩子

| 新增 | 用途 |
|---|---|
| `variant_note` | 无载荷变体要不要画一行说明。`Auto` 要（"按实体缩放"），`sfx` 不要 |
| `item_prefix` | 列表项第一行的标签用下标：`L0` / `L1` |
| `add_label` | "加一项"按钮的文字，兼作能力开关（`None` = 只读列表） |
| `VariantMeta.label` | 寻址名 `Cuboid` / 显示名 `Box`（S1 已加，S2 才真正用上） |

`ReflectComponentSpec` 新增两个钩子，都是元数据表达不了的：

- `on_variant(entity, field, variant)` —— `Auto → Box` 时要用**实体缩放**给
  半边长一个初值。变体声明在 core 的纯数据类型上，不知道实体存在。
- `footer(entity) -> String` —— Character 段的"胶囊中心 = 脚底 + 0.90 m"是
  算出来的派生量，不是字段也不是静态说明。

至此参数化程度到了：`FieldMeta` 13 个字段 + spec 3 个可选钩子。
**这与 UE 的 `UPROPERTY(meta=(ClampMin, UIMin, Units, EditCondition, DisplayName))`
是同一件事** —— S2 用实践确认了 §9.1 的判断：统一 UI 的能力来自元数据厚度，
不是来自"有个基类"。

### 14.4 接入的三个组件

| 组件 | 用到的能力 |
|---|---|
| `PhysicsBody` | 两个枚举（无载荷 + 带载荷）、`[f32; 3]` 轴行、条件无关 |
| `CharacterController` | 纯标量 + `footer` |
| `LodGroup` / `LodLevel` | 列表：每项一组行 + 删除 + 追加 + 组尾说明 |

`CollisionShape::Auto` 那行"按实体缩放的绝对值生成盒子"由 `variant_note` 打开，
文字取自变体的文档注释 —— 手写段那句是另抄的一份，现在同一份。

### 14.5 又动了两个字段顺序

反射按声明顺序排版，所以"声明顺序 = 界面顺序"这条（S1 为 `AudioSource.bus`
定下的）在 S2 又生效了两次：

- `PhysicsBody`：`mass` 从 `friction` 之前挪到 `restitution` 之后
  （界面是 Friction → Bounce → Mass → Gravity：材质参数在前、动力参数在后）。
- `CharacterController`：`height` 与 `radius` 互换（界面先总高后半径，
  半径的说明里要用到总高）。

老场景文件照常加载（serde 按名字解析），只是重新保存时这几行的**行序**会变。

### 14.6 验收

对比工程还是 `%TEMP%/xg-reflect-probe`，现在有 4 个实体，每个只挂一段组件
（这样 Inspector 不会超出一屏，避免滚动条把可用宽度改掉 —— 这一点在 S2 踩过：
多画一行促成滚动条，整列控件宽度全变，看起来像"排版全错"）。

| 用例 | 区域像素 | 差异 |
|---|---|---|
| Camera + Audio（spatial 开） | 634,400 | **0** |
| Physics（`Cuboid` + 轴行 + 5 个标量 + 勾选框） | 634,400 | **0** |
| Character（6 个标量 + 派生量说明） | 634,400 | **0** |
| LOD（2 级列表 + 删除 + 追加） | 634,400 | 61,970（9.77%） |

**Physics 那一组尤其说明问题**：`half_extents` 在磁盘上是 `[f32; 3]`、在反射里是
`List`，而界面上要和 `Transform.scale` 长得一模一样（`axis_field_width` 三等分 +
彩色轴标）。反射通道走的是"读成 `[f32; 4]` → 画三格 → 逐个写回"，与手写段逐像素一致。

### 14.7 LOD 为什么没做到一致 —— 以及这条验收标准的修正

差异三处，全部来自"手写段在 LOD 这一块用了别处没有的排版"：

| # | 手写段 | 反射通道 |
|---|---|---|
| 1 | 模型输入框紧贴标签列（`field_row`，无轴标占位） | 所有行统一走 `row()`，多 15px 轴标占位 |
| 2 | `Max Dist` 数值框宽度 = 可用宽度 − 26 | 统一 `FIELD_WIDTH`（54px） |
| 3 | ✕ 挤在 `Max Dist` 行尾 | ✕ 单独一行、靠右（数值框行不留尾部位） |

其中 #1 是**手写段自己的不一致**：同一个 `String` 字段，Audio 的 `Clip` 用了带
轴标占位的 `row()`，LOD 的模型却用 `field_row`。反射通道把两者统一了 ——
统一的结果必然是其中一个要动。

**所以这里改的是验收标准，不是实现**：S2 的验收改成"Physics / Character 逐像素
一致；LOD 替换后布局有上述三处变化，属统一排版语法的一部分"。要逐像素一致的话，
需要给行渲染加一个"尾部插槽"（把 ✕ 放进最后一行的控件区）与一个"拉伸"标记
（数值框占满可用宽度）—— 两个都是为单一组件服务的特例，暂不做。

### 14.8 行为差异（S2 新增一条）

**切变体后载荷在下一帧才出现。** 手写段是 `match &mut body.shape`，切完当帧就画
新变体的参数；反射通道在 `show_fields` 里拿到的是**切换前**的 `ValueRefMut`，
新载荷要等下一帧。60fps 下不可见（而且点击本身会触发重绘），但确实有这一帧。

### 14.9 还没做的

- S3：`ParticleEmitter`（`[f32; 2..4]` + `EmissionShape`）、`UiElement`（三层嵌套样式）。
  两者所需的机制 S2 已全部就位（带载荷枚举、数组轴行、嵌套结构体平铺）。
- MCP 的 `component_catalog_read` 仍然自己算一份目录。
- 手写 section 仍在（开关默认关）。按 §9.4：要么做完 S3 再删，要么别删。

## 15. S3 记录（粒子 + UI，以及"统一"的边界在哪）

### 15.1 元数据只加了 3 项，控件只加了 2 种

| 新增 | 用途 | 为什么非它不可 |
|---|---|---|
| `Widget::Color` | 取色块 | `[f32; 4]` 默认画成四根轴；颜色和"四个分量"是两种意图 |
| `Widget::Range` | `a → b` 区间对 | `[f32; 2]` 默认画成 `X / Y`，读起来像在填二维坐标 |
| `footnote` | 整行之后的独立说明 | 与挤在本行里的 `note` 排版后果不同：长句会把面板顶出去 |

`widget` 的取值在 **derive 里做编译期校验**：`widget = "color"` 挂到 `f32` 上直接报错，
而不是让编辑器静默退回数值框 —— 那种错作者永远发现不了，只会觉得"取色器没生效"。

### 15.2 `note` 与 `footnote` 分开

S2 时同一个 `note` 有两个渲染位置：单字段行画在本行内，行组尾部画在下一行。
同一个字段名承担两种排版，读代码的人得先看它属于哪种形状才知道画在哪。

S3 拆开：`note` 恒在本行内，`footnote` 恒独占一行。`AudioSource.max_distance`
与 `LodGroup.levels` 的长句改成 `footnote`，**渲染结果逐像素不变**（改的是归类，不是位置）。

### 15.3 行组能容纳混合类型

`Duration` 后面紧跟 `Loop` 勾选框、出生色后面跟死亡色 —— 一行里不再是"两个数值框"。
行组现在读成 `Vec<Cell>`（`Number` / `Bool` / `Color`），规则两条：

- **`→` 只夹在两个可比较的量之间。** `Duration → ☑ Loop` 那个箭头会把"一个数、一个开关"
  读成一条连续刻度，是误导。
- **组里有一个画不进一行的类型就整组退回逐行。** 合并是排版偏好，画错是信息错误。

### 15.4 又调了一次字段顺序（第三次）

`ParticleEmitter` 的 `spread` 挪到 `direction` 之前 —— 手写段的顺序是 Spread → Direction。
按 S1 定下的"声明顺序 = 界面顺序"，这里没有第三个选项：要么挪字段，要么给元数据加排序号。
挪字段是零成本的（serde 按名字解析，磁盘不受影响）。

至此这条规则的代价有了完整账目：`AudioSource.bus`、`PhysicsBody.mass`、
`CharacterController.height/radius`、`ParticleEmitter.spread` —— 四处，
全部只影响"重新保存时的行序"，不影响任何名字寻址。

### 15.5 "操作"不是字段：`presets`

粒子的 `Fire / Smoke / Sparks` 三个 chip、UI 的锚点预设，都是"点一下改一整片字段"。
它们做不到元数据里，因为**它不是某个字段的值**。

`ReflectComponentSpec::presets` 收这一类的按钮版（`Preset { label, tooltip, apply }`）。
它必须画在拿到组件借用**之前** —— `apply` 拿的是 `&mut Entity`。

### 15.6 `Render::Custom`：统一的是入口，不是画法

这是 S3 最重要的一条决定，也是对 §9.4 那个担心的正面回答。

```rust
pub enum Render {
    /// 按 `TypeMeta` 逐字段画。
    Fields,
    /// 专用渲染：`(ui, 实体, 信号, is_editing) -> 是否请求移除`
    Custom(fn(&mut egui::Ui, &mut Entity, &mut FieldSignals, bool) -> bool),
}
```

UI 段选择 `Custom`，理由**不是"做不完"**，而是它的版式本身承载信息：

| UI 段的成分 | 为什么元数据拼不出来 |
|---|---|
| 锚点预设（7 项） | 是**操作**：一次改 6 个字段，且新值依赖当前尺寸 |
| `Size` 派生读数 | 不是字段，是 `offset_max - offset_min` 算出来的 |
| 运行态 `hovered/pressed/clicked` 读数 | 每帧重算，不落盘 |
| 九宫格切片四连框 | 四个分量各有名字（L/R/T/B）与"图片像素"单位 |
| `image: Option<UiImageStyle>` 的存在开关 | `ValueRefMut` 没有"把 `None` 变成 `Some(默认值)`"的接口 |

硬塞进去要往 `FieldMeta` 加六七个只有这一个组件用得上的字段，而检查"改完了没"
仍然得靠手写代码。**那是把 DSL 造出来又不用它。**

关键是 `Custom` 与 `Fields` **登记在同一张表里、走同一个入口、共用 `FieldSignals`**：

```rust
show_section(state, ui, entity, &inspector_reflect::UI, &mut sig, &mut req, &mut refresh)
show_section(state, ui, entity, &inspector_reflect::PARTICLE, &mut sig, &mut req, &mut refresh)
```

所以"这个组件的 Inspector 在哪"永远只有一个答案。这与 UE 的 `Details` +
`IDetailCustomization` 是同一个安排：默认走反射，版式特殊的段落显式声明例外，
而不是让它散落在三千行的 `show_body` 里。

### 15.7 验收

对比工程 `%TEMP%/xg-reflect-probe` 现在有 6 个实体，每个只挂一段组件。

| 用例 | 区域像素 | 差异 |
|---|---|---|
| Camera + Audio（spatial 开） | 634,400 | **0** |
| Physics（`Cuboid` + 轴行 + 两个枚举） | 634,400 | **0** |
| Character（6 标量 + 派生说明） | 634,400 | **0** |
| **Particle（17 字段 / 3 个预设 chip / 2 个区间对 / 2 个取色块 / `u64` 种子）** | 634,400 | **0** |
| LOD（2 级列表 + 删除 + 追加） | 634,400 | 8.84%（S2 时 9.77%） |
| UI（专用渲染器） | 634,400 | **0**（开关不影响它，见下） |

UI 那一行是**自检**而不是验收：它走的是同一个函数，所以加不加
`--ui-reflect-inspector` 必须一模一样。若哪天真把它通用化了，这条会先失败。

LOD 剩下的 8.84% 是两处只有它用的排版：`Max Dist` 数值框按"可用宽度 − 26"拉伸
（反射统一用 `FIELD_WIDTH`）、✕ 挤在最后一行行尾（反射给它单独一行）。
S2 时还有第三处 —— `L0` 行用了 `field_row` 而 `Clip` 用 `row`，同一个 `String`
字段两种缩进；S3 顺手统一了（粒子段的 `Direction` / `Half` / `Gravity` 三行同一问题），
所以从 9.77% 降到 8.84%。

### 15.8 derive 新增两条编译期校验

1. **`row_group` 的孤组。** 只写一个成员的组永远合并不了，而写它的人一定以为隔壁字段
   也在组里。这个错在界面上完全看不出来（只是"多了一行"），S3 里我自己犯了两次
   （`duration` 忘了、`start_size` 忘了），所以加进 derive：`row_group` 出现次数 < 2 就报错。
2. **`widget` 与类型相容。** 见 §15.1。

### 15.9 剩下的组件

同一张表里现在有 6 个（Camera / Audio / Physics / Character / LOD / Particle 走 `Fields`，
UI 走 `Custom`）。还没进表的：

| 组件 | 现状 | 进表的难点 |
|---|---|---|
| `Mesh`（`model` + `morph_weights`） | `show_body` 内联 | Morph 权重的名字来自渲染器（`morph_targets`），不是编译期可知 |
| `Material`（资产 + 覆盖） | 内联 | 同上：`BaseColor` 等字段来自 `.mat` 资产，动态 |
| `Animator` | 内联 | 状态机是张图，§9.1 已判定保留专用编辑器 |
| `Scripts` / `Behaviors` | 内联 | `Vec<String>` + 按注册表查出来的参数表，与 `Inspect` 那条轨道重叠 |
| `Prefab` | 内联 | 是"实例 → 资产"的关系操作，没有字段 |
| `Transform` | 内联 | 四元数 ↔ 欧拉角的双向编辑，§13 的 `Widget` 体系表达不了 |

前两个与 UI 同类（**内容由运行时注册表决定**），要进表得先让 `Reflect` 能描述
"字段表在运行时才知道"的类型 —— 那是比 `TypeMeta` 更大的一次扩展。
后三个是"操作型/关系型"段落，`Custom` 是它们的正确归属。

## 16. 收尾：删掉旧路径与兼容开关

S1–S3 期间 Inspector 一直是**两条路并存**：`--ui-reflect-inspector` 默认关，
手写段还在 `show_body` 里。这种状态能换来逐像素对比，但不能是终态 ——
两套实现同时存在，改一处忘另一处就是新的漂移源。这一节把它收掉。

### 16.1 删掉了什么

| 删除项 | 量 |
|---|---|
| 六段手写分支（LOD / Physics / Character / Audio / Camera / Particle） | 961 行 |
| `EditorState::use_reflect_inspector` | 1 个字段 + 构造 |
| `--ui-reflect-inspector` / `UiShot::reflect_inspector` | 命令行开关 + 应用逻辑 |

删完之后每个组件只剩**一条**渲染路径，没有"翻个开关看看是哪边错了"的余地 ——
这正是想要的：元数据错了就修元数据，没有退路可走。

### 16.2 剩下七段也进了表

`Transform` / `Mesh` / `Animation` / `Scripts` / `Behaviors` / `Material` / `Prefab`
原先内联在 `show_body` 里（共约 1750 行）。现在它们搬到
`panels/inspector_sections.rs`，每段一个 `pub(super) fn show_xxx(ui, entity, cx)`，
通过 `Render::Custom` 登记进同一张 spec 表。

**函数体几乎零改动**：三处机械替换（`state.` → `cx.state.`、
`component_request =` → `*cx.request =`、`&mut refresh_scripts` → `cx.refresh_scripts`），
外加保留原有的 `touched` / `drag_began` / `drag_ended` 三个局部布尔，
在函数尾部折进 `FieldSignals`。这样"搬"和"改"没有混在一起 ——
搬迁的正确性由逐像素比对保证，改动只发生在边界上。

分类条 + 右键菜单这 12 行样板从 7 处手写收敛到 `show_section` 一处。

### 16.3 spec 的形状变了

```rust
pub struct ReflectComponentSpec {
    pub title: &'static str,
    pub indent: &'static str,          // 原先是 BuiltinComponent::code()
    pub menu: SectionMenu,             // 原先是 remove_label: &'static str
    pub render: Render,
    // …access / normalize / on_variant / footer / presets / toggle
}

pub enum SectionMenu {
    None,                                                        // Prefab
    Removable   { address: ComponentAddress, label: &'static str },
    Locked      { label: &'static str, reason: &'static str },    // Transform
    Collection  { label: &'static str, reason: &'static str },    // Scripts / Behaviors
}
```

两处变化不是为了整齐，是**被真实需求逼出来的**：

- `kind: BuiltinComponent` 装不下 `Scripts` / `Behaviors` —— 它们不是内建组件，
  而是 `Entity::scripts` / `behaviors` 字段里的一组实例。原先的
  `ComponentMenuTarget::Collection` 就是为了这件事，但 spec 结构里没有对应位置。
  现在菜单自己带 `address`，`kind` 这个字段就没有存在必要了。
- `indent` 独立出来：`Prefab` 的 `kind` 也不存在，但 egui 仍然需要一个 id
  来记住滚动状态。

### 16.4 `SectionCx`：专用渲染器能拿到的东西

```rust
pub struct SectionCx<'a> {
    pub state: &'a mut EditorState,
    pub sig: &'a mut FieldSignals,
    pub request: &'a mut Option<ComponentAction>,
    pub refresh_scripts: &'a mut bool,
}
```

四样恰好就是原先每个手写段都要碰的东西。打包之后有两个直接好处：

1. `show_section` 的签名不再随段落需求增长（原先要传 `state` / `sig` /
   `request` / `refresh_scripts` 四个参数，`Custom` 还得再补一个 `bool`）。
2. 专用渲染器**写组件结构动作的通道**与 `Fields` 那条路完全一致 —— 都走
   `cx.request`，不存在"手写段自己调 `apply_component_action`"这种旁路。

### 16.5 验收

因为两条路的输出必须完全一致，验收方式很直接：删代码**前后**同一场景、同一实体、
同一窗口尺寸各截一张，比 Inspector 整列。

| 用例 | 区域像素 | 差异 |
|---|---|---|
| Camera + Audio | 626,080 | **0** |
| Physics | 626,080 | **0** |
| Character | 626,080 | **0** |
| LOD | 626,080 | **0** |
| Particle | 626,080 | **0** |
| UI | 626,080 | **0** |
| Transform / Mesh / Animation / Scripts / Behaviors / Material / Prefab | — | 目视逐段核对（各自截图） |

左边缘还差 462 像素（3px × 154 行）—— 那是面板分隔线的高亮，不是内容，
把比对区域左边界从 2190 挪到 2198 就归零。

顺带把 LOD 的 8.84% 也消掉了：不是靠改渲染，而是**手写段被删掉之后**，
"两处排版差异"这个问题本身不存在了。反射通道的 LOD 就是 LOD 现在的样子。

### 16.6 踩到的坑：标题比内容先画

`show_section` 先画分类条、再进渲染器。所以存在性判断必须留在**调用方**：

```rust
if working.prefab.is_some() {          // ← 不能省
    show_section(state, ui, &mut working, &PREFAB, …);
}
```

第一版忘了这一句，结果每个实体下面都多出一个空的 "Prefab" 标题。
`Fields` 那条路没有这个问题（调用方本来就判了 `entity.physics.is_some()`），
`Custom` 段落却容易漏 —— 因为它自己会在内部再判一次"有没有数据"，
看起来像是重复。

判断依据：`show_section` 画的是**段落的框**（标题 + 右键菜单），
渲染器画的是**框里的东西**。框有没有必要出现，只有调用方知道。

### 16.7 现在的形状

| 文件 | 行数 | 职责 |
|---|---|---|
| `inspector.rs` | 1317（原 3503） | 实体的非组件字段（Name / Layer / 添加组件）、撤销与写回时序、组件结构动作 |
| `inspector_reflect.rs` | 1787 | 通用字段渲染 + spec 表（14 段全在这里登记） |
| `inspector_sections.rs` | 1403 | 7 个 `Render::Custom` 渲染器 |
| `inspector_ui.rs` | 464 | UI 段的专用渲染器 |

`show_body` 里已经没有一个组件专属的 `if` 块。想知道"某个组件的 Inspector 在哪"，
只需要在 `inspector_reflect.rs` 里搜它的 spec。
