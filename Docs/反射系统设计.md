# 反射系统设计（Reflect）

> 状态：**设计稿，未实现**。本文只描述方案与取舍，不描述现状能力。
> 现状能力见 `Docs/差距分析.md`；已落地的约束见 `Docs/决策记录.md`。
> 撰写依据：`crates/xgame-core/src/inspect.rs`、`crates/xgame-core/src/schema.rs`、
> `crates/xgame-derive/src/lib.rs`、`crates/xgame-editor/src/panels/inspector.rs`、
> `crates/xgame-core/src/{scene,component_view,scene_v2}.rs`。

---

## 1. 结论摘要

目标是让**内置组件与插件组件共用同一套枚举 / 读 / 写接口**，从而让 Inspector、MCP、Lua
不再各写一套。这件事在 Rust 里不需要 UE 的 UHT —— proc macro 直接拿到 AST，
`#[derive(...)]` 就是 UHT 的等价物且更可靠。

需要补的只有三样：**递归的值模型、嵌套类型的元数据、统一的路径寻址**。
磁盘格式、运行时热路径、`Inspect` / `FieldValues` 都不动。

**明确不做**：不把 `Entity` 的具名字段换成统一容器（见 §10.2）。

---

## 2. 问题陈述

### 2.1 现状：两套编辑路径，一份存储

| 组件种类 | 存储 | 字段元数据 | 编辑器怎么画 |
|---|---|---|---|
| 内置（10 种） | `Entity` 具名字段 | **无** | `inspector.rs` 手写 12 个 `section_bar` |
| Rust 插件组件 | `behaviors` + `behavior_params` | `FieldDesc` 静态表 | 通用循环 |
| Lua 脚本 | `scripts` | 无（只有路径） | 路径行列表 |

`grep "impl Inspect for"` 全仓只有两个实现（`inspect.rs` 的 `Handwritten`、
`world.rs` 的 `Tunable`），**没有一个内置组件实现 `Inspect`**。所以"统一"目前只统一到
`component_view.rs` 的 `AttachedComponent`（存在性 + 名字 + 参数），没有统一到字段读写。

### 2.2 为什么 `Inspect` 扩不动

`FieldValue` 只有 10 个扁平标量变体（`inspect.rs:143-155`）：

```rust
pub enum FieldValue { F32, F64, I32, I64, U32, Bool, String, Vec2, Vec3, Vec4 }
```

而内置组件的字段形态远超它：

| 组件 | 超出表现力的字段 |
|---|---|
| `PhysicsBody` | `shape: CollisionShape`（带载荷枚举，5 个变体各带尺寸） |
| `Animator` | `machine: Option<AnimMachine>`（内含 `BTreeMap<String,f32>` + 两个 `Vec`） |
| `ParticleEmitter` | `lifetime/speed: [f32;2]`、`gravity: [f32;3]`、`start_color: [f32;4]`、`shape: EmissionShape`（带载荷枚举）、`seed: u64` |
| `UiElement` | `style: UiStyle`、`text: UiTextStyle`、`image: Option<UiImageStyle>` |
| `LodGroup` | `levels: Vec<LodLevel>` |

并且 `FieldKind` **没有 `U64`**（`seed: u64` 无法表达），`FieldValue` 也没有数组/Map/嵌套。

### 2.3 为什么不能直接给 `FieldValue` 加变体

`FieldValue` 是 `ComponentData::Rust { fields: Option<StrictFieldValues> }` 的**落盘格式**，
`inspect.rs:145` 明写"变体名是**磁盘格式的一部分**——重命名会破坏已有场景文件"。

如果为了反射去扩它（加 `U64` / `Struct` / `List`），等于让**编辑器的一个显示需求**
去改**场景文件契约**。这条耦合必须断开。

---

## 3. 为什么不需要 UHT

UHT 的存在理由只有一个：C++ 没有语言内反射，只能造一个外部工具去读**头文件文本**。
它的代价是可见的 —— `.generated.h` 必须是最后一个 include、`GENERATED_BODY()` 必须在类体
最前面、UHT 自带一套 lexer/parser 且解析失败就是构建失败。

Rust 的 proc macro 拿到的是**已解析的 AST**，且：
- 不需要"约定 include 顺序"（生成代码走 `::xgame::...` 完全限定路径）
- 不会出现"工具看不懂某个语法"
- 属性（`#[reflect(...)]`）由编译器解析后交给宏，不用自己解析字符串

所以工作量不在"造解析器"，而在**元数据模型的设计**和**每个类型的元数据覆盖**。

---

## 4. 非目标

1. **不改磁盘格式**。反射不参与落盘（§7.1）。
2. **不进热路径**。反射是字符串路径 + 动态分发，只能服务编辑器 / MCP / Lua 等慢路径。
3. **不替换 `Inspect`**。它继续服务插件组件的 `behavior_params` 落盘（§5.6）。
4. **不追求"反射出完美 UI"**。见 §9。
5. **不做函数反射**（`UFUNCTION` 等价物）。脚本侧已有 `GameCtx` + `script_api` 清单，
   把它收敛成宏生成是另一条线，且会动脚本沙箱约定，不在本期。

## 5. 设计

### 5.1 四层结构

```
元数据层（编译期常量）   TypeMeta / FieldMeta / TypeRef        ← derive 生成
        ↓
访问层（借用）           Reflect::get / get_mut → ValueRef<'a>  ← 不拷贝、不分配
        ↓
路径层（运行期）         get_path / set_path                    ← "machine.states[0].name"
        ↓
消费层                   Inspector · MCP · Lua · --check        ← 只走慢路径
```

磁盘层（`ComponentData` / `FieldValues`）**独立在右侧，不经过这四层**。

### 5.2 元数据模型

```rust
/// 一个类型的完整元数据。全部 `'static`，编译期常量。
pub struct TypeMeta {
    pub name: &'static str,
    pub doc: &'static str,
    pub kind: MetaKind,                    // Struct / Enum
    pub fields: &'static [FieldMeta],      // Struct 用
    pub variants: &'static [VariantMeta],  // Enum 用
}

pub struct FieldMeta {
    pub name: &'static str,                // 寻址名（字段名）
    pub label: Option<&'static str>,       // 显示名（改它不动寻址）
    pub ty: TypeRef,
    pub range: Option<(f32, f32)>,
    pub speed: Option<f32>,
    pub step: Option<f32>,
    pub unit: Option<&'static str>,
    pub doc: &'static str,
    pub flags: FieldFlags,                 // HIDDEN / READ_ONLY / MULTILINE
}

/// 类型引用。递归指向另一个 `TypeMeta`，或标量。
pub enum TypeRef {
    Scalar(ScalarKind),                    // F32..U64 / Bool / String / Vec2..Vec4
    Struct(&'static TypeMeta),
    Enum(&'static TypeMeta),
    List(&'static TypeRef),
    Array(&'static TypeRef, usize),        // 定长 [T; N]
    Map(&'static TypeRef, &'static TypeRef),
    Option(&'static TypeRef),
}

pub struct VariantMeta {
    pub name: &'static str,
    pub doc: &'static str,
    pub payload: Option<TypeRef>,          // 带载荷变体
}
```

`ScalarKind` 相对现有 `FieldKind` **新增 `U64`**（`ParticleEmitter.seed` 需要）。
这不动磁盘 —— 它是独立类型（§5.6）。

**静态性怎么保证**：derive 为每个类型生成

```rust
impl ReflectMeta for Camera {
    fn meta() -> &'static TypeMeta {
        static META: TypeMeta = TypeMeta { /* 全 const */ };
        &META
    }
}
```

字段的 `TypeRef::Struct(T::meta())` 要求 `T::meta()` 可在 const 上下文调用 ——
所以元数据表用 `&'static TypeMeta` 而不是 `fn() -> &'static TypeMeta`。
**前提是类型图不递归**；已核实 `Animator` / `AnimMachine` / `AnimLayer` 之间无回指
（`animation.rs:109-119`、`:243-255`），`AnimLayer` 不回指 `AnimMachine`。
若将来出现递归，需退回 `fn()` 间接（届时再定）。

### 5.3 访问模型：借用，不拷贝

```rust
pub trait Reflect: Any {
    fn meta(&self) -> &'static TypeMeta;
    fn get(&self, field: &str) -> Option<ValueRef<'_>>;
    fn get_mut(&mut self, field: &str) -> Option<ValueRefMut<'_>>;
}

pub enum ValueRef<'a> {
    F32(&'a f32), F64(&'a f64), I32(&'a i32), I64(&'a i64), U32(&'a u32), U64(&'a u64),
    Bool(&'a bool), Str(&'a str), Vec2(&'a Vec2), Vec3(&'a Vec3), Vec4(&'a Vec4),
    Struct(&'a dyn Reflect),
    List(&'a dyn ReflectList),
    Map(&'a dyn ReflectMap),
    Enum(&'a dyn ReflectEnum),
    None,                                   // Option::None
}

pub trait ReflectList {
    fn len(&self) -> usize;
    fn get(&self, index: usize) -> Option<ValueRef<'_>>;
    fn get_mut(&mut self, index: usize) -> Option<ValueRefMut<'_>>;
    /// 增删：返回是否成功（越界 / 不支持时为 false）
    fn insert_default(&mut self, index: usize) -> bool;
    fn remove(&mut self, index: usize) -> bool;
}

pub trait ReflectEnum {
    fn variant(&self) -> &'static str;
    fn variant_mut(&mut self, name: &str) -> bool;   // 切变体（载荷重置为默认）
    fn payload(&self) -> Option<ValueRef<'_>>;
    fn payload_mut(&mut self) -> Option<ValueRefMut<'_>>;
}
```

**为什么借用而不是返回 `Value` 树**：Inspector 每帧都要读一批字段。如果读一次就分配一棵
`Value` 树，一个 `Animator` 展开后可能几百次分配 —— 与 `alloc_steady_state` 的纪律冲突
（虽然编辑器不在那条测试里，但没有理由自找）。借用式读是零分配的。

代价：`ValueRefMut` 只能一个一个拿（不能同时持有两个 `&mut`），且它的生命周期绑在
`&mut dyn Reflect` 上。Inspector 的实际用法是"读全部 → 画 → 改一个 → 重新读全部"，
不违反这个约束。

### 5.4 路径层

语法取 JSON Pointer 的**子集**（不用 `~0`/`~1` 转义，字段名不含 `.` 与 `[`）：

```
"clip"                       顶层字段
"machine.entry"              嵌套字段
"machine.states[0].name"     列表元素
"machine.parameters"         Map（整体）
```

MCP 的 `component_edit` 已经在用 JSON Pointer 语义（`patch_existing_field` 要求指向已有字段），
所以这一层可以直接复用同一套语义，不必新发明。

```rust
pub fn get_path<'a>(root: &'a dyn Reflect, path: &str) -> Result<ValueRef<'a>, ReflectError>;
pub fn set_scalar(root: &mut dyn Reflect, path: &str, v: ScalarValue) -> Result<(), ReflectError>;
// set_scalar 只写标量；结构改动（切变体 / 增删元素）走 ReflectEnum / ReflectList 的专用方法
```

**只允许写标量**是有意的：`set_path` 能写任意结构就等于"用字符串重建类型"，会绕开
所有类型检查。结构改动必须通过 `ReflectEnum::variant_mut` / `ReflectList::insert_default`
这类有明确语义的方法。

### 5.5 derive 契约

`#[derive(Reflect)]` 支持：

| 字段形态 | 处理 |
|---|---|
| 标量（f32…u64 / bool / String / Vec2..4） | `TypeRef::Scalar` |
| `Option<T>`（T 可反射） | `TypeRef::Option` |
| `Vec<T>`（T 可反射） | `TypeRef::List` |
| `[T; N]`（N ≤ 4 且 T = f32） | 映射到 `Vec2/Vec3/Vec4`（与现有 UI 一致） |
| 嵌套 struct（同 crate 或字段 `pub`） | `TypeRef::Struct` |
| 无载荷 enum | `TypeRef::Enum`（只能切变体） |
| 带载荷 enum | **拒绝**，要求手写 impl |

属性：`#[reflect(skip)]`（不出现）、`#[reflect(label = "...")]`、
`#[reflect(range = 0.0..=1.0)]`、`#[reflect(speed = 0.01)]`、`#[reflect(read_only)]`。

**拒绝编译**（给出明确错误而不是静默跳过）：泛型类型、元组结构体、`&'a T` 借用字段、
`HashMap`（无序）、带载荷 enum。理由与 `#[derive(Inspect)]` 现有做法一致 ——
`xgame-derive` 已经会因为"不支持元组结构体"直接报错（`derive/src/lib.rs:317`）。

### 5.6 与 `Inspect` / `FieldValues` 的关系

**两个 trait 共存，职责分开**：

| | `Inspect`（现有） | `Reflect`（新增） |
|---|---|---|
| 目的 | 插件组件参数**落盘** | 任意组件**编辑与查询** |
| 值类型 | `FieldValue`（磁盘契约） | `ValueRef`（借用，不落盘） |
| 表达能力 | 扁平标量 | 递归 + 集合 + 枚举 |
| 覆盖 | 插件组件 | 插件组件 + 内置组件 |

`Reflect` **不复用 `FieldValue`**，理由就是 §2.3：`FieldValue` 的变体名进了场景文件，
扩它就是改契约。反射自己一套值类型，磁盘一个字节都不用动。

`Behavior` trait 的约束不变（仍要求 `Inspect`），因为 `behavior_params` 仍要落盘。
将来若要支持"插件组件带嵌套参数"，那是一次**独立的磁盘格式变更**，需单独决策。

## 6. 表达力边界（诚实清单）

| 边界 | 影响 | 处理 |
|---|---|---|
| 带载荷枚举（`CollisionShape`、`EmissionShape`） | derive 覆盖不到 | 手写 impl（每个约 60-100 行） |
| `BTreeMap<String, f32>`（`AnimMachine.parameters`） | derive 可支持 Map，但 UI 表达是键值表 | S3 再决定；S1/S2 可先 `#[reflect(skip)]` |
| `u64`（`ParticleEmitter.seed`） | 现有 `FieldKind` 无 U64 | `ScalarKind` 新增 U64（不动磁盘） |
| 泛型类型 | derive 无法生成 | 不支持；现有组件无泛型，暂不受影响 |
| 跨 crate 私有字段 | derive 在定义模块展开，可访问私有；跨 crate 字段需 `pub` | 内置组件都在 `xgame-core`，不受影响 |
| 递归类型图 | `&'static TypeMeta` 会无限展开 | 已核实当前无递归；出现时改 `fn()` 间接 |
| 同时两个 `&mut` | 借用式访问不支持 | 现有用法（读全部→改一个→重读）不受影响 |

## 7. 三个关键取舍

### 7.1 反射不参与落盘

**取舍**：`Reflect` 只服务编辑与查询，不参与 `SceneV2` 的编解码。

**理由**：磁盘格式已经被 `ComponentData`（内置）+ `FieldValues`（插件）定义清楚，且
`deny_unknown_fields` + `serde_ignored` 两道闸门在保护它。让反射去碰落盘，就要么改
`FieldValue`（改契约），要么引入"反射驱动的序列化"（需要类型注册表 + 跨版本兼容）。
两者风险都远大于收益。

**代价**：内置组件的磁盘形状与反射形状可能不一致（例如 `MaterialData { asset, overrides }`
在磁盘是一个组件，在 `Entity` 是两个字段）。这个不一致**已经存在**（§2.1），反射不解决它，
也不加剧它。

### 7.2 借用而非拷贝

见 §5.3。核心是"读字段不分配"。

### 7.3 慢路径隔离

**取舍**：反射 API 只允许出现在编辑器、MCP、`--check`、Lua 的字段访问里。

**理由**：字符串比较 + 动态分发。`Entity` 的 10 个槽位之所以是字段，就是为了热路径零成本
（`pull_dynamic_bodies` 每帧 O(n)）。如果运行时系统改用 `get_path("physics.mass")`，
每帧几千次字符串比较，性能会直接崩。

**约束**：`Reflect` 不进入 `xgame-runtime` 的任何每帧函数。这条要写进决策记录。

## 8. 分期与验收

### S1 — Camera + AudioSource（垂直切片）

范围：`TypeMeta` / `Reflect` / `ValueRef` / `get_path` / `set_scalar` 全部落地；
`#[derive(Reflect)]` 支持标量 + `Option<标量>`；`Camera`、`AudioSource` 接入；
Inspector 新增"反射通道"但**默认关闭**，靠一个开关与手写 section 并存。

验收：
- `crates/xgame-core` 新增测试：`Camera` 全字段 `get_path` 读 → `set_scalar` 写 → 值相等；
  越界路径返回 `ReflectError` 而不是 panic。
- `crates/xgame-derive` 新增测试：拒绝元组结构体 / 带载荷 enum 的编译失败消息。
- Inspector：`--ui-shot --ui-select` 在带 Camera 的实体上截图，反射通道与手写 section
  **逐像素一致**（用 `.workbuddy/tools/rowscan.py` 量分段）。
- `cargo clippy --workspace --all-targets` 0 警告；`alloc_steady_state` 仍通过。

**S1 的意义**：证明"derive → 元数据 → 借用访问 → 路径 → UI"整条链路成立，且不动磁盘。

### S2 — 带载荷枚举 + 列表

`PhysicsBody`（含 `CollisionShape`）、`CharacterController`、`LodGroup`（`Vec<LodLevel>`）。
需要 `ReflectEnum` 与 `ReflectList` 落地，以及 `CollisionShape` 的手写 impl。

验收：Inspector 的 Physics / Character / LOD 三个手写 section 被反射通道替换，
截图一致；`CollisionShape` 的 5 个变体都能切换且载荷正确重置。

### S3 — 嵌套结构与数组

`ParticleEmitter`（`[f32;2..4]` + `EmissionShape`）、`UiElement`（三个嵌套样式结构）。

### S4 — Animator（建议不做通用反射）

`AnimMachine` 是"状态 + 转移 + 参数"的图，反射画出来是一堆表格，不如现有专用编辑器。
**建议保留专用 section，只把标量字段（`clip` / `speed` / `fade_time`）接入反射。**

### 不在分期里

- 函数反射 / `#[xgame_fn]`
- 插件组件的嵌套参数落盘
- 统一存储容器

## 9. 风险与反例

1. **"反射就等于统一 UI"是错觉。** UE 的 Details 面板背后是 `meta=(ClampMin, EditCondition,
   DisplayName)` 加大量 `IDetailCustomization` 手写定制。反射给的是**能用**的通用 UI，
   不是**好用**的。`Animator`、`UiElement` 大概永远需要专用编辑器。
2. **derived UI 的回归风险高。** 手写 section 有大量对齐/宽度细节（`theme::axis_field_width`
   必须在放控件前取一次、`add_sized` 只保证最小尺寸）。反射通道如果自己排版，很可能
   在 1280 窗口下溢出。S1 的"逐像素一致"验收就是防这个。
3. **元数据会漂移。** 手写元数据表与真实字段不同步，是这个模式最大的长期病。缓解手段
   与 `schema.rs` 一致：derive 生成而不是手写，且 `FieldMeta.name` 用 `stringify!(字段名)`，
   字段改名后不同步会编译失败。
4. **`Reflect` 与 `Inspect` 双轨并行，可能长期共存。** 如果最终只做到 S2 就停，
   会留下"内置组件走 Reflect、插件组件走 Inspect"的新不一致 —— 比现在还多一套。
   **这条是本期最大的战略风险**：要么做完 S3，要么别开始。

## 10. 备选方案

### 10.1 扩 `FieldValue`（否）

给 `FieldValue` 加 `U64` / `Struct` / `List`。看起来最省事，但它会改磁盘契约（§2.3），
且让"编辑器显示"与"场景文件格式"永久耦合。

### 10.2 把 `Entity` 的槽位换成统一容器（否）

`Entity { components: Vec<ComponentInstance> }`，内置与插件走同一容器。这就是 UE / Unity
的形态，也是**唯一能让反射变成唯一入口**的方案。

不选的理由（每条都有代码依据）：

| 代价 | 依据 |
|---|---|
| 约 1100 处直接字段访问要改写 | `transform` 369 / `animator` 166 / `ui` 140 / `physics` 136 / … |
| `serde` 失去编译期类型集 | `ComponentMap` 键是 `TypeId`，不可序列化，故 `#[serde(skip)]`（`scene.rs:201`） |
| `Clone` 需 `dyn_clone` | `ComponentMap::clone` 返回空表（`component.rs:147`），而 undo / Play 快照靠 `Scene::clone` |
| `Transform` 丢掉"必存在" | 它是唯一非 `Option` 组件字段，369 处访问无一处 `unwrap` |
| 脏检查失去编译期强制 | `impl PartialEq for Entity` 穷尽解构（`scene.rs:421`） |

> **判断**：等到内置组件数量从 10 涨到 30+，或者需要"内置组件运行时插拔"，这套交换
> 才划算。现在做是净亏。

### 10.3 只做"浅层标量视图"（部分采纳）

不建完整 `Reflect`，只给每个内置组件一个 `flat_fields(&Entity) -> Vec<(&str, ScalarRef)>`，
覆盖常见旋钮（mass / friction / fov / volume），嵌套部分保留专用编辑器。

- 优点：工作量约为完整方案的 1/3，能立刻消掉一半手写 section。
- 缺点：`Animator` / `CollisionShape` / `UiElement` 拿不到统一，且没有路径寻址，
  MCP 仍然只能按顶层字段改。
- 定位：**如果 S1 发现 derive 在真实字段形态上不成立，这是退路**。

### 12.2 实现中发现的三处与设计稿不符（已按实现修正）

**① `TypeRef::Struct` + `TypeRef::Enum` 合并成 `TypeRef::Named`。**
derive 只看得到字段的**类型名**，看不到目标类型的定义，所以它在生成元数据时
无法判断 `AudioBus` 是结构体还是枚举 —— 初版一律猜 `Struct`，测试
`nested_type_reference_points_at_target_meta` 当场抓到了。现在只记"指向哪个类型"，
结构体 / 枚举由目标 `TypeMeta.kind` 回答。**不猜比猜错好。**

**② 元数据从 `const` 改成 `OnceLock` 惰性构建。**
原设计想用 `static META: TypeMeta = …` 全静态。但嵌套引用要拿到 `&'static TypeRef`，
而 `Box::leak` 是运行期调用，不能出现在 `const` / `static` 初始化里；若改成
`<T as ReflectMeta>::META` 关联常量，递归类型图会让编译器无限展开。
现状：每种类型第一次访问时构建一次，`Box::leak` 一次（进程内总量与类型数同阶）。
代价可接受，换来 `TypeRef` 不必是常量表达式。

**③ `Reflect::meta(&self)` 改名 `type_meta(&self)`。**
`ReflectMeta::meta()` 是关联函数，两者同名会让 `Camera::meta()` 这种最常用写法
报 E0034（多个候选）。改名后 `Camera::meta()` 唯一指向静态元数据。

### 13.2 元数据补了五项，每一项都有真实消费者

手写段里有几处排版是"S1 的元数据表达不了"的，实测下来共五项：

| 新选项 | 谁在用（S1 内的真实用例） | 为什么必须进元数据 |
|---|---|---|
| `decimals = 1` | `fov` / `near`(3) / `far` | 不固定位数时 `60` 与 `0.100` 同列，拖动时文字宽度在跳 |
| `note = "米"` | `near` / `far` / `fov` / `pitch` / 距离组 | 控件**之后**那截说明是排版文案，与机器可读的 `unit` 是两件事 |
| `hint = "..."` | `clip` | 空路径时要有个示例，否则用户不知道写什么 |
| `visible_when = "spatial"` | `min_distance` / `max_distance` | 条件显示。`derive` 会校验目标字段存在且是 `bool` |
| `row_group = "distance"` | 上面两个 | 成对区间画一行。只合并**连续**同组字段 |

另外给 `VariantMeta` 补了 `label`：寻址名是 Rust 标识符（`Sfx`），界面显示的是
`AudioBus::name()` 的小写（`sfx`）。两者不能合并 —— 改显示名不该动寻址名。

### 13.3 一个绕不过去的前提：声明顺序必须等于界面顺序

反射按 `meta.fields` 的声明顺序排版，而 `AudioSource` 的 `bus` 是**最后加进来的字段**，
声明在末尾、界面排第三。两条路：加一个 `order = 2` 排序号，或者把字段挪过去。

选后者，理由是 `bus` 的末尾位置本来就是历史顺序而不是设计顺序；挪过去之后元数据
少一个字段，且"数据模型的阅读顺序"与"界面的阅读顺序"重新一致。代价是
`bus` 非默认（`Bgm` / `Voice`）的场景文件里那个字段的**行序**会变 —— 名字寻址
不受影响，老文件照常加载。`reflect` 模块的字段顺序测试已同步。

### 13.4 验收：逐像素一致

对比工程：`%TEMP%/xg-reflect-probe`（XGame 的副本，只有一张 `Scenes/probe.ron`，
里面两个实体各挂 Camera + Audio，一个 `spatial = true` 一个 `false`）。

```bash
# 手写通道
xgame-editor <probe> --ui-shot hand.png    --ui-select "Probe Spatial" --ui-size 1600x1200
# 反射通道
xgame-editor <probe> --ui-shot reflect.png --ui-select "Probe Spatial" --ui-size 1600x1200 --ui-reflect-inspector

python .workbuddy/tools/pngdiff.py hand.png reflect.png --rect 2190,80,2800,1120
```

结果（Inspector 整列，`spatial` 开 / 关各一对）：

| 用例 | 区域像素 | 差异 |
|---|---|---|
| `Probe Spatial`（距离区间可见） | 634,400 | **0** |
| `Probe Plain`（距离区间隐藏） | 634,400 | **0** |

反向自检：同一份工具比对控制台区（时间戳 / fps 每帧都变）报出 8.77% 差异 ——
说明"0 差异"不是因为工具坏了。

整图比对不成立的原因写在这里备查：控制台有时间戳、状态栏有 fps、Draws 计数，
这些每帧都在变，所以只能比 Inspector 那一列。

### 13.5 行为差异（有意保留的三条）

1. **每个字段都有悬浮说明**。手写段只给少数几个控件挂了 hover，现在把 `doc`
   统统当提示用（UE 的 Details 也是这样）。为了不丢文案，`active` / `looping` /
   `autoplay` / `spatial` 的注释扩写成了原来 hover 里那句话。
2. **`normalize` 在任意字段改动后都跑**，不只在那两个相关字段上。于是"改 Volume
   顺手把坏掉的 `max ≤ min` 修好"也会发生。不变式成立比"只动我碰的那一格"重要。
3. **钳制晚一帧**。手写在改 `near` 的那一帧里当场把 `far` 顶上去；反射通道先把
   所有行画完再 `normalize`，所以修正后的 `far` 在下一帧才显示。肉眼无差别。
