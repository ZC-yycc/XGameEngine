> 的实际盘点（grep 粒子 / LOD / 寻路 / 网络 / watcher / CI 全部为空、ROADMAP 逐条核对）。
> 盘点日期 **2026-10-12**；状态随实施进度更新。
>
> 可视化版（同内容）：`.workbuddy/artifacts/engine-gap-analysis.html`（git 外，浏览器打开）。

**总评**：基础设施层（运行时 / 帧调度 / 性能纪律 / 交互手感）已经达到甚至超过不少开源引擎的
水准 —— 真正的差距集中在三处：**游戏内容层**（动画前五片已落地：骨骼蒙皮 + 单剪辑播放 +
换剪辑交叉淡入 + 阈值状态机 + 单层叠加混合 + 多层混合栈与骨骼遮罩，音频/粒子/游戏 UI 仍缺）、**资产管线**（路径引用 + 无导入管线 —— 项目一大就是数据债）和
**编辑器产品化**（Preferences / 布局持久化仍缺失，Project Settings 与未保存保护本轮已补）。
渲染是"落后一代"而非"缺失"（Blinn-Phong 对 PBR）。建议顺序：内容层优先、资产管线尽早、
渲染追平观感、架构重构（ECS）放在规模真正到来之前；编辑器产品化与 **Agent-Native**
（见文末战略章）穿插推进。

## 推荐路线（排序即理由）

**P0 —— 做不出游戏的硬缺口、丢数据风险，或越晚改越贵的债：**
~~先动画（骨骼蒙皮 + glTF clip 加载）~~（✅ 2026-10-12 第一片已落地：蒙皮 + 单剪辑播放；
2026-10-13 第二片：换剪辑交叉淡入；第三片：阈值状态机；第四片：单层叠加混合；
第五片：多层混合栈 + 骨骼遮罩；morph target / 分层状态机是后续片）；音频成本最低、
感知最强，kira 集成 + AudioSource + 3D 声即可起步；~~项目设置 UI / 未保存保护~~
（✅ 2026-10-12 已落地，见上表）；资产 GUID / 导入管线必须在项目变大之前做 ——
引用格式是数据债，改晚了等于重写全部场景。

**P1 —— 能产出完整 demo 的差距：**
PBR + IBL（观感一整代的差距，glTF 本就带 metallic-roughness 数据，换的是 BRDF 与环境光）
→ 后处理链（先 RenderGraph 骨架，再 Bloom / ACES / FXAA）→ 实例化 + LOD（规模上限）
→ 编辑器 Profiler 面板（frame_probe 的数据面已经现成，缺的只是 UI）
→ CI（半小时工作量，267 个测试从此不再靠手动）→ Preferences / 布局持久化（编辑器
产品化第二波）。

**P2 / P3 —— 规模化与长期：**
ECS / 任务系统重构（rapier 瓶颈已实测，万级实体前要动）、跨平台打包验证、可视化 shader、
寻路、网络。多人是最贵的一类功能，放最后。

## 已经做对了的地方（别在重构里弄丢）

- 编辑器 Play 与独立游戏共用同一段 `World::update` —— 多数自制引擎在这里分叉成两套运行时，
  最后行为不一致（项目设置同样是单入口 `WorldConfig::from_project_runtime`）
- 帧调度纪律：frame_policy 停帧 + AutoNoVsync 上屏 + frame_probe 探针，输入→光子延迟已实测
  压到 ~20ms
- 稳态性能有量化：2000 实体下引擎自身 13µs/帧（纯视觉），热路径零分配
- Prefab 带 Apply / Revert 与来源追踪 —— Unity 级特性，同类自制引擎很少做到
- 交互细节扎实：Undo 快照分步、Gizmo 参考线锚定防抽搐、层级拖拽防环
- 脚本系统有工程化：编译缓存 + 热重载 + 崩溃 / 死循环隔离，不拖垮引擎
- 测试纪律：267 个回归测试，且坚持每条测试先证明旧实现下会红
- 数据即文本：场景 / 预制体 / 清单 / 输入映射全是 RON 纯文本 —— 版本控制友好，
  同时是下面 Agent-Native 路线的地基

## 战略方向：Agent-Native —— 让 AI 智能体深度操控引擎

> **目标**：用户的 AI 智能体（Cursor / Claude / 任意支持 MCP 的客户端）能够**深度、精确、
> 可验证地**操作本引擎做游戏开发 —— 不是"截图点按钮"，而是像人类开发者一样读写项目、
> 运行检查、拿到可机读的结果。
>
> **架构判决式**：往后的架构决策都要过一问 —— **「智能体没有鼠标时，这条路走得通吗？」**

### 支柱与现状

| # | 支柱 | 状态 | 说明 |
|---|---|---|---|
| 1 | **数据即文本** | ✅ 已具备 | 场景 / 预制体 / 清单 / 输入映射全是 RON 纯文本、稳定 ID、serde 向后兼容 —— 智能体可直接读写、diff、批量改，无需 GUI |
| 2 | **程序化验证入口** | ✅ 本轮落地 | `xgame-editor --check <项目>`：无头加载清单 + 场景 + 校验引用，**退出码契约 0=干净 / 1=加载失败 / 2=悬空引用**，秒级返回、可进 CI |
| 3 | **程序化配置** | ✅ 本轮落地 | 重力 / 步长进 `project.ron` `runtime` 节（含容错夹取）—— 智能体调参数 = 改一行文本，而非改引擎源码 |
| 4 | **脚本 API 契约** | 🟨 进行中 | `Docs/脚本API.md` 是对脚本（含智能体生成脚本）的 API 面；Lua 覆盖变换 / 实体增删 / 物理 / 输入 / 时间 / 日志 |
| 5 | **无头运行 / 采集** | ⬜ 规划 | `--headless` 跑 N 帧输出统计（实体数、帧耗时、物理状态）—— 智能体"改完看效果"的闭环 |
| 6 | **MCP 工具接口** | ✅ 本轮落地 | 新 crate `xgame-mcp`（`dist\xgame-mcp.exe`）：stdio 按行 JSON-RPC，6 个工具 `project_info` / `scene_read` / `scene_write` / `entity_upsert` / `entity_remove` / `project_check`，任何 MCP 客户端直接驱动引擎读写场景、动实体、跑验证（工具参考 [`MCP.md`](MCP.md)）；构建 / 无头运行工具随后续支柱补 |
| 7 | **机器可读 API 描述** | ⬜ 规划 | 导出场景 schema 与脚本 API 清单（JSON），智能体不靠猜字段名 |
| 8 | **可验证性纪律** | ✅ 已具备 | 267 个回归测试、每条先证红 —— 智能体改引擎代码后有安全网兜底 |

### 为什么这条路线对本引擎成立

1. **纯文本数据**（支柱 1）是前提 —— Unity 的 YAML + GUID 混合体反而难智能体友好地整段改写；
   我们的 RON 场景人类可读、结构扁平。
2. **单一运行时**（编辑器 Play == 游戏二进制）意味着智能体在无头环境验证的行为
   与玩家实际跑的完全一致 —— 不存在"编辑器里对、打包后坏"。
3. **小而清晰的 crate 边界**（core / runtime / physics / script / editor）让 MCP 工具能
   直接调库，而不是模拟 UI 输入。
4. 已落地的 `--check` 证明了闭环模式：**改 → 一条命令 → 退出码**。后续每个能力都按
   同样模式给无头等价物。

### 近期计划（按序）

1. ✅ **MCP server 最小工具集（本轮落地）**：`project_info` / `scene_read` /
   `scene_write` / `entity_upsert` / `entity_remove` / `project_check` —— "读改查验"
   闭环已通，配 20 条回归测试与工具参考 [`MCP.md`](MCP.md)。
   （原计划里的 `project_build` 与 `entity_remove` 对调：删除是写路径刚需，
   构建依赖打包编排，归入后续批次。）
2. **无头运行**：`--headless --frames N --dump-report`（帧耗时 / 实体 / 物理统计 JSON）。
3. **场景 schema 导出**：`--export-schema`，字段、类型、默认值一次导出。
4. 每步配回归测试 + 文档（`Docs/`），沿用"先证红"纪律。
