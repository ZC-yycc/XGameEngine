## 2026-10-28 预制体 ID 的跨文件诊断（101 关闭）

101 之前卡在"预制体 `source_id` 与场景 ID 算不算冲突"。结论是这根本不是冲突，
而是两个作用域：ID 只在**单个文件内**唯一，跨文件唯一的是 `(source, source_id)`。
于是真正缺的检查有两个：

- **预制体文件内的重复 ID**：场景那份能在加载边界静默重分配（同文件 `parent`
  引用），预制体的**不能** —— 它被场景的 `source_id` 跨文件引用，重分配会让所有
  既有实例失配、`Apply` 时整棵树被当成新增。所以只报告（`duplicate prefab id:`）。
- **`source_id` 悬空**：场景里指向预制体里不存在的实体（预制体被编辑过 / 手改 ID）。
  按 `(场景, 预制体)` 聚合成一条（`dangling source:`），进 `has_issues()`。

顺带发现并修掉一个自找的问题：新文案原先写成中文，而 `render()` 的契约是纯 ASCII
（控制台代码页不是 UTF-8 时乱码，而 CI 读的就是这行文本）。

证据：2 条旧行为红灯实跑（临时把 `push` 换成 `let _ =` → `2 failed`，其余 14 条
check 测试全绿）；真实 CLI 正负对照（注入 `source_id: (9999)` → 报 `missing 1
source_id(s) (first: StaleInstance -> id 9999)`、退出码 2；改成 `(1)` 后该行消失）。
全量 **956 passed / 0 failed / 9 ignored**，clippy 0 告警。见 PLAN 第七十三节，
契约见决策记录 §五十三。

## 2026-10-28 三个 G0 数值 / 交互边界（041 / 101 / 067）

三处"有缺陷也不报错、只是行为悄悄不对"的边界：

- **极小碰撞体质量（041）**：半径 1e-20 的球体积在 f32 下溢出成 0，密度变 inf，rapier
  算出的实际质量是 0 —— 声明 2.5 kg 的实体变 0 kg。现在密度不可表达时退回刚体附加质量，
  两条路径相加恒为声明值。
- **极值实体 ID（101）**：文件里写 `u64::MAX` 会把计数器顶到天花板，下一次 `new()`
  返回同一值（两个实体共用 ID → 删除连坐）。现在读盘直接拒绝，错误信息带原值与上限；
  `new()` 改 CAS 跳过 0。
- **视口外松手（067，已关闭）**：`UiPointer` 的"位置"与"按键"已解耦，"按下 → 移出
  视口 → 松手"当帧收尾（此前 `Release` 事件丢失、捕获残留到指针回到视口）。同时补测
  隐藏父节点的子元素不参与命中，以及"脚本改的 UI 矩形迟一帧生效"的时序契约（错序
  实跑红灯）。

3 条旧实现红灯均实跑（质量 0 / 解析成功 / 捕获残留），改后全绿；全量
**954 passed / 0 failed / 9 ignored**（`--all-targets`），clippy 0 警告。证据见 PLAN
第七十二节，契约见决策记录 §五十二。当时剩下的 101 跨文件诊断随后由本文件上方
那段关闭（PLAN 第七十三节）；G0 其余条目仍未整体关闭。

## 2026-10-28 CUBICSPLINE 三次样条采样（R04 / 032 关闭）

动画动作的加减速终于不再被抹平：`CUBICSPLINE` 的每帧 `(入切线, 值, 出切线)` 三份
原样保留，采样端走 Hermite（切线按"每秒"乘段长，旋转结果归一化，长度退化时退回
slerp）。此前读入即降级成线性，而 Blender / Maya 默认导出就是三次样条 —— 等于大多
数资产被静默拍平且不可逆。旧实现三条红灯实跑（段中点 0.5 应为 0.75、2 秒段 0.5 应为
1.0、morph 只剩 6 个值应为 18 个），改后全绿；全量 945 passed / 0 failed / 9 ignored。
新增采样成本基准显示样条为线性的 0.80×（`Quat::slerp` 比 Hermite+normalize 贵），
即保真在本实现下不付额外成本。证据见 PLAN 第七十一节，契约见决策记录 §五十一。

剩余边界：morph 多网格仍只取第一条权重轨道（v1，与插值无关）、根运动与动画 Phase B
未做；G0 不因此关闭。

## 2026-10-27 打包拒绝旧引擎播放器（173 的第一个缺口）

`builder::locate_player` 原先只判"文件存在"，改完引擎只重编编辑器就会把旧引擎的
播放器打进成品。现在播放器二进制自带源码指纹（`xgame-src-v1:…`，不含 profile，
用 `#[used]` 锚点避免被链接器回收），打包跳过源码不一致的候选、全不一致直接拒绝
并给出重编命令；跳过时在 `BuildReport::warnings` 里写明用了哪个。真实二进制三组
对照（同批通过 / 改指纹拒绝 / 跳过旧的用新的）见 PLAN 第六十六节。

这只关闭 173 的"播放器选择新鲜度"部分：**完整发布端到端仍未接进 hosted CI**，
打包出的插件、输入、切关依旧只有本地脚本验收；也不做内容签名与篡改防护。

## 2026-10-27 写盘实现统一与遗留暂存回收

G0 保存可靠性收口：同一段"同目录独占暂存 + 同步 + 替换"原先在 core / editor / input 各一份且差错点不同，现统一到 `xgame_core::fsx`；崩溃遗留的暂存文件按**精确命名**（`.tmp.<进程号>.<序号>`）+ 600 秒阈值在后续保存成功时回收，新鲜暂存与用户自己的同类文件一律不动。回收不挂在 `ProjectHandle::open`（那是 `--check` 的入口，检查必须只读）。POSIX 追加父目录 fsync，Windows 上无此手段。release 实测回收约占一次保存 2%（82.5 µs / 4.26 ms）。全量 942 passed / 0 failed / 8 ignored，dist 刷新与两类项目冒烟通过；证据见 PLAN 第六十五节。多进程同目标保存、跨文件事务、断电目录持久性仍未解决，G0 不整体关闭。

## 2026-10-27 跨平台构建计划（待实施）

跨平台属于 **G3 平台扩展**（下方历史矩阵称 P2）；由用户明确要求纳入后续计划。当前仅 Windows/MSVC 已构建并实测，Linux、macOS、Web 均未验证，不把 wgpu/winit 的跨平台能力等同于本引擎已支持。G0 的发布可靠性工作仍按既有优先级推进；跨平台实施时一次只选择一个目标平台。

1. **Linux 桌面首站**：在真实 Linux 环境确认 Rust 工具链、图形/音频系统依赖及渲染后端；修正平台相关的打包路径、可执行文件、动态库和启动逻辑。原生运行 workspace check、clippy、test，随后运行 `--check`、`--headless`、编辑器/播放器窗口，并从同平台产出的程序和插件构建独立包，搬离源目录验输入、切关、插件与退出。遇无 GPU 环境须显式记为未验证窗口渲染，不能把测试 skip 当作通过。
2. **macOS 桌面第二站**：在真实 macOS 主机分别完成同一组原生编译、无头及窗口/发布包验收；检查 Metal、音频、插件动态库格式、包内资源路径及应用分发形式。macOS 目标需要 macOS 构建与运行环境；仅在 Windows 上交叉编译或代码审查不能宣称通过。
3. **持续集成与发布**：每个平台首轮人工实测通过后再加对应 CI 构建、测试和无头冒烟；GPU 窗口/独立包验收需具备目标平台 GPU 的环境，未接入前单列人工门禁。平台预设和跨平台一键出包要以原生构建和独立包验收为前提设计，不能靠重命名 Windows EXE 交付。
4. **Web 单独评估**：调查 wgpu/winit、文件系统、插件 cdylib、音频及 Lua 在浏览器中的实际可用边界，先明确目标与替代机制，再决定是否立项；目前不承诺 Web 构建或与桌面同功能。

完成口径按平台分别记录：实际编译、实机启动、核心流程、独立包及已接入的 CI 结果与尚未覆盖项；任何平台未经实跑均保持「计划中」。具体实施顺序及取舍见 PLAN 第六十三节。

## 八、已经做对了的地方（别在重构里弄丢）

- **编辑器 Play 与独立游戏共用同一段 `World::update`** —— 多数自制引擎在这里分叉
  成两套运行时，最后行为不一致（项目设置同样是单入口）。
- **帧调度纪律**：`frame_policy` 停帧 + `AutoNoVsync` 上屏 + `frame_probe` 探针，
  输入→光子延迟压到 ~20 ms；空闲 CPU 0.00%。
- **稳态性能有量化**：2000 实体纯视觉 13 µs/帧、热路径零分配；渲染侧实例化
  2225 → 344 µs/帧、剔除 3295 → 1146 µs/帧，全部同机背靠背量过。
- **Prefab 带 Apply / Revert 与来源追踪** —— Unity 级特性，同类自制引擎很少做到。
- **交互细节扎实**：Undo 快照分步、Gizmo 参考线锚定防抽搐、层级拖拽防环、
  拾取用射线 × 世界 AABB（不是包围球）。
- **脚本系统有工程化**：编译缓存 + 热重载 + 指令预算沙箱，崩溃 / 死循环不拖垮引擎。
- **测试纪律**：858 条回归测试，每条先证明旧实现下会红。
- **数据即文本**：场景 / 预制体 / 清单 / 输入映射全 RON —— 版本控制友好，
  也是 Agent-Native 路线的地基。
- **无头三入口**：`--check`（引用完整性）/ `--headless`（固定 dt 逐位可复现）/
  `--screenshot`（同机逐字节一致）—— "改 → 查 → 验 → 看"闭环。

## 九、战略方向：Agent-Native

> **目标**：用户的 AI 智能体（Cursor / Claude / 任意支持 MCP 的客户端）能够**深度、
> 精确、可验证地**操作本引擎做游戏开发 —— 不是"截图点按钮"，而是像人类开发者一样
> 读写项目、运行检查、拿到可机读的结果。
>
> **架构判决式**：往后的架构决策都要过一问 —— **「智能体没有鼠标时，这条路走得通吗？」**

### 为什么这条路线对本引擎成立

1. **纯文本数据**是前提 —— Unity 的 YAML + GUID 混合体反而难智能体友好地整段改写；
   我们的 RON 场景人类可读、结构扁平。
2. **单一运行时**意味着智能体在无头环境验证的行为与玩家实际跑的完全一致 ——
   不存在"编辑器里对、打包后坏"。
3. **小而清晰的 crate 边界**让 MCP 工具直接调库，而不是模拟 UI 输入。
4. `--check` 已证明闭环模式：**改 → 一条命令 → 退出码**。后续每个能力都按同样模式
   给无头等价物。
