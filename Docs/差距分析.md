# XGameEngine 差距分析（2026-10-26）

## 2026-11-08 UI 手柄 / 键盘导航（P1 #4 的"手柄导航"缺口关闭）

之前 UI 只有指针一条交互路径：`ui_*` 那套按钮没有手柄玩家能碰的入口 —— 主机式
"十字键选、南键确认"在引擎里根本不存在，菜单只能靠鼠标点。

现在有了**焦点环**（`xgame_ui::UiFocus`）：方向键 / 十字键 / 左摇杆在**按钮**之间按
几何位置移动焦点，Enter / 手柄南键确认（把 `clicked` 置一帧，与鼠标点击同款），
被聚焦的按钮上画一圈 2px 的蓝色焦点环。五条语义定死：

- **一次一帧走一格**，全部取边沿（`pressed` / `crossed_up`）—— 按住方向键不连发；
- **不回绕**：到边停在原地（Unity 默认导航同款；回绕在三格菜单里很容易误触）；
- **邻居打分 = 主方向距离 + 1.5 × 垂直偏移**：同一行 / 列优先，所以"往下"不会
  横跳到隔壁列；平手由绘制顺序决定 ⇒ 与帧率无关、可复现；
- **鼠标按下即把焦点搬过去**（Unity EventSystem 同款），这样"点一下再推方向键"
  不会从零起步；
- **候选集只有 `UiKind::Button`**：`interactable` 反序列化缺省为 `true`，于是每块
  装饰背景板都是"可交互"的，而且恰好盖住整个 HUD —— 只按 `interactable` 筛会让
  首次方向键选中背景板，之后在原地打转（第一版截图取证时正是这样：环画在整块
  HUD 面板上，而不是按钮上）。手柄能"选"的必须是能"按下去"的东西。

焦点实体一旦不可见 / 不可交互（脚本刚隐藏或删掉）就清空，下一次推方向重选 ——
不留"幽灵焦点"。与 `hovered` 是两条独立通道：指针停着的按钮不会因为手柄选中别人
而变亮，反之亦然。

无头运行也接上了：`--screenshot` 时把视口喂给 `World::set_ui_viewport`（不截图时保持
原来更便宜的路径，性能数字不受影响），于是 `--input-script` 按下的方向键能真的变成
截图里的焦点环 —— CI 可以断言 UI 状态，而不是只能靠肉眼看编辑器。

脚本侧也能动焦点（2026-11-08 第二轮）：`ui_focused` / `ui_set_focus` /
`ui_clear_focus`。焦点表在 `World` 上、脚本只能改场景字段，所以设焦点走的是
"写场景标志 + 帧末结算命令"这条既有通道（与"脚本改 UI 矩形下一帧才参与命中"
同一时序）。目标必须是可见且可交互的 Button —— 与导航准入同一条规则，否则会造出
"脚本能选中、方向键选不中"的幽灵焦点。

**仍缺**：焦点自动滚进滚动区（还没有滚动容器）、手柄 `West` = 取消 / 返回、
焦点环颜色按主题可配。契约见决策记录 §一百零一 / §一百零二，实施与红绿证据见
PLAN 一百一十四 / 一百一十五。

## 2026-11-08 控制台分级统计与资产定位（P2 #26 的最后两条）

控制台早就会给每条消息标等级、折叠重复项，但"这一局报了几次错"只能靠眼睛数，
而"模型加载失败: Resources/Models/Box.glb"这种句子里的路径是一串死文字 ——
它恰好是最该被点的那一段。

**分级统计**：四个等级开关的标签直接带上条数（`Error 20`），统计覆盖**整个缓冲区**
（不是这一屏），按**出现次数**求和（重复消息的 `×N` 一并计入）—— "报了几次"问的是
次数，不是"屏上有几行"。与筛选无关：关掉 Info 不会让总数变小。为 0 时不显示数字
（窄窗口少几个像素，也避免一排 `Info 0 Warn 0` 的噪声）。

**资产定位**：正文里的项目相对路径（`.glb/.gltf/.png/.mat/.lua/.wav/.ogg/.mp3/.ron`）
可以点，点击在 Assets 面板里选中它。三条纪律：

- **先过 `normalize_project_relative`**：越界、盘符、Windows 非法写法一律不认，
  与场景 / 资产引用同一条规则（否则一条恶意日志能把面板指到项目外面）；
- **必须真的在资产库里**：预筛只看后缀（零分配，逐行调用），真按下去才查资产库
  —— "提到了 .png"不等于"这是资产"；
- **源码优先**：带 `脚本:行` 的报错点击仍然打开源码查看器（更精确），不走资产定位。

点击时若搜索框正把目标藏起来，会先清掉搜索词 —— 否则"点了报错行却什么都没发生"。

**仍缺**：错误列表的"上一条 / 下一条"跳转、按日志时间轴过滤（"最近 1 分钟"）、
双击折叠成组的重复消息展开。契约见决策记录 §一百，实施与红绿证据见 PLAN 一百一十三。

## 2026-11-08 Gizmo 吸附（P2 #28 旁的一条编辑器缺口）

`gizmo_snap` 这个字段从 Gizmo 落地那天就在 `EditorState` 里，但**没有任何代码读它**
（`#[allow(dead_code)]` 挂着）—— 面板上没有开关，拖拽照样连续。手摆关卡时"把箱子
摆到 2.0 米整"只能靠 Inspector 里手敲，一次拖拽终究要回去改数。

现在三档步长分开配：平移 0.5 m、旋转 15°、缩放 0.25×（出厂值，Preferences 可改，
写进 `editor.ron`）。工具栏的磁铁按钮一键开关，**拖拽中按住 Ctrl 临时反选**（开着
按 = 暂时不吸，关着按 = 暂时吸）。

吸的是**绝对值**：位置与缩放逐分量吸到步长整数倍，旋转吸**欧拉分量**（与 Inspector
显示同一把尺子）。只吸增量的话，起点 0.3 的物体永远停在 `0.3 + 0.5k` 这种读不出来
的数上。吸附点在"算完连续增量之后"，所以拖拽手感仍是跟手的，只是落点被吸住。

**仍缺**：Rect 工具（完全没有实现）、吸附时的"临时轴约束"（Unity 的 Ctrl 组合轴）、
按世界 / 局部坐标切换吸附。契约见决策记录 §九十九，实施与红绿证据见 PLAN 一百一十二。

## 2026-11-08 游戏 UI 九宫格（P1 #4 的"九宫格"缺口关闭）

UI 图片之前只有"整张拉伸"和"按比例内接"两种落位。窗口 / 按钮 / 对话气泡这类
"尺寸随内容变，但四角必须原样"的元素因此只有一条路：按最大尺寸出图，于是小窗口
把圆角压扁、大窗口把边框拉粗。现在 `UiImageStyle.slice = [左, 右, 上, 下]`
（**图片像素**）把它切成最多 9 块：四角原样贴、四边单轴拉伸、中间双轴拉伸。

两条换算规则是这块最容易写错的地方，都用测试钉住：

1. **像素边距**按"目标尺寸 ÷ 图片尺寸"缩放（横竖各一个比例 —— `Stretch` 下两者
   不同，只用一个比例会让贴图与几何错位）；
2. **UV 边距**只由图片尺寸决定，与目标尺寸无关。写反的症状是"图被拉扯但边角看着
   还在"，只有拿方角贴图放大了才看得出来。

其余边界：目标比两条边加起来还窄时按比例压缩边距、中段退化为 0（绝不画反向四边形
—— 负宽度在 GPU 上是镜面翻折）；图片尺寸未知时先按普通拉伸画一帧（边距没法换算）；
`fill < 1` 优先于九宫格（进度条要的是线性裁切，不是把九宫格压扁）。零尺寸格直接跳过，
九块仍落在同一条绘制指令里（合批没被切片打断，实测 `commands.len() == 1`）。

**仍缺**：九宫格平铺（`repeat` 采样 + 中段按像素切分）、圆角裁剪、输入框、
手柄 / 键盘导航、Canvas Scaler。契约见决策记录 §九十八，实施与红绿证据见 PLAN 一百一十一。

## 2026-11-08 动画事件（P1 #12 的后续缺口之一关闭）

「脚步要响、刀要判定、特效要在第 0.3 秒炸」是玩法逻辑，而之前的动画只输出姿势，
任何"第几帧出手"都只能靠脚本自己数时间 —— 而脚本的时间与动画剪辑的时间轴不是
同一把尺子（换剪辑 / 换状态时剪辑归零，脚本寄存器不会）。现在 `Animator.events`
给基础通道的剪辑时间轴打点：到点派发脚本 `on_anim_event(ctx, name)` 与 Rust 组件的
`Lifecycle::on_anim_event`，脚本与组件同语义同顺序。

事件表跟**实体**走而不是剪辑资产：剪辑全部来自 glTF，那里没有能写事件的位置；
重新引入一套剪辑资产格式的成本远高于收益（与"材质只用 `.mat`、动画只用 glTF"
同一条取舍）。代价是同一实体换剪辑沿用同一张表，时间在新剪辑上重新计时 —— 这在
Inspector 上看得见（时间轴提示当前剪辑时长、越界时刻用错误色标出）。

判定只有一份：`animation_runtime::crossed_events` 是纯函数，循环跨界、一帧跨多圈、
非循环只触发一次、`time = 0` 靠"刚起步"标记、越界不猜（`time >= 时长` 永不触发）
全部由单测钉死；运行时只负责查剪辑时长（它本来就有资产缓存）与派发。
`run_hook` 扩成 `Option<HookArg>` 而不是复制一份带字符串参数的派发，避免那套
预算 / 限流 / 清零纪律出现第二份实现。

**仍缺**：逐剪辑独立事件表（需要剪辑资产层）、事件的区间（"从 0.2 到 0.4 之间持续
生效"）、编辑器里拖动时间轴打点、事件触发可视化调试。契约见决策记录 §九十七，
实施与红绿证据见 PLAN 一百一十。

## 2026-11-03 预制体语义与发布输入（G0）

未实例化的预制体可由脚本在运行期创建，原先场景的语义检查无法照到它的父链成环、
非有限变换与非单位旋转。项目检查现对默认目录及引用到的目录外预制体共用场景的
实体判定，保持只读，重复 ID / 越界层号继续走已有专门诊断。发布器还会检查已复制
进 staging 的 `input.ron` 是否可由播放器的映射解析器读入，并拒绝链接输入文件，
避免打出启动正常但按键退回默认的成品。完成边界与红绿证据见决策记录 §九十六和
PLAN 一百零九；`--check` 本身仍不解析输入映射，设备 / 断电 / 平台专项验收不随此项关闭。

## 2026-11-03 预制体独有依赖与发布诊断（G0）

也纳入同一检查链。打包对照覆盖漏资源拒绝及已有问题放行。固定语义见决策记录 §九十五，
红绿与验收见 PLAN 一百零八。此项继续收窄 G0 的组合正确性风险；不改变独立设备、断电

## 2026-11-03 坏预制体诊断（G0 项目检查）

## 2026-11-03 物理父子层级回写（G0 R10 / 084）

父子动态刚体同时运动时，子实体原先用物理步开始前的父世界矩阵换算局部位姿，随后再叠上
父节点的新变换，导致显示位置 / 朝向偏离自己的物理刚体。直接父子与夹有普通中间节点的
逆序层级均已在旧实现第一帧复现。现在按父节点先于子节点的顺序回写，普通中间节点同步
传播，局部视觉缩放保持原值；相机与音频监听使用完成回写后的世界姿态。

层级解算收敛到复用工作区，每次重建关系以覆盖重排 / 重挂 / 换场景。活动物理后端仍有
分配，门禁区分其成本与帧编排新增成本。固定合同见决策记录 §九十二，红绿、性能对照与
交付验证见 PLAN 一百零五。此项关闭 R10 的父层级专项验证缺口，G0 其他设备、掉电与平台
边界继续按下文保留；任意剪切变换不属于场景 TRS 可精确表示的范围。

## 2026-11-03 输入失焦取消与恢复（G0 交互可靠性）

当前优先级仍是 G0。发布恢复已有进程级证据，输入焦点边界则发现了可在本机复现的实际
缺陷：只清按住状态会漏掉释放事件，后台手柄轮询可重新激活动作，编辑器 Play 未转发焦点，
游戏 UI 还会使用旧位置。它直接影响可玩的成品，因此本轮只处理这条输入链。

现已统一失焦取消、后台事件门控和恢复语义；输入重置保留窗口焦点与手柄名单，同帧失焦再
恢复仍让 UI 结束旧捕获。`tools/test-player-focus.ps1` 通过真实发布包、winit 窗口消息与 Lua
验证“按住 → 取消 → 后台静默 → 恢复 → 再点击”。固定合同见决策记录 §九十一，实际红绿与
全量验证见 PLAN 一百零四。

这关闭的是**输入层焦点语义、egui 桥接与 Windows 消息链**。真实 Alt+Tab / 系统前台策略、
物理键鼠、IME、真机手柄 / 触摸和其他平台仍需目标环境验收，G0 不因此整体关闭。

## 2026-11-02 发布事务进程强杀恢复（G0 R01 / R02 / 172 的异常退出缺口收窄）

并发文件锁只能防两个活进程交错，不能解释持锁进程死在 rename 之间留下的磁盘状态。旧包
原先被移入随机 staging 的 `previous`：进程死后，下一次构建既找不到它，也分不清“旧包
已移走”和“新包已提交”。结果要么正式输出一直缺席，要么新包旁边留着不可判别的旧包。

现在旧输出会先得到一个空的 `.xgame-publish-transaction` 标记，再整体改名到稳定的
`Build/.xgame-previous-<产物名>`。下一次构建在场景试装与播放器查找**之前**持同一把发布锁
恢复；进入最终 `publish` 后还会再检查一次，覆盖等待锁期间前一发布者被杀的情况。状态判定
只有三条：正式输出仍带标记 = 尚未移走，清标记保留旧包；只有带标记的 previous = 旧包已
移走，改回正式路径；正式输出与带标记的 previous 并存 = 新包已提交，保留新包并清旧包。
无标记的同名目录、链接或普通文件一律按路径冲突拒绝，不递归猜删；事务标记名也禁止成为
发布包内容根。

两条回归先在旧实现实跑为 **0 passed / 2 failed**：第一条读不到正式输出，第二条留下孤立
旧包。进程级夹具又启动真实测试子进程，在“事务已标记 / 旧包已移走 / 新包已就位”三处
精确停住，由父进程 `Child::kill` 强制终止；三次恢复分别选择旧 / 旧 / 新包，并能重新取得
同一把锁。最终 builder **28/28**，workspace **1230 passed / 0 failed / 19 ignored**，check、
严格 clippy 与 release 通过；release SampleScene 成品检查及 60 帧无头通过，稳态只留下成品
与长期锁文件。完整证据见 PLAN 一百零三，固定契约见决策记录 §九十。

这关闭的是**本地文件系统上进程终止后的下一次构建恢复**，不是掉电原子目录交换。Windows
仍无目录 fsync，机器断电时标记 / rename 是否持久化没有证据；两次 rename 间仍有瞬时缺席
窗口，网络文件系统、绕过构建器的外部改写及强杀遗留随机 staging 也不在完成范围。G0 继续

## 2026-11-02 并发发布互斥（G0 R01 / R02 / 172 的并发缺口关闭）

## 2026-10-30 点光立方体阴影（P2 #20 的点光那一半）

方向光是 4 级 CSM；点光一直没有阴影 —— 一盏吊灯 / 火把照下来，桌子底下和桌面上
一样亮。这一轮补上：**6 面深度图 + 立方体采样 + 3×3 PCF**，与方向光**并列**
（一盏方向光 + 一盏点光可以同时投影，深度图各用各的）。

两条最容易踩错、且"看起来都像有影子"的坑，都由测试钉住：

1. **参考深度必须用主轴分量**（`max(|dx|,|dy|,|dz|)`），不是欧氏长度。立方体每面
   是 90° 透视投影，透视深度用的就是视空间 z。用长度算的实际后果：**8565 个像素
   全黑**（整面墙被判成阴影），而症状看起来只是"偏置没调好"。
2. **水平轴（u）必须镜像**。WebGPU 的方向 → (u,v) 映射表对每个面都是"右手系朝向下
   u 反向"的；不翻的后果是**影子翻到另一侧**（箱子在 +Z，影子出现在 -Z），形状
   软硬全对，只有拿真实几何对表才发现。

**成本**（`point_light_shadow_cost`，2000 方块 / 1280×720 / RTX 2060，6 轮中位）：

| 档位 | 场景段 GPU | CPU（编码+提交） | 六面实例 |
|---|---|---|---|
| 点光阴影关 | 70.1 µs | 271.2 µs | 0 |
| 点光阴影开 | **159.7 µs** | 337.8 µs | **8070**（每面 1345） |

对照同一片场景的方向光 CSM：免剔 **+99.8 µs / 8000 实例**、逐级剔除 +62 µs / 1131。
也就是说**点光"六面全画"比方向光"4 级全画"还便宜**（6 × 1345 < 4 × 2000）。

**仍缺**：

- **逐面剔除**（v1 刻意不做）→ **已做（2026-10-30 第二轮）**：6 位面掩码 +
  索引重映射，实例 12000 → 2013（−83%）、场景段 −81 µs（决策记录 §八十三）。
- **软阴影（PCSS）**→ **已做（2026-10-30 第三轮）**：`render.shadow` 节
  默认关、关着走老路径逐位一致；PCSS 场景段 +9.0%（决策记录 §八十四）。
- 只支持**一盏**点光投影（多盏要更多立方体，按当前成本会翻倍）。
- 点光阴影的分辨率没有进质量档位（现在跟 `shadow_resolution` 走，缺省是方向光的

## 2026-10-30 阴影逐级剔除（性能：阴影 pass 实例 -85.9%）

LOD 之后渲染侧最大的一块"白干活"：**阴影 pass 每级都画全部投影物**。4 级级联时
顶点 / 实例工作量是实际需要的 4 倍 —— 而每一级的拟合框只罩住相机视锥的一小段，
框外的东西本来就会被裁掉。

现在每实体在收集阶段算一个**级联成员位**（bit k = 落在第 k 级拟合框里），批次内的
实例按 `(批, 成员位)` 分段，阴影 pass 每级只提交成员位带自己的那几段。

**实测**（`shadow_cost` 新基准，1280×720 / 2000 方块 / 4 级 CSM / 6 轮中位，RTX 2060）：

| 档位 | 场景段 GPU | CPU（编码+提交） | 阴影实例提交 |
|---|---|---|---|
| 阴影关 | 69.6 µs | 257.7 µs | 0 |
| 阴影开 · 免剔（引入前） | 165.3 µs | 398.6 µs | 8000 |
| 阴影开 · 逐级剔除 | **128.9 µs** | 439.1 µs | **1131（-85.9%）** |

阴影本身值 **+95.8 µs（+137.7%）**，逐级剔除拿回 **-36.4 µs（阴影部分的 -38%）**。
代价是每实体多一次点积 + 若干区间比较（本机 **+40 µs / 2000 实体 ≈ 20 ns/实体**）：
**GPU 换 CPU 的交易**，显卡越吃紧越划算（方块基准里的实例只有 24 个顶点，
真实资产下省下的顶点处理远多于这里）。

**踩到的两个坑**（都已写进决策记录 §七十七）：

1. **排"绘制项"而不是排下标**：`PendingDraw` 带整个 `DrawUniform`（约 200 字节），
   两千个元素互换位置要搬 400 KB，单这一步就要 40 µs —— 把省下的 GPU 时间在 CPU 上
   又吐回去。改成排打包了 `(批, 成员位, 下标)` 的 `u64`。
2. **不能拿"视线深度区间"当判据**：那是最先写的版本（更快、剔得更干净），但斜射光下
   拟合框沿光线方向被拉长，能装下视线深度之外的投影物 —— 用深度判据会把这些投影物
   漏掉，影子凭空缺一块。现在深度区间只做**安全前置剪枝**（框在 ⇒ 深度必在，
   逆命题不成立），真正的判据仍是完整视锥测试。

`cascaded_shadow_culling_matches_unculled_pixels` 钉住"开关两档逐像素一致"，
`offscreen_casters_still_cast_shadows` 钉住"相机外的投影物不会被剪枝剪掉"。

## 2026-10-30 编辑器正交投影（P2 #28 关闭）

视口相机加 **正交投影**（`5` 键切换，命令面板也有条目）。三条语义：

- **与"对轴视角"是两件事**：`1`/`3`/`7` 只转朝向（透视下也能正对轴看），`5` 才换投影；

## 2026-10-29 路径纪律：一条规则、两个边界、一套诊断（194 关闭）

## 2026-10-28 脚本内存上限（124 的记忆配额那一半）

脚本沙箱原来只有**指令预算**（20 万条指令内掐断死循环）—— 它挡"算不完"，挡不住
"存不下"。一个 `local t = {} while true do t[#t+1] = string.rep("x", 1 << 20) end` 的
结局不是脚本失败，而是操作系统 OOM 杀进程，编辑器里未保存的场景一起没。脚本是用户

## 2026-10-28 预制体 ID 的跨文件诊断（101 关闭）

101 之前卡在"预制体 `source_id` 与场景 ID 算不算冲突"。结论是这根本不是冲突，

  按 `(场景, 预制体)` 聚合成一条（`dangling source:`），进 `has_issues()`。

## 八、已经做对了的地方（别在重构里弄丢）

- **编辑器 Play 与独立游戏共用同一段 `World::update`** —— 多数自制引擎在这里分叉
  成两套运行时，最后行为不一致（项目设置同样是单入口）。
- **帧调度纪律**：`frame_policy` 停帧 + `AutoNoVsync` 上屏 + `frame_probe` 探针，
  输入→光子延迟压到 ~20 ms；空闲 CPU 0.00%。
- **稳态性能有量化**：2000 实体纯视觉 13 µs/帧、热路径零分配；渲染侧实例化
  2225 → 344 µs/帧、剔除 3295 → 1146 µs/帧，全部同机背靠背量过。
- **Prefab 带 Apply / Revert 与来源追踪** —— Unity 级特性，同类自制引擎很少做到。
- **交互细节扎实**：Undo 快照分步、Gizmo 参考线锚定防抽搐、层级拖拽防环、
  拾取用射线 × 世界 AABB（不是包围球）。
- **脚本系统有工程化**：编译缓存 + 热重载 + 指令预算沙箱，崩溃 / 死循环不拖垮引擎。
- **测试纪律**：最近一次全量为 1216 passed / 18 ignored；新增回归必须先证明旧实现下会红。
- **数据即文本**：场景 / 预制体 / 清单 / 输入映射全 RON —— 版本控制友好，
  也是 Agent-Native 路线的地基。
- **无头三入口**：`--check`（引用完整性）/ `--headless`（固定 dt 逐位可复现）/
  `--screenshot`（同机逐字节一致）—— "改 → 查 → 验 → 看"闭环。

## 九、战略方向：Agent-Native

> **目标**：用户的 AI 智能体（Cursor / Claude / 任意支持 MCP 的客户端）能够**深度、
> 精确、可验证地**操作本引擎做游戏开发 —— 不是"截图点按钮"，而是像人类开发者一样
> 读写项目、运行检查、拿到可机读的结果。
>
> **架构判决式**：往后的架构决策都要过一问 —— **「智能体没有鼠标时，这条路走得通吗？」**

### 为什么这条路线对本引擎成立

1. **纯文本数据**是前提 —— Unity 的 YAML + GUID 混合体反而难智能体友好地整段改写；
   我们的 RON 场景人类可读、结构扁平。
2. **单一运行时**意味着智能体在无头环境验证的行为与玩家实际跑的完全一致 ——
   不存在"编辑器里对、打包后坏"。
3. **小而清晰的 crate 边界**让 MCP 工具直接调库，而不是模拟 UI 输入。
4. `--check` 已证明闭环模式：**改 → 一条命令 → 退出码**。后续每个能力都按同样模式
   给无头等价物。
