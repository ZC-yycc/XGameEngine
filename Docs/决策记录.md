## 二、脚本层决策索引（D1–D11）

原文与完整论证在 [`双轨语言架构计划.md`](双轨语言架构计划.md)「决策记录」一节，
这里只留一行摘要，防止改脚本层时漏读：

| 决策 | 结论 |
|---|---|
| **D1** | 语言范围收敛为 **Rust + Lua**；C# / Verse / 多语言中立层已否决 —— 维护两套语言边界的成本远超收益 |
| **D2** | Rust 侧走 **UE 插件模式**（cdylib + 注册表），Bevy 式"组件即数据"因跨 DLL 类型信息不可用而否决 |
| **D3** | Lua 侧走 **Unity 模式**（脚本挂实体 + 四个生命周期钩子）+ 热重载 |
| **D4** | Rhai 的去留**由数据决定**：P2.5 三负载基准闸门，不靠直觉 |
| **D5** | 性能结论先量后动：没有探针数据的"优化"不进主干 |
| **D6** | P0 落地注记（门面 / 方法层 / 组件 / 插件边界） |
| **D7** | P0.5 落地注记（编辑器 PIE：后台构建 + 临时副本加载） |
| **D8** | P1 落地注记（`#[derive(Inspect)]` + 编辑器调参） |
| **D9** | P1.5 落地注记（组件参数落盘 + 撤销语义修正） |
| **D10** | P2 落地注记（Lua 宿主 + 路径驻留表） |
| **D11** | P3 落地注记（删 Rhai、收敛单一 Lua 轨） |

**仍然生效的脚本层约束**（P3 之后重述，去掉双轨时期的历史包袱）：

1. **单轨只认 `.lua`** —— `list_scripts` / 加载 / 热重载 / 检查都是这一条；残留
   `.rhai` 不进下拉、也不被 `--check` 误报（`check.rs` 只查文件存在，不查扩展名）。
2. **每脚本环境表的 `__index` 必须挂真元表** —— 往 env 表塞同名普通字段对读取无效，
   表现是"脚本里宿主 API 全变 nil"（P2 首跑 9 条红就是它）。
3. **路径驻留表 id 永不清** —— `invalidate*` 只清编译缓存；清表 = 热重载后每实体
   状态静默错位（`state_survives_hot_reload_even_when_intern_order_changes` 钉死）。
4. **沙箱预算 200_000 条指令**（Lua 指令钩子，每 1024 条查一次）；改预算要有
   性能/安全两侧的数据，别单方面放宽。
5. **API 名一字不改** —— `spawn_entity` 的 `_entity` 后缀是 Rhai 保留字时期的历史
   产物，迁移成本大于违和感；改名等于作废所有已写脚本。
6. **`host.rs` 不改名不搬家** —— `lua_host.rs` 的 `use crate::host::` 与再导出路径
   全不动，保持纯删代码的最小 diff。
7. **`ScriptCtx` 是地址束** —— unsafe 有严格调用窗口约定（见 `context.rs` 模块文档），
   窗口外解引用是 UB；改它之前先读那段文档。
8. **`GameCtx` 方法层是 API 真相源** —— `ctx.rs` 写实现，`lua_api.rs` 只是每函数
   一行的转发壳；新增 API 两处都要动，但逻辑只准写在 `ctx.rs`。

## 三、脚本宿主的实现事实（省得重新踩）

- **路径借用跨不过 `&mut self`**：借 `self.intern` 的 `&str` 调 `&mut self` 方法会被
  借用检查器拒绝（它看不出这是字段级拆借）—— `ensure_loaded` 因此拆成 path 外壳 +
  `ensure_loaded_id` 内核、`run_hook` 收 `path_id`，路径解析都在方法体内做。
- **钩子句柄编译期缓存**（`detect_funcs` 留 `Option<Function>`）省每钩子 `env.get`
  ~194 ns；**ctx 常驻槽 + 轻量指针传参**（`ctx_slot: Box<MaybeUninit<LuaCtx>>`）省每
  钩子现造 userdata ~284 ns。两处合计把 Lua 轨分发从 1670 压到 576 µs/帧（-65%）。
- **基准工具必须断言"脚本真跑了"**：宿主对编译失败只记日志是产品正确语义，但基准
  必须自己 panic —— 否则"空调度"会被当成假快（P2.5 首跑就栽在这）。

## 四、Rust 组件与插件（P0–P1.5）

**兼容检查的现状边界**：版本号一致不能推出同 rustc、依赖、源码或 flags；C ABI 入口与 `repr(C)` 宿主块也不会让句柄背后的 Rust 注册表、trait 对象成为稳定 ABI。历史 P0 版本握手只检查版本码，不能阻止同版本旧 DLL 在注册阶段破坏内存；构建指纹只能作为保守拒绝门禁，不能证明任意下游编译参数或 Rust ABI 兼容。

当前 G0 实现由 `crates/xgame/build.rs` 使用标准库生成确定性指纹：`rustc -vV`、TARGET/HOST、PROFILE、OPT_LEVEL、DEBUG、panic、target features、xgame features、可见 rustflags/wrapper 配置，以及引擎库源码、Cargo 清单、锁文件和构建脚本。输入按键/相对路径排序；文件标识不含仓库绝对路径，导出值仅为版本前缀与固定摘要。固定摘要不作密码学认证，可能保守拒绝不影响 ABI 的源码改动；xgame 的 build.rs 无法观察下游全部 flags、依赖 feature 合并和第三方源码状态。

`export_plugin!` 额外导出 `xgame_plugin_descriptor_v1(*mut u8, usize) -> usize`：返回所需长度，空指针或容量不足不写入。`LoadedPlugin::register_into` 首先以宿主定长缓冲区检查长度与全部字节，缺符号/不匹配在原入口之前拒绝；不改 `PluginHost` 布局，保留原版本握手。描述符不传 Rust 结构或所有权；库初始化仍早于校验，不防恶意本机插件或伪造描述符。

**三条不能推翻的约束（D7）**：

1. **`Plugins/` 是唯一规范目录** —— 玩家与打包器只认这里，编辑器构建产物同步进来。
2. **加载永远走临时副本** —— Windows 文件锁会让 `cargo build` 覆盖不了正在加载的
   DLL；临时副本是唯一稳的做法。
3. **旧 DLL 句柄永不卸载** —— 悬垂 vtable 是 UB（进程暴毙无 panic）。持有句柄的
   字段必须声明在 `game_runtime` / `world` **之后**（析构顺序）。

**四条不能推翻的约束（D8，其中第 ④ 条已被 P1.5 推翻）**：

1. **组件契约是 `Behavior: Lifecycle + Inspect`**（不是 `Lifecycle`）—— 编辑器不链接
   用户代码，拿 `&mut dyn Inspect` 只能靠实例自带的字段表；存 `Box<dyn Lifecycle>`
   时这条降级做不到（需 downcast，跨 DLL 无共享类型信息）。
2. **`Inspect` 是"表 + 下标"，别改成闭包** —— 跨边界闭包要处理 panic 隔离与函数
   指针生命周期，表 + 下标是唯一稳的形态。
3. **寻址名永远是 Rust 字段名**，`label` 只改显示名 —— 重命名显示名不能破坏脚本。
4. ~~组件字段改动不进场景撤销栈~~ → **已推翻**：参数进场景文件后已成为场景数据，
   不进栈会凭空丢一条编辑。现为拖拽挂 `undo_pending`、松手入栈、离散编辑当场 push，
   与 Name/Transform 同通道。**Play 中热调参仍不写回**（停止靠场景快照还原）。

**两条不能推翻的约束（D9）**：

1. 参数表的键是**注册名**而非 `behaviors` 数组下标 —— 下标会错位，参数是持久化数据，
   错位写参表现为"改 A 组件的参数写进 B 组件"，两边都是 `f32` 时无从发现。
2. `FieldKind` / `FieldValue` 的 serde **变体标签即磁盘格式**
   （`field_value_ron_variant_labels_are_stable` 钉死）；改标签名 = 作废所有旧场景。

**两条实现事实**：

- `PluginSession` 留的常驻注册表是每帧路径（查字段表 / 构造编辑态副本）的唯一通道，
  **别改回 `build_registry()`** —— 后者每次重跑插件入口且失败时 `log::error!`，错位时
  会变成每帧一条错误日志。
- **插件注册表是跨编译单元的内存布局**：给 `BehaviorEntry` 加字段 = 改 ABI，会让过期
  的 `target/*.dll` 变成 `0xc0000005`。而 `cargo test` 不产出 cdylib，那些 DLL 极易
  过期 —— `plugin_loading` 因此在取 DLL 前先嵌套构建一次（MCP 测试同理）。

## 五、音频（第八阶段）

**四条不能推翻的约束**：

1. **脚本层不引 kira** —— 脚本音频 API 只往 `AudioPort` 塞命令，`World` 帧末统一
   结算（`GameCtx.audio: Option<&mut AudioPort>`，None 静默 no-op）。设备失败走
   **silent 降级**（照常受理 / 计数 / GC，只是不出声），别改成"没设备就报错"。
2. **监听者与主音量是 port 上的状态字段，不进命令束** —— 姿态每帧被覆盖，混进
   "发生过的事"会变成回放一串状态更新的荒诞语义。
3. **`PlaySound.follow` 是实体绑定、不是空间化开关** —— 空间化只看
   `position.is_some()`；非空间化声音**也要绑实体**（否则"删实体音还在响"，
   `removed_entity_or_component_stops_its_sound` 钉死）。
4. **音频每渲染帧同步一次、不跟物理固定步同频** —— 人耳对 16 ms 的位置更新不敏感，
   固定步一帧可能跑多个。

**两条实现事实**：silent 模式用**墙钟** GC、设备模式看 `handle.state()==Stopped`；
测试要断言"声音在响"必须用 ≥1 秒的 WAV（50 ms 的会被 GC 先真掉，曾造成假红）。
kira 的 glam 0.33 与引擎 glam 0.29 **类型不出 `xgame-audio` 墙** —— 跨界只传
`[f32;3]` / `[f32;4]` 数组。

**热路径快速路径**：`sync_audio` 的实体表扫描在无音频场景实测 +5.7 µs/帧
（2000 实体纯视觉），故加 `audio_sources_seen` / `audio_scan_count` 守卫 ——
没挂过音频源、无 autoplay、实体数不变 ⇒ 整段跳过；实体数变化重新武装扫描。
**刻意取舍**：运行中给已有实体直接贴 `audio` 组件（不动实体数）不触发重扫 ——
动态发声正路是脚本 `play_sound`（不经扫描）。

## 六、Agent-Native（无头运行 / MCP）

**三条不能推翻的约束**：

1. **无头运行的实现住在编辑器二进制**（`headless.rs`，`--check` 的邻居），**不做第二份
   帧循环**（单一运行时铁律；MCP 只 spawn 透传）。
2. **退出码 `2`（跑完有问题）不是工具失败** —— 报告照常产出，`isError` 只留给
   "打不开项目"。
3. **报告 JSON 字段名是稳定契约** —— `json_contract_has_stable_keys` 钉死，消费方 =
   CI + MCP；新增字段可以，改名 / 删除不行。

**两条实现事实**：MCP 测试 spawn 编辑器**前必须嵌套 `cargo build -p xgame-editor`**
（`cargo test` 不产出常规 exe；过期编辑器不认 `--headless` 会弹窗挂死测试）；
`find_editor_exe` 找同目录 + **上一级**（`cargo test` 时 server 在 `deps/` 下跑）。

**实测**：SampleScene 300 帧墙钟 ~80 ms（帧循环 8.6 ms、帧均值 28.5 µs）；
BehaviorsDemo（插件 + Lua）~70 ms；进程启动固定成本 ~60 ms（与 `--check` 同量级）。

## 七、PBR 与材质（2026-10-19）

**四条不能推翻的约束**：

1. **灯亮度按 `radiance = intensity × π` 标定** —— 别"顺手修正"成物理严格的 intensity，
   全部旧场景会暗 3.14 倍。
2. **材质参数是逐 draw 的**（`DrawUniform` 112 B + 动态偏移）—— 别改回"每材质一个
   绑定组"（逐实体覆盖下按资产缓存要么重建绑定组、要么缓存键随数值膨胀）。
3. **`scene_signature` 必须哈希 material** —— 漏了 = 暂停时调色视口不刷新。
4. **默认截图机位必须顺光** —— 相机方位 = 主方向光 XZ 方位角 + 35°、仰角 26°；
   背光机位会把 PBR 画面拍成"渲染坏了"。

**三条实现事实**：`MIN_ROUGHNESS = 0.04`（GGX 在 roughness=0 时除零 → NaN 扩散整帧）；
`--screenshot` 是**唯一**推进动画时钟的无头路径（静态截图里角色不能停在绑定姿态）；
像素断言必须算一遍镜面项（光与相机同轴时 GGX 副瓣会在中心像素叠 ~0.24 线性白）。

**已知限制**：脚本侧有 `set_material`（写内联覆盖）与 `set_material_asset`
（引用 `.mat`），但材质资产目前只有 albedo 一个贴图槽；天空关着时环境反射仍是常量近似。

## 八、HDR + ACES + Bloom（2026-10-19）

**四条不能推翻的约束**：

1. **亮度基线不许动**（π 标定 + 曲线前 `/0.6`；动它 = 全部旧场景明暗整体挪档）。
2. **Bloom 阈值在曝光后判**（threshold = 1.0 ≈ 显示白点）—— 挪到曝光前会让"调曝光"
   与"调阈值"耦合。
3. **光晕加在曲线前** —— 曲线后加是贴纸：暗部蒙灰、高阈值时光晕先在 LDR 端被裁出
   硬边。
4. **Bloom 默认关**（`intensity == 0` 是唯一关闭形态），关着时**整段跳过**（不建纹理、
   不记录 pass、链丢 None）—— 别改成"跑一遍乘 0"。

**三条实现事实**：每级必须 a/b 纹理乒乓（同一张纹理不能既当输入又当输出，wgpu 提交时
校验）；合成绑定组键 =（源代, 尺寸, 开关），关着时 mip 槽位用源视图占位、着色器按
uniform 值分支；报告 / MCP JSON 里 f32 是精确加宽的 f64（`0.6` → `0.6000000238418579`），
消费方按 f32 精度比较。

## 九、程序化天空 + IBL（2026-10-19）

**四条不能推翻的约束**：

1. **默认关**（`enabled = false`）—— 关着时 uniform 照写（开关位 0）但**不重建任何
   资源、不采样三张环境纹理**，画面与天空上线前逐位一致；别改成"默认开"或"关也重建"。
2. **环境立方体 / LUT 固定分配、内容按 key 重建**（key = SkyUniform 字节 FNV 哈希）——
   绑定组对象身份必须稳定（换对象 = 每帧路径重绑），别改成"每帧重建"。
3. **加载恒等：太阳 = 场景 `packed`（active、≤8 盏）里第一盏方向光**（方向取传播方向
   的反向、颜色取灯色）；没方向光就没有太阳（强度写 0）。别引入第二套"天空光源"。
4. **IBL 与常量 `ambient` 相加**（SH 存 E/π 就是为这条标定 —— 均匀环境下两者逐值
   等价），别把 ambient 顶掉。

**三条实现事实**：`SKY_COMMON_WGSL`（`sky_radiance` / `sky_sh_eval`）**不声明绑定**，
三处（天空盒 FS / 场景 FS / 预过滤 FS）各自声明自己的绑定号（全局组 7–11 的契约集中在
`sky.rs` 的 `global_layout_entries()`）；场景 FS 用 `sky.sun_dir.w > 0.5` 判开关
（uniform 常量 ⇒ 采样在整个 draw 里控制流一致）；预过滤面基向量由 CPU 给
（`cpu::cube_face_basis`，`dir = forward + right·(2u-1) + up·(1-2v)` 对齐 WebGPU
立方体约定，错位表现 = "反射里太阳跑到反侧"，GPU 测试钉住）。

**性能实测**（RTX 2060 / 1280×720 / MSAA×4，`postfx_cost.rs` 的 `sky_ibl_cost`）：
稳态开相对关 **+29.5 µs/帧**；每帧重建（太阳每帧动的最坏情况）**+341.7 µs GPU /
+449 µs CPU**；开启那帧一次性成本 = 重建 + 71.6 µs（BRDF LUT + 冷态）。

## 十、GPU 实例化（2026-10-19）

**四条不能推翻的约束**：

1. **批次分组键 = 「图元地址 + 材质 key」**（只做相等判定）、**批次顺序 = 首次遇到顺序** ——
   无头截图 / 基准"同机逐字节确定"契约依赖槽位布局确定，别改成哈希序 / 按材质排序。
   材质这一维是 2026-10-21 加上的：同一个图元挂两份 `.mat` 却按图元地址合批，
   后一次 `set_bind_group` 会把整批盖成一份材质（见 §十七）。
2. **逐实例数据一律走 `draw_buffer`**（storage 整缓冲一次绑定）—— 别退回"逐 draw 动态
   偏移 uniform"，那是 2000 实体场景 ~1.9 ms/帧 的 CPU 税（本轮实测）。
3. **半透明不参与合批**（排序语义优先）。
4. **材质绑定组在收集阶段预热**（绘制循环只有 `&self`、不能惰性建组）—— 循环里的
   `material_cache.get(..).expect()` 是故意的硬失败（静默用错材质 = 画错色）。

**实测**（同机交替 3 轮取中位数，RTX 2060 / 1280×720 / MSAA×4 / 2000 实体，
`instancing_cost`）：共享网格 2001 批 → **2 批**、CPU **2225 → 344 µs/帧（-84%）**；
各自网格对照档 4139 → 3287 µs/帧（-21%）。端到端钉子：同一 SampleScene 无头截图
（150 帧 + `--screenshot`）在两版之间**逐字节一致**。

## 十一、视锥剔除 + 阴影补投（2026-10-20）

**四条不能推翻的约束**：

1. **保守性是硬合同** —— 开/关剔除逐位一致（`frustum_culling_matches_unculled_pixels`
   钉死）；矩阵退化（含 NaN / 零法线）必须返回 `None` 并**当作不剔除**，宁可白画不能
   黑屏。
2. **相机外投影物必须保留在阴影视锥里**（`offscreen_casters_still_cast_shadows` 钉死）——
   只按相机视锥剔会让影子凭空消失。
3. **蒙皮包围盒是绑定姿态，50% 余量不能删**（`cull_bounds_pads_skinned_meshes_only`
   钉死）；静态网格不得加余量。
4. **剔除不改变分组键 / 批次顺序**，只少实例或整批不出现 —— 槽位布局确定性的前提。

**三条实现事实**：收集顺序是**主 pass 不透明 → 半透明 → 仅阴影**三段连续槽位，仍只做
一次 `queue.write_buffer`；`FrameStats.opaque_instances` **只算主 pass**，仅阴影实例单独
记 `shadow_only_instances`，`cull_ratio()` 的分母两者都算；`Bounds::transformed_affine`
是 8 角点法的解析等价式（每帧省 7 次点变换，交叉单测钉住）。

**实测**（RTX 2060 / 1280×720 / MSAA×4 / 2000 实体 / 30° 窄视场 / 56.6% 剔除，
`culling_cost`）：未合批场景 **2000 → 868 批、CPU 3295 → 1146 µs/帧（-65%）、
场景段 158.0 → 108.5 µs（-31%）**；共享网格场景 CPU -3% / 场景段 -7%。
阴影刻意关（相机外投影物按设计保留，混进来测的是组合而不是剔除本身）。

## 十二、FXAA（2026-10-20）

**四条不能推翻的约束**：

1. **默认关，关着时整段跳过** —— 不建 scratch、不做 pass、不写 uniform，画面与上线前
   逐位一致（与 Bloom 同一条纪律）。
2. **luma 与混合必须在显示空间** —— sRGB 目标采样是线性值，着色器先 `srgb_encode`、
   混合后 `srgb_decode` 交还硬件；非 sRGB 目标（合成已手动编码）原样处理。
3. **边缘检测的采样必须用 `textureSampleLevel(..., 0.0)`** —— 分支建立在采样值上，
   WGSL 不允许隐式 LOD 采样出现在非一致控制流。
4. **平坦区域必须回原采样值**（范围低于阈值且亚像素项为 0 时），不做 encode/decode
   往返 —— 8 位量化边界上会悄悄差 1 LSB。

**两条实现事实**：scratch 的格式 = 输出格式、尺寸跟源走，尺寸变化整块重建并重建
绑定组；FXAA 测试**强制 1× MSAA**（4× 的硬件斜边会掩盖效果），旧实现下开 / 关两张图
逐字节相同就是它的先证红。

**实测**（RTX 2060 / 1280×720 / MSAA×4，`postfx_cost` 第四档）：HDR+ACES 后处理
24.7 µs/帧 → 开 FXAA **72.2 µs/帧（端到端 +47.6 µs，+30.6%）**；1× MSAA 测试场景
硬台阶 672 → 374（**-44%**）、中间调像素 0 → 804、平坦背景角点逐字节不变。

**阈值口径**：亚像素 0.75 / 方向收缩 1/8（下界 1/128）/ 跨度 8 texel 都是 3.11 原值；
边缘阈值取 1/12 与 1/6（stock 是 1/24 与 1/8）—— 默认已有 MSAA，stock 阈值会整幅柔化。

## 十三、性能纪律与工具链

**方法与数据**（微基准 `behavior_dispatch_throughput`，1000 no-op 实体 × 300 帧，
P2.5 会话）：Lua 轨分发 **562 µs/帧**、Rust 组件轨 71.7 µs、无轨基线 7.54 µs。
历史：P0 = 493.9、P0.5 = 68.4、P1 = 65.2、P2 = 713 µs。

**三条纪律**：

1. **先量后改**：没有探针数据的性能改动不进主干；改动前后同机背靠背，最好交替 3 轮
   取中位数。
2. **基准必须断言"真的发生了"**：脚本没跑、pass 没执行时，"更快"是假的（P2.5 与
   FXAA 基准都栽过，各自加了守卫）。
3. **绝对值随机器状态浮动 1.5× 以上**：跨版本比较必须同机背靠背；组件轨 < 50 µs 的
   验收线在本机持续红（P0.5 起已知，**不为了迁就机器上调验收线** —— 红了先对同机
   数字再判回归）。

**工具链注意**：仓库源文件是 UTF-8 **无 BOM** 且含大量中文注释。用 PowerShell 做
文本替换必须显式 `-Encoding UTF8` 读写，否则 PS 5.1 会按 GBK 解码把中文**有损**毁掉
（已发生过一次，PLAN.md 十六第七节）。改中文源文件优先用编辑器工具，shell 只做只读。

## 十四、资产管线：GUID + `.meta`（2026-10-20）

**要改的东西**：场景 / 预制体里的资产引用、资产导入、资源浏览器、
`ProjectHandle::load_*` / `write_*`、`--check` 的诊断项。

### 1. 磁盘存 GUID，内存存路径

这是本层最重要的一条，别推翻：

- **磁盘**（场景 / 预制体 RON）：`model: "guid://8f3a…"`。
  资产改名 / 挪目录只改 `.meta` 的位置，引用不断链。
- **内存**（`Entity::model` / `AudioSource::clip` / `scripts` / `PrefabInstanceRef::source`）：
  仍然是**项目相对路径**。渲染、物理、音频、脚本、UI 全部按路径打开文件，
  它们不需要知道 GUID 的存在。

转换点只有一处：`ProjectHandle::load_scene` / `write_scene` / `load_prefab` /
`write_prefab` / `load_material` / `write_material`（`xgame_core::asset` 的
`encode_*` / `decode_*`）。材质里的 `albedo` 也走同一条边界。

**为什么不做成"字段类型换成 AssetRef"**：那要把 243 个消费点全部改写，
还会把"GUID → 路径"的解析塞进每帧热路径；而边界转换是同一个语义、零热路径成本。
代价是资产被删后内存里会残留 `guid://…` 字符串 —— 这恰好是想要的：
`--check` 能把它点名（`dangling_guids`），而不是静默当成空引用。

### 2. `.meta` 的规则

- 每个被登记的资产生成一份 `<文件名>.meta`（RON）：`guid` + `kind` + `import`。
- **GUID 只在首次导入时生成一次，之后永不变**（改名 / 移动都不变）。
- 场景不登记资产（它由 `entry_scene` 按路径引用，没有"改名不断链"需求）；
  `project.ron` 不是资产。
- 构建产物目录（`target/` `dist/` `Plugins/` 等）不扫（`SKIPPED_DIRS`）。
- 资产类型按扩展名白名单推断（模型 / 纹理 / 音频 / 脚本 / 预制体 / 材质 / 着色器），
  未知扩展名不进库 —— 否则 `src/*.rs`、`Cargo.toml` 都想成为资产。

### 发布副本的扫描边界（2026-10-27）

资产库保留全项目递归扫描，不缩成默认 `Resources/` 等白名单，也不把 `Build` 加入任意层级的目录名黑名单。有效的嵌套 `project.ron` 标识独立项目：若与当前项目声明的内容根不重叠，剪枝整棵子树。这样默认 `Build/<项目名>` 和搬移到自定义目录的完整包都不会把重复 GUID、坏/缺失 `.meta` 注入源项目；以包目录为根打开时仍正常扫描。

内容根包括全部 `content.*_dir`、`search_paths`、入口与发布清单场景的父目录。内容根及其祖先/子树优先，内部即使有有效清单也不能隐藏用户资产；无效清单不构成边界，普通 `Build` 目录及散放资产照常扫描。Windows 重叠比较忽略大小写。`scan` 与 `refresh` 同源读取当前清单，不生成 `.meta`；既有 `SKIPPED_DIRS` 规则保持不变。

当前 `BuildConfig` 只有版本和关卡清单，构建器输出仍固定为 `Build/<安全项目名>`，没有新增自定义输出配置。嵌套项目边界兼容完整包的自定义存放位置；无清单的散落副本不能可靠识别，继续作为资产报告冲突。构建器的源/输出重叠拒绝规则不变，不用扫描过滤掩盖无效打包配置。回归和实际发布证据见 PLAN 第六十节。

### 3. `--check` 必须只读

`scan` 只读盘、只报告；**生成 `.meta` 是显式动作**（`ensure_metas`）。
`--check` / MCP `project_check` / `asset_list` 都不调用它 —— 检查一遍不能改变项目，
否则 CI 与智能体的"改 → 查 → 验"闭环会在工作区里留下意外的文件。

### 4. 迁移是隐式的，且不许吃掉注释

- 老项目：`--migrate-assets <项目>` 一次性生成 `.meta` 并把引用改写成 GUID。
- 迁移用**资产字段的 RON 字符串 token 替换**（`"Resources/Box.glb"` → `"guid://…"`），
  不是"读出来整体重新序列化"：本仓库的示例场景是**带注释的文档**，
  整份重写会把注释全部吃掉（第一次实现就踩了，`git diff` 才看出来）。
  词法扫描必须跳过行注释、可嵌套块注释，并只在资产字段改写；全局 `replace`
  会误改注释与恰好同名的实体名称。先解析原文件、再改 token，其他字节保持不变。
- 打开旧项目 + 保存一次也会完成迁移（`write_scene` 自动编码）。

### 5. GUID 冲突 = 必须修的错误

两台机器 / 两次手工拷贝可能让两个资产共用一份 `.meta` 内容。冲突时解析结果
取决于扫描顺序（= 随机），所以扫描按路径字典序**取第一个**保证确定性，
同时把冲突列进 `diagnostics.conflicts`，`--check` 与 `asset_list` 都会报。

### 6. 导入设置已接线（2026-10-21）

`ImportSettings`（`model_scale` / `texture_srgb` / `texture_nearest` /
`audio_streaming`）当年只落盘；现在前三个已经被消费（实现细节见 §十七）：

- `model_scale` 在**加载边界烘焙**：顶点、节点平移、动画 translation 轨道、
  逆绑定矩阵平移一起乘；非有限 / ≤0 退回 1.0。不放在世界矩阵外再乘一层 ——
  那样渲染对了，但物理碰撞、包围盒、射线拾取会与画面错位。
- `texture_srgb` / `texture_nearest` 由 `Texture::from_file` 的
  `TextureOptions` 消费（模型贴图与材质 albedo 都走同一条上传路径）。
- `audio_streaming` 仍是纯数据：流式播放还没落地。

改了导入设置必须让缓存的**网格与 GPU 纹理一起失效**（编辑器保存 `.meta`
后调 `SceneRenderer::invalidate_assets`）；否则会出现"参数改了、视口纹丝不动"
的假象。

### 7. 场景里的注释要保住

编辑器保存（`write_scene`）是全量序列化，会吃掉注释 —— 这是本功能之前就有的
行为，不是这轮引入的。所以**教程性质的示例场景不要用编辑器反复保存**；
需要保注释的批处理（迁移）走字符串替换那条路。

## 十五、角色控制器：封装 rapier + 四道绕过（2026-10-20）

**要改的东西**：`xgame-core::CharacterController` / `Entity::controller`、
`xgame-physics`（`character.rs` + `move_character`）、`xgame-script` 的 `character_*`
与碰撞钩子、`xgame-runtime` 的角色刚体与事件派发、Inspector 的 Character 区块。

### 1. 用 rapier 内置控制器，不自己写扫掠

"沿墙滑行、上台阶、坡度限制、贴地吸附、陡坡滑落"每一项手写都是坑。rapier 的
`KinematicCharacterController` 是上游多年验证过的实现，封装它是"参考开源引擎"最
省事的一条路。**但 rapier 0.22 的这条链路对胶囊角色有四处硬缺陷**（全部实测确认，
不是猜的），所以每一处都在**我们这层**绕过，并且把"为什么"写进了
`crates/xgame-physics/src/character.rs` 的模块文档。

### 2. 四处上游缺陷（改动前必读）

1. **grounded 恒为 false**：`detect_grounded_status_and_apply_friction` 用
   `(Capsule, Cuboid)` 的 contact manifold，而 parry 0.17.6 把这个组合**注释掉了**
   → 返回 `Unsupported`，rapier 用 `let _ =` 吞掉。→ 我们用自己的向下射线判
   grounded（法线点乘 ≥ 1e-3 且法向间隙 ≤ `predict_ground`）。
2. **`check_and_fix_penetrations()` 是空函数**（整段被 `/* */` 注释）。→ 一旦脚底
   与地面重叠，`cast_shape(stop_at_penetration: false)` 对手 "继续深入" 的扫掠返回
   `None`，整段位移被放行；实测从 2.6mm 重叠起步，两帧内退化成每帧沉 0.83m。
   → 移动前做**皮肤层硬约束**（间隙 < `skin_width` 就把向下的期望抬回
   `rest_gap`），并且静止间隙必须是 `skin_width × 1.1` 而不是 `skin_width` 本身。
3. **60° 薄板上胶囊扫掠返回 `None`**（0°/30° 正常，60° 退化；射线探测却正常）。
   → 陡坡滑落自实现：着地且法线超过 `slope_limit` 时，把向下的期望**投影到坡面**，
   切向天然带水平分量，间隙保持不变。
4. **autostep 对胶囊不可用**：`handle_stairs` 只在"第一次扫掠撞到墙"时触发（走路带
   向下期望时第一次撞的永远是地面），且 `min_width`（0.25×半径）不足以把胶囊的
   底面接触点推上台阶，算出的台阶高度恒为 0。→ 关掉 rapier 的 autostep，自己实现
   "抬到台阶高度 → 水平前进（多推一个半径）→ 向下贴回"，三次试探复用 `move_shape`。

**为什么不对 parry 打补丁**：0.17.x 最后一个发布版就是 0.17.6；0.18+ 要求
rapier ≥ 0.23（破坏性升级）。`[patch]` 一个 fork 会把"依赖升级"变成"维护 fork"。

### 3. 坐标约定：实体原点是脚底

`Entity::transform.position` = 角色**脚底**（Unity 同款），胶囊中心 = 原点 +
`center_height()`（`half_height + radius`）。理由：编辑器里把角色拖到 y=0 就是站在
地平面上；场景文件里的高度就是玩家看到的脚底位置。改这条会同时影响
`sync_bodies` 的建体偏移与 `move_character` 的写回，两处必须一起改。

### 4. 碰撞事件：两条来源，一个出口

- **动态刚体**：rapier 的 `CollisionEvent`（`World::step` 里收集，运行时 `drain`）。
- **角色**：运动学胶囊永远停在 `skin_width` 外，和墙 / 地板**从没真正接触过**，
  物理引擎一个事件都不会发（运动学 vs 静态本来也不生成）。所以角色的接触面由
  `CharacterMoveResult::contacts` 上报（`move_shape` 回调里的碰撞体句柄 → 刚体 id，
  固定容量 8、零分配），运行时与上一帧做差分得到 enter / exit。

两条来源都汇到 `World::dispatch_collision_to`，所以脚本与组件看到的语义完全一致：
**双方各收一次**、持续接触不刷屏、`other` 是对方实体 id。差分按
`(小 id, 大 id, started)` 去重，避免两个角色互撞时收到两条反向事件。

### 5. 运行时层：贴地速度必须是 0

`character_simple_move` 着地时**不再**给一个向下的"贴地速度"。带向下分量时
`move_shape` 的第一次扫掠先撞地面，剩余位移被吃掉，自动上台阶永远不触发（0.2m
台阶把角色焊死在原地）。贴地交给 snap（走下矮台阶）与坡面切向投影（走坡）。
下落时的竖直速度用 `effective_translation.y / dt` 反推，着地后按坡面跟随率
`-(n.x·vx + n.z·vz)/n.y` 重算并 `.min(0)` —— 只下不上，上坡的爬升交给物理层的切向投影。

## 十六、游戏 UI：实体锚点 + 单管线（2026-10-20）

### 1. UI 元素是**实体组件**，不是独立的 UI 树

`Entity::ui: Option<UiElement>`。层级 / 撤销 / 预制体 / 复制粘贴 / Inspector
全部复用。`transform` 对 UI 元素**不参与布局**（位置由锚点决定）—— 世界变换
解决不了"窗口变窄时按钮贴右边"，混用两套坐标只会互相打架。

### 2. 运行时状态放在组件里，但**绝不能进 `Entity::eq`**

`UiState { hovered, pressed, clicked }` 是 `#[serde(skip)]` 的每帧数据。
`Entity::eq` 是脏检查的真相源（`saved_snapshot` 比较）：把 state 算进去，
鼠标划过按钮就会让编辑器标题出现星号、关窗弹"未保存"。

- 唯一正确写法：`Entity::eq` 里对 `ui` 用 `UiElement::data_eq()`（只比落盘字段）；
- 回归测试：`ui::tests::state_changes_do_not_count_as_edits`。

### 3. 锚点公式只有一份，绘制与命中必须共用

```text
rect.min = parent.min + anchor_min * parent.size + offset_min
rect.max = parent.min + anchor_max * parent.size + offset_max
```

`layout::resolve` 是唯一实现。**命中测试与渲染各写一遍 = 迟早错位**
（点得到的地方画不出来 / 画得出来的地方点不到）。文本度量不参与矩形解算，
所以"没有字体时按钮照样能点"。

### 4. 绘制顺序 = 实体层级 DFS 先序，命中测试反向扫描

没有 z 序字段、没有排序。同层按实体顺序，后画的盖住先画的。
**不能按类型重排**（"先画所有背景再画所有文字"会让后面的面板盖掉前面的文字）——
这是第 5 条的前提。

### 5. 所有 UI 图元走**一条**实例化管线

矩形（圆角 SDF）、图片、字形共用一个 80 字节实例与一个着色器，模式在
`params.z` 里。矩形不采样纹理，但**绑定组用图集**，于是"背景 + 文字"相邻同批：

| 实现 | 900 元素命令段 | 真实 draw call |
|---|---|---|
| 两条管线（矩形 / 精灵） | 1200 | **1200** |
| 一条管线（本版） | 1200 | **1** |

拆回两条会直接退化成 1200 次 draw —— 别拆。

### 6. UI pass 必须在 `PostFx::render` **之后**

UI 颜色是作者按屏幕观感调的，不能参与曝光 / 色调映射 / Bloom。放在后处理
之前，调一下曝光血条就跟着变亮变暗。

### 7. 宿主的帧指纹必须混入 UI 内容签名

编辑器视口有指纹门控（输入不变就整帧跳过）。UI 的变化（悬停变色、血量数字
跳动）**不在场景签名里**，不混入就等于"场景没动 → UI 冻住"。
`UiRenderer::prepare` 返回内容签名，`SceneRenderer::render` 用 `mix_bits` 混进
场景签名。

### 8. 颜色有三个空间，各自约定不同

| 位置 | 空间 | 原因 |
|---|---|---|
| 组件字段（RON） | **线性 RGBA** `[f32; 4]` | 与材质 / 灯光一致；渲染直接可用 |
| 脚本 API | **sRGB 0..1** | 美术 / CSS 直觉；入口 `to_linear()` |
| egui 取色器 | **线性** | `color_edit_button_rgba_unmultiplied` 自己转显示空间 |

第一版在取色器上多套了一次 `to_srgb()`，色块比画面亮一大截（截图里按钮显示
成浅蓝）。改之前先确认函数要的是哪个空间。

### 9. UI 指针由宿主映射，运行时**不猜**

`World::set_ui_viewport` / `set_ui_pointer`（视口物理像素）。运行时拿不到
"视口在窗口里的位置 / DPI"，自己从 `mouse_pos` 推一定会错。
- 编辑器：`input_bridge::viewport_pointer`（减视口原点 × DPI，视口外返回 None）；
- 游戏：winit 的 `CursorMoved` 本来就是物理像素，但要等 `has_cursor()` 为真
  —— `mouse_pos` 的初值 `(0,0)` 是个合法位置，直接传会让左上角一开窗就"悬停"。

### 10. 没有 UI 时必须是零成本

`UiTree::build` 与 `Painter::build` 都以 `entities.iter().any(|e| e.ui.is_some())`
开头。少了这条，2000 个纯 3D 实体的场景每帧要往 HashMap 里塞 2000 条。

## 十七、材质资产（`.mat`）与导入参数接线（2026-10-21）

**要改的东西**：`MaterialAsset` / `Entity::material_asset`、
`xgame-render::material_library`、`ScenePipeline` 的批次键、glTF 加载器、
Assets 面板、Inspector、`material_*` 脚本 API、`--check` / `--migrate-assets`。

### 1. `.mat` 是一份**完整材质**，不是覆盖层

`MaterialAsset { base_color, metallic, roughness, albedo }`，语义固定：

- `base_color` / `albedo` 与模型自带颜色 **相乘**；
- `metallic` / `roughness` **替换**模型值（材料身份，乘系数没有直觉含义）；
- `albedo` 为空 = 用 1×1 白纹理 —— **不回退到模型贴图**。

最后一条是刻意的：如果空 albedo 保留模型贴图，"换材质"就会变成"有时换、
有时不换"的玄学。想保留模型贴图就别引用资产，用逐实体覆盖微调。

**优先级只有一条链**：模型材质 → 材质资产 → 实体覆盖（`Entity::material`）。
覆盖在资产的结果上逐字段打补丁，两者正交；脚本 `set_material` 写的是覆盖，
不会清掉 `material_asset`。

### 2. GUID 边界不许多一个

- 场景 / 预制体里的 `Entity.material_asset` 磁盘存 `guid://…`（与模型同款）；
- `.mat` 里的 `albedo` 也在 `load_material` / `write_material` 边界换成路径 / GUID；
- 渲染热路径只认**项目相对路径**，`MaterialLibrary` 的缓存键就是路径。

别把 `guid://` 传进 `MaterialLibrary`：它每帧都要查表，解析 GUID 会变成热路径
成本；而且同一个材质用两种写法引用会被当成两份。

### 3. 材质库住在 `ScenePipeline`，失效是显式的

`MaterialLibrary` 管 `.mat` 解析、albedo 纹理上传、绑定组与负缓存：

- 按引用缓存 `None`（坏文件 / 没绑项目）—— 坏 `.mat` 一帧只读一次，不刷日志；
- `MaterialKey::{Model(id), Asset(id)}` 两个命名空间：模型材质随模型缓存走，
  资产材质跨模型共享；
- `set_project` / `invalidate` 清空资产材质缓存并把 `revision` +1；编辑器把它
  混进渲染指纹，保存 `.mat` 或改导入设置后调用，否则"改了文件但视口不动"。

### 4. 批次键必须带材质

不透明批次键 = **（图元地址, 材质 key）**；半透明 draw 也带 key（它们本就不合批）；
阴影批只看深度，保持图元地址。原因：同一个 `builtin://cube` / 同一份 glTF 网格，
两个实体挂不同 `.mat` 时，按图元合批会在一次 `set_bind_group` 里把整批盖成
最后一份材质 —— 表现为"两颗箱子同色"。回归钉子
`material_assets_split_opaque_batches`：不同资产 = 2 批，改成同一资产 = 1 批。

### 5. `model_scale` 在加载边界烘焙

缩放因子乘四处：顶点位置、节点平移、动画 translation 轨道、逆绑定矩阵平移
（`w_axis.xyz *= s`）。**不要**只在世界矩阵外乘一层：画面会缩放，但物理碰撞、
包围盒与射线拾取仍按原尺寸 —— 三者错位比不缩放更难查。非有限 / ≤0 的缩放
在读取 `.meta` 时退回 `1.0`。

### 6. 纹理导入设置走 `TextureOptions`

`Texture::from_rgba8_with` / `from_file` 接 `TextureOptions { srgb, nearest }`；
模型贴图与材质 albedo 都按 `.meta` 读取（默认 sRGB + 双线性）。纹理缓存键是
路径，所以**改 `.meta` 后必须清缓存**（编辑器已调 `invalidate_assets`）；
独立游戏只在启动时读一次，不做文件监听。

### 7. 编辑器：草稿 + 显式 Apply

材质编辑器（Assets 里选中 `.mat` 后点「编辑材质…」弹出的浮窗）改的是
`MaterialDraft`，点 Apply 才写盘，Revert 丢弃：

- 写盘有 IO + GPU 纹理重传，逐帧写会把一次拖动变成几十次落盘；
- 撤销栈是**场景快照**，不该混入资产文件的历史（所以材质编辑本身不可撤销，
  Revert 是它的替代品）；
- 播放态整体禁用（与"运行时副本不算改动"一致）。

Tint 的 `color_edit_button_rgba_unmultiplied` **只在 `response.changed()` 时回写**：
该控件会先转成 `Color32` 再无条件写回 `[f32; 4]`，直接传草稿字段会让打开
`Wood.mat` 立刻显示「未保存」，Apply 还会把磁盘颜色悄悄量化。

浮窗必须由应用层在所有 dock 面板之后调用（`assets::show_overlays`）：在 Assets
的 `show_content` 里画时，后画的 Output Log 会在 1280×720 下盖住窗口下半截，
且 `ScrollArea` 的期望高度会让窗口自动尺寸少算最后一行。

指派材质是场景改动，会压撤销栈。三个入口共用 `EditorState::assign_material`：
Inspector 下拉、Assets 双击（给当前选中实体）、拖到视口（优先鼠标下实体，
其次选中实体；拖到空白且无选中时给提示，**不会**生成新实体）。

### 8. 检查与迁移的契约

`--check` 新增 `material_refs` / `missing_materials` / `missing_material_textures` /
`invalid_materials`；同一条材质路径被 N 个实体引用只检查一次。`--check` 仍严格只读。
`--migrate-assets` 除了场景 / 预制体，也改写 `.mat` 里的 albedo 字面量，并给
`.mat` 自己补 `.meta`。MCP `project_check` 把这四项原样暴露为 JSON 字段（字段名是契约）。

### 9. 刻意的限制

- 只有 albedo 一个贴图槽，没有法线 / 金属-粗糙 / 自发光贴图；
- 没有材质变体 / 继承 / 实例参数；
- 没有材质缩略图预览与文件监听（保存后靠显式失效，刷新靠 ⟳）；
- 脚本 `set_material` 一次性写颜色 + 金属度 + 粗糙度三个字段，不提供逐字段清除
  （要清就 `clear_material` 或改用资产）。

## 十八、粒子系统：运行态不进实体 + 确定性模拟 + 场景 pass 内 billboard（2026-10-21）

### 1. 模拟层的位置：新 crate，不住 runtime 也不住 render

粒子位置 / 速度是运行态，量大且每帧全变。三个候选位置都被否：

- **进 `Entity`**：场景 diff、撤销快照、脏检查全部失真（UI 的 `state` 字段在 §十六
  已经示范过这个坑 —— 运行态就地挂组件比另开一张表少一份同步义务，但那只适合
  "每实体一小块"的 UI 状态；粒子是"每实体几百个浮动点"）。
- **进 render**：无头运行没有渲染器，却要在 `--headless` 报告里报粒子数；
  而且"换个视角就重算一遍模拟"是错的（模拟不该知道相机）。
- **住 runtime 字段**（选定）：`World::particles` 与 `AudioEngine` / `PhysicsWorld`
  同级，是三宿主共用的编排者；渲染只是消费者。core 只留声明式 `ParticleEmitter`。

模拟与渲染之间只靠 `&[ParticleQuad]` 通信（世界中心 + 世界半边长 + 线性 RGBA +
blend）。这条缝就是将来上 GPU 模拟的接口：换掉 `xgame-particle` 的内部实现，
三个宿主一行不用改。

### 2. 确定性：一把 RNG per 发射器，且刻意不用 `rand` / `SystemTime` / 哈希序

同一颗种子 + 同一串 dt ⇒ 逐位相同的四边形序列。无头截图与回归测试的地基。
所以：每发射器一把 xorshift（种子取组件 `seed`），所有随机数只从这一把流里取；
绝不用 `thread_rng()`（不可复现）、`SystemTime`（同）、`HashMap` 迭代序（每次运行
发射器顺序都不同）。代价：跨编译器不保证逐位一致（f32 运算顺序由代码固定）——
对截图回归够用，不作为跨平台承诺。

### 3. dt 用渲染帧而不是固定步长；update 之后推进

- **渲染帧 dt**：粒子是纯视觉，跟着画面走比跟着物理走更合理（与动画时钟同一取舍）。
  无头运行 dt 固定，所以仍逐位可复现。
- **放在 `update` 之后、音频之前**：脚本这一帧写的 `particle_burst` 当帧就能炸出来
  （"按下开火键 → 这一帧看见火花"）。放前面则慢一帧，手感差。

### 4. 渲染：为什么在场景 pass 里，而不是像 UI 那样在后处理之后

粒子是**场景里的东西**：要被几何遮住（深度测试开）、要参与曝光 / 色调映射 /
Bloom（加色火焰写 2.0 的亮度就该在 Bloom 里晕开）。UI 的规矩正好相反（颜色是作者
按屏幕观感调的，见 §十六），因此落在 pass 的不同侧。

深度**写关**：粒子之间不互相遮挡（半透明物体互相遮挡会很丑），也不污染后续 pass
的深度。Alpha 混合片元输出**预乘**（`rgb * coverage * alpha`），管线用 `src = One`
—— 用 `SrcAlpha` 会把 alpha 乘两遍，烟雾薄一半。Alpha 远→近排序；Additive 不排
（加法可交换）。

### 5. billboard 朝向从 `view_proj` 逆矩阵现算

取 NDC 近平面上的「左-右」「下-上」两对点映射回世界空间做差，相机基就出来了。
这样渲染入口只多一个 `quads` 参数；让三个宿主各自传相机 right / up 的话，有三个
会写错的地方，且每次加新宿主都要再传一遍。

### 6. 帧调度与指纹：两个读数，缺一不可

- `particle_signature` 进渲染指纹（`mix_bits`）：静止时恒定（静态帧照旧跳过），
  有粒子在飞时每帧都变。缺了它，"只有粒子在动"会被静帧门控整帧跳过 —— 火焰看起来
  是冻住的。
- `particles_animating` 进帧调度 `animating`：视角不动、只有粒子在飞时必须继续
  出帧，否则火焰一格一格地跳。

两者是不同问题（"画面变了吗" vs "还要不要出帧"），`viewport_animating` 只覆盖前者。

### 7. 组件语义

- **`duration` / `looping`**：`duration > 0` 时只在窗口内发射，非循环到点停；
  循环则每轮把累加余量也清零（否则"每一轮都多一颗"）。
- **`max_particles` 是硬顶**：满了丢欠账不攒（一旦有空位会瞬间灌满）；单帧最多
  补 256 颗，`rate` 手滑写成 1e5 也不会一帧锁死。
- **重力不取自物理世界**：火焰要往上飘、烟要慢慢散，与场景全局重力无关；粒子是
  纯视觉，不该被物理世界的参数牵着走。
- **出生点随实体世界变换，出生后活在世界空间**：实体移动不拖着已飞出的粒子走
  （Unity `Simulation Space = World` 同款）；实体缩放不参与尺寸（尺寸是绝对世界
  单位，否则同一个火苗挂在不同大小的物体上大小不一）。
- **实体删除 ⇒ 粒子立即消失**：没有实体做锚点的粒子属于泄漏；爆炸类特效用
  `duration` 一次性发射器表达，而不是靠"删掉实体让粒子继续飞"。
- **`burst` 是 `#[serde(skip)]` 的运行态请求位**：模拟层消费后清零，天然"一次性"；
  可累积（连按两帧 = 两次爆发相加）。`data_eq()` 忽略它，脚本写 burst 不会让
  编辑器显示未保存。

### 8. 加载边界钳制

`sanitized()` 在 `ProjectHandle::load_scene` / `load_prefab` 各一道（与 `sanitize_ui`
同款）。NaN 的半径 / 颜色会让 GPU 拿到垃圾实例，表现是"粒子整块消失或糊满屏"。
非有限值退回**默认值**而不是钳到上界：`inf` 几乎总是手改坏了，猜"作者想要极快"
不如回到一份确定可用的配置。

### 9. 刻意的限制

- CPU 模拟：万级以上粒子会吃满一个核。真要上万，上 GPU 变换反馈 / compute
  （§1 的缝已经留好）。
- 只有软圆片一种片元形状：没有图集帧动画 / 网格粒子 / 拖尾 / 纹理粒子。
- 编辑器内没有发射器预览（编辑态不模拟，Play 才喷）—— 另造一条编辑器内模拟
  回路不值得，Play 就是那条回路。
- 粒子不与场景碰撞。

## 十九、编辑器 Profiler：采样口径 + 停靠区布局的两条硬规则（2026-10-21）

### 1. 两条时间口径：FPS 只认连续帧，纵轴只认中位数

- **FPS 只统计 `live` 帧**（帧调度决定继续出帧的那些）。帧调度在静止界面上会停帧，
  停帧期间没有 `update()`，所以"停帧后重新出帧那一帧"的 `dt` 是整段空闲时长。
  把它算进平均帧时间 → 用户打字停三秒再动一下，FPS 塌到个位数，然后截图/汇报里
  就写着"编辑器 5 fps"。这是测量假象，必须在口径上掐死：空闲帧单独计数、图上压暗，
  FPS 只用 live 帧。
- **图的纵轴按中位帧 ×3 定标**（下限 6ms / 上限 100ms），**不用最大值也不用 p99**。
  一次 80ms 的唤醒间隔会把其余 599 帧压成一条贴底的线；反过来按 33ms 固定画，
  300fps 的构建里所有柱子只有 9% 高。中位数描述"典型帧"，3 倍余量让抖动有形状；
  超出的柱子裁到顶，图例里写明纵轴上限。

### 2. 采样只写预分配槽位，面板只读

`Profiler` 是 600 帧定长环，`record` 一次只写一个槽位（稳态零分配）；面板每帧
现算 `Summary`（600 个 u32 排序，微秒级）。**采集与绘制完全解耦**：面板没打开时
照样采（切过去就能看到刚才那段），关掉面板也不省成本（一次写入）。
面板**不 `request_repaint`** —— 出不出帧由 `frame_policy` 决定；为了"图能动"而
在此强推重绘，会让静止的编辑器永远满速。

### 3. `CentralPanel` 必须最后画（状态栏在它之前）

egui 的 `CentralPanel` 会把**当时剩下的整块矩形**全吃掉；之后再加的
`TopBottomPanel` 不会让它缩短，只会叠在它上面。此前状态栏画在停靠区之后，
于是停靠区底部有 24px 永远压在状态栏底下：Console 是滚动列表看不出来，
Profiler 的绘制读数整行正好落在那条缝里（1280×800 截图里"一行被切掉半截"）。

**新面板里任何"贴底"的内容都要知道这条**：面板的 `available_height` 就是它的真实
可视高度（状态栏已经让位），别再自己减一个魔法数。

### 4. 脚注高度按字体行高现算，且在分配"吃高度"的控件之前扣掉

流式布局是"画到哪算哪"：先给图 `available_height - 常量`，图之后剩下的空间才是
脚注的。写死 14px 会切掉半行；写死 18px 会少算行距、把第二行脚注顶到面板外。
正确写法：`fonts(|f| f.row_height(10.5pt)) + item_spacing.y`，在 `allocate_exact_size`
之前把两行扣掉。

### 5. Profiler 与 `frame_probe` 分工，别合并

探针是**离线**口（`XGAME_FRAME_LOG` 落盘、事后脚本分析，字段为输入延迟 / 丢弃重跑
设计），面板是**在线**读数（不落盘、零分配、滚动窗口）。合并会让探针多背一条永不
落盘的路径，面板反过来还得解析文本格式。两者共用同一个时间口径（`stable_dt`）即可。

### 6. 刻意的限制

- 帧级读数，不做函数级采样（引 profiler crate 或 `#[profiling]` 埋点才能有栈；
  定位"渲染还是物理慢"现有两段够用）。
- 无帧快照 / 点选回看；窗口 600 帧，长时段趋势仍看探针。
- 面板与 Output Log 同组、默认不激活：老截图逐像素不变，`--ui-profiler` 才切过去。

## 二十、相机：实体组件 + 本地 +Z 朝向 + 单入口解析机位（2026-10-21）

这一轮之前，"镜头在哪"是三个宿主各自写死的常量：`xgame-game` 里是
`(5,5,5) → 原点` 的硬编码 `look_at`，编辑器视口用自己的自由相机（Fly），
无头截图是 `auto` 自动取景。也就是说**玩法代码无法决定镜头** —— 做跟随、
过肩、俯视、过场，全都得改引擎源码。这次把相机补成实体组件，同时给三处宿主
接同一根线。

### 1. 相机是实体组件，不是场景级数据

`Transform` 的层级、父子带动，是相机最需要的能力（骑在载具上、挂在骨骼上、
肩视角挂在角色下面）。如果相机像 `Scene::lights` 那样存场景级数组，那么每一帧
都得自己写一遍"父节点世界变换 × 偏移"的换算，而且这套换算会和 `hierarchy()`
的遍历两套逻辑并行维护。

代价是**每个实体多一个 `Option<Camera>`**（`Entity` 已经从 6 个 `Option` 涨到 11 个）。
接受这个代价的理由和当年 `Light` 一样：组件化之后，"是不是相机"就是数据问题，
不是类型问题 —— 运行期切相机不需要重建实体，序列化也自动跟着实体走。

**为什么不做单独的 `Camera` 实体类型**：本引擎的实体是**纯数据行**（`Entity`
没有 enum 分派），加类型标签会立刻分裂出"相机能不能挂脚本/能不能挂碰撞体"
这类需要逐个回答的问题，而它们现在的答案都是"能，无所谓"。

### 2. 本地 **+Z** 是镜头朝向

这是本引擎唯一一次在这种约定上可能被误读的地方，所以写死并测死：

- `Camera::forward(rotation) = rotation * Vec3::Z` —— 和 `Transform::forward()`、
  glTF 模型的"正面"完全一致。美术把模型脸朝 +Z 摆进来，相机实体也脸朝 +Z 摆，
  看到的就正好是模型正脸。
- 但**右手系视图空间的镜头看向 −Z**。所以视图矩阵永远是
  `Mat4::look_at(position, position + forward, up)`，**绝不手拼 `look_at_rh` 的
  `-forward` 参数**。少一次符号翻转，就少一个"相机反着看"的 bug。
- `up` 也从旋转里取（`rotation * Vec3::Y`），不额外存 `up` 字段：存了就会有
  "旋转改了 up 没跟着改"的不一致状态，而相机 roll 本来就应该由旋转表达。

`look_rotation(forward, up_hint)` 是反解（朝向 → 四元数），保证 +Z 落在 `forward`
上；`forward` 退化（零向量 / 与 `up_hint` 共线 / 含 NaN）时返回**单位四元数**
而不是 NaN 矩阵 —— 一次坏输入不该让整屏变黑。

### 3. 主相机解析只有 `Scene::active_camera_index` 一个入口

规则三段，写在 core 里，三宿主都只能读它：

1. 第一个 `camera.active == true` 的实体；
2. 没有 active 的 → 退回**第一台**相机（`first_any`）；
3. 一台都没有 → `None`（宿主自己决定兜底机位）。

为什么不要求"必须恰好一台 active"：场景里临时放两台相机试构图是常态，硬性
唯一性校验会让"另存一份看看"变成报错。反之 `set_active_camera` 是**独占式**的
（脚本 API），因为它表达的是"从现在起用这台"——不做独占，第二次调用就永远
轮不到第二台（第一台还是 active）。两个方向的不对称是有意的：
**读宽松、写严格**。

### 4. `look_at` 只改朝向，不改位置

脚本里最常写的是 `set_pos` + `look_at(target)`。如果 `look_at` 顺便"保持距离"
（像某些引擎那样做 track-to），那么跟随相机就得反推距离、越写越绕。
分开之后两条语句各自可预测，跟随相机的写法就是：

```lua
local p = get_pos(target)
set_pos(self, p.x + OFF.x, p.y + OFF.y, p.z + OFF.z)
look_at(self, p)
```

`look_at` 内部把世界朝向**经父节点逆变换**折回局部旋转，所以挂在父节点下面的
相机也不会因为父节点旋转而转头转错方向。

### 5. 坏参数在 core 钳制，不在出问题的宿主钳制

`Camera::sanitized()`：`fov ∈ [1°, 179°]`、`near ≥ 0.001`、`far ≥ near + 0.001`、
NaN/Inf 换默认值。理由：坏 fov 的表现是**整屏黑或整屏拉伸**，且发生在最下游的
投影矩阵里 —— 那时候已经没有任何上下文（哪个实体、哪个脚本写的）能报出来。
钳在数据进矩阵之前，是唯一能保住"坏数据不出屏"的位置。

### 6. 三宿主共用一条机位解析，编辑器 Play 态让位

| 宿主 | 编辑态 | Play 态 |
| --- | --- | --- |
| `xgame-game`（独立游戏） | —— | `world.camera_view()` |
| 编辑器视口 | 自由相机（Fly） | **游戏相机**，自由相机让位 |
| 无头 `--screenshot` | `explicit` → `scene` → `auto` | 同左 |

编辑器 Play 态切到游戏相机是 Unity Game 视图的语义：**Play 时你看到的就是
玩家看到的**。为了让这件事在视觉上不引起误解，Play 态下：

- 飞行相机自动退出（`fly_state = false`），拖拽不再偷偷改机位；
- HUD 右上角角标从 `Cam` 改成 `GameCam` 并显示游戏相机坐标 —— 否则用户会以为
  自己还在自由飞，然后疑惑"为什么 WASD 不动了"。

无头截图的优先级顺序是**显式参数最高**（`--camera-pos/--camera-target` 是调试
手段，必须能覆盖场景相机），其次是场景相机，最后才是自动取景。报告里的
`camera.mode` 就是这个判定的回执：`"explicit" | "scene" | "auto"`。**它是契约字段**，
因为"这张基准图到底是谁拍的"决定了比对失败时该怀疑渲染还是该怀疑场景。

一处已知的不一致：截图路径**忽略**场景相机的 `near/far`（沿用自动取景的
0.05/500），因为基准图是看构图的，不是做深度精度验证；这条写在
`Docs/无头运行.md` 里，不打算"修"。

### 7. Inspector 的旋转统一 YXZ

Inspector 此前按 XYZ 分解显示，而脚本 `rot` 与 `set_rot` 用 YXZ。同一个朝向
在两处显示成两套数字（样例相机实测 `153.415 / −46.291 / 160.153` vs
`−130.602 / 18.000`），用户会合理地认为有个地方算错了。

现在统一 YXZ（先绕 Y、再绕 X、最后绕 Z），并把 `|v| < 1e-3` 抹成 0 —— 否则
`-0.000°` 会让人以为有微小的非零 roll。

### 8. 刻意的限制

- **单机位**：不做多相机 / 分屏 / 画中画。`active` 已经能表达"用哪台"，
  要做分屏得先让 `render` 接受多个 view-projection，那是另一个工作量级。
- **不做相机切换过渡**（淡入淡出 / 插值）：属于玩法层，脚本两行 `lerp` 更灵活。
- **不做景深 / 运动模糊**：`postfx` 里没有深度重建，加了也是一次性大改。
- **不做相机调试可视化**（视锥线框）：目前靠 HUD 坐标读数定位就够。

## 二十一、编辑器偏好与停靠布局：出厂值只读 + 坏布局回退（2026-10-22）

### 1. 偏好是编辑器级，单独一份 `editor.ron`

相机手感、网格开关、面板布局描述的是"这个人怎么用编辑器"，换项目不该重置；
重力 / 步长是项目内容，改了对玩家行为有影响，归 `project.ron`。两者不混。

也不和 `recent_projects.ron` 合并：最近项目坏了丢了无感，布局坏了会让人一打开
编辑器就找不到面板。分成两份文件后，一次布局序列化失败不会连最近项目一起丢。

位置：`%APPDATA%\XGameEngine\editor.ron`（其它平台按 `XDG_CONFIG_HOME` / `~/.config`）。
`XGAME_CONFIG_DIR` 可以整体覆盖配置目录 —— 无头验证与便携运行都用它隔离，
测试不会碰用户真实的布局与最近项目。

### 2. 从磁盘读回来的布局必须先校验

`editor.ron` 是**外部输入**：老版本写的布局可能少了后来新增的面板，手改过的文件
可能有悬空 tile / 环 / 重复 pane / 孤儿 tile。`egui_tiles::Tree::ui` 假定这些不变量
成立，直接喂坏树轻则少几个面板，重则整帧 panic。

`dock::is_usable_layout` 的四条判据（全部满足才恢复）：

1. 根存在，且从根能走到的每个 tile 都真实存在；
2. 没有环 / 重复引用（同一个 tile 不能走到两次）；
3. 没有不可达的孤儿 tile（否则会跟着下次保存越积越多）；
4. 每个 `PanelTab::ALL` 变体恰好出现一次 —— 少一个就永远打不开那个面板，
   多一个说明文件被改坏。

校验不过 → 记一条 warning、本次用**出厂布局**继续跑，**不阻塞启动**；
`layout_for_startup` 本身不修改磁盘内容，等下一次保存触发时用实际使用的布局
覆盖它（自愈）。空容器也按坏数据处理：它不显示任何东西，只会让树多一层。

恢复后还要 `normalize_layout`：用固定的树 id `"editor_tree"` 重建一次 `Tree`。
`egui_tiles` 把这个 id 当页签 / 分隔条状态的 key，旧文件里的 id 可能不同或被人
手改过；重建只花几个分配，换来"布局状态一定挂在当前树 id 下"。

### 3. 保存只在低频时刻，且内容不变不写

触发点只有五个：

- 指针**松手**那一帧（拖页签 / 拖分隔条结束）；
- Preferences 窗口的 **Apply**（数值 + 当前树一起写）；
- **Reset Layout**（立即重建出厂布局并写盘）；
- 返回枢纽 / 关闭项目；
- `eframe::App::on_exit`（干净时直接点窗口 X 不走关闭确认分支）。

`sync_layout` 比较整棵树，相同就返回 `false`，调用方**不写盘** —— 同一棵树
反复同步（松手 / 关闭 / 退出）不该反复写磁盘。第一次运行时 `layout` 是 `None`，
第一次松手或关闭会把实际使用的布局写下来；之后只有布局真的变了才会再写。
比较 + 克隆只在上述低频时刻发生，不进每帧热路径。

写盘先写 `editor.ron.tmp` 再 rename；Windows 的 rename 覆盖目标，杀软 / 索引器
短暂占用导致失败时退回直接写。拖页签时保存是"顺手"发生的，写到一半被杀的半截
RON 会让下次启动静默回退默认布局，用户的调整全白费。

### 4. `--ui-shot` 默认只读（截图确定性是硬约束）

截图必须永远对应**出厂界面**：开发机换过一次布局 / 关过一次网格，不能让基准图
跟着变。所以 `--ui-shot` 默认：

- 不读 `editor.ron`（用 `EditorPreferences::default()`）；
- 不写 `editor.ron`（`save_preferences = false`，Apply / 松手 / on_exit 全部跳过）。

需要验证恢复逻辑时显式加 `--ui-restore-prefs`；要在截图里打开偏好窗口加
`--ui-preferences`。正常启动（无 `--ui-shot`）始终读写真实配置。

### 5. `PanelTab` 变体名是磁盘格式

布局序列化用枚举变体名（`SceneView` / `Profiler` …），和 `egui_tiles` 的 pane
variant 一起构成磁盘格式。**改枚举名等于让老布局失效**；失效时会走上面的校验
回退出厂布局，不会崩，但用户的布局会丢一次。要改名就得同时写迁移，不能只改代码。

### 6. 刻意的限制

- **主题选择没做**：当前只有固定深色主题，加一个只有一项的下拉框没有意义。
- **`gizmo_snap` 没进偏好**：字段在 `EditorState` 里但还没有任何 UI / 逻辑消费，
  存一个永远不生效的值只会误导人。
- **布局是全局的，不按项目存**：同一台机器上换项目仍用同一套面板位置；按项目存
  会让"我习惯的布局"在每个新项目里重新丢一次。
- **不做关闭 / 打开面板**：七个面板是产品定义的一部分，校验要求全部存在；
  真要做可关闭面板，必须先放宽第 2 节的判据并定义"面板关闭后布局怎么表示"。
- **Cancel 不回滚布局**：布局是直接拖动产生的，回滚它需要额外维护快照；
  「恢复默认布局」已覆盖"弄乱了想重来"。数值走草稿 + Apply，不在此列。
- **多窗口 / 独立面板窗口**不做：egui 单窗口，成本与收益不成比例。

## 二十二、多场景编辑：当前场景与启动场景分离（2026-10-22）

### 1. `current_scene` 与 `entry_scene` 是两件事

- `current_scene`：编辑器**此刻正在编辑**的场景文件（项目相对路径，只在内存）；
- `entry_scene`：游戏**从哪里启动**（`project.ron` 的字段，构建 / 独立游戏 / 下次
  打开项目都读它）。

早先两者是同一个值：`save_scene` 永远写 `entry_scene`。只有一张地图时等价，一旦
打开第二关，在 Level2 里按 Ctrl+S 会把入口场景覆盖成 Level2 的内容 —— 这是会
**静默毁掉关卡**的语义，必须先拆开。

规则：

- **Save / Ctrl+S** 写 `current_scene`，不碰 `entry_scene`；
- **Save As** 写一个新文件、把编辑器切过去，**不改启动场景**；
- **新建场景**落盘并切过去，**不自动设为启动场景**；
- 改启动场景只有一个显式入口：Scenes 菜单的 **Set Current as Startup**
  （`set_startup_scene`，写 `project.ron`，下一次打开 / 构建 / 独立游戏生效）。

"另存为 = 让游戏从这里开始"曾经是旧语义；它把"做一个副本"和"改发布配置"绑在
一起，用户只想备份关卡时也会悄悄改掉启动场景。现在拆开后两个动作各自可预期。

### 2. 场景列表以磁盘为真相源

`Scenes/*.ron` 就是全部场景，不新增 `project.ron` 的场景清单字段：

- 用户在资源管理器里加 / 删关卡，菜单下次打开就能看到；
- 不会出现"清单说有三个、磁盘上只有两个"的第二真相源；
- 入口场景与当前场景即使不在 `Scenes/` 下也会补进列表（老项目可能用自定义目录）。

`ProjectHandle::list_scenes()` 只收 `.ron` 且排除 `.prefab.ron` —— 预制体也是
RON，混进场景列表会被当成关卡打开然后写坏。

### 3. 场景路径是外部输入，必须校验

路径来自设置窗口、对话框、菜单（以后还可能来自脚本 / MCP），统一走
`normalize_scene_relative`：

- 只接受**项目相对路径**：拒绝 `/abs`、`C:` 盘符、UNC；
- 拒绝任何 `..` 组件（保存时越界会把文件写到项目外，读取时越界等于允许读任意文件）；
- 必须以 `.ron` 结尾，且拒绝 `.prefab.ron`。

新建 / 另存为的**名字**再额外拒绝路径分隔符与 Windows 非法字符（`:*?"<>|`），
由 `scene_path_for_name` 补上 `content.scenes_dir` 与 `.ron`。同名文件已存在时
**拒绝而不是覆盖**：一次手滑不该让整张关卡消失。

### 4. 切换场景必须重置跨场景状态，脏时先确认

`adopt_scene` 在换场景后清空：撤销栈、选中实体、折叠集合、Edit 组件副本、
Gizmo 悬停 / 拖拽、资源拖拽、Play 快照、脏检查 memo。这些状态都绑定上一张场景：
不清撤销栈会把旧场景整个撤回来，Edit 组件副本还会按 `(EntityId, slot)` 撞到新
场景的同名实体上。

有未保存改动时，菜单动作只挂起（`pending_scene_change`），由确认框三选一：

- **保存**：先 `save_scene` 当前场景，成功才切换；写盘失败弹窗留着；
- **不保存**：丢弃当前改动，继续切换；
- **取消**：清掉挂起请求，留在当前场景。

播放中**禁用**所有场景操作（菜单置灰 + 状态层硬保护）：`self.scene` 是运行时副本，
切场景会把 `play_snapshot` 的退路一起丢掉。

### 5. `--check` 覆盖全部场景

- **入口场景加载失败**：仍返回 `Err`（退出码 1）—— 启动契约断了，不是"某张关卡
  有点问题"；
- **非入口场景加载失败**：记 `invalid_scenes`，检查继续跑完（退出码 2）。多场景项目
  里一张关卡写坏，不该让整条命令失去"其他关卡怎么样"的视野；
- 根实体 / 引用检查对每张场景都跑；问题消息统一加 `<场景路径>: ` 前缀，否则
  多关卡的 `Ghost -> ...` 定位不到是哪一关；
- `entities` / `lights` 改为**全部场景合计**（`scenes` 字段给成功加载数）；
- MCP `project_check` 的 JSON 同步增加 `scenes` / `invalid_scenes`；退出码契约不变。

材质按路径**跨场景**去重：同一个坏材质挂在十张关卡的一百个实体上，只报一行。

### 6. 刻意的限制

- ~~**不做运行时 `load_scene` 脚本 API**~~ → **2026-10-22 已补（§二十五）**。
  当时的判断是"资源驻留与实体生命周期不是同一件事，留给独立一刀"——这个拆分
  是对的，补的就是那一刀：装载来源由宿主注入、切换只在帧末发生、只重置与实体
  绑定的状态。**"换一张正在编辑的文件"（编辑器 Scenes 菜单）与"运行期切关卡"
  现在仍是两条路**，前者动 `state.scene` + 撤销栈，后者只动运行时。
- **不做多场景同时打开 / 叠加编辑**：当前模型是一张场景一个文件、编辑器只认一张；
  Unity 那种 additive 多场景需要重做场景所有权与保存语义。
- **不在 `project.ron` 里维护构建场景清单 / 排序**：构建仍以 `entry_scene` 启动，
  全部场景文件随 `content_dirs()` 一起打包；清单 / 平台预设 / 图标版本号留给
  "构建设置"那一刀。
- **新建场景不自动设为启动场景**：新建关卡 ≠ 游戏从这里开始。要改启动场景必须
  显式点 Set Current as Startup。
- **不做场景重命名 / 删除的专用 UI**：文件操作交给资源管理器；列表每次打开现扫，
  不维护缓存，所以外部改动天然可见。

## 二十三、级联阴影（CSM）：视线深度切分 + 纹素吸附 + 每层一个 pass（2026-10-22）

### 1. 单级拟合法为什么必须换掉

阴影图的分辨率是固定的，正交视锥每开大一点，一个纹素覆盖的世界尺寸就大一
点 —— 这是"精度换覆盖"的死账。单级实现按**整场景包围盒**拟合，于是：

- 相机拉远看全景 → 盒子没变，但屏幕上每个像素对到的纹素变少 → 影子边缘糊成噪点；
- 场景里飞进一个远物体 → 盒子长大 → 全场景影子一起糊。

真正的解法不是"提分辨率"（4 倍面积换 2 倍精度，显存直接翻），而是**把距离切成
几段，每段单独拟合**：近段只需要罩住眼前几米，纹素自然细。这就是 CSM。

### 2. 切分口径：视线方向的线性深度

`splits[i]` 是"第 i 层的远平面距相机多远（世界单位，沿视线）"，**不是 NDC z**。

- NDC z 在透视下被非线性压缩（近处稀疏、远处挤成一片），按它切出来的段长在
  世界空间里完全不成比例，第一层会罩住半个场景；
- 线性深度对透视 / 正交、对任意 near/far 都可比，CPU 拟合与着色器选层用的是
  同一个标量：`dot(world_pos - camera_pos, forward)`。

切分用 practical split（λ = 0.7：对数项与均匀项的混合）。纯对数让第一层窄到装
不下脚下的地面，纯均匀又浪费近处精度，0.7 是 PSSM 论文与各引擎的常用折中。

**覆盖距离** = `min(相机远平面, 场景 8 角点在视线上的最远投影, 120)`：

- 编辑器相机远平面常是 1000，照它切等于把 99% 的纹素花在玩家看不见的地方；
- 按场景收紧能让小场景白拿精度；
- 120 是硬上限，防止"有物体飞出视野"把最后一级拉成一片糊。

最后一级的远平面**恰好**等于覆盖距离：浮点少一点点，就会在正好那一圈留下一道
"没有影子"的环。

### 3. 每层怎么拟合

1. **从 `inv_view_proj` 反推视锥 8 角点**，而不是让宿主多传一份 near/far。
   编辑器自由相机、游戏相机、无头截图三套调用各自组装矩阵，多传一份就有
   "传的和用的不是同一组"的可能，错了的表现是分层错位或近处一段没有影子 ——
   极难查。反推只需要渲染本来就有的那份矩阵。
2. **子视锥 = 近角点与远角点的线性插值**。透视下它与解析式
   `near + (d - near)/near · v_near` 恒等，正交下棱边本来就平行 —— 一个式子
   覆盖两种投影。
3. **逐轴求紧致包围**，不用外接球。子视锥是梯形，外接球比它胖得多，多出来的
   是纯浪费的纹素（单级实现当年图省事用了球，这里不能用）。
4. x / y 取**同一个尺寸**（正方形范围）：纹素在屏幕上是方的，PCF 的 3×3 核才
   不会在某个方向上被拉长成条。
5. 宽度向上取整到**整数个纹素**，再把中心**吸附到纹素网格**。相机连续移动时
   中心在格子之间跳，采样相位不变 —— 这就是 shimmer 的根因。
6. **深度范围的符号**：`look_at_rh` 的视空间"前方"是 -z，而 glam 的
   `orthographic_rh` 要的是**正的距离**（z_view = -near → 0，-far → 1）。
   所以 `near = -max.z - pad`、`far = -min.z + pad`。直接把 z 值传进去，整段深度
   会被推到 `[0,1]` 之外，表现是"全屏没有影子"—— 这个坑在写测试时被
   `shadow_cascades_cover_their_own_slab` 当场抓住。

### 4. GPU 侧的四条决定

- **深度图改成 4 层深度数组**，一层一级联。图集（2×2 象限）也能省一次绑定切换，
  但每层 UV 要各自缩放、PCF 在象限边界要夹紧，不值得。
- **阴影 pass 每层一个 render pass**。wgpu 不允许把 D2Array 视图直接当一层的
  渲染目标 —— 必须另建单层 D2 视图。采样用数组视图、渲染用单层视图，两套视图
  不是冗余。
- **每层矩阵走动态偏移**（`SHADOW_PASS_STRIDE = 256`），而不是每层一个绑定组：
  省三次绑定组创建，也不依赖 push constant 设备特性。主 pass 则一次读走整组
  级联（选层在片元里做）—— 两个 pass 对同一份数据的取法不同，所以分成两条
  缓冲，别混用。
- **绑定必须显式写 size（64 B）**。`as_entire_binding()` 会把绑定钉成"整条缓冲"，
  wgpu 于是只允许动态偏移 0，四层全画进同一层 —— 这个错不会崩，只会让影子出现
  在错误的位置，属于"必须靠规矩防"的那类。
- **剔除用最后一级的视锥**（覆盖最广）。用第 0 层会漏掉"近处看不见、影子却落在
  远处"的那批物体。

### 5. 为什么保留单级拟合 `fit_directional_shadow`

两条理由：它是"关掉 CSM"的等价退路，也是精度账的**基准**——测试里直接拿两者的
纹素尺寸比（第 0 层必须细于单级的一半），而不是只断言"没崩"。只留新代码的话，
这种"确实变好了多少"的问题就只能靠肉眼。

### 6. 刻意的限制

- **不做级间混合（blend band）**：边界处是阴影锐度的突变，不是接缝（相邻层覆盖
  连续的段，两边都有有效深度）。混合要一次额外采样，收益是消除"锐度跳变"，留到
  软阴影那一刀一起做。
- **不按光源方向扩展剔除视锥**去抓"画面外投影物"。当前只保证落在该层包围盒里的
  物体参与绘制；盒外的物体其影子本来也落不进这张图。
- **层数写死 4**：常量 `SHADOW_CASCADES`、`MAX_SHADOW_CASCADES`、WGSL 的
  `array<mat4x4<f32>, 4>` 三处必须一致，有单测钉住（漏改是"着色器越界读"）。
- **还没接到质量档位**：覆盖距离 / 层数 / 分辨率将来应该由 Quality 设置统一给，
  现在分别是常量与灯上的 `shadow_resolution`。

## 二十四、自动保存与崩溃恢复：副本只在 `.autosave/`，且"自动保存 ≠ 保存"（2026-10-22）

差距分析 P1 #14 / 编辑器产品化最后一处硬缺口。目标只有一句：**崩溃不要让人丢掉
一下午的工作**。为此定下的规矩，比实现本身更重要。

### 1. 副本落在 `<项目根>/.autosave/<场景相对路径>`

**绝不能**放在 `Scenes/` 下（哪怕是 `Scenes/.autosave/` 或 `*.autosave.ron`）：
`ProjectHandle::list_scenes` 是**递归扫描** `Scenes/` 下所有 `.ron` 的，副本一旦进去，

- Scenes 菜单会把它列成一个真场景（用户点一下就以"未命名副本"打开）；
- `--check` 会校验它（一次崩溃残留就能让 CI 变红）；
- `--migrate-assets` 会把它当场景改写。

放在项目根的点目录里，场景 / 预制体 / 资产三条扫描一条都碰不到。保留子目录结构
（`Scenes/Level2.ron` → `.autosave/Scenes/Level2.ron`）而不是压平成
`Scenes_level2.ron`：出问题时能一眼对上是哪个场景，不需要额外的映射表。

新建项目自带 `.gitignore`（`Build/` / `Plugins/` / `.autosave/`）——副本是"这台机器
这一刻的现场"，跟着项目入库只会在别人的 diff 里冒出与内容无关的整文件差异。

### 2. 自动保存**不是**保存

写副本之后：

- `saved_snapshot` 不动 → `scene_dirty()` 仍为真；
- 标题栏星号还在，关窗 / 回枢纽仍然要确认；
- `save_scene` 的语义一个字都没变。

反过来做（写副本就当"已保存"）会有两个具体后果：用户以为落盘了，实际磁盘上还是
两小时前的版本；关窗时被放行，那份"已保存"的内容其实还在 `.autosave/` 里。

### 3. 触发：计时器到点 + 场景脏

计时器**干净时也推进**。于是"改了东西之后最多等一个间隔"，而不是"每次改动后重新
计时"（后者在连续拖拽时永远不会到点）。代价是"刚打开就改一个字"也要等满一个间隔
—— 这段窗口由用户自己的 Ctrl+S 覆盖，可接受。

用 `Instant` **注入**时间（`autosave_tick(now)`），单测可以把时钟拨快三分钟去验证
间隔语义，不需要真的等。

### 4. 空闲停帧必须 `request_repaint_after`

这一条不做，功能在真机上**形同不存在**：编辑器界面静止后帧调度会停帧（见
`frame_policy`），`update()` 不再被调用，`autosave_tick` 也就永远不会被问"到点没"。
结果是自动保存只在"用户一直在拖东西"时触发 —— 恰恰是最不需要它的时候；用户一停手
去泡咖啡然后崩溃，刚好什么都没存。

所以 `AutoSave::wait(now)` 返回距下次到点的剩余时间，主循环在 `!live` 时
`request_repaint_after(wait)`：准点醒一帧，醒完继续睡。`wait` **刻意不看脏不脏**
（脏检查是 O(实体数) 而它每帧都会被问），代价是干净时每个间隔白醒一帧。

### 5. 副本只服务**崩溃**

- 手动保存成功后 → 删副本。不删的后果很具体：下次启动问"要不要恢复两小时前的
  版本"，用户点"恢复"就把刚保存的内容盖回去了（正确性问题，不是省磁盘）。
- 正常退出 / 回枢纽（含明确选"不保存"）→ 删副本。用户已经做过决定。
- 崩溃（进程被杀）→ 没有退出钩子 → 副本留着 → 下次打开弹恢复框。

### 6. 恢复之后仍然是**未保存**

恢复走 `adopt_scene` 之后再单独覆盖 `saved_snapshot = 磁盘版本`，于是恢复出来立刻
是脏的。把它标成干净等于谎报"磁盘上已经是这个内容了"，用户直接关窗就真丢了。

恢复后还会 `schedule_now()`：恢复出来的内容尚未进任何副本，中间再崩一次就白恢复了。

### 7. 写盘格式与 `write_scene` 同源

抽了 `scene_text()` 给两条路共用（GUID 编码 + `.meta` 补齐 + pretty RON）。不一致
的后果很隐蔽：副本里是路径、真文件里是 GUID，恢复一次就把引用退回路径，下一次保存
再编回去 —— 每次 diff 都像"引用被改过"，排查时找不到原因。

**原子写**（`.tmp` + rename）：自动保存是在用户没看着的时候写的，恰好那一刻断电
不能留下半截 RON —— 那比没有自动保存更糟，因为恢复流程会拿它去覆盖内存。

### 8. 刻意的限制

- **只探测入口场景**。切场景不弹框：多场景的副本仍然在 `.autosave/` 里（打开项目时
  Console 会说一句"另有 N 个场景留有副本"），等它作为启动场景打开时会问。
- **不自动恢复**。把场景换成一份"两小时前的现场"必须由用户点头。
- **不做多版本 / 时间线**（Unity 那种 `Temp/` 多份快照）。一份就够救命，两份以上是
  另一个产品决策。
- **`--ui-shot` 是只读的**（同 `--ui-shot` 不写 `editor.ron`）：截图会跑几十帧、还要
  等布局稳定，不该在用户的真实项目里留下副本，更不该让下一次正常打开多弹一个框。

### 9. 验证

- 新增 21 条回归测试（core 3 + editor 18）。新模块没有"旧实现"可对照（类型不存在，
  编译即红）；照仓库惯例，初版断言真的失败过 3 条（间隔语义 / `play_mode` 归属 /
  `create` 的 root），逐条修的是断言 —— 详见 PLAN 四十二。覆盖面：触发条件、脏标记不动、
  手动保存清除、间隔、Play 态跳过、不进 `list_scenes`、原子写无残留、恢复后仍脏、
  丢弃、正常退出、关闭开关、GUID 编码一致、新项目 `.gitignore`。
- 实机：造一份副本后 `--check` 仍 `scenes=1 / exit 0`，`--headless` 正常出图；
  `--ui-shot` 截图确认恢复框文案与三个按钮，且截图后副本字节数未变（只读）。

## 二十五、运行期场景切换：帧末唯一时机 + 只重置"与实体绑定"的状态（2026-10-22）

`load_scene` 是"游戏能做出来"的最后一道门槛（此前只能跑一张图）。它的难点不在
读盘，而在**什么时候换**与**换的时候清什么**——两者错了都不报错，只表现为难以
定位的串味。

### 1. 只有帧末一个时机，脚本只能"登记请求"

脚本的 `load_scene()` **不在调用点生效**：它进 `ScriptCommand::LoadScene`，
由 `World::apply_pending_scene_load` 在 `update` 的固定位置应用。三条理由都不可退让：

| 位置 | 为什么必须是这里 |
|---|---|
| 钩子都已返回 | 钩子执行期间 `scene` 正被 `&mut` 借给 `GameCtx`，中途换等于把脚下那份抽走 |
| 固定步长循环已结束 | 否则本步的 `pull_dynamic_bodies` 会把**旧**刚体位姿写进新场景的实体（新实体 id 与旧刚体表对不上，位置静默错位） |
| 在 `sync_bodies` / 粒子 / 音频之前 | 新场景的发射器与 autoplay 音源当帧就开始推进，不用空等一帧 |

代价是**新场景的 `start` 下一帧才跑**（与"脚本刚生成的实体"同一时机）。这条写进
`Docs/脚本API.md`，别当成 bug 去修。

一帧内多次请求**只认最后一个**：中间那些场景根本不会被装载，也就不该产生"装载了
又立刻丢弃"的物理重建与脚本重编译。聚合点在 `LuaHost::take_commands`。

### 2. 装载失败 = 不动 + 一条错误日志

`World::load_scene` 先装载、成功了才换。装不上就记一条 error 日志（来源写"运行时"）
继续跑旧场景：路径写错不该让游戏停摆，而且这条日志会进编辑器 Console 与
`--headless` 的 `logs.error`（→ 退出码 2），CI 与智能体都看得见。

**"宿主没接装载器"是单独一种错误**，不是静默 no-op。静默会让作者以为脚本写错了；
`World` 只收一个根目录，不该自己猜项目布局 —— 装载来源由宿主用
`with_scene_loader(project)` 注入（`ProjectHandle` 是共享资产索引的轻句柄）。

### 3. 换场景时**必须**清的，与**绝不能**清的

| 状态 | 清的理由 |
|---|---|
| 物理刚体 / `body_of_entity` | 实体 id 是进程内单调分配的，新场景 id 与旧的不重合；旧体既没人引用，还会继续参与模拟与射线查询 |
| `character_contacts` | 接触差分拿旧帧的接触面当基线，进新场景立刻误报 `on_collision_exit` |
| 脚本 `started` / `states` | 都按实体 id 存：不清则新场景的实体永远不跑 `start`，每实体状态全错位 |
| 粒子 | 旧发射器的粒子会留在新场景里飞，且找不到自己的发射器 |
| `audio_autoplayed` / 扫描计数 | 不清则新场景里"同名"的 autoplay 音源不会响 |
| UI 布局 / 交互捕获 | 悬停与按下指针指向已不存在的实体 |
| 组件实例 | 组件持有旧场景状态，且绑在旧实体 id 上 |

**不能清的**：脚本编译缓存、路径驻留表（`intern.rs` 的 id 永不清，见 §二 第 3 条）、
以及**日志 / 命令缓冲**。

最后一条踩过：第一版直接调 `LuaHost::reset_runtime_state()`（它连日志缓冲一起清），
结果"切场景那一帧的日志"全没了 —— 恰好是最该留下的诊断（A 场景的
`start:Scenes/A.ron` 就这么消失过）。为此单独加了 `reset_scene_state()`，
只清 `started` + `states`。

于是**脚本模块级全局变量跨场景保留**，与 Unity 不重载 domain 的语义一致：
"随实体走"的数据该用 `state_*` 或存进场景。这是刻意的，不是遗漏。

### 4. 编辑器 Play：切换不写回项目

Play 期间换场景只动运行时那份；Stop 时 `play_snapshot` 整个覆盖回来。因为编辑器
每帧与运行时 `mem::swap` 场景，换过场景后两边会在**下一帧自动收敛**到新内容
（`state.scene` 与 `world` 各持一个 `Scene` 对象，内容每帧交换一次）。
Console 会在 Stop 时说一句"Play 期间场景切到了 X"，否则用户会以为切过去的关卡丢了。

### 5. 无头报告新增两个契约字段

`scene_current`（跑完时所在场景）与 `scene_loads`（成功切换次数）。没有它们，
"这一跑最后停在哪一关"只能靠数日志猜。新增字段允许（读方按需取），
契约测试 `json_contract_has_stable_keys` 已同步。

## 二十六、关卡顺序是数据：顺序即索引、未配置即空、构建前逐关试装（2026-10-22）

上一刀把"换场景"做出来了，但"下一关"还得在每张关卡的脚本里写死路径：加一关要
改两处，删一关直接断链。这一刀把**关卡编排**变成 `project.ron` 里的一份有序清单。

### 1. 顺序即索引，启动场景仍是 `entry_scene`

`build.scenes` 的**下标就是关卡索引**，`entry_scene` 仍然是"启动哪一张图"。两者
分工明确：前者是"关卡轮转的顺序"，后者是"开局在哪"。

**没有让 `build.scenes[0]` 兼任启动场景**（Unity 是这么做的）。理由是本引擎已经有
`entry_scene`，而它被 `--check` 的硬失败、构建器的快速失败、编辑器"设当前为启动"
三处依赖。再造一个"启动来源"必然出现"改了清单第一项，游戏启动的图变了但没人知道"
这类事故 —— **一个事实只有一个真相源**。

代价是清单第一项与启动场景可能不一致（比如入口是"启动器"场景）。这不是错误：
`--check` 只提示"入口不在发布清单里"，因为那时脚本的 `scene_index()` 会返回 `nil`，
而"启动器场景不参与关卡轮转"是完全合法的编排。

### 2. 未配置清单 = **空**顺序，不退回 `[entry_scene]`

第一版写成"空清单 ⇒ 有效顺序 = 只有入口场景"，看着更"友好"，实际有毒：单场景
项目的脚本会拿到 `scene_index() == 0`，作者顺手写 `load_scene_at(i + 1)`，然后在
运行时撞越界。**返回 `nil` 是诚实的**：没有关卡顺序，就只能按路径切。
老项目因此也不需要任何迁移（`#[serde(default)]` 补一个空的 `build` 节）。

### 3. 下标 0 起，不折成 Lua 的 1 起

Lua 数组是 1 起，但 `scene_index` / `load_scene_at` 都用 0 起：它们俩天生配对
（`load_scene_at(scene_index(ctx) + 1)` 就是"进下一关"）。折成 1 起会让每个调用点
都要 `+1 / -1` 往返一次，错一次就是串关，而且错得非常安静。

### 4. `--check` 分两级：缺场景算问题，未列入只提示

| 情况 | 判据 | 退出码 |
|---|---|---|
| 清单指向的关卡不存在 / 路径越界 | `build_missing_scenes` | **2**（有问题） |
| 盘上有、清单没列 | `build_unlisted_scenes` | 0（提示） |

第二级必须是"提示"：Unity 的 Build Settings 也不会因为你多写了一张场景就判构建
失败。若把它算成 issue，每个配了清单的项目都会在 CI 里红，久而久之大家就把
`--check` 关了 —— **永远会响的警报等于没有警报**。

清单里的关卡会被**真正装载**（哪怕它在 `Scenes/` 之外，比如 `Levels/L1.ron`），
否则那些关卡的悬空引用永远查不出来。

### 5. 构建前逐关试装 + `--build` CLI

`build()` 现在会按清单把每一关读一遍再动手，失败就列出**全部**失败项（不是遇到
第一个就退 —— 作者往往一次改几处路径）。原因很实在：构建本身只是复制目录，
清单里的关卡少一个文件，构建**不会**报错，玩家却会在切关卡那一刻撞黑屏。

顺带加了 `xgame-editor --build <项目>`：起窗口点按钮那条路不适合 CI / 智能体
（拿不到退出码、捞不到错误文本）。它调的是**同一个** `builder::build`，只是不起窗口。
**没有**加 MCP 工具：`run_headless` 已经能验证运行时行为，构建是一个"产文件"的动作，
让智能体通过 CLI 跑更容易看清产物路径。

### 6. 面板用列表而不是文本框

版本号 + 关卡列表放在「⚙ 项目设置 → 构建」，列表用 ↑↓ 调整顺序。不用"逗号分隔
的一行文本"是因为**顺序本身是这份数据的语义** —— 让用户手打顺序，等于把
`index + 1` 的 bug 从脚本挪到配置里，而且顺序错了没有任何提示。

两个实现细节：

- **空行直接丢**，不报错。手改 `project.ron` 时留一个空串很常见，它不是"需要用户
  修的配置错误"，报错只会挡住整次 Apply。
- 校验失败的返回从**闭包**改成了关联函数 `EditorState::reject_settings`。闭包捕获
  `&mut self` 会把它锁到最后一个使用点，中间任何 `self.log_warning(...)` 都变成
  E0501 借用冲突 —— 补这一刀时撞上了，别改回去。

### 7. 路径规则收进 core

`normalize_scene_relative` 从编辑器搬到 `xgame_core::project`，`same_scene_path`
（0 分配的分隔符无关比较）也放在那里。消费方现在有四个：编辑器改清单、`--check`
校验清单、构建器试装、运行时 / 脚本的 `scene_index`。四处各抄一份的必然结果是
"检查通过、构建成功、运行时打不开"。

### 验证

- 新增 13 条回归测试（core 8：顺序解析 / 旧清单兼容 / 路径规则 / 清单装载 / 缺场景
  与越界 / 未列入提示 / 未配置静默；runtime 4：按索引推进 / 越界报错 / 无清单返回
  nil / 宿主入口；editor 1：草稿规范化与去重 + 越界在 Apply 挡住）。
- 全量 `735 passed / 0 failed / 7 ignored`；clippy 0 警告。
- 双关卡临时项目实跑：`--check` 打出 `check: build scenes=2 order=[...]` 且 exit 0；
  `--headless` 里脚本用 `scene_index(ctx) + 1` 推进 → `scene_loads: 1`、
  `scene_current: Scenes/Level2.ron`；把清单指向 `Scenes/Missing.ron` 后
  `--check` exit 2（`build scene missing`）、`--build` exit 1 并**不留半成品目录**。
- 设置面板截图（`--ui-settings`）确认版本号与两行关卡（↑↓ 首末项正确置灰）排版正常。

## 二十七、运行时预制体实例化：`spawn_prefab` 让内容能被玩法调用（2026-10-22）

编辑器里能把预制体摆进场景，但**脚本不能** —— 子弹、敌人、掉落物、技能特效
一条都写不出来，玩法永远停在"场景里预先摆好的东西"。这一刀把预制体实例化
接进脚本轨，并把装载注入点从 runtime 搬到 core。

### 1. 为什么 `SceneLoader` 要搬到 core

脚本层（`xgame-script::GameCtx`）要能在钩子里按路径装载预制体，而依赖方向是
`script ← runtime ← editor/game`：**脚本层看不到 runtime 的类型**。trait 与它
唯一的真实实现（`ProjectHandle`）一起待在 core，两边都能命名；runtime 只做
`pub use xgame_core::SceneLoader` 转出，宿主侧的 `use xgame_runtime::SceneLoader`
一行不改。装载器的设计理由（为什么是注入而不是 `World` 持有 `ProjectHandle`）
随模块文档一起搬走，没有改写。

`load_prefab` 走**默认实现返回 `Err`**：场景是必需能力，预制体是增量能力；
既有实现者（含测试里的假装载器）不必为了拿新能力改代码，而"没接"仍然是可诊断的。

### 2. 为什么是"立即生成"而不是延后命令

与 `spawn_entity` 同一条理由：`local e = spawn_prefab(...); set_entity_pos(e, ...)`
是最自然的写法，延后执行会让第二句对着一个还不存在的实体静默失效。安全性依据
也相同：派发遍历的是 `(实体 ID, 脚本路径)` 快照，查找一律"按 ID 现取索引"，
增删实体最多让后面的脚本少看到一个实体。

### 3. 位置语义：两条函数都是"设置"，不是"叠加"

- `spawn_prefab(path, x, y, z)` —— 覆盖根的**世界**位置（Unity
  `Instantiate(prefab, pos, rot)` 语义）；
- `spawn_prefab_under(path, parent, x, y, z)` —— 挂到父节点下，坐标是**局部**偏移。

子节点的相对位置**原样保留**：一棵"炮口在 (0,1,0)、炮身在原点"的预制体实例化到
(10,0,0) 之后炮口就在 (10,1,0)。没有做"可选保留预制体自己写的位置"的第三个形态 ——
需要时把预制体根摆到原点再传偏移就行，别提前给两个参数三种解释。

### 4. 刚体靠 `EntitySpawned` 补建，每个新实体一条

运行时只为**新实体**建刚体，判据是脚本 / 组件推来的 `ScriptCommand::EntitySpawned`。
所以实例化之后要**逐实体**推一条（含各自的 `physics`），漏一条就少一个刚体，
表现是"生成的敌人不参与碰撞"—— 无头报告的 `bodies` 计数就是这条的守门测试。
父引用在命令被消费之前就已进场景，因此刚体建出来就在正确的世界位置，不需要
额外的 `Reparented`。

### 5. 失败分三种，日志分开说

宿主没接装载器（接线问题）/ 文件读不到或 RON 坏（资产问题）/ 预制体是空的
（内容问题）。三种都返回 `nil` 并留一条日志，**不留半个实例** ——
`instantiate_prefab` 是"要么整棵进、要么不进"的，中间态只会让世界更难查。

### 6. 故意没做的两件事

- **预制体缓存**：现在每次调用都读盘 + 解析 RON（约几十微秒）。等真的出现
  "每秒上千发子弹"再在宿主侧加缓存 —— 缓存还要处理"编辑器改了预制体文件"
  的失效问题，提前做是用一个未发生的性能问题换一个会发生的正确性问题。
- **实例根改名 / 传旋转**：Unity 的 `Instantiate(prefab, pos, rot)` 还给旋转。
  当前没有调用方需要，加了就是第三个位置语义。需要时按同一形状补，不改现有签名。

### 7. 顺带修掉的一处不一致

`dispatch_collision_to` 的脚本轨上下文此前只注入了 input / physics / audio，
**没有** `scene_name` / `scene_order`（现在补上了装载器）。结果是
`on_collision_enter` 里读 `current_scene()` 恒为空串、切场景与生成预制体全部
静默失败 —— 同一份 API 在不同钩子里行为不一致，是最难查的那类 bug。
修法与其它派发路径对齐，没有新增分支。

### 验证

- 新增 10 条回归测试：core 2（默认实现可诊断 / `Arc` 转发两个能力）；
  script 5（子树与位置 / 挂父与局部坐标 / 没装载器 / 资产读不到 / 父缺失退回场景根）；
  script Lua 层 1（真实解释器 + 假装载器，含"失败时脚本拿到 nil"）；
  runtime 2（真项目 + `ProjectHandle` + 无头同一条命令路径，断言刚体数与世界位置）。
- 全量 `745 passed / 0 failed / 7 ignored`；clippy 0 警告。
- **dist 版无头实跑**（`--headless --frames N`）：基础场景 24 实体；每帧两次
  实例化各 +3（n=1 → 30、n=14 → 108），实例根 ID 连续不重复，
  `error: 0 / warn: 0`；把路径改成不存在的文件 → Error 日志带绝对路径、
  脚本拿到 `nil`、实体数不变、进程不崩。恢复项目后 `--check` OK（exit 0）、
  30 帧冒烟 `entities: 24 / error: 0`。

## 二十八、时间缩放：一处生效，四个子系统同源（2026-10-22）

暂停菜单、慢动作、打击停顿、快进调试，都要同一个东西：**"模拟变慢，但游戏还在跑"**。
`xgame-core/src/time.rs` 里 `time_scale` 字段和 `set_time_scale` 早就在，`GameClock::tick`
也确实乘了它 —— 但全仓库**没有任何调用点**，能力存在却完全不可触达（差距分析 P2 #33
记的就是这条）。这一刀把它接到脚本与三个宿主上，并把"缩放到底作用在哪"钉死。

### 1. 为什么只能有一个作用点

天然的做法是"每帧算一次 `dt * time_scale` 再分发给各子系统"——错在**每多一个分发点，
就多一次漏掉的机会**。真正的做法是让缩放只活在 `GameClock::tick` 里：
`delta_time` / `total_time` / 固定步累计器三者都是它的下游，于是

- 物理固定步（`consume_fixed_update` 读累计器）自动跟上；
- 脚本 `delta` / `time`（`update` 传的是 `clock.delta_time()`）自动跟上；
- 粒子（`particles.update(frame_dt, …)`）自动跟上；
- 宿主的动画钟（游戏侧读 `world.frame_dt()`）自动跟上。

所以没有 `Time::scaled_dt(dt)` 这种"再过一道手"的 API。`World` 对外只多三个只读口
（`time_scale` / `frame_dt` / `game_time`）和一个写入口（`set_time_scale`）。

### 2. `time_scale = 0` 是"停模拟"，不是"停引擎"

暂停期间 `World::update` **照常每帧被调用**：`update` 派发照跑、UI 命中测试照跑、
音频照跑，只是固定步循环一次都不转、`delta` 为 0。这是暂停菜单能工作的前提——
菜单本身要靠脚本 `ui_clicked` / 输入来恢复。与编辑器 Play 工具栏的 Pause 是**两件事**：
那个是干脆不调用 `World::update`（连 UI 都不重算），它属于"调试器"。

### 3. 音频与 UI 不缩放

kira 有自己的时钟，UI 交互由宿主驱动 —— 两者都不吃 `time_scale`，与 Unity 一致。
副作用是暂停时 BGM 会继续放：要静音请显式 `stop_sound`，引擎不替用户做这个决定
（"暂停菜单里音乐该不该停"是设计选择，不是引擎该猜的）。

### 4. 刻意不发"未缩放时间"

Unity 有 `unscaledDeltaTime` / `unscaledTime`，我没加。理由是**多一份时间读数，
每个调用点就多一次"该用哪个"的决定**，而这个决定几乎总是选错（用未缩放时间做位移，
暂停时物体就穿过墙了）。代价要写清：暂停菜单里"照常走"的呼吸动画现在做不了，
得等真有这个需求时再加两个**只读**函数（`unscaled_delta` / `unscaled_time`），
不会牵扯架构。`delta` / `time` 的文档里明确标注"已缩放"。

### 5. 动画钟为什么不能吃同一份 dt

三个宿主的动画推进方式本来就不同，缩放必须分别对待：

| 宿主 | 动画钟如何推进 | 怎么跟缩放 |
|---|---|---|
| 独立游戏 | `anim_driver.tick(dt, …)` | 直接改吃 `world.frame_dt()`（缩放后） |
| 编辑器 Play | `anim_driver.tick_wall()` 自己取墙钟 | 每帧从运行时同步一个 `f32` 系数，`tick_wall` 里乘 |
| 编辑器（非 Play） | 同上 | 恒 1.0 —— 脚本在编辑态不跑 |
| 无头运行 | `anim.tick(dt, …)` | 改吃 `world.frame_dt()` |

编辑器为什么是"同步一个系数"而不是让 `SceneRenderer` 直接读 `World`：
`scene_renderer` 属于编辑器渲染层，让它看见 `runtime::World` 会把依赖方向搞乱
（而且视口渲染与运行时更新本来就是两条独立的路）。所以只在 `render_scene` 里
`set_anim_time_scale(...)` 传一个数 —— 但**必须每帧传**，少传一帧就少走一格，
"只在进出 Play 时传"是个会留下静默 bug 的省事写法。

`tick_wall` 的顺序也有讲究：**先夹墙钟（`min(0.1)`）再乘缩放**。反过来写的话，
100 倍速会把"拖动窗口三秒"放大成一次 300 秒的长跳。

`AnimationDriver` 的 `Default` 从 derive 改成手写：`f32` 的默认值是 **0.0**，
derive 出来的驱动会让编辑器的预览动画永远停在第一帧、且不报任何错。测试里钉住了。

### 6. 坏值：钳制而不静默冻住

`GameClock::set_time_scale`：负值 → `0`（Unity 同样处理），`> MAX_TIME_SCALE(100)` → 100，
`NaN` / `∞` → **忽略**（保住上一档）。最后一条是有意的：`NaN` 多半是脚本里表达式算炸了，
把游戏冻住会让故障看起来像"卡死"而不是"脚本写错"。`AnimationDriver::set_wall_time_scale`
用同一套规矩，免得两个入口对同一个坏值给出不同结果。

上限 100 与"每帧最多 5 个固定步"的预算是两回事：预算是防死亡螺旋的，
不能被缩放绕过（`accelerated_time_still_respects_the_step_budget` 守这条）。

### 7. 生效时机是下一帧

脚本在 `update` 里写缩放时，本帧的固定步循环**已经跑完**（`clock.tick` 在 `update`
函数最开头）。所以 `set_time_scale` 的效果从下一帧起算，不能回头重算已经走完的步。
这一点写进了脚本文档，因为"我在这一帧暂停了，为什么这一帧的固定步还跑了"是会被问的。

## 二十九、TAA：抖动只进相机、重投影要"上一帧的抖动"、历史必须被钳制（2026-10-23）

差距分析 P1 #10 的最后一刀。MSAA 只在**几何边缘**上多采样，对"着色器里高频变化的东西"
（细金属丝、远处栏杆、高频纹理）无能为力；FXAA 是拿邻域亮度猜边缘，猜错就把细节抹平。
TAA 换成时域：每帧把投影抖动一个亚像素，把重投影后的历史混进来，等价于"这个像素采了
8 个子像素"。

### 1. 抖动只能叠在相机上

`ScenePipeline::render` 收到的仍是**未抖动**的 `view_proj`，另外多一个 `jitter_ndc`
参数；抖动只在写相机 uniform 时叠加（矩阵的"行 0 / 行 1 += d · 行 3"）。剔除视锥与
**级联阴影拟合**继续用未抖动的矩阵 —— 阴影的"整数纹素宽度 + 中心吸附"经不起每帧半个
像素的来回拉扯，抖进去就是影子边缘持续抖动，比锯齿难看得多。

抖动量用 **二维 Halton(2,3)、周期 8 帧**，是**纯函数**（`jitter_offset(frame)`）：
无头截图两次运行要逐字节一致，回归测试也要能钉住"第 k 帧抖多少"。引入随机数或墙钟
这条契约立刻失效。

### 2. 重投影必须补"上一帧的抖动"

世界点先按**未抖动**的上一帧 `view_proj` 投到 uv，再加上**上一帧的抖动**（`jitter_to_uv`），
才是历史纹理里真正存着这个点的地方。少这一项，历史永远差半个像素 —— 表现不是报错，
而是"整体轻微模糊"。`jitter_to_uv` 的 y 还要取反（NDC 的 y 朝上、纹理 v 朝下），
写反 = 历史差两个像素、画面糊成一团。

当前帧那边则要用**抖动后**的逆矩阵反投影（深度就是抖动着渲出来的）。

### 3. 历史必须钳制在当前帧邻域内

v1 **没有逐物体运动向量**（重投影只跟相机走），所以运动物体的残影只能靠 3×3 邻域的
[min, max] 钳制挡住：历史落在邻域外就说明它讲的是别的东西（遮挡变了 / 物体移开了 /
相机甩太快），钳到边界等于"部分接受"。这是刻意画的边界，不是偷懒：真做运动向量要给
每个刚体存上一帧的模型矩阵、给蒙皮存上一帧的骨骼矩阵，量级是"另一刀"。

### 4. 首帧 / 越界 / 相机背后：直通，不猜

`blend = 0` 时着色器直接返回当前帧。猜错的代价是画面里出现上一帧的鬼影，不猜的代价
只是这一帧没抗锯齿。三种情形都走这条：历史为空（首帧 / 刚重置）、重投影 uv 越界、
`prev_clip.w <= 0`（点在上一帧相机背后）。

**这里踩过一次真坑**：`resolve` 首帧返回了"刚读的那张历史"而不是"刚写的那张"，
于是后处理读到的是一张**从未写过**的纹理 —— 整屏全黑。12 帧的收敛测试发现不了它
（慢一帧的那张上一帧已经写过，图只是旧一帧），只有"只看第一帧"的断言能抓住
（`taa_first_frame_is_not_black`，先把它改回旧写法证明会红）。

### 5. 乒乓 + 源代号

同一张纹理不能既当输入又当输出 ⇒ 两张 HDR 历史纹理乒乓。这带出一个连锁要求：
`PostFx` 的合成绑定组缓存原来只有**一个槽**（键含"源代"），而 TAA 让源视图每帧都换；
单槽等于每帧重建绑定组，TAA 的收益被这层分配吃掉一半。缓存改成有界多槽（容量 8），
TAA 交出的源代号**最高位固定为 1**，与宿主的 `target_gen`（小整数）永不相撞 ——
两者共用一个缓存表，撞了就是"绑定组指向别的纹理"这类静默错误。

### 6. 与 FXAA 的关系：TAA 开着时 FXAA 让位

两者都在抹边缘，叠起来只是把画面糊两遍。判定只有一处：`RenderConfig::effective_fxaa()`
（core），三宿主不需要各自判断，也不会出现"编辑器糊、游戏不糊"。用户填的
`fxaa.enabled` **原样保留不偷偷改写**，只是实际生效时被压掉。

### 7. 深度纹理要能当纹理读

`HdrTargets` 的深度附件原来只有 `RENDER_ATTACHMENT`。TAA 要 `textureLoad` 它反投影，
必须加 `TEXTURE_BINDING`；少这一位时**关着 TAA 的路径完全正常**，只有开着才会在
建绑定组时校验失败。深度用 `textureLoad` 而不是采样：深度纹理不接受过滤采样器，
1:1 后处理本来也要精确到像素。MSAA 开着时深度是多采样纹理，WGSL 类型要换成
`texture_depth_multisampled_2d`（`textureLoad` 的调用形式两者相同，所以只有一行不同，
用占位符替换 —— 维护两份几乎一样的 WGSL 迟早漂移）。

### 8. 编辑器：抖动不进指纹

抖动每帧都变，掺进渲染指纹等于把静态帧门控彻底废掉（空闲 CPU 从 0% 变成满速重绘）。
指纹用未抖动的 `view_proj`；TAA 的**开关与历史权重**进指纹（它们真的改变每个像素）。

**已知限制（写清楚，不掩盖）**：编辑器编辑态静止画面**不会继续收敛** —— 指纹门控
让"什么都没变"的帧整段跳过，TAA 自然没有新帧可积累。拖相机 / Play 态是连续出帧的，
那才是它起作用的地方。无头 `--screenshot` 只渲染一帧，同理等于直通（`--ui-frames`
多帧才会积累）。

## 三十、动画脚本控制：状态机优先、只写 `Animator`、层剪辑硬切（2026-10-23）

差距分析 P1 #13 的最后一个**纯软件**缺口。交叉淡入早已存在（编辑器 / RON 能触发），
但脚本只能 `set_anim_param` 推状态机；没配机器的项目想"按距离播 Walk / Run"或
"按攻击键播 Attack"，只能在 RON 里预配或改引擎代码。手柄 / 触摸要硬件才能验收，
动画这一刀可以当场闭环。

### 1. 只写字段，不另造播放路径

`GameCtx::set_anim_clip` 只改 `Animator.clip`。下一帧 `AnimationDriver::tick` 发现
剪辑名变了，照旧把时间归零、在 `fade_time > 0 && is_active()` 时记下旧剪辑做交叉
淡入。脚本层不算混合、不缓存剪辑、不复制 `tick` 的一行逻辑 —— 否则"脚本切的剪辑"
与"Inspector 切的剪辑"迟早出现两套淡入行为。速度 / 循环 / 淡入同理：只写字段，
播放仍由驱动器唯一实现。

### 2. 状态机优先是既有顺序，不是新增判断

`tick` 的解析顺序一直是：`animator.active_machine()` 可用 → `(clip, speed, looping)`
全从状态表取；没有可用机器 → 才读 `Animator` 字段。因此机器模式下
`set_anim_clip` / `set_anim_speed` / `set_anim_looping` 会**写进字段但不改变实际播放**，
与 Inspector 完全一致。**不自动停用 / 移除机器**：静默改配置比"写了没反应"更难排查。
要直接控制就明确删掉机器；要状态机就用 `set_anim_param` 推转移条件。

`set_anim_fade_time` 是例外：`fade_time` 在两种模式下都被 `tick` 读取（换状态与换剪辑
共用同一条淡入路径），所以它对状态机过渡同样生效。

### 3. `set_anim_clip` 不碰 `autoplay / speed / looping`

只换剪辑的调用方不该被悄悄改掉播放参数。`autoplay = false` 的实体切完仍停在第一帧
—— 这正是"摆好第一帧再播"的制作流程。需要"切剪辑同时设参数"就多调几行，
每个 setter 职责单一。

### 4. 叠加层 / 层栈换剪辑是硬切

`AnimationDriver` 对叠加层与层栈只维护独立时钟（`animation.rs` 的 4.5 / 4.6 段），
没有 `Prev`，所以 `set_anim_additive_clip` / `set_anim_layer_clip` 换剪辑时**只把该层
时钟归零**，基础层的淡入状态不受影响。想平滑就先把权重拉到 0、换剪辑、再拉回 ——
v1 不为此扩混合栈（与"0.25 秒内连切两刀不值得多层混合栈"是同一取舍）。层按**名字**
匹配，重名取栈内第一个；层名不存在 / 没配叠加层 → 静默 no-op。

### 5. 容错边界

- `speed` 钳 `[0, 100]`、`fade_time` 钳 `[0, 10]`；非有限值（NaN / inf）**忽略**，
  不写字段。
- 负速度钳到 0：v1 的负速语义是"定格"不是倒放（与状态表同款）。
- 没挂 `Animator` → 全部静默 no-op：通用移动脚本可以挂在任意实体上，不用先探测
  组件（与 `set_anim_param` 同款）。
- 不做 getter：脚本要判断"现在播的是不是 Attack"，目前只能自己记状态。补 getter
  要先定义"返回配置值还是驱动器的实际值"，等真有需求再定。

### 验证

- 先写测试再实现：`lua_host::tests::script_controls_base_clip_additive_and_layers`
  在旧实现下报 `attempt to call a nil value (global 'set_anim_clip')`。
- `ctx::tests::animation_setters_clamp_and_apply_to_the_owning_entity_only` 钉住
  钳制 / 非有限值忽略 / 只改自己实体 / 缺组件与缺层名 no-op。

  `--headless --frames 5 --dump-scene` 退出码 0、`ok: true`、`error: 0 / warn: 0`；
  dump 里六项都落地（`clip: "Run"`、`speed: 1.5`、`looping: false`、

## 三十一、资产 / 脚本热重载：1 Hz 轮询、动作后 rebase、场景永不自动覆盖（2026-10-23）

差距分析里 P1 的"资产热重载"是**最后一刀纯软件缺口**（morph 缺资产、手柄缺硬件）。
目标很具体：在编辑器里改脚本 / 换模型 / 调材质 / 加预制体，不用重启项目就能看到效果。
实现见 `crates/xgame-editor/src/hot_reload.rs` 与 `EditorState::hot_reload_tick`。

### 1. 为什么是 1 Hz 轮询，而不是文件系统通知

文件系统通知（`notify` / `ReadDirectoryChangesW`）有两笔账：**新依赖 + 平台分支**，以及
**事件去抖**。不同编辑器保存文件的方式不一样（直接覆盖 / 写临时文件再改名 / 先删后建），
事件序列并不统一；去抖窗口定小了会重复触发、定大了会漏掉最后一次。而本项目的内容目录
是清单里显式配置的几棵**小树**（`Scenes` / `Scripts` / `Prefabs` / 模型 / 贴图 / 音频 /
shader），一轮扫描只是一串 `metadata` 调用，**不读文件内容**。

所以选轮询：**不引依赖、行为确定、测试可以把时间拨快**。1 秒是"手离开保存快捷键就能
看到"与"空闲时每秒醒一次"的折中；扫描成本与内容目录的文件数成正比，不随资产大小变。

**别为了省那一次 `stat` 把间隔调成 5 秒 / 10 秒**：这个数字直接决定用户以为"热重载坏了"
的时长；1 Hz 的 metadata 扫描在编辑器整体开销里可以忽略。

### 2. 判据是 `(项目相对路径, mtime, 长度)`

不读内容、不做哈希：这里回答的是"值不值得重新加载"，不是"内容是否逐字节相同"。
真正的加载器（glTF / 材质 / Lua）自己有解析与负缓存；**多报一次只是多一次重载，漏报才是
bug**。长度是给 mtime 打补丁：某些文件系统 / 编辑器的 mtime 粒度粗，快速改一版长度不同
的内容时 mtime 可能原地不动，长度会把它抓出来。

### 3. 基线推进 + 动作后 `rebase`（防自激的硬约束）

`poll()` 报告差异后，基线**立即**推进到本轮扫描结果；动作跑完后调用 `rebase()` 再扫一遍。
原因：应用资产改动时会顺手给新资产补 `.meta`（`ensure_asset_metas`）。如果不 rebase，
这些**自己写下的** `.meta` 会在下一秒被当成"外部新增"，触发资产刷新；刷新又可能补 `.meta`
或改导入设置 —— 形成每秒一次的自激循环。

`hot_reload::tests::rebase_absorbs_metas_written_by_the_reload_action` 钉住这条。
**删掉 rebase 不是优化，是回归**。

### 4. 改了什么，走哪条重载路径

| 变化 | 编辑器动作 |
|---|---|
| `Scripts/*.lua` | **编辑态**只重扫脚本清单（下次 Play 重新编译）；**Play 中**调 `reload_scripts()` 让运行时重新编译。脚本全局变量与 `state_*` 的既有语义由脚本宿主保证（见 §二 / §三） |
| 模型 / 贴图 / 材质 / 音频 / `.meta` | `refresh_assets()`（重扫 + 补 `.meta` + 刷新资产 / 预制体 / 脚本三个列表）+ `renderer.invalidate_assets()`（丢模型 / 材质 / 纹理缓存与渲染指纹） |
| 预制体 `.prefab.ron` | `refresh_assets()`；**不**碰渲染缓存（预制体文件本身不参与当前帧渲染） |
| 场景 `.ron` | 只写一条 `debug` 日志，**不动内存场景** |
| 当前打开的材质草稿 | 干净 → 丢弃草稿（下次访问从磁盘重读）；脏 → 保留草稿 + 一条 warning（Revert 可载入磁盘版） |

材质草稿的分支是刻意的：直接覆盖会丢掉用户在 Inspector 里敲的字段；直接丢弃会让正在
编辑的界面突然清空。两者都不可接受，所以按"脏不脏"分开处理。

### 5. 刻意**不**自动重载的四类

- **场景文件**：磁盘 `.ron` 变了就覆盖内存，会把未保存的编辑直接冲掉。Scenes 菜单本来
  就现扫，新场景不需要热重载也能出现；"重载场景"应该是用户的显式动作。
- **已实例化的预制体**：实例是场景里的普通实体，热替换得先定义"哪些字段该保留"
  （Unity 也要 Prefab Mode）。现在只刷新预制体面板的清单。
- **`project.ron`**：窗口 / 渲染 / 关卡顺序是项目级配置，改动生效需要重建运行时；
  重启编辑器是最可预期的语义。
- **已解码的音频片段**：kira 的解码缓存没有公开失效口，正在播的声音不会换。

把这四类"补全"之前，先定义清楚数据保留 / 撤销 / 正在播放的语义；没有语义的自动覆盖
比不重载更危险。

### 6. 扫描边界与只读会话

- 只扫清单声明的目录；重叠目录（默认 `Resources` 同时是模型 / 贴图 / 音频根）按
  `(目录, 类别)` 去重，同一文件取更具体的类别（`.prefab.ron` > `.ron` > 其他）。
- 跳过 `.autosave` / `target` / `Build` / `Plugins` / `.git`：前四个是本引擎自己的产物，
  扫进来会让热重载永远停不下来。**不跟随符号链接**：内容目录里链到父目录会形成环。
- `--ui-shot` 等只读会话**不驱动**热重载，也不排 1 Hz 唤醒：截图必须只对应项目内容，
  不能因为开发机上的临时文件而变。

### 7. 空闲唤醒与"CPU 0.00%"

界面静止时帧调度会停帧，没人来调 `hot_reload_tick` 就永远发现不了外部改动，所以主循环在
`!live` 时用 `request_repaint_after(hot_reload_wait(now))` 排一次**定时**唤醒（不强制立刻
重绘）。这意味着"空闲时完全不唤醒"不再成立：会有每秒一次的 metadata 扫描，但**没有**
视口重画、没有资产加载。文档 / 汇报里不要把它写成"零唤醒"。

## 三十二、场景 schema：唯一源 + 确定性 + 四重防漂移（2026-10-23）

### 1. 唯一内容源是 `scene_schema()`

`xgame-core::schema::scene_schema()` 是场景格式说明书的**唯一**真相源：

- CLI `xgame-editor --export-schema` 与 MCP `schema_read` 都调它；
- 编辑器 / MCP 里**不许**再抄一份字段表或工具描述里的默认值；
- 加字段、改默认值、改枚举变体，只改 `schema.rs` 一处。

两条出口只是序列化方式不同：CLI 用 `serde_json::to_string_pretty` + 末尾换行；MCP 用
同样的 pretty JSON 走文本内容块。**不要**让 MCP 复用 CLI 的进程 / 文件，也不要在
编辑器里另建目录 —— 那会立刻产生第二份会漂移的文档。

### 2. 目录放 core，JSON 放 editor

core 的落盘格式是 RON，**刻意不依赖 `serde_json`**（依赖面越小越好；`serde_json` 只在
编辑器里已有用途）。所以：

- `SchemaDoc` / `TypeSchema` / `FieldSchema` / `VariantSchema` 等是 core 里的普通
  `Serialize + Deserialize` 结构体；
- JSON 序列化在 `xgame-editor/src/schema_cli.rs`；
- MCP 只依赖 core，直接序列化同一个结构体。

把 `serde_json` 加进 core 不是「顺手」，而是扩大所有下游（含无窗口的 MCP）的依赖面；
真要加，先证明有第二个必须用 JSON 的 core 内部场景。

### 3. 确定性是硬契约

同一份代码连续导出两次必须**逐字节相同**。为此：

- 不写时间戳、构建号、随机 ID；
- 实体 / 场景 / 预制体示例里的 `EntityId` 固定为 `from_raw(1)`（默认构造会读全局原子
  计数器，导出两次就不同）；
- `FieldValues` 用 `BTreeMap`，键序稳定；
- 所有默认值 / 示例都由**真实 Rust 值**序列化得到，不手写字符串。

这条契约让 schema 可以进版本库做 diff，也让智能体能用哈希判断「引擎格式有没有变」。
导出文件当前 76,685 字节（36 个类型），两次文件出口与 stdout 出口的 SHA256 都是
`4DC0B0A9…B419207`（完整值见 PLAN 五十）。

### 4. 防漂移靠测试，不靠自觉

目录是手写的（serde 运行期没有字段元数据），所以用四类测试钉住：

1. **穷举解构 / 穷举匹配**：每个结构体在测试里逐字段解构、每个枚举逐变体匹配。
   给落盘类型加字段或变体而不同步目录 → **测试编译不过**，不是运行期才发现；
2. **反解真实类型**：每个 `default_ron` 解析回 `T` 并与 `T::default()` 比较；每个
   `example_ron` 解析回真实类型并断言关键字段；每个枚举变体示例必须解析成那个变体；
3. **引用完整性**：字段 `ty` 里的 `Option` / `Vec` / `BTreeMap` / 数组递归展开后，
   叶类型必须能在目录或基元表里找到 —— 防「文档里有、代码里没有」；
4. **真实读写边界**：示例场景 / 预制体走一遍 `ProjectHandle::write_scene` /
   `write_prefab` → `load_*`，验证 GUID 编码 / 解码、默认值补齐、二次写盘文本稳定。

新增落盘字段的流程：改 Rust 类型 → 测试编译失败 → 补 `schema.rs` 的字段 / 默认值 /
说明 → 跑 `cargo test -p xgame-core schema`。

### 5. 运行时字段不进目录

`Entity.components`（`#[serde(skip)]`）、`UiElement.state`、`ParticleEmitter.burst`
**刻意排除**。它们写进 RON 也不会生效；列进目录只会让智能体写出「看起来合法但没效果」
的文件。测试里有一条 `runtime_only_fields_never_leak_into_the_catalog` 同时检查
「目录里没有」和「没有同名字段混进来」。

### 6. 资产引用：schema 只描述内存形态

`asset_references` 表列出每个引用字段的两种形态：

- 磁盘：`guid://<uuid>`（`ProjectHandle::write_scene` / `write_prefab` 编码）；
- 内存 / MCP：项目相对路径（`load_scene` / `load_prefab` 解码）。

schema 的 `example_ron` 用**内存形态**，因为智能体经 MCP 拿到的场景就是内存形态；
GUID 转换只发生在 `ProjectHandle` 的读写边界（§十四）。**别把 `guid://` 写进示例**，
否则智能体会以为磁盘 / 内存是同一套字符串，手写 GUID 必然断链。

### 7. `UiElement` 用 serde 有效默认值，不用 `Default::default()`

`UiElement::default()` 是面板预设（`interactable: false`、面板样式），但省略字段
反序列化得到的是字段级默认值（透明样式、`interactable: true`、`offset_max = [200, 100]`）。
目录描述的是**后者** —— 智能体写 RON 时的真实语义。测试同时断言
`UiElement::default().interactable == false`：如果构造器预设变了，schema 的说明要同步。

### 8. CLI 退出码与 `--check` 分开

`--export-schema` 只有 0（成功）/ 1（参数或序列化错误），**不复用** `--check` 的
0/1/2。否则智能体看到 2 会误判成「项目有悬空引用」，而实际上只是 `--out` 缺参数。
输出位置也固定：无 `--out` 打 stdout；有则写文件、stdout 只回一行确认（便于脚本判断）。

### 验证

- 新增 16 条测试：core schema 10（含项目往返 1）+ CLI 5 + MCP 1；
  全量 `799 passed / 0 failed / 7 ignored`；clippy `-D warnings` 0 告警。
- 二进制级导出：两次 `--out` + 一次 stdout 的 SHA256 完全一致（76,685 字节），
  stderr 为空、退出码 0；Python 按 UTF-8 解析通过（`format_version=1`、`types=36`）。
- `--check projects/SampleScene` 退出码 0（24 实体、全部引用存在）；

- MCP 进程级：Python 起真实 `xgame-mcp.exe`，`initialize → tools/list`（9 个工具，
  首个 `schema_read`）→ `tools/call schema_read`，返回 `format_version=1`、`types=36`。
- **未验证**：没有在真实 MCP 客户端（Cursor / Claude）里走一遍 `schema_read` 交互
  （只在协议层起了真实 server 进程）；schema 只覆盖场景 / 预制体。脚本 API 清单导出
  当时仍未做，已在 §三十三 补齐。

## 三十三、脚本 API 清单（Agent-Native ③ 的另一半）

### 1. 清单放 `xgame-core`，不放 `xgame-script`

`xgame-core::script_api::script_api()` 是 `--export-script-api` 与 MCP
`script_api_read` 的唯一内容源。它是**纯数据**，不依赖 mlua。

原因：`xgame-mcp` 只依赖 `xgame-core`。如果把清单放进 `xgame-script`，MCP 会被迫
依赖 mlua / vendored Lua，工具进程的体积与构建面都会无谓变大。脚本运行时需要清单
时反过来依赖 core 即可（`xgame-script` 已经依赖 core）。

### 2. 注册名真相源是 `lua_api.rs` / `ui_api.rs`

清单是**手写**的：Lua C 函数没有可用的参数名 / 返回类型反射，强行从 Rust 闭包
类型推导会把 `LuaCtx`、`f32`、`Option<T>` 等实现细节漏给脚本作者。手写签名 +
防漂移测试比“自动但不准确”更有价值。

漂移由三层钉子拦住：

1. `xgame-script` 从注册源码提取全部 `globals.set("…")`，与清单逐名比对；再在
   真实 Lua VM 里确认每个名字都是函数。**不要**改成“枚举全局表再做差集”：Lua
   基础库也有 `error`，而引擎恰好覆盖了同名全局，差集会漏掉它。
2. `xgame-editor` 从 `Docs/脚本API.md` 的 API 表提取函数名，与清单比对。
3. `xgame-core` 检查类别引用、签名与函数名一致、名字唯一、函数 / 钩子数量。

新增 / 改名 / 删除脚本 API 时，必须同步 `script_api.rs`；只改注册会立刻红。

### 3. 文档只钉函数名，不钉文案

`Docs/脚本API.md` 继续承担叙述、示例与易错点；清单的 `summary` 可以更精炼。
名字集合必须完全一致（否则智能体会照着文档写出不存在的函数），但文案允许各自
演进。改语义时仍要人工同步两处。

### 4. 参数 / 返回值是契约字符串，不是 JSON Schema

第一版刻意收敛：`params` 从签名解析成名字数组，类型放在签名字符串里；`returns`
是 `EntityId | nil` / `RayHit` 这样的字符串。Lua 的 `nil`、表、userdata 用 JSON
Schema 表达很别扭，硬套会让“返回值”失去可读性。等出现“按类型生成强类型桩代码”
的真实需求，再升级成结构化参数。

### 5. 输出确定性与退出码

- 没有时间戳 / 随机 ID；函数与类别按 `Docs/脚本API.md` 的顺序排列；
- 同一份代码连续导出两次逐字节相同（实测 50,695 字节，
  SHA256 `DBF83431BE494BB675734F8C18BA69EC57DF293AD1F432DAB0F5C6FEE7486CDC`）；
- `--export-script-api` 只有 0（成功）/ 1（参数或序列化错误），不复用 `--check`
  的 0/1/2。

### 6. MCP 第 10 个工具，项目无关

`script_api_read` 追加为第 10 个工具（不重排已有 9 个工具的章节），入参为空，
不需要 `project`。`tools_list_shape` 对 `schema_read` / `script_api_read` 两个
项目无关工具单独放行。

### 7. 格式版本

`SCRIPT_API_FORMAT_VERSION = 1`。加字段不涨；改语义 / 删字段 / 改返回值才涨。
与 `SCHEMA_FORMAT_VERSION` 的纪律一致。

### 验证

- 新增 14 条测试：core 6 + editor 6（含文档函数名比对）+ script 1 + MCP 1；
  全量 `813 passed / 0 failed / 7 ignored`；clippy `-D warnings` 0 告警。
- 二进制级导出：两次 stdout + 两次 `--out` 逐字节相同（50,695 字节），stderr
  为空、退出码 0；Python 按 UTF-8 解析通过（`format_version=1`、17 类、155 函数、
  6 钩子、7 值类型、9 条约定）。
- MCP 进程级：Python 起真实 `xgame-mcp.exe`，`initialize → tools/list` 返回
  10 个工具 → `tools/call script_api_read` 返回同一份清单；stderr 只有启动横幅。
- **未验证**：没有在真实 MCP 客户端（Cursor / Claude）里走一遍 `script_api_read`
  交互；参数 / 返回值的结构粒度仍是第一版。

## 三十四、CI（Windows + stable + 无 GPU 截图）

### 1. 只跑 Windows

`.github/workflows/ci.yml` 的 runner 固定 `windows-latest`。引擎目前只在 Windows
实测；Linux 还要补 ALSA 等系统依赖、验证 winit / wgpu 后端，macOS 完全没碰过。
在没验证前加矩阵，只会得到"红得没意义"的 CI。跨平台真正开始时再扩矩阵。

### 2. 命令顺序与缓存

单 job 顺序跑：`check` → `clippy -D warnings` → `test --all-targets` → 示例项目
`--check` / `--headless` → 两份 JSON 导出。共用同一份 target 缓存；拆成并行 job
会让每个 job 各自冷编译，反而更慢。`Swatinem/rust-cache@v2` 缓存 cargo + target，
`CARGO_INCREMENTAL=0` 缩小缓存体积。

### 3. `--locked` 与 stable

所有 cargo 命令带 `--locked`：`Cargo.lock` 是提交物，CI 不允许静默升级依赖。
工具链用 stable（`dtolnay/rust-toolchain@stable` + `clippy`），不钉具体版本；
如果将来 stable 的 clippy 新告警造成漂移，再决定加 `rust-toolchain.toml` 或
在 workflow 里钉版本，不要两边各钉一份。

### 4. 不跑 `--screenshot` / 基准 / 格式

- **`--screenshot` 不进 CI**：hosted runner 没有 GPU。渲染测试在无适配器时靠
  `gpu_or_skip` 跳过；截图要的是真实像素，不能用 skip 冒充验证。留给带 GPU 的
  自托管 runner。
- **7 条 ignored 基准不进 CI**：性能基准受机器噪声影响，需要稳定机器与基线；
  目前只保留 `cargo test ... -- --ignored --nocapture` 的手动入口。
- **不加 `cargo fmt --check`**：当前工具链没装 rustfmt，仓库也没有格式化门禁；
  先守住 check / clippy / test，等格式化一次性收口后再加。
- **不跑 release build**：发布打包仍由 `一键构建.cmd` / `tools/build-release.ps1`
  负责；首版 CI 先守住 debug 编译与测试，避免时间过长。

### 本地真实发布验收补充（2026-10-27）

`tools/test-published-player.ps1` 使用既有 --build 与真实播放器，不新增 World 循环或 headless 替身。每次唯一目录保留源项目、包与日志，移动包后改名源目录，从无项目清单 cwd 无参数启动；核对播放器、input 原字节及 DLL 哈希。Windows WM_KEYDOWN/WM_KEYUP 经 winit 输入桥与 InputMap，Lua 只观察 Spinner 所在实体的旋转变化，不自行改旋转；每关 START/PLUGIN/PRESS/RELEASE/DESTROY 各一次，按松开触发下一关。正常关闭之后用原生进程句柄查退出码，日志断言失败即失败，不能仅凭 exit 0 判通过。

负对照通过错绑 K 键或省略 DLL 证明断言有辨别力，不称引擎缺陷回归。PrintWindow 保存真实窗口画面，需人工检查；三关同视觉夹具，图像不能单独证明关卡身份。输入仅验证窗口消息链，不覆盖物理设备、系统焦点、IME；此桌面 GPU 测试不塞进现有 hosted CI，不改变此前 CI 约束，G0/182 保留未关闭。PowerShell 5.1 脚本需 UTF-8 BOM，读取仍在写入的日志使用 FileShare.ReadWrite。

### 5. 二进制冒烟与已知噪声

单元测试之外，CI 必须跑真实 CLI：`--check projects/SampleScene`（退出码 0/1/2）、
`--headless --frames 30 projects/SampleScene`（退出码 0/1/2）、
`--export-schema --out` 与 `--export-script-api --out`。导出写 `RUNNER_TEMP`，
不污染工作区；CI 目前不把"工作区必须 clean"当门禁（测试自身会生成临时文件）。

`xgame-derive` 的 MSVC 链接器警告是已知非致命噪声；CI 日志会出现，但不影响退出码。

## 三十五、MCP 资产写侧：单资产、部分更新、GUID 不变

### 1. `asset_import` 只碰点名的那个资产

`AssetDatabase::ensure_meta()`（单资产）与 `ensure_metas()`（批量）是**两条不同语义**
的入口，不要合并：

- `ensure_metas()` 是"打开项目"的语义 —— 把一个目录树里所有缺 `.meta` 的文件一次
  补齐；
- `ensure_meta()` 是"我点名了这个文件"的语义 —— 只写这一张。

智能体点名一个资产却顺手给整个资源目录 GUID 化，会把一次小操作变成一次**范围外
写入**（用户可能还没准备好让那批文件进版本控制）。编辑器侧同理：`set_import`
在资产没身份证时只补**这一张**，不再退化成 `ensure_metas()`。

### 2. 导入设置是部分更新，不是整体替换

MCP `asset_import` 的四个导入参数都是可选的，缺省 = **不改该字段**（从现有设置
基线出发覆盖）。不要改成"传了就用传入值整体替换"：那会让"只调 `model_scale`"
把用户改过的 `texture_srgb` 冲回默认，而且第二次调用才会发现。

`set_import` 内部一律先 `sanitized()`：`model_scale` 非有限值退回 1.0、有限值钳到
`[0.001, 1000]`（下限不是 0 —— 0 会把模型缩成一个点，看起来像"资产加载失败"；
上限防手写 `1e30` 把包围盒 / 剔除算爆）。**读盘边界也要净化**
（`AssetMeta::from_ron`），否则扫描 / 资产面板 / 渲染热路径会拿到三份不同的值。

### 3. 越界要钳，但"请求值"必须一起返回

钳制是对的，静默钳制是错的：智能体设 `1e9` 而实际落盘 `1000`，如果不报，它会
以为设置生效了。MCP 返回值同时给 `import`（实际）与 `model_scale_requested` /
`model_scale_clamped`（请求）。

判断"是否被钳"要拿**请求值**和**落盘值**比。曾经写成"先 `clamp` 再和落盘值比" ——
两边都是钳后值，永远相等，于是永远报不出钳制（本轮的实测 bug，测试先红后绿）。

**非有限值在 MCP 层直接拒绝**：`NaN` 没有"钳到边界"的合理含义，core 退回 1.0 是给
手写 `.meta` 的用户留的兜底；智能体的入口应该报错，而不是悄悄给它一个 1.0。
注意 `serde_json` 无法表示 NaN / Infinity，真正可触发的是"f64 里有限、转 f32 溢出"
（如 `1e39`）—— 这条有测试。

### 4. 场景不是资产库管理的对象

`asset_import` / `asset_move` 都拒绝 `.ron`：`collect` 本来就不收录场景，而场景被
`project.ron` 按**路径**引用（入口场景、发布清单）。搬场景要同步改清单，那不是资产
库能单方面决定的事。其他资产被 `guid://` 引用，GUID 不变即不断链。

### 5. `asset_move` 不"顺手改写引用"

磁盘场景 / 预制体存 `guid://`，移动时搬资产 + `.meta` 两个文件、GUID 不变，
**引用文件一个字节都不用改**。这正是 GUID 引用相对路径引用的价值；如果移动逻辑里
出现"遍历场景改写路径"，说明引用模型被写坏了，先修模型而不是修移动。

拒绝判定全部在**动盘之前**：源 / 目标路径归一与安全（`normalize_asset_relative`）、
源未登记（缺 `.meta`）、目标已存在（资产或 `.meta`，用 `symlink_metadata` 而不是
`exists`，悬空链接也算占用）、改变资产类型、源 / 目标是场景。`.meta` 搬失败时回滚
资产文件；两者都失败时错误文本给出两个路径让人手工收拾（唯一无法自动回滚的情形）。

移动成功后**全量 `refresh()`**：移动同时改了 `by_path` / `by_guid` / 诊断三处，
手工同步容易漏；低频交互（毫秒级扫盘）换"索引绝不会半新半旧"。

### 6. Windows 的路径静默变换必须显式挡

`normalize_asset_relative` 拒绝：结尾空格 / 点（Windows 会**静默**吃掉，于是写下的
`.meta` 与扫描看到的资产对不上）、冒号（`file:stream` 会把写入引到别的数据流）、
控制字符与 `<>"|?*`、以及 `target` / `dist` / `.git` 等跳过目录（扫描器逐级剪枝，
写进去等于制造"写成功但永不存在"的资产）。

### 7. MCP 每次调用是独立 handle

server 每次 `tools/call` 都新开一个 `ProjectHandle`，内存索引是那一瞬的盘上快照。
**同进程的另一个 handle 看不见工具刚写下的 `.meta`**，要 `refresh_assets()` 或重新
打开。测试里踩过：工具返回 `import.model_scale = 2.5`，测试 handle 的
`asset_import()` 仍读到默认 1.0 —— 不是写入失败，是索引没刷新。编辑器侧由 1 Hz
扫描负责，不需要额外处理。

### 验证

- MCP `36 passed`（原 33 + 3：导入语义 / 移动保引用 / 六种拒绝不动盘）；
  core 新增 5 条（路径归一 / 两边界净化 / 单资产 meta / 移动保 GUID / 拒绝不动盘）。
- 全量 `821 passed / 0 failed / 7 ignored`；clippy 0 告警。
- 移动测试先断言"盘上场景确实存的是 `guid://`" —— 否则那条测试什么都没证明。

## 三十六、层与碰撞矩阵：存覆盖、双侧相与、查询只看成员位

### 1. 层是清单里的数据，不是代码里的常量

`project.ron` 新增 `layers` 节（`Layers`），`Entity` 新增 `layer: u8`。三层
（清单 / 场景实体 / rapier 碰撞组）里只有清单是真相源，实体的 `layer` 是"引用哪个层"。

`Layers` **只存覆盖**：`names: BTreeMap<u8, String>`、`masks: BTreeMap<u8, u32>`，
缺省一率按"有名字 = 空、掩码 = 全通"解释。所以默认清单序列化出来是 `layers: ()`，
老项目的 `project.ron` 一个字节都不用改（`skip_serializing_if = "Layers::is_default"`）；
`Entity.layer` 同理（`layer: 0` 不落盘）。**新增能力默认关 = 老行为逐位一致**这条红线
在这里的具体形态就是这两个 `skip_serializing_if`。

### 2. 碰撞是"两侧都同意"，矩阵必须对称写

rapier 的 `InteractionGroups` 判定是
`(a.memberships & b.filter) != 0 && (b.memberships & a.filter) != 0` —— 单边关掉就
不碰。所以：

- `Layers::collides(a, b)` 用**两侧相与**算，而不是读 `masks[a]` 的第 b 位；
  手改 RON 写出不对称的一对时，编辑器显示的必须是**实际生效**的结果。
- `set_collides(a, b, on)` **同时写两侧**，让数据永远对称。UI 上点一个格子等于
  "这一对碰不碰"，不是"a 对 b 碰不碰"。

### 3. 查询掩码只看成员位，不看碰撞矩阵

Unity 的 `Physics.Raycast(layerMask)` 语义是"只命中这些层"，与"这两层碰不碰"无关。
rapier 侧如果用 `QueryFilter::groups` 表达，会被矩阵一起过滤掉 —— 于是"幽灵层"
（不与任何层碰撞，但脚本要射线检测它）就查不到。正确做法是
`QueryFilter::predicate`：只读 `collider.collision_groups().memberships & mask`。
`RaycastFilter.layer_mask = None` = 老行为（不看层）。

### 4. 角色控制器必须带上自己的组

`move_character` 内部的 `QueryFilter` 默认没有 `groups`，于是矩阵里被关掉的一对
（角色 × 墙）在**移动求解**里仍然生效，表现为"射线查不到、人却撞住了"。必须
`QueryFilter.groups = Some(self.body_groups(body_id))`。这条有专门的回归测试
（先证红：把 `groups` 改回 `None`，`character_respects_its_own_layer` 立刻红）。

### 5. 改层要立刻改 rapier，不能等 `sync_bodies`

`sync_bodies` 的稳态早退判据是"结构性变化"（实体数 / 变换 / 碰撞体形状），
只改 `entity.layer` 不构成结构性变化，等着重同步就是**永远不生效**。所以
`World::set_entity_layer()` 里两件事一起做：写场景字段 + 立刻
`physics.set_body_groups(id, memberships, filter)`。

`set_body_groups` 刻意**不重建 query pipeline**：`QueryFilter::test` 在查询时现读
碰撞组，重建是纯浪费（顺便避免了 `Raycast` 一时新一时旧）。

### 6. 脚本改层走命令，因为脚本只读场景

Lua 的 `ctx` 只拿得到场景的只读视图，写不回去。所以 `set_layer` 走
`ScriptCommand::Relayered { id, layer }` → `CommandReport.relayered` →
`World::consume_script_commands()`。这条链与 `Despawn` / `SetParent` 同构，别在
`ctx` 里绕开。

### 7. 32×32 矩阵必须手工画，不能交给 `Grid`

实测（都是量截图得来的，只看代码看不出来）：

- `Grid` 的行高由格子里的子控件决定：塞 `ui.label` 行距 **25px**、塞定尺
  `allocate_exact_size` 行距 **21px** —— 都不是 `LAYER_CELL + 1 = 12`。32 行就是
  670~800px，矩阵顶出窗口，连页脚的 Apply 都被挤出屏幕（用户连"确认"都点不到）。
- `Grid` 的 `min_col_width` 默认是 `interact_size.x`（40px），32 列 = 1280px，
  窗口会被撑到半屏宽（这是另一半坑，两个坑叠加时先修宽再修高，不然看不出真因）。

现在矩阵是**一张画布 + 一个交互矩形 + 一次命中测试**：`LAYER_GUTTER + 32 × 12` 宽、
`LAYER_HEAD + 32 × 12` 高，一格不多；1024 个格子也不再是 1024 个 widget。
悬浮时用白框标当前格 + 完整层名提示（11px 里放不下"3 Enemy"这种文字）。

设置窗口宽度维持 **470px**：矩阵按 32 × 11px + 1px 间隙（≈ 383px）+ 行标 13px 设计，
正好塞得下（截图量过：32 个 9px 蓝格，横跨 380px，右边界离窗口边还有 76px）。
变宽会让其他区块的输入框跟着拉长，整页比例全变。

### 7.1 设置窗口必须是**固定高度**，滚动区高度不能靠窗口自身算

同一个面板上还踩了两个连锁的坑，最后都靠"高度写成常量"收口：

1. **按屏幕算 `body_max`（`screen_h - 190`）在高屏上会把页脚顶出去。**
   `egui::Window` 自身有高度上限 —— 实测 1080 与 1400 高的屏上，窗口内部都只给到
   **1005**（900 高的屏上是 871 = 屏高 - 29）。所以 1400 的屏上按 `screen_h - 190`
   算出的 1210 > 1005，滚动区吃掉全部可用高度，`Apply / Reset / Cancel` 被挤出窗口外，
   **用户连"确认"都点不到**。当时截图看着像"矩阵太大"，实际是页脚不见了。
2. **改用 `ui.available_height()` 会掉进反馈环。** 窗口高度由内容决定，而内容里的
   滚动区高度又由 `available_height()` 决定 —— 窗口小时算出的上限更小，窗口于是更小，
   实测整个面板塌成 ~400px 高（而且状态稳定，不会自己长回来）。

收口方案：`Window::fixed_size(vec2(470, clamp(screen_h - 60, 360, 920)))`，滚动区高度
`= window_h - TITLE_RESERVE(34) - FOOTER_RESERVE(52)`，三项全是常量。
验证方式是**在截图里用像素找 `Apply` 按钮那块 80×26 的纯蓝矩形**：
1280×900 / 1440×900 / 1920×1080 / 1280×1400 四档都能找到（y=838 / 838 / 968 / 1128），
"看着像有按钮"不算验证。

### 8. 越界层号一律取模，但要报出来

`sanitize_layer(layer) = layer % 32`（`LAYER_COUNT = 32`）。理由：层号来自脚本 /
MCP / 手写 RON，越界是"配置错了"而不是"必须崩"；取模至少落到一个真实存在的层。
但**静默修正等于欺骗**，所以 `--check`（与 MCP `project_check`）多一项
`invalid_layers`，逐条列出"场景: 实体 -> layer N"。

### 9. 默认值就是"老行为"，不要用"默认值更安全"当理由改它

`Collider.memberships / filter` 的默认是 `u32::MAX`（全通）。看着"更安全"的选择
是默认 `0`（谁都不碰），但那会让所有老场景里的碰撞体瞬间失效 —— 默认值的第一
职责是让旧工程保持原状。

## 三十七、形变目标：CPU 变形、增量已烘焙、动画优先于手动权重

### 1. 变形放在 CPU，别急着上 GPU

`morph_vertices` 是纯 CPU 函数：权重变了才算、算完 `write_buffer` 整段重写顶点缓冲。
商业引擎把增量塞进 storage buffer、在顶点着色器里累加；这里 v1 不走那条路，理由与
CPU 粒子同构：

- 只有**权重变化时**才重算，静止的模型零开销（`apply_source` 比对上次权重）；
- 面部网格量级很小（几千顶点 × 每顶点 76 字节），一帧一次 `write_buffer` 远没到
  PCIe 的痛处；
- 换来的是**零着色器改动、零新增绑定、零槽位分配** —— 而代价那侧是一个能在无显卡
  CI 上逐位断言的纯函数。

要改 GPU 时**别改数据布局**：`positions` 本来就是 target-major 平铺的
（`positions[t * vertex_count + v]`），搬进 storage buffer 只差一次上传和一段 WGSL。
判据是"万级顶点 / 几十个角色同屏"，不是"感觉该上 GPU 了"。

### 2. 增量必须与顶点位置同一套烘焙规则

`model_scale` 是**烘焙进几何**的（顶点、动画位移、IBM 平移都乘），morph 增量也必须乘
—— 否则把导入缩放从 1 调到 2，模型大一倍而表情幅度纹丝不动，看起来像"表情坏了"。

**法线增量是唯一例外**：均匀缩放不改变方向，乘了还要归一化回来，纯浪费。

### 3. 权重优先级：剪辑 > 实体 > 模型默认

- 剪辑里有 `MorphWeights` 轨道 → **以动画为准**，`Entity.morph_weights` 被忽略
  （Unity 同款：被动画驱动的属性不听手动覆盖）；
- 没有轨道 → 用实体权重；
- 实体没写 / 写短了 → 用 `mesh.weights` 默认值补齐；写长了 → 截断。

补齐 / 截断不是"顺手做的好事"，是**换模型不错位**的唯一安全解释：morph 目标只按
下标标识，下标跨模型没有意义，宁可丢弃也不能把"眨眼"的权重套到"张嘴"上。

### 4. 长度不自洽就整段放弃，不要"尽力而为"

`MorphTargets::new` 在 `positions.len() != target_count * vertex_count` 时返回 `None`，
这个图元当静态网格渲染。增量错位会把顶点挪到不存在的位置 —— 画出来是一团谁都认不出
的几何，而"没有表情"至少是正确渲染。

### 5. 权重没变就不许写缓冲

`apply_source` 里比对的是**解析后**的权重（`resolved`），不是调用方传进来的原表：
调用方传的可能是空表 / 短表，同一个 `resolved` 才等价于"同一个画面"。跳过逻辑必须
在 `write_buffer` 之前，否则每帧无谓上传几百 KB。

### 6. 法线只在真的加过增量之后才归一化

权重全 0 时 `out` 必须与 `base` **逐位相同**（测试钉住）。不这么做的话，"关掉表情"
与"从来没有表情"会在截图里差出浮点级噪声 —— 而这类噪声会让"逐字节一致"的回归
判据失效。

### 7. `Mutex` 是为了不推翻"多实体共用一个网格"

`GltfPrimitive` 挂在 `GltfMesh` 上，渲染期拿到的是 `&GltfMesh`（模型缓存共享给多个
实体）。要让 `apply` 取 `&mut self`，就得把模型缓存改成"每实体一份网格"或者给渲染
路径加一层可变借用 —— 两条都推翻现有结构。锁只出现在单线程渲染里，零竞争；
中毒时 `into_inner()` 继续用（纯缓存，最多多重算一帧）。

### 8. 脚本 API 逐下标、立刻生效、不进命令队列

- **逐下标**：目标名活在渲染资产里，脚本层看不到网格。名字 API 留到"core 认识资产
  清单"那天。
- **立刻生效**：渲染每帧读 `Entity.morph_weights`，不需要命令队列 —— 注意这**不是**
  `set_layer` 的模式，那个必须走 `Relayered` 是因为物理侧的碰撞组要跟着改。
- **钳位 + 稀疏写 + 上限 256**：钳位挡"算法算错"，稀疏写让"只动第 5 个表情"有写法，
  上限挡 `set_morph(id, 1e9, 1)` 把场景文件撑爆。

### 9. Inspector 扫过去不许改场景

Morph 区块**只在用户拖动时**扩容 `morph_weights`。检查时扩容会把"打开面板"变成
一次编辑（脏标记 + 撤销栈都得跟着动），这是老的"面板只读"约定的延伸。

### 10. 没有 morph 的模型，零成本

`GltfPrimitive.morph == None` 时：不加 `COPY_DST`、不调 `apply_morph`、渲染循环里
一次 `any(|p| p.morph.is_some())` 就整段跳过。默认路径必须与引入 morph 之前**逐位
一致** —— 与 §三十六.9「默认值就是老行为」是同一条红线。

## 五十九、打包必须验自包含：差集判据 + GUID 翻回路径（2026-10-28）

### 契约

`build` 只复制 `content` 声明的目录（**外加发布清单里每一关的父目录**）。复制目录
不会报错，所以"清单之外的引用"会**静默**落不进包 —— 编辑器正常、`--check` 全绿、
玩家拿到的成品缺子树或第二关黑屏。

发布前自检 `audit_package`：

1. 对**包**跑 `check_project`；
2. 对**源码工程**跑 `check_project`；
3. 取两次 `reference_issues()` 的**差集**；
4. 差集非空 → `BuildError::PackageIncomplete`，**构建失败**，上一版发布目录不动。

### 判据：差集，不是"有没有问题"

打包前后**一样缺**的东西归 `--check` 管。一条早就存在的坏引用不该让作者连包都打不
出来，判据必须落在"**构建有没有引入新问题**"。（`already_missing_assets_do_not_block_the_build`）

### `reference_issues()` 的边界

只收**引用 / 装载**类：模型、材质、材质贴图、坏材质、脚本、音频、UI 图、预制体、
悬空 GUID、坏场景、清单里装不起来的关卡。

**不收**：`missing_metas` / `orphan_metas` / `invalid_metas` / `guid_conflicts` /
`duplicate_ids` / `invalid_layers` —— 这些是**身份与格式**问题，同一个工程打包前后
一模一样，让构建替它们背锅没有意义，归 `--check`。

### 报错必须可操作

场景里存的是身份（GUID），所以自检报出来的原文是 `guid://3444c856…`。**光有 GUID
等于没说**：既不能定位文件，也不能提示怎么修。`explain_guids` 按**源码工程**的资产
库把它翻译回路径：

```
- Scenes/scene.ron: Pillar -> guid://3444c856…  （源码工程里是 Assets/Pillar.prefab.ron，它没进包）
```

### 别翻案的取舍

- 自检放在 `publish` **之前**：失败时上一版发布目录原封不动，"构建失败"不该变成
  "上一版也没了"。
- 源码工程 `check_project` 读不出来时**不当基线**（`unwrap_or_default`）：那是
  `--check` 的事，硬当成"基线为空"会把每一行都报成构建漏的。
- 代价是每次构建多扫两遍工程（源码 + 包）。构建是用户点一下的动作，不是每帧路径，
  这个代价换"不发残缺包"值。

### 能力边界

包内**真实窗口 + 键鼠输入**的玩家端到端、并发发布、断电事务仍未验证（R01/R02 的
其余部分）。本门禁只保证"包里不比源码工程少引用"，不保证引用的内容是对的。

## 五十八、预制体 Revert 保留实例 ID：删了重建 ≠ 还原（2026-10-28）

### 契约

`Revert`（用资产覆盖回实例）**必须保留实例里已有实体的 `EntityId`**：

| 情况 | ID |
|---|---|
| 实例里已有（按 `source_id` 对上） | **沿用旧 ID** |
| 资产里新增 | 新 ID |
| 实例里多出来（资产里没有） | 该实体被删除 |

理由不是"好看"：整棵重建会把子树里每个 ID 换一遍，① 场景文件凭空多出一大段纯 ID
变化（用户只点了一下还原）；② 任何按 ID 记住这些实体的东西（外部工具、用户脚本里
存的 id、跨帧缓存）全部失联。Unity 的 Revert 同样保留 ID。

### 落地方式

- `Prefab::instantiate_with(source, id_for)` 是唯一新增点：ID 由调用方决定，父子
  重定向仍按资产 ID 建索引。`instantiate` 就是 `id_for = |_| EntityId::new()`。
- `Scene::revert_prefab(root, &prefab, source) -> Option<usize>` 返回**新实例根**的
  索引。子树是整块重建后追加到末尾的，**索引会变**，调用方必须用返回值，不许用旧
  索引。编辑器侧的 `revert_prefab` 只用它保住"用户亲手摆的东西"（世界变换 + 父节点）。

### 三条不许翻的边界

1. **空资产不动手**：`prefab.is_empty()` 直接返回 `None`，场景逐位不变。旧行为是
   "先把实例删掉，再发现没东西可放" —— 点一下还原反而丢了整棵子树。
2. **不动根的世界变换**：还原是还原**内容**；把用户摆好的位置一起抹掉那叫回到出厂。
   世界变换与父节点由宿主恢复。
3. **撞 ID 要自愈**：沿用旧 ID 的前提是旧数据合法。手改过的场景里两条实体共用一
   个 ID 时，`revert_prefab` 末尾 `ensure_unique_ids()` 兜一次，只可能动到"多出来
   的那条"。与 §五十三「场景的重复 ID 可静默修、预制体的不许」同源。

### 能力边界

嵌套预制体（实例里再嵌实例）与**字段级覆盖**（实例只改一个字段、Revert 只还原那一
个字段）都还没做。当前 Revert 是**整树内容覆盖**，不要按 Unity 的"只还原被覆盖的字
段"来理解。

## 五十七、销毁钩子里的结构性改动：立即进场景，但命令下一帧才结算（2026-10-28）

### 语义

`on_destroy`（以及任何钩子）里调 `spawn_entity*` / `destroy`：

- **场景改动立即生效** —— `spawn` 出来的实体当场就在 `Scene` 里，同帧 `find_entity`
  找得到；`destroy` 掉的实体当场不在。
- **命令结算推迟一帧** —— 命令缓冲在派发前已被 `take_commands()` 取走，途中产生的
  命令落在**新**缓冲里，下一帧才结算（建刚体、派发 on_destroy）。

这两条不矛盾：`Scene` 是立即的真相，物理 / 通知是延迟结算的。写脚本时按这个理解，
别假设"spawn 完就有刚体"。

### 必须成立的三件事

1. `on_destroy` **只派发一次**，spawn 只结算一次，后续帧不重复。
2. 链式销毁（A 的 `on_destroy` 里 destroy B）里，**B 也必须收到 `on_destroy`**，
   且能读到它自己销毁前的状态。忽略"处理途中产生的删除"会让 B 永远收不到通知、
   状态表永远不释放。
3. 位置 / 模型等字段在 spawn 当帧就生效。

### 能力边界（别当成 bug 查）

`spawn_entity(ctx, name, model)` **不带脚本**，Lua 侧也没有"给已有实体挂脚本"的 API。
要分裂出**带行为**的实体必须走 `spawn_prefab`（预制体里的实体自带 `scripts`）。

## 五十六、`World::update` 必须确定性：同输入 → 逐位同轨迹（2026-10-28）

### 契约

同样的初始场景 + 同样的每帧 `dt`，两次运行的世界轨迹必须**逐位相同**
（`crates/xgame-runtime/tests/determinism.rs`，不 ignore，进 CI）。

- 判据用 `f32::to_bits` 比对，**不用容差**：真值差异就是 0，容差会吞掉微小分叉，
  而那正是这类 bug 的第一形态。
- 场景必须**顺序敏感**（叠放、接触、碰撞）。纯静态场景等于没测。

### 为什么"同进程两次运行"就够

`HashMap` 的 `RandomState` **每个实例都用不同种子**。所以两次 `World::new` 的哈希
顺序天然不同 —— 任何"按哈希顺序决定谁先谁后"的地方都会立刻分叉，不需要换个进程。

### 规则

- 凡是影响**物理 / 派发顺序**的集合，不能直接拿 `HashMap::keys()` 当输入：
  要么按场景顺序（`Scene::entities` 是 `Vec`，天然确定），要么显式排序。
- 实测案例：`sync_bodies` 清理段按 `body_of_entity.keys()` 收待删列表。已改成
  `sort_unstable_by_key(|id| id.raw())`。**注意这不是修 bug** —— 当前 rapier 对
  `remove_body` 先后不敏感，加排序前后测试都绿；这是去掉一个**未受契约保护**的
  顺序依赖（换求解器后症状是"偶发对不上"，极难查）。写文档时别把它说成"已修的缺陷"。
- 排序只允许出现在结构性变化的路径上（稳态帧不能为它付代价，见 §五十四）。

### 三宿主的接线（R10/084 的一半）

`update_with_scene` 只把编辑器场景 `swap` 进 `World` 再调同一个 `world.update(dt)`；
headless 也直接调 `world.update(dt)`。"三宿主跑同一段逻辑"是**结构保证**，
不需要跑三次的测试去证明。R10 的"父层级对照"仍未做。

### 未覆盖

跨机器 / 跨编译器的浮点一致性、`wrap` 模式差异；将来若给 rapier 开并行求解
（rayon），这条性质要重测 —— 并行归约的顺序不受我们控制。

## 五十五、脚本错误：指数退避限流，成功清零，但不许自动禁用（2026-10-28）

### 契约

一个每帧都出错的脚本，日志必须是**指数退避**的：只在第 1、2、4、8… 次报，第 2 次
起的文案带「已连续报错 N 次」。同一 `(实体, 脚本, 钩子)` **成功执行一次即清零**。

- 不清零 = "修好之后的第一条错误"被当作第 N 次静默掉，正好吞掉用户最想看的那条。
- `invalidate*` / `reset_runtime_state` / `reset_scene_state` 必须清空计数
  （热重载换了内容、换场景换了实体 ID、新 Play 会话应当重新报）。
- 计数表超过 1024 条时扫一遍删掉已不在场景的条目，防"每帧 spawn + 报错 + destroy"
  把表撑大。

### 为什么不禁用脚本

禁用会**悄悄改变游戏行为**（渲染脚本报错后连移动逻辑都不跑了），比刷屏更难查。
限流的目标是"让故障可见而不刷屏"，不是替用户决定"这个脚本别跑了"。

### 为什么必须做（不只是观感）

每次 `format!("{err}")` 都在热路径上分配。一个坏脚本就能把稳态零分配整个破坏，
而 `alloc_steady_state` 门禁测的场景不带脚本，正好测不到 —— 两条防线互补，缺一不可。

### 限制在哪

只限流引擎**捕获到的** Lua 错误（含指令预算超限）。脚本自己 `log(ctx, …)` 打的
内容不受节流 —— 那是用户的输出，宿主不该替它决定抑制什么。

## 五十四、稳态零分配是**门禁**，不是口号（2026-10-28）

### 契约

`World::update` 在预热之后**每帧不得分配**。覆盖两条主要稳态路径（200 实体 + 静态
物理、12 按钮 UI + 布局命中），实测都是 0 次 / 0 字节。判据在
`crates/xgame-runtime/tests/alloc_steady_state.rs`，**不 ignore**，跟着全量测试进 CI。

要新增缓冲就提前分配、复用；`collect()` / `format!` / `to_vec()` 出现在每帧路径上
一律视为回归。

### 为什么不能用帧时间基准代替

60 FPS 下每帧几块临时 `Vec` 不进均值，只让帧时间抖动、让分配器变热点。而分配器在
Web / 主机上比桌面弱得多 —— 桌面测不出来不代表没问题。

### 三个必须记住的坑

1. **必须证明"真的跑了"**。只断言"分配 0 次"时，`update` 因为任何原因没跑都成立。
   加"世界时间推进约 1.0s"之后立刻暴露：预热 30 帧被算进去了，期望 1.0s 实得
   1.5s → 改成测**窗口内增量**。
2. **全局分配器是进程级的**。同一 test binary 里的测试默认并行，各自开关计数窗口
   会互相记账 → 随机假红。所有变体合进**一条**测试，别加锁（锁自身的分配也会入账）。
3. **UI 变体要单独证明命中跑了**。`UiElement::at` 的第一个参数是**归一化锚点**不是
   位置；锚点越界会让布局走异常分支，此时"零分配"等于"没跑"。

### 计数实现

`#[global_allocator]` 包 `System`，`alloc` / `alloc_zeroed` / `realloc` 先记账
（`AtomicUsize` + `AtomicBool` 开关）再原样转交；`dealloc` 不动。记账只用无锁原子
操作，不分配、不 panic、不递归。开关的存在是必须的 —— 预热期的分配是**一次性**的，
把它算进来会让门禁永远红。

## 五十三、ID 的唯一性是**每个文件内**的；跨文件引用不许静默改（2026-10-28）

### 1. 唯一性作用域

| 文件 | ID 被谁引用 | 唯一性要求 | 加载边界能不能修 |
|---|---|---|---|
| 场景 | 同文件的 `parent` | 场景内唯一 | **能**（`Scene::ensure_unique_ids`） |
| 预制体 | **另一个文件**的 `PrefabInstanceRef::source_id` | 预制体内唯一 | **不能**，只报告 |

"场景 ID 与预制体 ID 重叠"**不是**冲突：实例化时全部换新 ID，资产里的 ID 只作为
`source_id` 留档。跨文件唯一的是 `(source, source_id)` 这个二元组。

### 2. 为什么预制体不能照着场景"对齐"

看上去 `load_prefab` 少了 `ensure_unique_ids` 是不一致，其实是必须的。重分配会让
**所有既有场景实例**的 `source_id` 集体失配；`Apply` 时 `capture_subtree_ids`
取不到值就退回 `EntityId::new()`，于是资产里凭空长出一份重复实体，而且不再对位。
**判据：能被静默修的前提是"坏了也只有本文件受影响"。跨文件引用坏了，修就是二次
破坏。**

### 3. `--check` 报什么

- `duplicate prefab id:` —— 回到**磁盘原文**统计（`project.prefab_duplicate_ids`），
  含没被任何场景引用的预制体。修法：打开该预制体重新保存一次。
- `dangling source:` —— `source_id` 在对应预制体里找不到。按 `(场景, 预制体)`
  聚合成一条，报缺失数量 + 首个缺失实体。成因通常是预制体被编辑过（删了实体）
  或外部手改 ID。

两者都进 `has_issues()` ⇒ `--check` 退出码 2。

### 4. 输出文案必须纯 ASCII

`CheckReport::render` 的产物是给 CI 和 AI 智能体读的**文本契约**，不是给控制台
看的漂亮输出。控制台代码页不是 UTF-8 时中文会变成乱码（实测 PowerShell 下
"里找不到"→"閲屾壘涓嶅埌"）。所以文案一律英文；实体名 / 路径里的中文是**数据**，
照原样打，那部分不可避免也不该改。

## 五十二、三条数值 / 交互边界：质量回退、ID 上限、指针拆分（2026-10-28）

### 1. 密度表达不了质量时，质量挂在刚体上

场景的 `mass` 是**总质量**，靠 `density = mass / 单位体积质量` 兑现，好处是惯量由
同一形状算出。但极小碰撞体（半径 1e-20）的体积在 f32 下下溢成 0，密度变 `inf`，
rapier 拿它乘体积后实际质量是 **0** —— 声明值被静默丢掉。

判据：`unit_mass` 必须有限且 > 0，`density` 也必须有限；任一不成立就退回
`RigidBody.mass = def.mass`（附加质量），碰撞体密度给 1.0。两条路径的质量之和恒等于
声明值。**别**为了省事给密度加"看起来安全"的上限 —— 那会破坏质量守恒，而真正的问题
是"这个形状没法用密度表达"，不是"密度太大"。

### 2. `u64::MAX` 是坏数据哨兵，不是合法 ID

`EntityId` 的计数器靠 `fetch_max(raw + 1)` 前进。接受 `u64::MAX` 等于把水位顶到天花板，
下一次 `new()` 返回同一个值 —— 两个实体共用一个 ID，删除时连坐。

判据：`MAX_ASSIGNABLE_ID = u64::MAX - 1`；读盘严格大于它即 serde 错误（带原值与上限）。
`new()` 用 CAS 循环跳过 0：`fetch_add` 回绕会落到 0，而 0 从来不是分配器的产物
（手写文件里可能有）。语义保证是**不回绕**，不是无限供应 —— 走到耗尽需要 2⁶⁴ 次分配。

### 3. 指针的"位置"与"按键"是两件事

`UiPointer.pos: Option<Vec2>` 只表达"指针在不在视口里"，`down` / `pressed` / `released`
始终有效。把两者合成一个 `Option` 的后果是"在视口外松手"那一帧整个被丢掉：捕获留在
按钮上，`Release` 事件也发不出去。

- runtime 永远传 `Some(UiPointer { .. })`；视口尺寸为 0 时传 `None`（没有 UI 可交互）。
- 捕获状态用 `World::ui_pressed()` 断言，别只看 `UiElement::state.pressed` ——
  后者的可见症状要等指针回到视口才消失，测试会假绿。
- 父节点隐藏 = 整棵子树不进命中表（`layout::walk` 的既有契约，测试已钉）。

### 4. UI 阶段排在脚本之前，脚本改的矩形迟一帧生效

`World::update` 第 0 步是 `update_ui()`，早于 `start` / `fixed_update` / `update`。
原因是 `ui_clicked(ctx, id)` 必须读到**本帧**的点击状态 —— 脚本在 `update` 里问
"这个按钮刚被点了吗"，答案不能是上一帧的。

代价：脚本本帧挪动 / 显隐 / 改尺寸的 UI 元素，**本帧的命中测试仍按旧布局**，下一帧才
生效。这是刻意取舍，与 Unity 的 EventSystem（输入先于 `Update`）同构。

判据：不要为了"更跟手"把 `update_ui()` 挪到 `run_dispatch(Phase::Update, …)` 之后 ——
那会让 `ui_clicked` 永远慢一帧，且 `script_moved_ui_takes_effect_on_the_next_frame`
会先红。要改这段顺序，先改这条测试，并同步 `ConsumeScriptCommands` 的时序文档。

## 五十一、CUBICSPLINE 必须原样保留，采样走 Hermite（2026-10-28）

### 1. 切线是内容，不许在读入时丢

`CUBICSPLINE` 的每关键帧输出是 `(入切线, 值, 出切线)` 三份，切线单位**每秒**。
早先读入时只留中间那份、把插值降成线性 —— 数值上不崩，但 Blender / Maya 默认导出
的就是三次样条，等于把大多数资产的关键帧曲线拍平，而且不可逆。

**判据**：`Track::values` 的长度必须等于 `times.len() × frame_len()`，
`frame_len = stride × slots`（样条 `slots = 3`，其余 1）。读入端形状不符就整条丢弃，
采样端形状不符就跳过（morph 返回 `false`）。某一帧的"开始 / 值 / 切线"位置只能通过
`frame_start` / `value_start` 取，**别在别处手算下标**。

### 2. 值在"三份里的中间那份"

`value_start(k) = frame_start(k) + value_slot × stride`，`value_slot` 由插值给出
（样条 1，其余 0）。写成 `(slots-1)` 会读到**出切线** —— 不 panic、不报错，只是整段
动画偏移。这条必须由测试钉住（`regression_r04_cubic_spline_midpoint_is_hermite_not_linear`
在写错时实得 1.25 而非 0.75）。

### 3. 切线乘段长，旋转归一化

- Hermite 用 `p(u) = h00·p0 + h10·m0 + h01·p1 + h11·m1`，其中 `m0/m1` 是
  **已乘 `dt = t1 - t0`** 的切线（glTF 规范附录 C）。漏乘会让长段欠冲
  （2 秒段实得 0.75 而非 1.0）。
- 旋转逐分量 Hermite 后**必须归一化**：不归一等于给蒙皮乘一个随动画变化的缩放，
  模型会越动越大。长度接近 0（手工改坏的曲线）时退回 `slerp`，避免 NaN 进矩阵。
- 线性 / 阶梯的读数保持不变（同样 `lerp` / 取左帧）；新增分支每条轨道走一次，
  不在每采样点里。

### 4. 成本实测（同机 release，84 条轨道 × 16 帧，7 轮取最快）

| 档位 | 单次 `sample_clip_into` |
|---|---|
| 线性 | 2031–2061 ns |
| 阶梯 | 891–902 ns |
| 三次样条 | 1652–1662 ns（0.80–0.81 × 线性） |

样条比线性便宜，是因为 `Quat::slerp` 的 `acos` + 两次 `sin` 比 Hermite 的
4 次乘加 + `normalize()` 贵。**别据此把线性资产改成样条** —— 插值是资产的事实，
不是性能旋钮。基准：
`cargo test -p xgame-render --release --test animation_cost -- --ignored --nocapture`。

## 五十、打包必须拒绝「引擎源码不一致」的播放器（2026-10-27）

`builder::locate_player` 原来只判"文件存在"，取第一个候选。于是改完物理 / 脚本、
只重编了编辑器，点 Build 就会把一个**旧引擎**的 `xgame-game.exe` 拷进成品，而且
没有任何征兆 —— 作者在编辑器里验过的效果到了成品里可能全不成立。

### 1. 判据是二进制里自带的源码指纹

`xgame/build.rs` 现在产出两份指纹：

| 指纹 | 覆盖输入 | 用途 |
|---|---|---|
| `xgame-build-v1:…`（`BUILD_FINGERPRINT`） | 全套，**含** `PROFILE` / `OPT_LEVEL` / `DEBUG` | 插件门禁：同一**构建单元**才谈得上跨 DLL 调用 |
| `xgame-src-v1:…`（`SOURCE_FINGERPRINT`） | 同上但**排除**那三个 profile 键 | 播放器新鲜度：debug 编辑器配 release 播放器是开发期正常组合 |

两份都是 `include_bytes!` 常量，会被链接进每个依赖 `xgame` 的可执行文件 ——
编辑器与播放器都有，**不需要**额外的清单文件，`.exe` 拷到哪都自证。

### 2. 必须有 `#[used]` 锚点，否则常量会被链接器扔掉

实测：没有锚点时 `xgame-game.exe` 里**找不到** `xgame-src-v1:` —— 没人引用它，
`/OPT:REF` 就把整段回收了（插件那份没这问题，因为握手代码真的读它）。加一个
`#[used] static SOURCE_FINGERPRINT_ANCHOR: &&[u8]` 之后指纹稳定留在二进制里。
**删这行等于关掉整个门禁**，而且症状是"永远报旧引擎"，很容易查错方向。

### 3. 行为：跳过旧引擎，全旧则拒绝

候选顺序不变（编辑器同目录 → `target/release` → `target/debug`），但**跳过**源码
指纹不一致的：跳过了就打一条 `BuildReport::warnings`（"用的是哪个"），一个都不
匹配才报 `BuildError::PlayerStale` 并给出重编命令。为什么不一概拒绝：debug 编辑器
配 release 播放器必须还能用；为什么不在全旧时警告了继续：那等于把一款跑旧引擎的
游戏当成功交付，比一次明确的失败糟得多。

### 4. 副作用与边界

指纹的输入是各 **lib crate** 的 `src`、各 `Cargo.toml` / `Cargo.lock`、工具链与
flags；编辑器自己的 bin 代码不在其中（它不会进播放器）。所以动了这些就得先重编
播放器再打包 —— 这正是要表达的契约。反过来，`dist/xgame-editor.exe` +
`dist/xgame-game.exe` 同批构建时指纹一致，用户点 Build 不会被打扰。仍然只看指纹
不看内容签名，不防篡改；第三方源码不同就该重建。

### 5. 「哈希相同」不等于「新鲜」，而字节哈希本身也不适合当新鲜度判据

 **第一课（dist 与 target/release 同哈希 ≠ 新鲜）**：实测 2026-10-28 收尾时先比
`dist/*.exe` 与 `target/release/*.exe`，三个全 `SAME`；照约定重建 release 后，
`xgame-editor.exe` / `xgame-game.exe` 字节**变了**，而源码指纹前后一致。即两者只是
"同源"，可能**一起陈旧**。

**第二课（字节哈希逐次不同，这不是 bug）**：同一天再测，源码一字未改、只 `touch`
改 mtime 强制重编，`xgame-editor.exe` 字节**又变了**（大小完全一致）。逐字节比对：
**19 个字节不同，首处在 `0x100`** —— 那是 PE 可选头里的 `TimeDateStamp`，外加
校验和一类元数据。代码段逐字节相同。**所以本项目的 release 产物不可逐字节复现**，
拿 exe 的 SHA-256 当"新鲜 / 一致"的判据永远会失败。

**正确判据**：
1. 收尾必须**真的跑一次** `tools/build-release.ps1`；
2. 新鲜度看**内嵌指纹**（`xgame-src-v1:` / `xgame-build-v1:` 字符串，用 ASCII 扫描
   exe 就能取到），与当前源码算出的值比对；
3. `dist` 与 `target/release` 字节相同只能证明"是同一份拷贝"，**不能**证明新鲜。

若将来需要逐字节可复现（对外发布校验），得在链接层处理时间戳（`/Brepro` 一类），
并重新验证一次；现在不做，因为门禁已经由指纹承担。

## 四十九、写盘只有一份实现，暂存回收只认精确命名（2026-10-27）

`core::project`、`editor::prefs`、`input::action` 各自抄了一份"同目录独占暂存 + `sync_all`
+ 替换"，三份的差错点还各不相同：一份补建父目录、一份支持"只发布到空位"、一份两者都
没有。写盘可靠性是 G0 的头等项，抄三遍等于三处漏，现在全部收敛到 `xgame_core::fsx`
（`write_atomic` / `write_atomic_new` / `sweep_staging`），调用方只做错误类型映射。

### 1. 暂存命名就是回收判据

暂存叫 `<主名>.<扩展名>.tmp.<进程号>.<序号>`，回收只认**收尾恰好两段数字**的名字。
理由：单段数字（`notes.tmp.5`）和旧版固定暂存名（`scene.ron.tmp`）与用户自己的文件
无法区分，猜错就是**删用户文件**。这类残留留着手删，不自动清理。**改命名必须同步
`is_staging_name`**，否则垃圾会重新开始堆积。

阈值 600 秒是为了不误删**并发写入者**正在用的那份：本引擎落盘都是小文本，一次写完
远不到 10 分钟；真超过还没替换的，基本只能是崩溃残留。时间戳读不到或早于当前时钟
（时钟被回拨）一律当作"不确定"，宁可不删。

### 2. 回收只在保存成功后，绝不在打开时

`ProjectHandle::open` 也是 `--check` 的入口，而检查必须**只读**（§十四）。
所以回收挂在 `write_atomic` 发布成功之后：刚保存过是最自然的时机，读路径一个字节
都不动。回收是尽力而为——目录不可读、文件删不掉都只返回 0，**不能把清理失败
报成写失败**。

### 3. 父目录 fsync 只在 POSIX 成立

数据文件 `sync_all` 只保证内容落盘，目录项可能丢，所以 POSIX 上发布后再同步父目录。
Windows 的标准库打不开目录句柄（需要 `FILE_FLAG_BACKUP_SEMANTICS`，std 没暴露），
那里退化成空操作，**没有"替换已持久"的硬保证**，只有 NTFS 元数据日志。

### 4. 输入 crate 因此依赖 core

§四十五 曾写"输入 crate 不引入 core 依赖"——那是当时为了避免再造一份实现而定的边界。
统一之后这条边界不再成立：`xgame-input` 增加 `xgame-core` 依赖，方向仍是向下的
（core 在栈底），不违反"不许反向依赖"。留一份会漂移的副本比多一条向下的依赖边贵。

### 5. 仍然不承诺的东西

同一目标的多进程同时保存仍是最后完成者胜出；多文件迁移不是整体事务；断电后的
目录持久性在 Windows 上没有验证手段，只做了 POSIX 的 fsync 目录。

## 四十八、最近项目列表与偏好共用可靠写盘（2026-10-27）

`recent_projects.ron` 也属于用户配置：旧实现直接 `fs::write` 截断目标，锁定目标但允许写入时仍报告成功。它与 `editor.ron` 共用编辑器内 `write_staged`，独占同目录暂存，`sync_all` 后替换；失败留下旧字节并允许解除占用后重试，旧固定 `.tmp` 残留不阻断。读取失败仍退空列表、UI 写失败仍记警告；不把该文件与项目内容混合。断电目录持久性未验证。

## 四十七、编辑器偏好保存不得覆写被占用的旧文件（2026-10-27）

`editor.ron` 在替换失败时不能退回直接覆写：Windows 目标句柄允许写但不允许删除时，这会把一次布局保存变成原文件被截断的风险。采用同目录独占暂存名，写入并 `sync_all` 后替换；失败返回错误、保留原字节，释放占用后可重试。旧版固定 `.tmp` 残留不阻断后续保存，也不自动清理。断电后的目录持久性仍未专项验证。

## 四十六、资产引用迁移的单文件替换（2026-10-27）

`--migrate-assets` 的场景、预制体、材质替换仍只改原文完整字符串字面量，不能通过反序列化整份重写吞掉注释。写回必须复用主保存的同目录独占暂存与替换；目标被锁定时逐文件报错，原字节不被截断，解除占用后重复迁移即可完成。单文件写入保护不提供跨文件原子事务，也不证明断电目录持久化。

## 四十五、输入配置主保存失败保护（2026-10-27）

`InputMap::save` 将 `input.ron` 写入同目录、独占命名的暂存文件，`sync_all` 后替换目标；替换失败返回错误并保留目标原字节，不能退回直接覆写。旧固定暂存文件不阻塞新写入（新命名暂存由 §四十九 在保存成功后回收，旧命名仍留着手删）。~~输入 crate 不引入 core 依赖~~（该边界已由 §四十九 取消：写盘实现统一到 `xgame_core::fsx`，输入 crate 因此依赖 core）；断电目录持久化未证明。

## 四十四、资产 `.meta` 写入与身份发布（2026-10-27）

已有元数据的导入设置更新复用 `project::write_atomic`：同目录独占暂存、写入同步后替换，替换失败保留目标原字节和内存索引。首次生成元数据则先写同步的独立暂存文件，再用同目录硬链接只向空目标发布；并发者已先创建 `.meta` 时拒绝覆盖其 GUID，批量生成保留错误并等待刷新索引。扫描仍只读，成功发布后才登记内存身份。异常残留的新命名暂存由 §四十九 在后续保存成功后回收；不承诺目录断电持久化，也不把多个 `.meta` 的批量生成视为单次事务。

## 四十三、主保存暂存文件独占与残留（2026-10-27）

`ProjectHandle` 的项目清单、材质、场景、预制体及自动保存共用 `write_atomic`：暂存必须在目标同目录，`create_new` 独占；每次分配 `进程号 + 原子序号`，同进程内不重复，跨进程路径冲突则重试。旧版固定 `<文件>.tmp` 及其内容保留，不能自动推断已无写入者而删除。只有本次创建的暂存文件在写入/rename 失败时清理，失败绝不退回直接覆写目标。原子替换不保证目录项断电持久化，多进程对同一目标的最后完成者胜出，仍需更强并发控制时另行设计。

## 四十二、morph 包围盒必须覆盖同时启用的目标（2026-10-27）

`MorphTargets::conservative_bounds` 在导入阶段按顶点、按目标累加负增量下界与正增量上界，覆盖现行 `[0,1]` 权重范围内的所有组合，再并入 `GltfMesh::bounds`。仅并原始顶点或各个单目标终点都不够：多个目标可以同时启用。增量已经烘焙 `model_scale`，这里不重复缩放。

剔除在动画/morph 权重采样之前发生，因此不能依赖上一帧的变形缓存；保守盒由相机剔除、场景 bounds 与阴影拟合共同消费，不增加逐帧顶点扫描。代价是盒子可能比当前姿态大。既有蒙皮 50% 余量保留，这次不将任意骨骼位移的保守性标为已证明，也不宣称容量超限策略完成。

真实 glTF 导入与 GPU 像素测试均先在旧实现失败，修复后通过；测试会确认形变确实进入画面，再比较开/关剔除逐字节一致。另有纯 CPU 正负目标/分数权重回归，避免无 GPU 环境完全缺少验证。

## 三十八、实体 ID 的唯一性是**跨进程**契约：读盘要预留、删除要按索引（2026-10-25）

`EntityId` 是"进程内原子递增"，而场景 / 预制体文件里存的是**裸 ID**。两者之间有一条
很容易被忽略的缝：文件里的 ID 是上一次运行分配的，新进程的计数器却从 1 重新开始。

### 1. 症状：删一个物体，别的物体跟着消失

1. 打开项目，从 `Scenes/*.ron` 读回实体（`id: (1)`…`id: (24)`）；
2. `EntityId::new()` 在本进程里仍返回 1 —— 新建实体与读盘实体**撞 ID**；
3. 删除新实体时，`remove_subtree` 收集"要删的 ID"再按 ID 筛选，两条同 ID 实体
   一起被收走。作者的观感是"删了这个，那个也没了"。

它不是每次都出现，所以特别难归因：只在"先读盘、后新建"的会话里发生。

### 2. 四条约束（都不能推翻）

1. **反序列化必须预留计数器**。`EntityId` 的 `Deserialize` 走 `reserve`：
   `COUNTER.fetch_max(raw + 1)`。用 `fetch_max` 而不是 `store`，并发加载不会把
   计数器往回拽；`saturating_add` 挡住 `u64::MAX` 回绕。**不要**把它"简化"回
   `#[derive(Deserialize)]` —— 那正是这个 bug 的来源。
2. **`remove_subtree` 按索引掩码筛，不按 ID**。`subtree()` 给的是索引，索引天然
   唯一；按 ID 筛等于给删除路径加了一个"ID 全局唯一"的前置条件，而这个条件会被
   读盘破坏。顺带把 `O(n²)` 降成 `O(n)`。
3. **父子解析的批量路径与逐次路径必须同解**。`index_of` / `find_entity` 是
   `position()`（第一个匹配），`parent_indices` 建表时也必须 `or_insert`（第一个
   占位）。用 `.collect()` 会变成"后出现的覆盖前面的" —— 撞 ID 时子节点会被挂到
   另一条实体名下，删除时连带删掉不该删的东西。
4. **读盘边界修复落盘伤**。`Scene::ensure_unique_ids` 把重复 ID 重新分配：bug 一旦
   发生过，坏 ID 已经写进文件，光修分配器救不回旧文件（`--check` 也不会报，因为
   加载时已被修好，只在 stderr 留一条告警）。**已知局限**：文件里出现重复 ID 时
   "谁是父"已不可还原，指向该 ID 的 `parent` 落到第一个同 ID 实体上 —— 修的是
   "不再连坐删除"，不是原样复原。

### 3. 同一类问题的其他入口

- **预制体实例化**按**位置**分配新 ID，不按旧 ID 建映射：`id_map` 以旧 ID 为键时，
  两条撞 ID 的源实体会互相覆盖，最后共用一个新 ID（实例化自己造出重复 ID）。
- **撤销 / 重做**换的是整份场景，选中必须按 **ID** 还原、找不到就取消选中。
  只做 `clamp_selection`（夹到合法范围）会留下一个"合法但指向别人"的索引，
  下一次 Delete 就删错对象 —— 这是同一个症状的第二条路径。
- **显示名**也要去重：`next_entity_id` 只用于名字、不随加载同步，新建实体会造出
  第二个 `GameObject (1)`。删除日志与层级面板都只有名字，重名会让"删错了"无从辨认。

### 4. 验证

- `remove_subtree_spares_other_entities_that_share_an_id`（旧实现删两条）
- `deserializing_an_id_reserves_the_id_counter`（旧实现计数器不动）
- `ensure_unique_ids_reassigns_duplicates` / `scene_ids_round_trip_unchanged`
- `instantiate_keeps_new_ids_distinct_when_the_source_has_duplicates`
- `undo_does_not_leave_selection_pointing_at_another_entity`（旧实现留下 `Some(1)`）
- `created_entities_never_reuse_an_existing_name`（旧实现两条同名）

## 三十九、身份、名字与注册表：同一族缺陷的其余入口（2026-10-25）

§三十八 修的是"删一个物体连带删别的"。按同一族又扫了一遍，补掉四处**同源**的
入口。它们的共同点不是"某段代码写错"，而是一条**没人写下来的隐含前提**：

> 场景里实体 ID 唯一、名字唯一，且所有"ID→索引"的建表方式取值一致。

这条前提会被三件事打破：旧文件里的落盘伤、复制 / 粘贴自己造出来的副本、
手写 RON。逐个入口：

### 1. 复制 / 粘贴：新 ID 按**位置**分配，不以旧 ID 建映射

`EditorState::duplicate_entity` / `paste_entity` 原来是
`id_map.insert(entity.id, EntityId::new())`。源子树里一旦出现重复 ID（父子撞号），
第二次 `insert` 覆盖第一次 —— 两条副本拿到**同一个**新 ID。"复制"这个动作本身
就把重复 ID 造进了场景，接着 §三十八 修掉的后果（删连坐、父子错位、脚本状态
错位）全部原样回来。

改法与 `Prefab::instantiate` 一致：`new_ids: Vec<EntityId>` 按位置分配；旧 ID →
新 ID 的表**只用于重定向父子引用**，并且用 `entry().or_insert()` 取第一个。

### 2. 名字也是身份：复制出来的实体必须去重

`format!("{} (Copy)")` 连按两次 Ctrl+D 就得到两个 `A (Copy)`。层级面板、删除
日志、控制台里**只有名字** —— 重名之后作者无法确认"我删的到底是哪一个"。
与上次修的两个 `GameObject (1)` 是同一个坑，只是入口不同（`copy_name` +
`EditorState::unique_name`）。

`unique_name` 与 `claim_entity_name` 是**两个**函数，别合并：后者会连带消耗
`next_entity_id`（名字里带序号的新建流程用），前者只解决"名字撞了"。

### 3. 所有"ID→索引"的批量建表都必须取第一个

`Scene::index_of` / `find_entity` 用 `position()`（第一个）；`parent_indices`
曾经用 `.collect()`（后写覆盖 ⇒ 实际取最后一个），§三十八 已修。

**同族的第三处是 UI**：`xgame_ui::layout::UiTree::build` 也用 `insert` 建表，
于是子元素被挂到**后一个**同 ID 实体下 —— 布局错位、点击命中到别的元素。
撞 ID 现在会在读盘边界被修掉，但内存里传进来的场景**不保证**经过那道门，
所以按"取第一个"写死，而不是依赖上游。

### 4. 加载期修复必须配一个**只读**检测，否则 CI 永远绿

`parse_scene_text` 在加载边界调 `ensure_unique_ids` 把重复 ID 修好。好处是老
文件不再连坐删除；代价是任何"加载之后再检查"的路径（`--check` / CI / MCP
`project_check`）**永远看不到**这类落盘伤 —— 项目可以带着病一路绿灯。

所以补了 `Scene::duplicate_ids()`（只报告、不动数据）+
`ProjectHandle::scene_duplicate_ids()`（回到原始文本再解析一次）+
`CheckReport::duplicate_ids`，MCP 的 JSON 里加同名字段。检查仍然**只读**
（§十四 的硬约束）：查一次不会把文件改好，测试里专门钉了这条。

输出顺序按**首次出现**排，不用 `HashMap` 迭代顺序 —— CI 的 diff 必须稳定。
代价是每个场景多解析一次；检查是低频 CLI，换"能看见文件里的病"划算。

### 5. 预制体与场景的**不对称**（刻意，不是漏了）

`load_scene` 修重复 ID，`load_prefab` **不修**。理由：`PrefabInstanceRef.source_id`
是**跨文件的裸 ID 引用**，改预制体里的 ID 会让已有场景实例指向错实体 ——
那比"保留重复"更糟。预制体侧只保证两件事：`Prefab::instantiate` 按位置分配
（实例之间不会共用 ID）、读盘时看得见重复。

读预制体若发现重复 ID：手工重排 ID 并检查场景里的来源引用，别指望加载器代修。

## 四十一、G0 追加保存与脚本调用窗口（2026-10-27）

- `ProjectHandle::save/write_material` 与 scene/prefab 共用原子替换。Windows 允许读写但禁止删除的句柄用于注入 rename 失败，旧目标必须保持原字节；任何失败不得降级直接覆写。固定 tmp、meta/input/迁移与断电持久化边界仍保留。
- Lua 顶层 exec 单独重置指令预算，坏脚本不能耗尽下一份脚本预算。
- `LuaCtx::from_lua` 在读取槽之前，先验证 VM 的活动窗口与槽地址；窗口仅包住钩子调用，RAII 在成功、Lua 错误或 Rust 展开时失效。顶层执行并非钩子窗口，不能读取之前保存的 ctx。跨帧旧句柄在下一有效窗口仍表示当前上下文，未承诺实体绑定或 generation。
- Lua 非 Destroy 钩子只派发给仍在场的实体；Destroy 使用移除通知携带的脚本清单，不能被存在检查拦掉。Rust 行为按阶段入口实体 ID 快照派发，删除当前元素不得移动下标后跳过后继，每组件调用前复查实体。
- 零尺寸 UI 视口也必须清除上一帧 clicked/pressed/hovered、布局和事件；清捕获而不清组件状态不足以保证“一帧事件”。
- 新增回归的红灯证据、最终验证和限制见 PLAN 第五十七节；这些切片不代表 ABI、递归卸载、全部 unsafe 或发布端到端已验收。

## 四十、G0 首轮修复契约与验收边界（2026-10-26）

本节由本轮工作区 diff 核对后追加；此前数量和验证是历史快照。正式优先级唯一入口仍为 `Docs/差距分析.md`，现采纳 **G0 优先于 G1—G4**；深度报告原文不回写。R01—R12 均已有代码改动，**G0 未全部关闭**。

### 1. 发布与窗口所有权（R01/R02/R05）

- `content_dirs` 必须包括 `scripts_dir`，项目根 `input.ron` 存在时原字节打包；缺省 input 可不带。默认 Scripts 与自定义目录都需覆盖。
- 先在同盘 staging 复制，再将旧包移至 previous、发布新包；复制失败不得删除旧包，发布失败尝试回滚，回滚失败保留旧副本并报告位置。不是单次原子目录交换，也不保证断电事务。

### 2. 主保存与 Prefab 身份（R06/R07）

- 本轮新增原子主保存范围只有 `ProjectHandle::write_scene/write_prefab`。独占创建 `<文件>.tmp`，写入并 sync_all 后 rename；任何失败返回错误，禁止退回直接覆盖旧文件。不能据此宣称 project/input/material/meta 等所有主文件已原子化，也未证明目录持久化或断电恢复。
- **历史说明（已由 §四十三修复）**：固定 tmp 曾使崩溃残留阻止后续保存；现在新保存使用独立暂存名，按 §四十九 在保存成功后回收超龄的那批（旧固定名仍留着手删），不会推断其它写入者已退出。
- Apply 对同来源节点保留 source_id，并映射父引用；新节点分配来源身份，只有资产写成功才回绑场景，场景来源变动进入 Undo。另存新 Prefab 的 `from_subtree` 保持独立语义。尚无字段覆盖/嵌套事务，Revert 的实例 ID 稳定性不能据此宣称完成。

### 3. 时间与监听者（R08/R10）

- `time_scale=0` 时禁止消费固定步积压；**冻结积压，恢复续用**。单帧 max_steps 仍有效，既有保留时间策略不变；不是清空积压或丢步策略。
- `World::update` 帧末、音频同步前，以本帧更新后的场景相机世界姿态设置 listener。**场景相机优先于本帧脚本/宿主手动 listener**；无场景相机时保留已有监听姿态。此前“脚本可覆盖”的表述仅适用于没有随后场景相机同步的情形，不能理解为持久覆盖活动相机。

### 4. 卸载生命周期（R11）

`unload_scene` 幂等，切关换场景前、编辑器 Stop、headless 正常完成与独立游戏正常退出调用；卸载后 update 不再推进，换场景才重新启用。钩子执行时旧场景与脚本状态仍可读，之后重置场景状态、清理行为与结构命令、停止音频，日志保留给宿主。

编辑器先交换最新运行场景再卸载，之后恢复 Play 前快照；headless 先冻结终点统计/截图，再把卸载日志计入报告（含错误）。这不是异常终止/panic/强杀的保证；回调中新增/删除、递归销毁、Lua 快照与 Rust 行为索引变化、ctx 窗口等复杂情况仍需定向验证。
